# strict — Codex·Claude 공통, 증거로 끝내는 엄격 작업 모드

> 한 줄 계약: 무엇을 증명할지 먼저 고정하고, 만든 주체가 아닌 엔진이 깨뜨린 뒤 그 판정까지 다시 공격한다. 필수 단계가 하나라도 빠지면 완료가 아니다.
>
> **공통 계약:** 저장소 정본 `docs/sot/strict-workflow.md`가 Codex·Claude의 순서·판정·승인 경계를 고정한다. 플랫폼별 유일한 차이는 G/V1/V2 독립 엔진의 실행 순서다.

## 0.0. 저장소 SOT 우선 계약

`docs/sot/strict-workflow.md`를 먼저 읽고 그 순서를 따른다: Issue/goal → DB/API 계약 → Type·런타임 검증 → EARS/counter-AC → WU → RED 로컬 시험·커밋 → 최소 구현·첫 GREEN → 회귀·적대검증 → WU 커밋 → Strict/codeaudit/통합 적대검증 → push·Draft/Ready PR → 최종 SHA CI·Owner review → merge → deploy/readback. Type은 DB/API 계약의 표현이지 새 권위나 P-원칙이 아니다. RED 직후 원격 PR과 `--no-verify`는 금지한다. 코드량 수치는 P11에서만 읽고, 실행 가능한 LLMOps 평가셋이 없으면 PASS로 표시하지 않는다.

## 0.1. 코딩 원칙 직접 로드 계약 — 모든 Strict 실행에 필수

Strict 시작 시 메모리나 이전 보고서에 의존하지 말고 현재 저장소에서 다음 순서를 실제로 수행한다.

1. `docs/sot/coding-principles.md`를 직접 읽는다.
2. `docs/sot/principles.yaml`을 직접 읽는다.
3. `bash scripts/acceptance-principles-check.sh`를 실행한다.
4. 각 단계의 명령, 시각, 종료값, 전체 출력, 현재 commit/hash, 세션 식별자와 `PASS / FAIL / NOT_RUN` 상태를 T 계약과 goal의 검증 장부에 기록한다.
5. 파일 누락·빈 파일·파싱 실패·원칙 ID 누락·검사기 누락·검사 대상 0개·pre-push 또는 CI 미배선·미실행 중 하나라도 있으면 전체 Strict 판정을 PASS로 만들지 않는다.

`.omx/project-memory.json`, Claude memory, 과거 대화와 이전 보고서는 보조 정보일 뿐 원칙의 정본이 아니다. 메모리가 없거나 잘렸어도 현재 저장소 파일의 직접 로드와 검증을 계속하며, 메모리 로드 성공을 원칙 파일 직접 로드 성공으로 간주하지 않는다. 현재 저장소의 두 정본 파일을 직접 로드하지 못하면 해당 단계를 `FAIL` 또는 `NOT_RUN`으로 기록한다.

원칙의 유일한 정본은 `docs/sot/coding-principles.md`이고, `docs/sot/principles.yaml`은 기계 판독용 장부다. 두 플랫폼은 같은 원칙 장부와 판정 계약을 사용한다. 플랫폼별 G/V1/V2 엔진 순서는 이 파일의 플랫폼 계약만 따른다. V1이 FAIL이면 최종 PASS를 금지하고 V2를 실제 실행해 재현·재공격한다. 프롬프트 표시나 실행 예정 문구는 실행 증거가 아니며, V1/V2 미실행은 `NOT_RUN`이다.

## 0. 발동과 범위

즉시 선언한다: "**엄격 모드(Lx)** — 공통 SOT 계약 + 계약 고정 + Harness 게이트 + 독립 V1 적대검증 + V2 재공격 + goal 프롬프트로 진행합니다. 보고는 §8의 결론 → 판단 근거 → 증거 원문 순서로 드립니다."

- 작업값이 비었거나 `<<...>>`뿐이면 아무것도 만들지 말고 한 줄 작업을 요청한다.
- 코드·제품이 아닌 후보자·매칭·고객사 운영 데이터는 ClickUp 소관으로 분리한다.
- ValueHire 문맥의 `Search <채용공고 URL>`, `AI Search`, 잡코리아·사람인·LinkedIn/RPS·ChatGPT는 일반 웹 검색이 아니라 저장소의 실제 AI Search 실행 경로로 처리한다. 포지션/카드 ID를 확인하고 채널별 실행·후보 수·저장·실패를 분리 보고한다. 공개 검색은 JD 확인 보조일 뿐 후보 발굴 완료 증거가 아니다.
- 후보 발송·메일 발송·포털 등록·운영 머지/배포는 별도 승인 전 실행하지 않는다. 자동 등록 옵션도 승인 없이 붙이지 않는다.

### 사용자 단계와 승인 표면

사용자에게 보이는 진행 단계는 `PLAN → SKELETON → BUILD → AUDIT → CHECKPOINT → SHIP` 여섯 개뿐이다. Harness 게이트, G/V1/V2/T, R2~R5는 이 여섯 단계 안에서 수행하는 내부 검증이며 별도 사용자 단계나 승인 요청으로 올리지 않는다.

| 단계 | 사용자에게 보이는 결과 |
|---|---|
| PLAN | 범위·정본·계약·인수 기준·반례·중단 조건을 고정한다 |
| SKELETON | 제품 표면을 새로 만들거나 교체하면 운영 주소·인증·환경·DB·상태 확인·배포 SHA·롤백의 최소 골격을 첫 작업 단위로 증명한다. 배포 무관 작업은 근거와 함께 제외한다 |
| BUILD | 승인된 계약 범위 안에서 구현하고 RED→GREEN을 만든다 |
| AUDIT | 독립 검증과 재현으로 구현 및 판정을 공격한다 |
| CHECKPOINT | 검증된 변경을 되돌릴 수 있는 로컬 안전 커밋으로 보존한다 |
| SHIP | 승인된 원격 전달을 사람이 직접 실행하고 원격 결과를 다시 읽는다 |

자동 실행은 `CHECKPOINT`의 로컬 안전 커밋까지다. push·PR 생성·병합은 수동 실행이며, 저장소 정본이 자동화를 허용하도록 개정되고 그 개정이 사람에게 승인된 뒤에만 자동화할 수 있다.

사람에게 올리는 승인은 ① 계약 승인 ② 병합 승인 ③ 메일·포털·운영 쓰기·push·PR 생성처럼 외부에 영향을 주는 행동의 직전 승인 세 종류로 제한한다. 현재 사용자 요청이 정확한 대상·범위·행동을 이미 명시하면 해당 승인이므로 같은 내용을 되묻지 않는다. 그 범위를 벗어나거나 대상이 달라지면 새 승인 없이는 실행하지 않는다.

### Production-first 배송 상태

검사 결과인 `PASS / FAIL / NOT_RUN / BLOCKED / SKIPPED`와 제품 배송 상태를 섞지 않는다. 제품 변경은 최종 보고에 `NOT_APPLICABLE / LOCAL_ONLY / PREVIEW_VERIFIED / PRODUCTION_REACHABLE / PRODUCTION_VERIFIED / BUSINESS_USED` 중 하나를 기록한다. 상태는 운영 증거가 생긴 순서대로만 올라간다.

- 제품 표면을 새로 만들거나 교체하는 작업은 구현보다 먼저 운영 smoke를 RED로 고정하고, 첫 WU를 최소 운영 골격으로 둔다. 최소 smoke는 로그인, 승인된 실제 데이터 조회, 한 건 저장, 새 세션 재조회를 포함한다. 공급자별 운영 URL, 인증 경계, 환경변수 로딩, DB 연결, `/healthz` 상당 상태 확인, 실행 중인 commit SHA, 한 명령 롤백을 검증한다.
- 승인된 실제 데이터 쓰기와 독립 readback 없이는 `PRODUCTION_VERIFIED`를 주장하지 않는다. 사용자가 운영 주소에서 실제 업무 한 건을 끝낸 영수증 없이는 `BUSINESS_USED`나 제품 완료를 주장하지 않는다.
- fixture·seed·mock은 골격 검증에 쓸 수 있지만 실제 데이터나 실제 업무 증거로 부르지 않는다. Preview 성공도 운영 성공으로 부르지 않는다.
- 문서·내부 검사·순수 리팩터링처럼 운영 배송과 무관한 작업은 이유와 회귀 검증을 기록하고 `NOT_APPLICABLE`로 분류한다.
- 이 계약은 운영 배포·운영 쓰기의 승인 경계를 넓히지 않는다. 권한이 없으면 가능한 가장 높은 상태까지만 증명하고 나머지는 `BLOCKED` 또는 낮은 배송 상태로 보고한다.
- DB 스키마는 버전 관리되는 마이그레이션으로만 변경한다. 운영 drift, DB 제약, 스키마 생성 타입, 지표의 단일 계산 authority를 검증하며, 필수 환경변수는 부팅 시 실패시키고 운영 오류를 빈 값이나 성공으로 접지 않고 비밀값 없는 관측 신호를 남긴다.

## 0.5. 시작 전 회수와 위험등급 L0~L3

손대기 전에 현재 저장소의 `CLAUDE.md`, `AGENTS.md`, 관련 `docs/sot/`, `docs/engineering/`, 검증 명령, CI, 훅, 스크립트를 찾고 실제로 읽는다. `git log --all -- <대상>`, 관련 PR/이슈, 무시된 `private-reviews/`·`artifacts/`·`.harness/`, 메모리와 과거 goal도 확인한다. 다른 저장소나 과거 버전으로 자동 전환하지 않는다.

| 등급 | 범위 | 필수 강도 |
|---|---|---|
| L0 | 오타·주석·표현처럼 동작 불변 | 자체 점검 G |
| L1 | 분석·조언·리서치·비코드 산출물 | R3 근거·출처·반례·한계 |
| L2 | 단일·중간 코드 변경 | goal, 계약, R2, RED→GREEN, 검증, R4, V1 |
| L3 | 공유모듈·보안·인증·개인정보·과금·블랙리스트·파괴 작업·SOT 수정·3파일 이상·라이브 동작 변경 | 전체 게이트, V1→V2, 롤백·영향반경·데이터 안전 AC |

애매하면 한 단계 올린다. L3 전용이라고 적지 않은 코드 변경 규칙은 L2 이상에 적용한다.

## 1. Goal prompting과 계약 스펙 — L2+

코드 전에 `docs/engineering/<주제>-goal-<YYYY-MM-DD>.md`를 만든다. 사용자가 더 좁은 파일 범위를 명시하면 그 범위를 우선하고, goal을 만들지 못한 이유와 세션 목표를 기록한다.

Goal 문서 맨 앞에는 §8의 1층 결론과 2층 판단 근거를 두고 아래를 포함한다.

1. 현재 상태: 직접 확인한 `file:line`과 실행 출력.
2. 근본 원인: 증상이 아니라 원인.
3. 인수 기준(AC): 한 단언씩 EARS 문법으로 쓴다.
   - EARS 단언: `When/While/If/Where ... 시스템은 ... 해야 한다.`
   - 검증 명령: 그 단언을 기계로 확인하는 정확한 명령과 기대값.
   - counter-AC: 겉보기만 합격인 가짜 완료 시나리오. 알려진 최소 목록일 뿐 검증 공격을 제한하지 않는다.
4. 입출력·오류·경계 계약: 함수/API/CLI의 입력 스키마, 출력 스키마, 오류 형태, 빈 값·최소/최대·권한·동시성·재시도 경계를 JSON·타입·시그니처로 고정한다. 계약이 불명확하면 구현하지 않는다.
5. Harness 게이트 계획, 적대검증 정조준 항목, 읽은 SOT, 비범위.
6. L3이면 롤백 절차, 영향 반경, 데이터 안전 AC.
7. 제품 변경이면 배송 상태 목표·구현 전 production smoke RED·첫 SKELETON WU·운영 URL/인증/환경/DB/SHA/health/rollback 증거·실제 데이터 readback·업무 1건 영수증을 적고, 배포 무관이면 `NOT_APPLICABLE` 근거를 적는다.
8. DB 변경이면 migration-only, schema drift, DB 제약, DB 생성 타입, 지표 단일 authority, 부팅 환경검증, 운영 오류 관측 계약을 적는다.

새 검사·훅·억제 장치는 다음을 먼저 답한다.

1. 자기 선언이 참인지 누가 독립 확인하는가.
2. 장치가 있으면 통과하는 킬 스위치인지, 있으면 차단하는 안전장치인지.
3. 막아야 할 N종 차단과 막지 말아야 할 M종 통과를 한 쌍으로 재는가.

### 직접 작성 코드 파일 한도 계약

- 직접 작성 코드 파일의 물리적 줄수 한도는 작업 중인 저장소의 코딩 원칙 정본(`docs/sot/coding-principles.md` 상당)에서 매 실행마다 직접 읽어 확정한다. 정본에 soft/hard가 함께 있으면 hard를 실패 경계로 사용한다. 해당 정본이나 파일 한도 조항이 없을 때만 기본 한도 500줄을 사용한다.
- 생성물·외부 벤더·압축 산출물은 직접 작성 코드가 아니다. 예외는 첫 검사 전에 goal/SOT에 경로·근거·생성 명령을 고정해야 하며, 실패 후 소급 예외는 금지한다.
- 책임을 나눠 분리한다. 줄수를 옮기기만 한 무의미한 래퍼·재수출·복사 파일은 counter-AC다.
- 검사기는 확정한 hard 한도와 같은 줄수의 정상 사본이 통과하고 한 줄 초과한 고장 사본이 실패하는지 둘 다 실행한다. 검사 대상 0개도 합격으로 세지 않는다.

## 2. 증거 없는 완료 금지

- 완료는 테스트 초록만이 아니라 실제 제품 호출 경로 연결과 필요한 라이브 1건 증거다.
- `고쳤습니다`, `should`, `probably`, `될 겁니다` 대신 명령·시각·전체 출력·화면·호출 경로를 남긴다.
- 먼저 기존 구현을 찾고 재사용·연결·보강한다. 참조 한 건만 보고 정상이라 하지 말고 제품 진입점부터 끝까지 호출을 추적한다.
- 정적 경로는 검색/AST를 쓸 수 있다. 동적 import·이벤트·미들웨어·DI는 실행 추적으로 증명한다. 테스트만 import하면 고아다.
- 전수감사는 범위를 먼저 적고 빠진 영역을 범위 밖으로 밝힌다.
- 패턴·정규식은 반례 입력을 실제 실행한다. 안전하다는 주장은 대표 반례 하나가 아니라 정한 전체 범위를 확인한다.
- 증거 장치는 0바이트 통과, 같은 작성자의 장부 전량 재생성, 마지막 기록 이후 보호 부재를 공격한다. 내부 해시 재계산만 가능한 장부를 라이브 증거라 부르지 않는다.
- 파괴적 실증은 `mktemp` 아래에서만 하고 git 환경변수를 unset한다. 끝나면 원본 저장소 `git status --porcelain`이 시작 기준과 같은지 확인한다.

### 필수 검사 상태와 복구

| 상태 | 뜻 | 완료 가능 |
|---|---|---|
| PASS | 원명령의 종료값과 출력 필드 등 성공 계약 전체 충족 | 가능 |
| FAIL | 실행됐지만 계약 위반 | 불가 |
| NOT_RUN | 시작 못 함·시간 초과·무출력 등 아직 판정 못 함 | 불가 |
| BLOCKED | 복구 후에도 권한·자격증명·외부 서비스 등 권한 밖 원인 | 불가 |
| SKIPPED | 첫 실행 전 사용자/SOT/goal이 선택 검사로 정한 비범위 | 가능 |

필수 FAIL/NOT_RUN은 ① 원명령·폴더·필수 여부·시각·경과·종료값·마지막 출력·환경 기록 ② 하위 명령으로 분해 ③ 원인 수정 ④ **같은 원명령 재실행** ⑤ PASS/FAIL/BLOCKED 승격 순으로 복구한다. 대체 검사는 원명령 PASS가 아니다. 한 번 실행한 실패를 뒤늦게 SKIPPED로 바꾸지 않는다. 개인정보·인증·과금·블랙리스트 결함은 유예 후보가 아니다. 필수 PASS 외 상태가 하나라도 남으면 진행 중이다.

검증자와 구현자 환경이 다르면 OS·런타임·캐시 권한·네트워크·홈 격리를 비교하고 구현자 환경에서 독립 재현한 뒤에만 환경 차이라고 판정한다.

### Finding 상태 — 다섯 값만 사용

결함 후보(Finding)의 상태는 아래 다섯 값으로만 기록한다. 검사 명령의 `PASS / FAIL / NOT_RUN / BLOCKED / SKIPPED` 상태와 섞지 않는다.

| Finding 상태 | 뜻 |
|---|---|
| REPRODUCED | 독립 실행으로 현상이 재현되고 증거가 보존됨 |
| BLOCKED | 권한 밖 원인 때문에 필요한 재현을 완료하지 못함 |
| NOT_REPRODUCIBLE | 명시한 환경·명령에서 재현을 시도했으나 현상이 나타나지 않음 |
| NOT_TESTED | 아직 재현 명령을 실행하지 않음 |
| UNRESOLVED | 증거가 충돌하거나 원인을 확정하지 못함 |

모델의 자기 서술, 자체 점수, `12/12 PASS` 같은 요약 문구는 실행 증거가 아니며 Finding 상태를 승격하지 못한다. 명령·입력·시각·종료값·전체 출력·해시나 커밋·세션 식별자가 있는 독립 재현만 증거로 센다.

## 4. SOT 준수

- 사용자 명시 지시 > 현재 저장소 최상위 규칙 > 기능 SOT > 기본 관례 순으로 따른다.
- SOT와 코드가 충돌하면 SOT를 먼저 바로잡고 같은 변경에 동봉한다. 단 사용자가 SOT 비수정을 명시하면 건드리지 않고 불일치를 보고한다.
- 현재 저장소 밖 경로·이전 버전·특정 회사 구조를 하드코딩하지 않는다.
- 기존 검사·훅·유틸을 먼저 찾고 새 의존성은 명시 요청 없이는 추가하지 않는다.

## 5. 독립 1차 적대검증 V1 — L2+

- 구현 맥락과 격리해 현재 플랫폼의 독립 검증 엔진에 산출물, T 계약, 증거만 준다. 구현자의 결론·의심·정답을 누설하지 않는다.
- 전역 strict 두 파일을 검증할 때는 먼저 저장소의 `guard-global-skill-files.sh lock`으로 읽기 전용 잠금을 걸고, 끝나면 `check` 성공 뒤 `unlock`한다. 프롬프트 경고만으로 보호됐다고 하지 않는다.
- 정조준: 가짜 완료, 고아·부분 배선, 계약 누락, 동시 요청, 권한 경계, 기존 기능 파손, 정본에서 확정한 파일 한도 경계, 검사 대상 0개.
- 단순 PASS는 무효다. 무엇을 어떤 방법으로 깨려 했고 왜 실패했는지 반증 기록을 요구한다. 빈 결과·`Done` 한 줄도 무효다.
- 프롬프트 끝에 §8-7 블록을 붙인다. 판정 원문, 호출 명령·세션 식별자·전체 출력·해시를 goal의 `## 적대 검증 로그`에 보존한다.
- 독립 엔진의 실제 외부 실행인지 확인한다. 같은 엔진의 하위 세션이면 V1이 아니다.
- 실제 독립 검증을 실행하지 못하면 복구 전에는 `NOT_RUN`, 권한·자격증명·외부 서비스처럼 권한 밖 원인이 확정되면 `BLOCKED`로만 기록한다. 자기 검증이나 다른 검사를 V1 대신 사용해 `PASS`로 바꾸지 않는다.

## 6. 새 맥락 2차 적대검증 V2 — L3 필수, L2 권장

V1을 액면 그대로 믿지 않는다.

1. V1의 모든 `file:line`, 명령, PASS/FAIL 근거를 깨끗한 맥락에서 다시 실행한다. 재현되지 않으면 해당 판정은 무효다.
2. V1의 PASS는 누락·고아·공유 가정을 공격하고, FAIL은 과장·오탐을 공격한다.
3. 둘이 같은 테스트만 보고 제품 경로를 놓치는 등 상관된 맹점을 새 각도로 공격한다.
4. 뒤집힌 판정은 `V1이 잡은 G 과장 N건 / V2가 잡은 V1 과장·누락 M건` 표로 공개한다.
5. 갈리면 결론 내리지 않고 독립 명령이나 새 V1으로 교차확인한다.

V2 명령·전체 출력과 V1 대비 일치/불일치 표를 같은 적대 검증 로그에 덧붙인다. 원문과 사용자 요약의 판정, 결함 수, 심각도, `file:line`, 제목·원인·사업 영향을 1:1로 대조한다.

## 6.5. G/V1/V2/T 계약

| 역할 | 현재 플랫폼 주체 | 책임 |
|---|---|---|
| G | 구현 엔진 또는 executor | 산출물을 만든다. 자기 검사는 통과 근거가 아니다 |
| V1 | 다른 독립 엔진 | 격리 상태에서 산출물을 T로 깨뜨린다 |
| V2 | 새 맥락의 검증 엔진 | V1 증거를 재현하고 판정 자체를 재공격한다 |
| T | 계약 스펙 + EARS AC/counter-AC + SOT | 세 주체가 함께 쓰는 채점 기준 |

G·V1·V2가 T에 대해 일치해야 통과한다. verdict 장부는 명령·시각·전체 출력·해시/커밋·세션 식별자를 재현 가능한 형태로 보존한다.

## 6.6. 규칙 R2~R5

### R2 — 가짜 GREEN·시험 약화 차단 (L2+)

- 테스트가 구현을 복사하지 않고 T의 기대 동작을 검사해야 한다.
- RED는 문법/import 오류가 아니라 빠진 동작 때문에 실패해야 한다.
- 구현 한 줄을 일부러 고장 내 검사가 실패하는지 확인한다. 상시 참·단언 없음·skip은 통과로 세지 않는다.
- 경계 검사에는 저장소 정본에서 확정한 hard 한도 정상 사본의 통과와 한 줄 초과 고장 사본의 실패를 포함한다.

### R3 — 비코드 답변 검수 (L1+)

주장마다 출처를 붙이고 반례를 한 번 찾는다. 추정은 `※`로 표시하며 스캔 범위·빠진 영역·확인 못 한 한계를 적는다. 최신·고위험 외부 사실은 공식 출처로 확인한다.

### R4 — 배선 완결·고아 금지 (L2+)

제품 진입점부터 끝까지 호출 경로를 증명한다. 동적 경로는 실행 추적한다. 테스트·백필에서만 불리는 코드는 고아이며 미완료다.

### R5 — 반복 실패 차단 (L2+)

실패 원인을 기록한 뒤 접근을 바꾼다. 과거 goal·판정·무시된 증거에서 이미 실패한 길을 회수한다. 같은 방식으로 두 번 막히면 세 번째 반복 대신 다른 방법을 쓴다.

## 8. 브리핑 계약 — 전 등급 필수

대상은 대화, goal, 프롬프트, 판정서, 작업 보고, PR 본문이다. 기술 배경은 없지만 판단은 직접 하는 성인 사업 책임자에게 내용은 줄이지 않고 표현만 푼다.

### 8-1. 세 층

| 층 | 내용 | 전문용어 |
|---|---|---|
| 1층 결론 | 현재 상태, 뒤집힌 판정, 사용자가 결정할 것 | 0개 |
| 2층 판단 근거 | 핵심 논리, 선택·버린 길, 틀리면 깨지는 것 | 첫 등장 문장 안에서 풀이 |
| 3층 증거 원문 | 명령·전체 출력·코드·`file:line` | 제한 없음 |

1층은 결정 하나당 1~2문장이고 전체 상한은 없다. `VERDICT: PASS|FAIL`은 결론 앞 기계 표식으로만 예외다. 3층은 같은 문서나 저장소 안 추적 파일에 보존한다. 임시 폴더는 경유지일 뿐이다. 민감정보는 원본 제한 위치·가린 항목·원본 해시를 남기고 저장소에는 넣지 않는다.

### 8-2. 용어 통행세

전문용어·약어·명령은 첫 등장 문장 안에서 풀어 쓴다. 뒤 용어집으로 미루지 않는다. 최소 표준은 다음과 같다.

| 용어 | 그 자리 풀이 |
|---|---|
| 종료값 | 프로그램의 성적. 0은 합격, 0이 아니면 불합격이며 숫자별 뜻은 명령마다 다름 |
| 글로브 | 이름 규칙으로 파일을 모으는 방식. 0개가 잡히면 가짜 합격이므로 차단 필요 |
| RED→GREEN | 빠진 동작 때문에 실패하는 시험을 먼저 만들고 최소 변경으로 통과시킴 |
| 배선/고아 | 실제 제품 호출 경로 연결 / 만들었지만 제품이 부르지 않는 코드 |
| 뮤테이션 | 일부러 고장 내 검사가 진짜 실패하는지 확인 |
| SOT/AC/counter-AC | 정본 / 합격 조건 / 가짜 합격 시나리오 |
| 해시체인/바깥 지문 | 앞 기록 지문을 잇는 내부 장부 / 장부 밖에 남긴 변경 탐지용 지문. 둘 다 같은 권한의 재작성과 기록 이후 구간에는 한계가 있음 |

### 8-3. 증거 해석

터미널 출력·코드 블록·표 바로 아래에 `→`로 1~3줄 해석한다: 무엇을 시켰나, 무엇이 나왔나, 좋은/나쁜 소식인가. `file:line`에는 그 줄의 역할을 붙이고 숫자에는 기준을 붙인다. 잘라낸 출력이나 재구성 출력은 금지한다.

### 8-4. 결정 카드

코드·설계 결정마다 다섯 줄을 쓴다.

> **무엇을** — 선택
> **왜** — 이유
> **버린 길** — 검토했지만 기각한 대안과 이유
> **대가** — 비용·한계
> **되돌리기** — 복구 방법과 비용

버린 길이 없으면 결정 카드가 아니다. 사용자 판단이 필요하면 선택지를 2~3개로 좁힌다.

### 8-5. 진행·심각도

중간 보고는 `지금 위치 → 방금 확인한 사실 → 다음 행동` 순서다. 도구·명령·파일명으로 문장을 시작하지 않는다. 판정이 뒤집히거나 건너뛴 것이 있으면 앞부분에 쓴다. 심각도 라벨은 유지하고 옆에 그대로 둘 때의 사업 영향을 쓴다.

### 8-6a. 기계 검사는 보조다

문서 산출물은 `brief-lint.sh`로 명백한 누락만 센다. 위반 0은 품질 합격 근거가 아니다. 검사기를 바꾸면 `brief-lint-test.sh --mutate`로 정상·고장 사본을 함께 시험한다. 실행 불가하면 선택 검사 `SKIPPED` 사유를 적되 §8-6b 사람 검사는 생략하지 않는다.

### 8-6b. 제출 직전 셀프 감사 — 전부 `아니오`

- [ ] 결론에 전문용어가 있나?
- [ ] `→` 해석 없는 출력·코드·표가 있나?
- [ ] 결론에 결정할 사항이 빠졌나?
- [ ] 결정에 버린 길·대가가 빠졌나?
- [ ] `file:line`의 역할 설명이 빠졌나?
- [ ] 쉽게 쓰며 증거·수치·한계를 뺐나?
- [ ] 초등학생 비유로 내용을 깎았나?
- [ ] 건너뜀·미확인·실패 후 재시도가 앞부분에서 빠졌나?
- [ ] 추정을 확인된 사실처럼 썼나?

### 8-7. V1 출력 형식

아래 블록을 V1 프롬프트 끝에 그대로 붙인다.

<!-- lint:skip -->
```text
[출력 형식 — 반드시 지킬 것]
첫 줄은 VERDICT: PASS|FAIL.
그다음 결론 → 판단 근거 → 기술 상세와 증거 원문 순서로 쓴다.
결론에는 전문용어를 쓰지 않는다. 판단 근거에는 선택·버린 해석·틀리면 깨지는 것을 쓴다.
전문용어는 첫 등장 문장 안에서 풀고, 출력·코드·표 바로 아래에는 → 해석을 붙인다.
file:line에는 줄의 역할을 붙인다. 결함마다 심각도, 원문 제목, 원인, 사업 영향을 쓴다.
설계 지적은 무엇을/왜/버린 길/대가/되돌리기 다섯 줄로 쓴다.
건너뜀·미확인·실패 후 재시도와 추정을 판정 앞부분에 밝힌다.
증거를 생략하지 말고 무엇을 어떻게 깨려다 실패했는지 반증 기록을 남긴다.
한국어 존칭체로 쓰되 내용을 축소하거나 초등학생 비유를 쓰지 않는다.
```

받은 판정은 형식과 정조준 항목을 먼저 검사한다. 위반이면 같은 작업임이 확인될 때 한 번 재요청하고, 아니면 새 검증을 돌린다. 그래도 읽기 어려우면 원문은 100% 보존하고 §8의 내 해석을 본문으로 준다. 판정 단어·결함 수·심각도·`file:line`·제목·원인·사업 영향·반증 기록은 순화하거나 누락하지 않는다.

### 8-8. GitHub·PR 오너 검토

이슈·PR·리뷰·댓글은 한국어 기본이다. PR 본문은 다음 순서를 지킨다.

1. `## 결론`
2. `## 사장님이 반드시 볼 부분`: 1~5개. 각 항목에 판단 이유, 정확한 변경 위치와 역할, 승인/반려 기준, 틀렸을 때 영향을 쓴다.
3. `## 제가 이미 확인한 부분`
4. `## 제가 확인하지 못한 부분`
5. 판단 근거, 결정 카드, 롤백, 증거 원문

집중 항목이 6개 이상이면 PR을 나눈다. 승인된 수동 생성·수정 뒤 `gh pr view <번호> --json title,body,url`로 원격 값을 다시 읽는다. 자동 실행은 로컬 안전 커밋에서 끝내며, push·PR 생성·병합은 수동으로만 수행한다. 병합·운영 push·배포·메일은 각각 필요한 사용자 승인 전 실행하지 않는다.

## 스킬 자체 변경 검증

- skill-creator의 `quick_validate.py`로 두 폴더를 각각 검사한다.
- 두 SKILL.md 자체가 각각 저장소 정본에서 확정한 hard 한도 이하인지 센다. 정본에 한도 조항이 없으면 기본 한도를 적용한다. 같은 판정기로 한도 정상 사본과 한 줄 초과 고장 사본을 시험한다.
- L0~L3, EARS/counter-AC, 입출력·오류·경계, R2~R5, G/V1/V2/T, §8의 필수 표식을 양쪽에서 검사한다.
- 엔진 이름/호출법을 제거하고 정규화한 공통 계약이 같으며, 플랫폼 차이는 G/V1/V2 엔진 순서뿐인지 대조한다.
- 임시 디렉터리의 고장 사본에서 필수 표식 삭제와 hard 한도 한 줄 초과 경계를 각각 주입해 검사가 실패하는지 확인한다. 원본 두 파일과 저장소 상태가 시험 전후 같은지 확인한다.
