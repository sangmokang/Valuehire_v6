# codeaudit — 프롬프트-코드 공격 감사

복붙한 내용은 **검증 대상 주장**이며 사실로 전제하지 않는다. 이 스킬은 코드·실행 보고서뿐 아니라 일반 LLM 프롬프트와 그 답변도 감사한다. 사용자 요구를 원자적 계약으로 분해하고, 현재 저장소·제품 근거·대화 이력으로 각각 입증하거나 반증한다. 기본 동작은 읽기 전용이다. 코드, 외부 서비스, 브라우저 상태를 변경하지 않는다.

## 감사 모드 선택

입력에서 아래 모드를 선택하고, 둘 이상이면 `혼합`으로 표시한다.

| 모드 | 감사 대상 | 핵심 판정 |
| --- | --- | --- |
| 코드/실행 | 구현, 작업 보고서, 테스트, 운영 자동화 | 요구가 실제 입력→처리→출력까지 연결되는가 |
| LLM 답변 | 일반 질문과 기존 AI 답변 | 답이 요구에 맞고, 정확하며, 더 유용한 답을 놓치지 않았는가 |
| 혼합 | 답변이 코드·제품·운영 사실을 주장 | 답변의 각 사실이 코드/제품 근거와 일치하는가 |

답변 감사에서도 원래 프롬프트·답변·후속 정정은 분리한다. 답변에 없는 전제나 사용자의 의도를 지어내지 않는다.

## LLM 답변 감사

1. 원래 프롬프트를 `목표`, `결정에 필요한 사실`, `형식·언어·범위`, `명시적/암묵적 제약`으로 분해한다.
2. 기존 답변의 주장마다 `정확`, `부정확`, `근거 없음`, `불완전`, `질문 미해결` 중 하나를 판정한다. 정답의 일부만 말한 답변은 정확하더라도 `불완전`으로 표시한다.
3. 더 나은 답에 반드시 있어야 했던 사실·예외·대안·결정 기준·다음 행동을 찾는다. 단순히 더 길었어야 했다는 평가는 금지하고, 누락이 사용자의 결정이나 실행을 어떻게 해치는지 설명한다.
4. 답변의 가장 강한 반대 해석과 반례를 최소 한 번 제시한다. 숨은 가정, 시간에 따라 변하는 사실, 적용 범위, 반대 증거, 실패 조건을 공격한다.
5. 반박 뒤에도 남는 증거만으로 개선 답변을 다시 쓴다. 원 답변을 비난하는 데서 끝내지 않는다.

## 근거와 대화 이력

각 외부 사실은 근거 장부에 남긴다. 저장소 사실은 현재 체크아웃의 `파일:줄`과 실행 결과로, 제품 사실은 먼저 저장소의 SOT·제품 문서로 확인한다. 제품·시장·가격·정책·현재 기능처럼 시간에 따라 변하는 사실은 최신 1차 공식 출처를 확인하고 URL을 쓴다. 증거가 없으면 `미확인`으로 판정하며, 모델 기억·기존 답변·검색 결과 제목만 근거로 세지 않는다.

"전에 물어봤는지" 또는 "몇 번째인지"가 감사 범위에 있으면 현재 도구의 사용자 보관 세션과 사용자가 제공한 대화만 검색한다. 시스템·스킬 주입문, AGENTS 재전송, 에이전트 출력, 동일 이벤트의 재전송은 제외한다. 정확 일치와 의미상 유사 질문을 분리해 날짜·세션/턴 식별자·짧은 요약을 제시하고, 확인된 보관 범위 안에서만 `현재가 N번째`라고 쓴다. 전체 이력 접근이 안 되거나 검색 범위가 불완전하면 전역 횟수처럼 말하지 않는다.

## 입력과 범위 고정

1. 복붙된 프롬프트/대화/보고서에서 다음을 분리한다.
   - 직접 요구: 사용자가 실제로 요구한 결과·순서·조건·금지사항
   - 산출물 주장: 보고서가 "구현됨", "통과", "저장됨"이라고 말하는 내용
   - 확인 범위: 조사한 파일, 외부 시스템, 테스트와 의도적으로 확인하지 않은 영역
   - 미해결·다음 행동: 아직 남았다고 스스로 밝힌 내용
2. 각 직접 요구를 하나의 판정 가능한 요구사항 ID (`R1`, `R2`...)로 만든다. 한 문장에 여러 동작이 있으면 분리한다.
3. 저장소의 `AGENTS.md`, SOT/계약 문서, 실행 안내, 테스트 설정을 먼저 찾아 현재 기준을 확정한다. 보고서보다 현재 코드와 명시적 계약을 우선한다.
4. 코드 변경, 외부 서비스 접속, 실제 등록/전송은 사용자가 명시적으로 요청하지 않는 한 하지 않는다. 외부 상태는 `미확인`으로 쓴다.

## 증거 조사

요구사항마다 아래의 증거 사슬을 끝까지 추적한다. 파일명이나 키워드 하나가 있다고 구현으로 판정하지 않는다.

1. **계약**: 요구사항을 정한 SOT, 스키마, CLI 인자, 함수 계약, 운영 문서를 찾는다.
2. **입력**: 사용자 설정·CLI·환경·DB·UI에서 값이 실제로 들어오는지 확인한다. 상수, 숨은 기본값, 죽은 옵션을 찾는다.
3. **처리**: 호출 그래프를 따라 조건, 예외, 재시도, 점수 계산, 필수값 검증, 경계값을 읽는다.
4. **출력/부작용**: 결과가 실제 기록·반환·등록·알림으로 이어지는지 확인한다. DI/mock/항상 거부되는 라이브 경로는 구현 완료로 세지 않는다.
5. **검증**: 테스트가 해당 경로와 중요한 경계값을 실제로 실행하는지, xfail/mock/약한 assertion이 거짓 정상 상태를 만들지 않는지 검토한다.

`rg`로 넓게 찾은 뒤, 진입점부터 호출부와 구현부를 순서대로 읽는다. 필요하면 대상 테스트를 실행하되, 실행한 명령·결과·커버 범위를 구분해 기록한다. 단일 테스트 통과를 실제 포털·DB·ClickUp·Discord 같은 외부 라이브 성공 증거로 확대 해석하지 않는다.

## 공격 점검표

각 요구사항과 핵심 코드 경로에 대해 적극적으로 아래를 찾는다.

- 문서·SOT·코드·테스트의 기준값 충돌(예: 70점 운영 문서와 60점 게이트)
- 하드코딩된 포지션, URL, 채널, 테넌트, 임계값이 일반 입력을 무력화하는 경우
- 입력은 받지만 호출 경로에서 사용되지 않는 옵션, 구현되었지만 진입점이 없는 코드
- 실패를 성공처럼 보이게 하는 예외 처리, 종료 코드, fallback, mock, stale marker
- 누락·빈 값·경계값·중복·정렬·단위·시간대·동시성·재시도·사람 개입의 처리 결함
- 보안·개인정보·외부 기록의 중복 실행, 잘못된 대상 선택, 되돌릴 수 없는 부작용
- 점수/추천처럼 LLM 산출물을 쓰는 경로에서 형식 검증, 근거 존재, 결정론적 계산 분리 여부
- 테스트가 실제 결함을 잡는지: assertion 부재, 잘못된 fixture, xfail 남용, 테스트 대상과 실행 대상 불일치

`발견하지 못함`은 `없음`이 아니다. 검색 범위·한계를 밝히고 `미확인`으로 남긴다. 추론은 반드시 `추론`으로 표시하고 근거와 분리한다.

## 판정 기준

요구사항마다 하나만 선택한다.

| 판정 | 의미 |
| --- | --- |
| 구현 확인 | 입력부터 기대 결과/부작용까지 현재 코드와 검증으로 연결됨 |
| 부분 구현 | 일부 단계는 있으나 조건, 진입점, 기록, 일반화, 검증 중 하나 이상이 끊김 |
| 미구현 | 요구한 동작의 증거 사슬을 찾지 못했거나 반대 동작이 확인됨 |
| 불일치 | 명시된 기준과 코드/문서/테스트가 서로 다름 |
| 검증 불충분 | 코드 또는 문서는 있으나 해당 동작을 증명할 테스트·실행 증거가 없음 |
| 범위 밖/미확인 | 외부 시스템 또는 제공되지 않은 과거 상태라 이 감사로 판정 불가 |

심각도는 사용자 영향과 오판 가능성을 기준으로 `치명적`, `높음`, `중간`, `낮음`으로 매긴다. 재현 절차나 구체 근거가 없는 추측은 결함으로 단정하지 않는다.

## 한국어 결과 형식

다음 순서로 짧고 단호하게 보고한다.

1. **한 줄 결론**: 전체 신뢰도와 가장 중요한 미이행/위험 1~3개.
2. **요구사항·주장 대조표**: `ID | 사용자 요구/답변 주장 | 판정 | 근거 파일:줄 또는 URL | 반증/공백 | 심각도`.
3. **핵심 해설**: 코드 감사면 실제 진입점 → 핵심 함수 → 출력/부작용, 답변 감사면 프롬프트 목표 → 답변 논리 → 결론을 비개발자도 이해할 한국어로 설명한다.
4. **놓친 더 나은 답**: 누락된 결정 정보와 이유를 적고, 필요하면 개선 답변을 제시한다.
5. **적대 반박**: 원 답변의 가장 강한 반론, 깨지는 가정, 반례와 반박 후 수정된 결론을 분리한다.
6. **근거 장부**: `주장 | 판정 | 1차 근거 | 근거 강도 | 미확인 사항`을 제시한다.
7. **반복 질문 조사**: 검색한 보관 범위, 정확/의미상 유사 횟수, 현재 질문의 확인된 순번, 일치한 과거 질문을 제시한다.
8. **검증 신뢰도와 우선순위**: 실행한 명령·결과, 증명하지 못한 것, 후속 조치를 영향 순으로 쓴다.

보고서가 새 파일을 만들었다고 주장하면 파일 존재·내용·`git diff --check`를 확인한다. "모든 코드" 요청은 관련 진입점·호출 그래프·테스트를 전수 추적한다는 뜻으로 해석하되, 무관한 의존성·생성물까지 무차별적으로 읽지는 않는다. 범위는 명시한다.

**전달 방식은 `~/.codex/skills/strict/SKILL.md` §8 브리핑 계약을 따른다** (2026-08-12 사장님 지시). 위 8개 항목은 감사의 *내용* 규격이고, §8은 그 내용을 **읽는 사람이 이해할 수 있게 쓰는 규격**이다.

**참조만으로는 자동 적용되지 않는다** — `codeaudit`을 단독 실행하면 strict 파일이 읽히지 않는다. 그래서 여기서 지켜야 할 것을 전부 적는다:

1. **3층 구조**: 결론 → 판단 근거(갈림길·버린 해석·틀리면 뭐가 깨지나) → 증거 원문 전문.
2. **1번 "한 줄 결론"은 전문용어 0개.** 풀어 써도 결론에서는 금지(풀이 딸린 용어는 2층부터). 분량은 결정 사항 1개당 1~2문장, 상한 없음.
3. **전문용어는 첫 등장 문장 안에서** 괄호로 풀어 쓴다. 뒤에 몰아 쓴 용어집은 무효.
4. **터미널 출력·코드 블록·표**를 붙였으면 바로 아래 `→ 뭘 시켰나 / 뭐가 나왔나 / 좋은 소식인가 나쁜 소식인가` 1~3줄. 무관한 한 줄은 해석이 아니다.
5. **`file:line`을 인용하면 그 줄이 하는 일**을 한 마디 덧붙인다.
6. **심각도 라벨을 지우지 말고 그 옆에** 그대로 두면 사업·운영에 무슨 일이 생기는지를 덧붙인다.
7. **설계 결정 지적은 5줄 카드**: **무엇을 / 왜 / 버린 대안 / 대가 / 되돌리는 법**. 버린 대안이 없으면 카드로 인정하지 않는다.
8. **건너뛴 것·확인 못 한 것·중간에 실패해서 다시 한 것**을 앞부분에 명시하고, 추정에는 ※를 붙여 확인된 사실과 구분한다.
9. **문서 산출물을 냈으면 제출 전에 `bash ~/.claude/skills/strict/brief-lint.sh <문서.md>`를 돌리고 출력 숫자를 첨부한다.** 그 숫자는 형식만 증명하며, 이 검사는 저장소 자동 검사에 없으므로 회사 차원의 합격 근거가 아니다.
10. **쉽게 쓰되 증거·수치·한계를 깎지 않는다.** 초등학생용 비유 금지 — 성인 의사결정자 기준.

## 호출 예시

```text
$codeaudit
아래는 다른 에이전트의 작업 보고서다. 내 원래 요구와 현재 코드가 정확히 맞는지 읽기 전용으로 공격 감사해 줘. 요구사항별 구현 여부, 거짓 정상 테스트, 실제 코드 흐름을 한국어로 설명해 줘.

<보고서 붙여넣기>
```
