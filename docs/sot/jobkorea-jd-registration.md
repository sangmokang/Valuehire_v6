# 잡코리아 후보자 제안용 JD 등록 정본

최종 확인: 2026-09-21. 적용 대상: 밸류커넥트의 Aside 로그인 세션에서 **등록 포지션**을 준비·저장하는 업무.

## 결론과 완료 기준

후보자가 회사와 역할을 판단하는 데 필요한 원문을 지키면서, 지원은 밸류커넥트로 연결한다. 원문·회사 조사·후보자용 문안·포털 저장값 네 가지가 대조되고, 저장한 항목을 다시 열어 확인했을 때만 등록 완료다.

이 문서는 검증 가능한 업무 절차다. 등록 자동화 프로그램이 구현됐다는 뜻이 아니다. 후보자에게 제안을 보내는 일, 공개 채용공고 게시, 유료 상품 구매는 각각 별도 범위다. 사용자가 해당 대상과 행동을 이미 지시했으면 같은 승인을 되묻지 않는다.

## 1. 권위와 현재 구현

사용자 명시 지시, 저장소 최상위 규칙, 이 기능 정본, 과거 실행 메모 순으로 적용한다. 기존 `docs/engineering/recruiting-search-playbook.md`의 포지션 등록 절차는 이 문서를 따른다. 그 문서의 약 1,700자 제안내용 기준은 현재 UI 실측으로 대체한다. 이전 HumanSearch의 전용 브라우저 정책을 이유로 사용자 지정 Aside 로그인 세션을 재시작하지 않는다.

- `scripts/recruiting_browser.py:24`: 실행 모드는 jd/profile/search/snapshot이다. JD 캡처·검색·프로필 수집은 구현되어 있다.
- 같은 파일 `:39`: Aside로 원문 페이지를 읽는 진입점이다. 본문 수집만으로 링크·이미지 검사가 끝나지 않는다.
- `contracts/recruiting-search.json:5`: 인재검색 경로 계약이다. 포지션 등록 계약으로 오인하지 않는다.
- `docs/engineering/recruiting-search-playbook.md:48`: 등록 자동화 미구현을 명시한다. 위 파일들은 이번 조사 시 미추적 상태였으며, 문서만 존재하는 절차를 배포 기능으로 부르지 않는다.
- 과거 v4 감사에 등장하는 등록 스크립트는 현재 저장소 모듈의 존재·작동 근거가 아니다.

## 2. 실행 입력·출력과 범위 고정

입력에는 원문 URL 또는 원본 파일, 회사·포지션명, 작업 식별자(run_id), 대상 계정, 승인된 행동(신규 저장/기존 갱신/발송)을 적는다. 공고 등록 요청이라도 문맥이 후보자 제안용이면 ‘등록 포지션’을 사용한다. 공개 공고 화면의 0건은 등록 포지션 0건을 뜻하지 않는다.

출력 묶음은 원본 본문·링크·이미지 목록·캡처 시각, 회사 조사, 삭제 장부, 후보자용 문안, 필드별 글자수, 중복 조회, 저장 직전 입력값, 저장 후 재조회, 수정 전후 포지션 ID와 그룹 ID다. `artifacts/<run_id>/`는 git 제외 내부 원본 저장소로 사용한다. 고객 운영 장부는 ClickUp 소관이며 별도 요청 없이 포지션·후보자 DB 구조를 만들거나 바꾸지 않는다.

상태는 `준비 중 → 입력 검증 → 저장 결과 미확인 → 재조회 확인`으로 구분한다. 오류·빈 페이지·인증 만료·저장 결과 불명확은 완료로 바꾸지 않는다.

## 3. 원문 수집과 최신성

1. Aside에서 지정된 URL을 직접 열고 회사·제목·본문의 실제 로딩을 확인한다. 로그인 요청·오류·빈 본문·제목만 있는 페이지는 수집 실패다.
2. 원문 텍스트, 링크의 표시 문구와 실제 목적지, 이미지·첨부·QR 여부를 저장한다. 이미지에 JD가 있으면 시각 확인 후 내용까지 기록한다. 이미지 내용을 확인할 수 없으면 원문 전량 보존을 주장하지 않는다.
3. URL·제목·조회시각·원문 파일 지문(SHA-256, 파일 변경을 비교하는 값)을 기록한다. 지난 실행의 원본은 참고자료일 뿐 현재 원본을 덮어쓰지 않는다.
4. 회사/팀 소개, 업무, 필수, 우대, 동등경험 예외, 근무조건, 전형, 수습, 제출서류를 각각 구분한다. ‘필수 5년’과 ‘5년 또는 이에 준하는 경험’은 다른 조건이다.
5. 원본 파일은 수정하지 않는다. 후보자용 사본에만 줄바꿈 정리·보이지 않는 공백 제거·지원경로 제거를 적용하고 변경 목록을 남긴다.

## 4. 회사 조사 — 원문과 분리

공식 회사 홈페이지·연혁·보도자료를 우선하고, 투자사 원문으로 보완한다. 회사명·주요 제품·대표·설립·최근 투자·사업 규모를 확인 가능한 범위에서 조사하며, 각 사실에 출처 URL·발표일 또는 기준시점·조회일을 붙인다. 재무·직원수·투자액을 확인하지 못하면 ‘미확인’으로 남기며 추정 수치를 채우지 않는다.

원문에 적힌 회사의 자체 발표와 독립적으로 검증한 사실은 구분한다. 매출 실적과 목표, 누적 투자와 이번 라운드, 월 사용자와 일 사용자를 혼용하지 않는다. 회사 조사에서 발견한 기술·학력·근무문화를 해당 포지션의 필수조건으로 추가하지 않는다.

공식 출처끼리 숫자·단위·시점이 다르면 기록하고, 후보자용 조사 요약에는 해당 수치를 제외하거나 귀속·시점을 명시한다. 사용자 요구가 원문 보존이면 회사 소개는 ‘채용공고 원문’으로 표시하고 임의 교정하지 않는다. 차이는 조사 메모에 남기고, 본문 수정이 필요한 중대한 충돌은 사실관계를 먼저 해결한다.

## 5. 직접 지원 경로 제거와 원문 보존

후보자용 사본에서 회사 직접 지원 이메일·채용 문의 전화·회사 ATS 지원 링크·지원 버튼·지원 양식·메신저·QR/이미지 안의 지원경로를 제거한다. 이메일 표시 문구뿐 아니라 `mailto:` 목적지, 짧은 URL의 최종 목적지, HTML 링크도 확인한다. 포털 자체 문의처나 밸류커넥트 담당 연락처를 회사 직접 지원 경로로 오인해 지우지 않는다.

회사명, 업무·기술·경력, 근무지, 보상·전형·수습, 필수 제출서류는 지원경로가 아니다. 예를 들어 ‘포트폴리오를 X 이메일로 보내주세요’는 이메일 제출 경로만 제거하고 포트폴리오 요구를 남긴다. ‘자사 서비스 개발’의 ‘자사’를 일괄 삭제하지 않는다. 개인정보처리방침·SNS·사이트 메뉴·푸터는 본문과 구분해 제외 내역을 기록한다. 푸터 주소에만 있는 층수 등은 완전 중복으로 처리하지 않는다. 회사 소재지와 실제 근무지를 구분해 차이를 기록하고, 근거 없이 근무층을 추가하지 않는다.

후보자용 문안에는 밸류커넥트로 지원한다는 안내를 붙인다. 기술 참고 URL이 필수 업무 이해에 필요하면 내용과 목적지를 검토해 보존한다. 원문 출처 URL은 내부 장부에 보존하고, 회사 직접 지원이 가능한 채용 원문 URL을 후보자용 본문에 다시 붙이지 않는다.

## 6. Aside에서 기존 등록부터 확인

1. Aside의 기존 로그인 세션과 밸류커넥트 계정을 확인한다. 비밀번호를 읽거나 세션·브라우저를 재시작하지 않는다. 동일 탭 조작은 한 실행자가 맡고 사람 개입이 감지되면 쓰기를 멈춰 화면을 다시 읽는다. 현재 절차는 DB 좌석 잠금 자동화까지 구현한 상태가 아니다.
2. 인재검색 또는 이력서 화면의 ‘포지션 제안’으로 작성창을 연다. 차감 안내의 ‘확인’은 작성창 진입이며, 최종 ‘제안보내기’는 발송이다. 단계 명칭만으로 판단하지 말고 현재 UI를 확인한다.
3. ‘등록 포지션’ 목록을 열고 회사명·정확한 제목·다른 표기를 조회한다. 검색어 입력만으로 필터 적용을 가정하지 않는다. 목록이 전체 표시되는 경우 각 행의 실제 제목과 ID를 읽는다. 페이지·추가 로딩이 있으면 끝까지 확인한다.
4. 0건이면 ‘채용포지션 등록’. 1건이면 내용을 열어 원문과 비교해 재사용 또는 승인 범위의 갱신. 여러 건이면 제목만으로 선택하지 말고 회사·역할·고용형태·본문을 비교한다.
5. 완전히 같은 중복이면 이번 작업에서 사용할 ID 하나를 명시하고 다른 항목은 보존한다. 과거 제안과 연결된 항목을 자동 삭제하지 않는다. 회사·역할이 다르거나 동명이어서 대상이 모호하면 해당 쓰기만 보류한다.

## 7. 필드 배치와 문자 제한

2026-09-21 실측: 채용포지션 제목 50자, 입사후 업무 1,000자, 우대사항 1,000자, 최초 제안내용 3,000자. 실행마다 실제 `maxlength`·화면 카운터·입력 후 값을 다시 확인한다. 글자수는 Python 길이만 믿지 말고 브라우저 문자열 길이와 저장값까지 비교한다. 한글 외 이모지·복합문자·줄바꿈이 있으면 서로 다를 수 있다.

일반 배치는 입사후 업무에 팀/역할·주요 업무·자격 요건, 우대사항에 우대 조건, 제안내용에 인사·회사 소개다. **그러나 제안내용 작성창은 포지션과 별개다. ‘입력 내용 저장’ 체크만으로 저장됐다고 하지 않는다.** 별도 저장·재호출이 확인되지 않은 문안은 로컬 준비 상태다. 발송해야 저장되는 기능이면 등록만 요청된 작업에서 발송하지 않는다.

원문 전체가 두 포지션 필드 안에 들어가면 명확한 소제목으로 회사 소개·전형·근무조건을 재배치할 수 있다. ‘우대사항’ 안에 다른 정보를 넣을 때에도 내부 제목으로 경계를 표시하고 필수요건을 우대로 읽게 만들지 않는다. 형식 정리를 제외한 원문 각 문장에 저장 위치를 연결한다. 원문이 한도를 넘으면 요약·절단으로 몰래 해결하지 말고 허용된 별도 저장 수단을 검증하거나 사용자에게 보존/축약 범위를 확인한다.

회사는 제목에 원문대로 표시한다. 정규직·직무는 원문에 근거해 선택한다. 별도 주소·근무조건 입력란은 기존 운영 절차상 비워 두되, 원문에 기재된 근무지·고용조건은 본문에 보존한다. 학력·급여·직급·원격근무 등을 임의로 만들지 않는다. 기존 갱신이면 무관한 필드를 바꾸지 않는다.

### 후보자 읽기 흐름과 편집 검증

원문을 무단 윤문하지 않되 문장 끝 불필요한 공백을 정리하고 업무·필수·우대·전형에 일반 하이픈 불릿을 붙인다. 각 섹션 사이에는 한 줄을 비우고, 불릿의 하위 줄바꿈은 화면 폭에 맡긴다. 원문에 없는 보상·보고 체계·직급을 설득 문구로 만들어 넣지 않는다.

메일 미리보기는 회사·포지션명 → 역할과 팀 → 업무 → 필수 → 우대 → 근무조건 → 회사소개 원문 → 전형 → 밸류커넥트 지원 안내 순으로 구성할 수 있다. 포털의 저장 필드 배치와 메일의 읽기 순서는 별도 결과물로 검증한다. 두 필드 한도 때문에 저장본의 순서가 제한되면 그 사실을 보고하고, 메일 미리보기를 실제 잡코리아 수신 화면과 동일하다고 주장하지 않는다. 가독성이 좋아졌다는 사실만으로 우수 인재의 지원 의향까지 보증하지 않는다.

## 8. 저장·재조회와 오류 복구

1. 쓰기 직전 작업 식별자·대상 계정·원문 지문·선택 ID·수정 전 본문·수정 후 문안·승인 범위를 기록한다. 새 등록은 회사+직무+원문 URL로 같은 작업인지 확인한다.
2. 원문 문장별 보존, 직접 지원경로 없음, 필수/우대 구분, 문자 한도, 중복, 대상 ID, 미요청 필드 변경 없음을 대조한다. 후보 제안의 수신자 정보는 증거에 불필요하게 포함하지 않는다.
3. ‘포지션 등록/수정’만 실행한다. ‘제안보내기’·상품 결제·지원자 연락을 함께 실행하지 않는다.
4. 버튼 클릭 직후는 ‘저장 결과 미확인’이다. 수정창을 닫았다가 목록을 새로 불러와 해당 그룹의 현재 ID로 수정창을 열고 서버에서 불러온 제목·필드 내용·고용형태·직무를 다시 읽는다. 2026-09-21 실측에서 수정은 포지션 ID를 1455461→1600230으로 바꾸고 그룹 ID 1413865를 유지했다. 따라서 이전 ID가 사라진 것만으로 실패로 판단하지 않는다. 그룹·제목·본문과 변경 전후 목록을 함께 대조한다. 작성 중 DOM 값을 그대로 읽은 것은 재조회가 아니다.
5. 저장된 각 필드를 준비 문안과 정확히 비교하고 지원경로·절단·문자 깨짐을 재검사한다. 그룹의 연결과 새 ID, 중복 건수도 확인한다. 성공 알림만으로 완료하지 않는다. 2026-09-21에는 en dash(U+2013) 3개가 저장 후 물음표로 바뀌었고, 2026-09-22에는 작은따옴표(')가 백틱(`)으로 치환됐다. 같은 날 사람인은 화살표(U+2192)를 통째로 삭제해 전형 순서가 사라졌다. 포털별 저장 변환 목록과 기계 검사는 `jd-channels` 스킬 §3.5와 `scripts/jd_channels/measure.py`의 `PORTAL_RISK`가 소유한다. 이때 단어·순서를 유지한 일반 하이픈 치환을 변경 장부에 남기고 재저장·재조회했다. 문자 깨짐을 원문 일치로 통과시키지 않는다.
6. 응답 유실·타임아웃이면 다시 등록하지 말고 목록과 저장값부터 확인한다. 저장이 안 된 것으로 확정될 때만 같은 작업을 재시도한다. 결과를 확인할 수 없으면 미확인으로 보고한다.
7. 후보자 발송이 없었음을 행동 기록 및 가능한 잔여건수 재조회로 확인한다. 잔여건수만으로 다른 실행의 발송까지 판정하지 않는다. 불필요한 작성창을 닫아 오발송 가능성을 줄인다.

## 9. 합격 시험과 반드시 공격할 반례

아래 항목은 정본의 검증 계약이며, 상시 자동 검사기가 모두 구현됐다는 뜻은 아니다. 실행 기록에 사용한 실제 명령·입력·시각·전체 출력·종료값·현재 commit·세션을 남긴다. 종료값은 프로그램 실행 결과이며 0도 내용 검증이 없으면 등록 합격이 아니다.

- 원문 보존: 각 비어 있지 않은 본문 문장을 정규화 후 합친 저장 필드에서 찾는다. 삭제된 모든 문장은 지원경로/페이지 UI 제외 장부에 대응해야 한다. 반례: ‘또는 이에 준하는 경험’ 삭제·우대 필수화·제출서류 삭제.
- 직접지원 제거: 표시 텍스트·href·이미지/QR를 점검한다. 반례: 이메일 글자만 삭제, 회사 채용 URL을 출처라는 이름으로 재삽입, 기술 링크를 무차별 삭제.
- 글자 제한: 실제 maxlength와 입력값·저장값 비교. 반례: 1,001번째 문자가 자동 절단, 유니코드 계수 차이, 로컬 파일만 완전함.
- 중복: 동일 제목 두 ID, 회사명이 빠진 제목, 검색 무적용, 저장 후 응답 유실을 공격한다. 반례: 목록 첫 행/큰 ID가 최신 정본이라고 추정.
- 보존 범위: 포지션 필드와 일회성 제안내용을 각각 재조회한다. 반례: 화면에 쓴 회사소개가 저장된 줄 알았으나 다음 제안에서 사라짐.
- 외부 효과: 등록과 발송을 구분한다. 반례: 템플릿 저장을 위해 후보에게 실제 발송, 제안 잔여건수 감소를 등록 성공 증거로 사용.
- 조사 신뢰: DAU/MAU, 실적/목표, 발표일/조회일을 구분한다. 반례: 오래된 시리즈 B 정보를 현재 누적투자로 사용.
- 실제 구현: UI 1건 성공과 무인 반복 자동화는 별개다. 반례: 이 문서와 일반 캡처 시험 통과만으로 등록 모듈 구현 완료 선언.

## 10. 영향·되돌리기·인수인계

**무엇을** — 기존 동일 포지션은 그룹 연결과 수정 전후 ID를 추적해 갱신하고 원문을 명시적 소제목으로 보존한다.
**왜** — 중복과 정보 손실 없이 밸류커넥트 지원 경로를 유지하기 위해서다.
**버린 길** — 매번 새 등록하거나 글자수를 맞추려 무단 요약하는 방식은 중복·조건 변형을 만든다.
**대가** — 포털의 두 필드 구조 때문에 회사소개 등 섹션 순서를 바꿀 수 있고, 별도 제안내용은 저장 여부를 추가 확인해야 한다.
**되돌리기** — 기존 항목은 보관한 수정 전 값으로 같은 그룹의 현재 항목을 복원하고 재조회한다. 복원 수정도 새 ID를 만들 수 있어 그 연결을 남긴다. 새 항목의 삭제/종료가 필요하면 대상과 과거 발송 연계를 먼저 확인한다. 복구 실패 시 원본·ID·실패 기록을 유지한다.

최종 보고에는 신규/갱신/기존 재사용 여부, 회사·직무·포지션 ID, 원문 보존 범위, 제거한 경로, 회사 조사 출처, 재조회 여부, 발송 여부, 남은 중복/미확인을 적는다. ‘등록 후 120일간 발송 이력이 없는 포지션 자동 삭제’ 안내가 2026-09-21 UI에 존재하므로 다음 발송 때 해당 ID의 존속을 재확인한다.
