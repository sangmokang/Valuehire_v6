# 후보 서치 운영 정본

최종 갱신: 2026-09-22

이 문서는 JD 기반 후보 서치의 반복 실행 정본이다. `$search` 스킬은 이 문서를 먼저 읽고, `docs/engineering/recruiting-search-playbook.md`는 실행 명령과 현재 구현 상태를 보조로 둔다. 사용자 최신 지시가 이 문서와 충돌하면 최신 지시를 우선하되, 충돌한 위치와 선택 이유를 결과에 남긴다.

## 1. 범위와 승인 경계

대상은 사람인 인재검색, 잡코리아 인재검색, LinkedIn Recruiter RPS에서 후보를 찾아 원장에 저장하고 내부 브리핑을 보내는 업무다. 채용사이트 원문, 후보 프로필, 리스팅, 저장 영수증, 평가, 메일 영수증을 서로 연결한다.

사용자가 특정 실행에서 내부 보고 메일 발송을 승인하면 같은 실행의 같은 수신자에게 재확인하지 않는다. 그 승인은 후보자 이메일, LinkedIn InMail, 연결 요청, 포지션 제안, 포털 등록, 운영 배포, 데이터 삭제로 확대되지 않는다. 후보자 연락은 별도 명시 지시가 있어야 한다.

공개 웹 검색은 JD·회사 식별과 공개 재직자 사전조사의 정식 근거 수집 경로다. 다만 공개 조사만으로 로그인 인재검색 채널의 후보 발굴 완료를 주장하지 않는다. 정식 로그인 세션과 각 채널의 실제 검색 화면을 사용한다. 로그인 만료, CAPTCHA, 세션 충돌, 접근 제한은 우회하지 않고 해당 채널의 상태와 재개 지점을 저장한다.

## 2. 착수 전 회수

착수 전에 현재 저장소의 AGENTS/CLAUDE 파일, 이 SOT, `docs/engineering/recruiting-search-playbook.md`, 관련 goal prompts, 브라우저 계약, 아카이브 계약, 저장 계약, 현재 run goal을 확인한다. 특히 별도 비공개로 이전한 실행 장부처럼 과거 지시가 남아 있으면 현재 문서로 대체된 부분과 재사용할 수 있는 근거를 구분한다.

과거 특정 포지션에만 붙었던 학교, 연차, 지역, 연결 차수, 회사 제한은 이번 JD에 명시되어 있거나 사용자가 이번 실행에서 다시 말한 경우에만 쓴다. 과거 프롬프트를 전부 읽지 못했으면 실제로 읽은 범위와 못 읽은 범위를 결과에 쓴다. "SOT에 있다"는 말만 쓰지 말고 파일과 근거 위치를 남긴다.

## 2A. 회사·조직 사전조사와 검색 가설

기본 순서: JD 입력 → 회사 식별 → 기존 Company Intelligence(회사·조직·재직자 근거 기록) 조회/갱신 → 공개 회사정보·현/전 재직자 조사 → 조직/인재 패턴 → JD별 Search Hypothesis(검색 가설) → 채널 검색 조건 → 후보 탐색/평가 → 저장/보고. 별도 선택 기능으로 우회하지 않는다. 상세 계약은 [회사 조사 정본](company-intelligence.md)을 읽는다.

같은 회사의 두 JD는 회사 snapshot을 재사용하되 직무별 가설·배점·검색 계획을 분리한다. 회사명만으로 확정하지 않으며 근거 부족 시 조사 시도·미확인 범위를 남긴다. 모호한 회사 기록을 JD에 연결하지 않는다. 회사 식별을 해결하지 못하면 회사 기반 조건은 차단하고 JD-only 탐색 여부와 한계를 명시한다.

관찰된 현직자 출신 회사·학력·기술은 채용 필수조건이 아니다. JD 필수와 조직 패턴의 차이를 저장하고, 확장 검색은 허용하되 원문 필수 요건을 조용히 완화하지 않는다. 회사 조사 대상은 외부 후보 원장 인원에 자동 포함하지 않는다.

## 3. JD 해석과 배점

검색 전에 JD 원문과 해석을 분리하고, 같은 JD 전체에 적용할 100점 배점표를 확정한다. 배점 합계는 100이어야 하며 모든 후보에게 같은 기준을 적용한다. 현재 스택과 달라도 지원 가능하다는 JD는 특정 기술을 전부 필수로 만들지 않는다.

권장 기본 축은 다음과 같다. JD에 맞춰 항목명과 세부 배점을 조정할 수 있지만 실행 전에 합계 100점으로 확정하고, 변경 시 버전을 올린다. 특정 회사의 JD·배점표·실행 기록은 이 공통 규칙에 넣지 않고 해당 run artifact와 goal에 저장한다.

| 축 | 예시 배점 | 기준 |
|---|---:|---|
| 핵심 직무 수행 | 30 | JD의 주 업무를 수행한 구체적인 역할과 성과 |
| 기술 연관성 | 25 | 필수·우대 기술의 실제 사용 근거와 JD가 허용하는 전이 가능한 경험 |
| 문제해결 기반 | 15 | JD에서 요구하는 기본기와 문제 해결 과정의 직접 근거 |
| 학습·협업·제품 이해 | 15 | 새 지식의 학습·적용, 협업 방식, 사용자 또는 사업 문제 개선 근거 |
| 직무 확장성 | 10 | JD의 부가 업무나 성장 방향에 맞는 경험 |
| 우대·언어 | 5 | 해당 JD의 우대사항, 언어 사용 등 확인된 근거 |

점수는 `humansearch.recruiting_review.review_candidate()`를 사용할 수 있으면 그 함수로 계산한다. 함수가 없거나 배점 구조가 맞지 않으면 같은 의미의 결정적 기준을 run artifact에 남기고 `NOT_RUN` 한계를 적는다. `met=1`, `partial=0.5`, `unmet=0`, `unknown=0`으로 계산하며 unknown은 분모에서 제거하지 않는다. 점수는 조사 우선순위 자료일 뿐 자동 채용·탈락 판단이 아니다. 평가에는 A JD 직접 일치(100점), B 조직 패턴 유사성(독립된 비필터 관찰), C 전이 가능한 경험, D 추가 확인을 분리 기록한다. B의 부재/낮은 유사성이 A 점수나 필수 게이트를 변경하지 않는다.

확인되지 않은 역량은 충족으로 계산하지 않는다. 학력은 실제 확인된 학교, 전공, 학위 범위만 기록하고 컴퓨터 관련 전공 우대와 학교 서열을 혼동하지 않는다. 영어, 학습 역량, 협업 능력은 이름, 국적, 회사명만으로 추정하지 않는다.

## 4. 탐색 방식

세 채널은 사람인, 잡코리아, LinkedIn RPS다. 각 채널에서 검색어, 필터, 정렬, 페이지, 스크롤 위치, URL, 표시 후보를 저장한다. 결과가 바뀌면 후보를 계속 열기 전에 필터와 검색어 상태를 다시 확인한다. 재연결한 탭·검색 URL·페이지/스크롤 이동은 실제 화면의 URL, 적용 필터, 선택 페이지, 스크롤 값을 확인한다. 이동 시도값이나 파일명을 관찰값으로 사용하지 않는다. 잘못 연결된 이전 검색 화면은 진단 증빙으로 보존하고 현재 검색의 후보 집계에서 제외한다.

프로필 수에 임의 상한을 두지 않는다. 관련 결과가 남아 있으면 검색어와 필터를 확장하고 다음 페이지나 다음 스크롤로 진행한다. 단 무한 실행이 아니다. 실제 세션, 접근, 시간, 브라우저 상태, 사이트 제한으로 중단되면 진행분을 저장하고 미탐색 검색식, 페이지, 다음 후보, 남은 채널을 재개 지점으로 남긴다. 중간 저장이나 중간 보고를 검색 완료로 표현하지 않는다.

인원 상한 없음은 무차별 수집을 뜻하지 않는다. 숫자 채우기를 위해 상세 조사 대상을 늘리지 않으며, 회사 브랜드만으로 적합성을 판단하지 않는다. 학교 등급은 `contracts/school-tier.json`의 가중 요건으로 반영한다. 학교 정보가 없거나 등급표에 없는 학교면 재직 회사 수준(`contracts/company-tier.json`)과 업무의 JD 부합도로 대신 검증한다. 등급표가 APPROVED 되기 전에는 점수를 내지 않고 사람 검토로 넘긴다. 학교만으로 자동 탈락시키지 않는다. JD가 허용하는 전이 가능 경험을 무시해 모든 스택을 필수화하거나 원문에 없는 연차 조건을 추가하지 않는다. 학교·회사 등급은 포지션별 가중 요건으로만 반영한다. 리스팅 단계에서 JD와 관련된 실제 직무 경험, 원문 경력 범위와 동등 경험 예외, 서비스 운영·문제 해결의 구체적 근거를 보고 상세 조사할 후보를 선별한다. 백엔드 JD라면 백엔드 실무 근거를 보되, 특정 회사의 조건을 공통 기준으로 고정하지 않는다. 나이·성별·국적으로 후보를 배제하지 않는다. 국적은 판정·점수 입력으로 쓰지 않고, 필요하면 한국어 업무 능력·국내 취업 자격·근무 가능 지역·비자 후원 필요 여부를 근거가 있는 업무 가능 요건으로 가중한다. 리스팅에 정보가 부족하면 미확인으로 남기며, 단순 기술 스택 나열만으로 제안할 만한 후보라고 추천하지 않는다.

발견한 리스팅 관찰과 이미 열람한 원문은 보존하되, 발견 수·상세 조사 대상 수·직무 적합성이 확인된 후보 수·신규 제안 검토 가능 후보 수를 구분한다. 상세 조사 선정 또는 보류 이유를 JD 근거와 함께 원장에 남긴다. 잠재 적합성을 뒷받침하는 확인된 근거와 제안 전 핵심 확인사항을 분리하여, 정보 부족을 부적합으로 단정하지 않는다. 유력 후보의 역할·경력·구체적 성과와 기컨택 이력을 깊이 확인하는 일을 단순 프로필 수 늘리기보다 우선한다. 적합성이나 컨택 이력이 미확인인 후보는 보완 대기로 남기고 제안 추천 수에 포함하지 않는다. 제안 검토 가능 판정은 후보자에게 실제 연락할 승인이 아니다.

프로필은 하나씩 열어 원문을 읽고 저장한 뒤 다음 후보로 이동한다. 대량 탭 열기, 병렬 프로필 열람, 과도하게 빠른 연속 이동, 근거 없는 자동 추출은 금지한다. 봇 탐지, CAPTCHA, 접근 제한은 우회하지 않는다.

LinkedIn RPS는 1촌부터 탐색하고 2촌·3촌으로 확장한다. 연결 차수는 관찰값이며, 이메일 공개 여부는 실제 화면 확인으로만 기록한다. 촌수만으로 이메일 가능 여부를 단정하지 않는다.

### 1촌 연락처 필수 확인

상세 조사 대상으로 선택한 1촌은 RPS 상단뿐 아니라 공개 프로필의 `연락처/Contact info`를 실제 열어 이메일과 컨택 주소를 확인·추출한다. RPS의 `Add email`만 보고 확인을 끝내지 않는다. 컨택 주소는 실제 LinkedIn 프로필/메시지 경로, 공개 전화번호, 본인이 게시한 연락용 웹 주소를 포함하며, 확인된 범위만 보존한다. 이메일·각 경로마다 값, 상태, 출처, 확인 시각, 화면 증빙을 원장에 연결한다. 미공개·빈 값·접근 제한은 해당 시도와 사유를 기록하고 보완 대기로 유지한다. 1촌이라는 이유로 이메일 존재를 가정하거나 이름·회사 도메인으로 생성하지 않는다.

## 5. 단일 후보 원장

후보자별 정본 레코드는 하나다. 채널별 원본 관찰, 포지션별 평가, 보고서, 메일은 모두 이 원장에서 파생한다. 동일인 판정은 채널 내부 안정 ID, 실제 프로필 URL, 명확한 공개 식별자 등 근거로만 수행하고 이름 하나로 합치지 않는다.

필수 필드는 다음이다.

| 필드 | 요구 |
|---|---|
| 후보자 ID와 이름 | 채널 원본 ID와 내부 ledger ID를 분리 |
| 현재 회사·직책 | 실제 확인된 범위와 시각 |
| 실제 열람 URL·채널 | 로그인 상세 URL과 공개 URL을 구분 |
| 공개 프로필 URL·Recruiter URL | 둘 다 있으면 둘 다 |
| 학력 | 학교·전공·학위 등 확인된 범위 |
| 주요 경력 | 회사·역할·재직 기간·직무 관련 성과 |
| 매칭 이유 | JD 항목과 직접 연결 |
| 적합도 | 100점 만점, 항목별 획득점수·근거·미확인 사항 |
| 정보 확인 수준 | 확인된 내용과 보완 필요 내용 |
| LinkedIn 연결 차수 | RPS일 때 실제 관찰값 |
| 이메일 | 확인 가능한 값 또는 확인 시도·값 없음·사유 |
| 과거 컨택·InMail·동일 포지션 제안 | 확인한 시스템, 탭, 기간, 결과 |
| 추천 액션 | 추천, 보류, 보완 대기, 신규 컨택 제외 등 이유 |
| 출처·확인 시각·증빙 경로 | 리스팅과 프로필 증빙 모두 |
| 저장 식별자 | SQLite ID, Supabase ID, 검증 상태 |

각 필드는 값과 별도로 상태를 가진다: `확인됨`, `확인 시도, 값 없음`, `접근 불가`, `조사 범위 밖`, `해당 없음`. `해당 없음`에는 이유를 쓴다. "못 찾음"은 "없음"이 아니다. 과거 컨택 이력이 없다고 보고하려면 실제 확인한 시스템, 탭, 기간을 함께 기록한다.

동일 포지션 기컨택자는 신규 컨택 추천에서 제외하되 원장에는 보존한다. 동일 포지션 컨택 이력이 미확인이면 신규 컨택 추천을 보류하고 확인할 시스템·기간을 남긴다. 수신자 설정만으로 메일 승인을 추정하거나 이전 실행의 승인을 재사용하지 않는다. 다른 포지션 컨택 이력은 별도 표시한다. 미완성 후보도 저장하고 `보완 대기`로 둔다. 사용자가 누락이나 오류를 지적하면 해당 필드만 덧붙이지 말고 프로필을 다시 열어 전체 레코드와 파생 보고서를 갱신한다.

## 6. 리스팅·프로필 저장

프로필 상세뿐 아니라 검색 결과 리스팅 화면을 저장한다. 리스팅 증거는 채널, 검색어, 필터, 페이지 또는 스크롤 위치, URL, 확인 시각, 표시된 후보, 상세 프로필 연결, 텍스트, 가능한 스크린샷을 포함한다.

프로필은 열람 직후 원문, URL, 확인 시각, 화면 증빙을 저장한다. 원문과 평가를 분리한다. 추천하지 않은 후보와 중복 후보도 저장한다. 원문 개인정보와 화면 증빙은 git 추적 대상이 아닌 `artifacts/` 같은 ignored 위치에 둔다.

개인정보 외부 전송(2026-09-23 사장님 결정): 밸류커넥트 검증 컨설턴트가 다루는 후보 원문·학력·경력은 요건 판정을 위해 Jev로 보낼 수 있다. 활성화(`contracts/jev-evidence-assessment.json`의 `live_calls_allowed=true`)는 실호출 1건 검증 뒤에 하며 그 전까지 전송은 꺼져 있다.

기존 아카이버와 스키마를 먼저 확인하고 재사용한다. 현재 확인된 구현에서 `scripts/recruiting_archive.py`는 상세 원문을 SQLite와 Supabase에 쓰고 재조회하지만, POST payload의 `screenshots`는 빈 배열이다. 따라서 스크린샷 이중 저장은 별도 캡처 경로와 readback 증거가 있어야 완료로 보고할 수 있다.

리스팅·프로필 화면을 양쪽에 저장하라는 요구는 클라우드에 이미지 바이너리 자체를 보존하고 인증 다운로드한 바이트의 SHA256·크기를 로컬 원본과 대조하는 것까지 포함한다. 로컬 경로 문자열만 Supabase에 있으면 화면 이중 저장은 미완료다. 기존 아카이버를 우선 재사용하고, 화면은 비공개 저장소의 덮어쓰기 없는 경로에 보존한다. 공개 버킷과 공개 URL은 사용하지 않는다. manifest에 로컬·원격 archive ID, 화면 순서·원본 참조, object key, SHA256, 크기, 참조 수·고유 객체 수, 검증 시각을 실제로 연결한다. 최신 리스팅·프로필 화면 참조 집합과 manifest 범위를 대조하며 누락·후속 캡처를 이전 검증 완료에 포함하지 않는다. 클라우드 복사가 실패해도 로컬 저장과 성공한 진행분을 보존하고 실패 원인·재시도 상태·정확한 재개 지점을 남긴다.

이번 실행이 외부 쓰기를 금지하면 Supabase/외부 아카이버 쓰기를 실행하지 않고 `NOT_RUN_PERMISSION`으로 둔다. 로컬 증거와 회사 재사용 기록은 보존하며 이중 저장 완료를 주장하지 않는다. 내부 메일 승인만으로 외부 DB 쓰기 승인을 확대하지 않는다.

SQLite 저장 후 재조회, Supabase 저장 후 재조회로 검증한다. 두 저장소의 ID 연결, 대상 레코드 수, 핵심 필드, 원문, 증빙 참조가 일치하는지 대조한다. raw profile archive와 structured candidate assessment는 서로 다른 저장 표면일 수 있으므로 각각 검증한다. 실패한 저장·동기화는 실패 사유와 재시도 상태를 기록한다. 로컬 저장만 된 상태를 양쪽 저장 완료라고 보고하지 않는다. 기존 데이터 삭제나 임의 덮어쓰기는 하지 않는다.

## 7. 브리핑 메일

사용자가 실행 지시에서 내부 브리핑 메일 발송을 승인했으면 저장소·SOT의 최신 수신자 설정과 충돌이 없는지 확인한 뒤 보낸다. 같은 run_id와 수신자 조합의 보낸메일을 먼저 조회하고, 응답이 유실됐으면 재발송 전에 보낸메일과 message ID를 확인한다.

메일에는 포지션과 조사 범위, 채널별 리스팅 수·발견 수·고유 후보 수·상세 검토 수, 후보별 profile URL·학력·주요 경력·매칭 이유·점수와 근거, 확인된 내용과 미확인 사항, 기컨택·중복·보완 대기 상태, SQLite·Supabase 저장 및 대조 결과, 미완료 사항과 다음 재개 지점을 포함한다.

후보가 많으면 본문에는 우선 검토 후보와 집계를 넣고 전체 원장과 전체 후보 브리핑은 첨부 또는 접근 가능한 링크로 제공한다. 본문을 줄인다는 이유로 전체 결과를 누락하지 않는다. 발송 후 실제 message ID와 발송 시각을 증빙으로 남긴다.

## 8. 현재 구현 상태와 한계

### 후보별 JD 메일 본문

사용자 확정 운영 범위: 후보에게 보낼 JD 제안 메일 초안은 **사용자에게 보내는 내부 브리핑의 메일 본문**에 포함한다. 같은 맥락에서 발송 범위를 다시 묻지 않는다. 후보 직접 연락은 별도 명시 지시가 있어야 한다.

선정한 1촌 후보에게 보낼 JD 본문은 기존 `$jd` 스킬을 호출하고 [JD 정본](jd-connected-registration.md)에 따라 작성한다. 스킬 실제 경로·내용 hash, 원본 JD 식별자, 생성 본문과 출처를 저장한다. 의존성이 없으면 이 단계만 명시적으로 차단하고 다른 검색·연락처 확인은 진행한다. 후보의 확인된 경력에 연결한 소개와 JD의 핵심 업무·요건·근무조건·채용절차, ValueConnect 회신 안내를 메일 본문에 포함한다. 첨부나 JD 링크만으로 대체하지 않으며, 회사 직접 지원 경로는 JD 스킬 기준대로 제외한다. 포털·InMail 글자 제한을 이메일에 임의 적용하지 않는다.

수신자, 제목, 전체 본문, 후보 ID, 포지션 ID, 본문 hash, 초안/발송 상태를 원장과 연결해 저장한다. 내부 브리핑에는 확인된 이메일·컨택 주소와 후보별 완성 본문 또는 전체 본문 산출물 경로를 포함한다. 실제 발송 대상이 내부 담당자인지 후보자인지 최신 지시로 판별한다. 모호한 경우 해당 범위만 한 번 질문하면서 본문 작성·연락처 확인·저장을 먼저 진행한다. 명확한 이번 실행 후보 발송 지시는 그 범위에서 이전 연락 금지를 대체하며 재승인을 반복하지 않는다. 1촌·이메일 확보·내부 메일 승인은 그 자체로 후보 발송 승인이 아니다.

승인된 후보 발송 전 실제 수신 주소와 동일 포지션 기컨택 여부를 검증하고 기존 기컨택 제외 규칙을 지킨다. 후보+포지션+승인된 메일 작업을 기준으로 중복 발송을 막으며 내부 브리핑 중복 방지와 구분한다. 발송 반환 message ID·시각·보낸메일 재조회 증빙을 저장한다. 작성된 본문을 발송 완료로 보고하지 않는다.

회사 조사 입력·불변 기록·조회·검색 계획의 계약은 `docs/sot/company-intelligence.md`와 `scripts/company_intelligence.py`를 따른다. 공개자료의 의미 판독과 브라우저 실행은 에이전트가 담당하며 CLI 성공을 사실의 독립 검증으로 확대하지 않는다.

현재 저장소에는 `scripts/recruiting_browser.py`, `scripts/recruiting_archive.py`, `humansearch/src/humansearch/recruiting_review.py`가 있다. 이들은 일부 브라우저 캡처, 원문 아카이브, SQLite/Supabase raw archive readback, 결정적 점수 계산을 지원한다.

RPS 조작, 사람인·잡코리아 로그인 화면 전부, JD별 수동 판독, 과거 컨택 탭 확인, structured assessment의 영속화, 브리핑 메일 발송은 실제 연결 도구와 로그인 세션을 사용하는 에이전트 실행 절차다. 구현이 없는 부분은 성공으로 꾸미지 말고 `NOT_RUN` 또는 `BLOCKED`로 기록한다.

## 9. 최종 보고

최종 보고에는 회사 식별 근거·현재/과거/미확인 표본·조직 관계의 확인/추정 구분·표본 한계·오래된 사실과 충돌·검색 가설에서 실제 검색 조건으로의 연결·평가 A/B/C/D를 먼저 제시한다. 이어 채널별 검색·열람 범위와 미탐색 범위, 발견·중복·상세 검토·평가 완료·보완 대기 후보 수, SQLite·Supabase 저장 수와 대조 결과, 리스팅·프로필 증빙 위치, 브리핑 메일 수신자·message ID·발송 시각, 사용한 스킬·SOT 경로, 미완료·차단 사항과 정확한 재개 지점을 실제 증빙과 함께 쓴다.
