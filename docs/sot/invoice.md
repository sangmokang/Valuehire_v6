## 목적과 적용 범위

`invoice` 스킬은 밸류커넥트 주식회사가 고객사에 청구할 채용 수수료를 결정 연봉에서 계산하고, 한 페이지 A4 PDF를 만든 뒤, 최종 승인된 경우에만 지정 Gmail 수신자로 보낸다. Codex와 Claude는 이 문서와 같은 기계 계약·렌더러를 사용한다.

같은 스킬은 청구가 성사된 뒤 회사 몫, Account Manager, Coworker, 원천징수와 RPS 선결제 상태를 계산하는 내부 `계산서 발행 정산 내역`도 만든다. `Deduction`은 과거 호출 키워드와 실행기 이름에만 남기고 PDF 제목이나 섹션명에는 표시하지 않는다. 외부 청구서와 내부 정산 내역은 파일·계약·발송 상태를 분리한다.

이 문서는 일반 청구서의 업무 계약이다. 세금계산서 발행, 회계 분개, 계약서 법률 해석은 포함하지 않는다.

## 영역별 정본과 충돌 처리

하나의 전역 우선순위로 모든 값을 덮어쓰지 않는다. 각 영역의 정본은 다음과 같다.

| 영역 | 정본 | 강제 지점 |
|---|---|---|
| 현재 거래 사실 | 사용자가 현재 요청에서 명시한 회사·입사자·입사일·직책·연봉·참여자·RPS 값 | 입력 검증기 |
| 청구·정산 업무 규칙 | 이 문서와 `invoice-v1.json`·`deduction-v1.json` | 렌더러와 회귀시험 |
| 고객사·포지션 수수료 | Supabase `recruitment_fee_agreements`의 적용일 기준 활성 계약 정확히 한 건 | 원격 조회와 DB RPC |
| DB 계산 상수 스냅샷 | `invoice_business_contract_versions`의 활성 버전·SHA-256 | Supabase RPC |
| 로컬 복구 상태 | SQLite 원장·outbox | 로컬 저장기 |
| 메일 전달 사실 | Gmail Sent 읽기 결과와 같은 메시지 ID를 가진 `invoice_delivery_receipts` | Gmail 읽기와 전달 기록 RPC |

현재 요청은 현재 거래의 사실값을 제공하지만 기본 수수료 금지, 계산식, 계약 버전, 승인·증빙 같은 불변조건을 일회성 문장으로 우회하지 않는다. 업무 문서와 JSON이 다르거나 JSON 묶음의 SHA-256과 DB 활성 스냅샷이 다르면 `CONTRACT_ERROR`로 중단한다.

렌더러는 계산·계좌·수신자 값을 JSON에서 읽는다. 최종본 렌더링은 Supabase 활성 수수료 계약을 다시 조회해 입력의 고객사·포지션·적용일·계약 참조·수수료율이 모두 일치할 때만 시작한다. DB RPC는 같은 JSON 묶음의 버전과 SHA-256으로 식별되는 불변 스냅샷에서 값을 읽어 원격 저장도 독립 검증한다. 이 스냅샷은 별도 기본값이 아니라 JSON 계약의 DB 집행본이다. 스킬은 계산에 상수를 공급하지 않으며 실행기와 계약을 호출한다. 회귀시험은 드리프트를 빨간불로 만들기 위해 기대값을 잠글 수 있다.

## 입력 계약

한 인보이스는 한 입사자만 다룬다. 여러 입사자는 각각 별도 PDF로 만든다.

필수 입력:

- 수신 회사명
- 입사자명
- 입사일 `YYYY-MM-DD`
- 직책
- 결정 연봉: `annual_salary_krw` 원 단위 양의 정수 또는 `annual_salary_manwon` 만원 단위 양의 정수 중 정확히 하나
- 고객사·포지션·적용일에 정확히 일치하는 수수료 계약 참조 `fee_agreement_ref`
- 위 계약에 저장된 수수료율 `fee_percent`: 0보다 크고 100 이하인 십진수 문자열
- 발행일 `YYYY-MM-DD`
- 인보이스 번호
- 검수본 여부

수수료 금액·총액·납부 기한은 입력받지 않고 계산한다. 수수료율과 계약 참조는 사용자가 매번 외우는 기본값이 아니라 저장소에서 고객사·포지션·적용일로 조회한 계약값이어야 한다. 입력에 `fee_amount`, `requested_fee`, `total_amount`, `due_date`가 있으면 자동 계산을 우회하려는 값이므로 거부한다.

문자열은 앞뒤 공백 제거 후 1~120자이고 HTML 예약 문자는 이스케이프한다. 만원 입력은 코드가 10,000을 곱해 원화로 바꾸며, 변환한 연봉은 1원 이상 10,000,000,000원 이하의 정수여야 한다. 날짜는 실제 달력 날짜여야 한다.

## 계산 계약

### 요청 수수료

- 기본 수수료율은 없다. 15%, 20%, 25% 등 어떤 수치도 시스템 기본값으로 사용하지 않는다.
- 수수료 정본은 고객사·포지션·유효기간별 `recruitment_fee_agreements`의 활성 계약 한 건이다.
- 조회 키는 정규화된 고객사 키, 정규화된 포지션 키, 적용일이다. 현재 문서에서는 입사일을 적용일로 사용한다.
- 일치 계약이 0건이면 `FEE_AGREEMENT_NOT_FOUND`, 2건 이상이면 `FEE_AGREEMENT_CONFLICT`로 중단한다. 가장 최근 계약이나 20%로 추정하지 않는다.
- 계산: `결정 연봉 × (계약 수수료율 ÷ 100)`
- 계산기는 이진 부동소수점이 아니라 십진수 연산을 사용하고 원 단위에서 반올림한다.
- 인보이스와 내부 정산서는 같은 `fee_agreement_ref`, 수수료율, 기준 연봉, 청구 금액을 사용해야 한다. 하나라도 다르면 `DOCUMENT_PAIR_MISMATCH`로 저장·발송을 중단한다.
- 과거 20% 예시는 해당 고객사·포지션 계약 데이터의 예일 뿐 정본 규칙이 아니다. 고객사 또는 포지션이 바뀌면 기존 비율을 재사용하지 않는다.

### 납부 기한

- 계산: `입사일 + 달력 날짜 14일`
- 예: 2026-09-01 입사 → 2026-09-15 납부 기한
- 주말·공휴일·영업일 보정은 적용하지 않는다. 계약서 원문이 다른 규칙을 정하면 이 SOT를 먼저 고친다.

### 총 청구 금액과 세금

- 부가가치세 기준은 사용자가 2026-09-01 확정한 `NOT_APPLICABLE`이다.
- 부가가치세를 더하거나 수수료에서 분리하지 않으며 요청 수수료와 총 청구 금액은 같다.
- 기계 계약의 `final_total_policy`는 `FINALIZED`이고 최종본 생성을 허용한다.
- 세금 기준을 바꾸려면 이 SOT와 기계 계약, 총액 계산·표시·시험을 같은 변경에서 갱신한다.

## PDF 양식 계약

- A4 세로 1페이지, 흰 배경, 짙은 남색과 중립 회색만 사용한다.
- 상단에는 `INVOICE / 채용 수수료 청구서`, 발행자, 발행일, 인보이스 번호, 수신 회사를 둔다.
- 본문은 입사자명, 입사일, 직책, 결정 연봉을 행 단위로 정렬한다.
- 금액 영역은 요청 수수료와 총 청구 금액을 오른쪽 정렬하고 원화 천 단위 쉼표를 사용한다.
- 하단 결제 영역은 납부 기한, 은행, 계좌번호, 예금주를 한눈에 읽게 분리한다.
- 검수본은 `DRAFT · 검수용` 표식과 “메일 발송 안 됨” 문구를 표시한다.
- 계산용 입력이나 내부 수수료율 필드는 본문에 노출하지 않는다. 사용자가 요구한 `요청 수수료` 결과만 표시한다.
- 페이지 밖 넘침, 글자 겹침, 잘린 계좌·금액, 한글 대체 글리프, 2페이지 분리는 실패다.

## 계산서 발행 정산 내역 / 성사 배분 계약

`계산서 발행 정산 내역`은 내부 정산 자료이며 세금계산서가 아니다. 사용자 예시의 “세금계산서 발행일·발행금액”은 각각 “청구서 발행일·청구서 발행 금액”으로 표시해 법정 세금계산서와 혼동하지 않는다. PDF의 국문 제목은 `계산서 발행 정산 내역`이고, RPS가 이번 Term 미공제인 문서의 영문 상태는 `RPS NOT DEDUCTED THIS TERM`이다.

기계 계약과 실행기:

- 계약: `contracts/invoice/deduction-v1.json`
- 실행기: `tools/invoice/generate_deduction.py`
- 한 성사 건당 A4 1페이지 PDF, HTML, 메타데이터를 각각 만든다.

계산 규칙:

1. 청구서 발행 금액 = 기준 연봉 × 고객사·포지션 수수료 계약의 수수료율
2. 회사 배분 = 청구서 발행 금액 × 25%
3. Account Manager 배분률 + Coworker 배분률 + 회사 25%는 정확히 100%여야 한다.
4. 혼자 성사한 경우 참여자 한 명의 배분률을 75%, 다른 참여자를 0%로 둔다.
5. 참여자 배분액 = 청구서 발행 금액 × 각 참여자 배분률
6. 참여자 원천징수 = 각 참여자 배분액 × 3.3%, 원 단위 반올림
7. 세후 지급액 = 참여자 배분액 - 원천징수 - 해당 참여자가 부담하는 RPS 공제

사용자가 제공한 익명화 기준 예시는 80,000,000원 × 15% = 12,000,000원이다. 회사 25%는 3,000,000원, Account Manager 40%는 4,800,000원과 세후 4,641,600원, Coworker 35%는 4,200,000원과 세후 4,061,400원이다. 이 값이 3.3% 원천징수 규칙을 잠근다.

RPS 선결제 상태:

- `rps_status`는 `pending`, `none`, `deferred`, `deducted` 중 하나를 명시한다. `0원`만으로 RPS 없음과 추후 공제를 구분하지 않는다.
- `pending`은 금액과 부담 주체가 미확정인 검수본 전용 상태다. `미입력`을 표시하고 RPS 반영 전 세후 지급액만 보여주며 지급 또는 이메일 발송을 금지한다.
- `none`은 RPS가 없는 상태다. 금액 `0`, 부담 주체 `null`을 함께 사용한다.
- `deferred`는 이번 Term에서는 미공제하고 추후 별도 공제할 상태다. 현재 공제 금액 `0`, 부담 주체 `null`을 사용하고 PDF에 `이번 Term에서 미공제, 추후 공제 예정`을 표시한다. 지급액 열은 `이번 Term 세후 지급액`으로 표시한다.
- `deducted`는 이번 Term에 실제 공제하는 상태다. 정확한 양의 원화 금액과 최종 부담 주체를 함께 입력한다. 부담 주체는 `account_manager`, `coworker`, `company`, `pro_rata` 중 하나다.
- 공제가 지정된 배분액을 초과해 음수 지급액이 되면 실패한다.

검수본은 참여자 이름을 임의로 만들지 않는다. 특히 입사자명을 Account Manager나 Coworker 이름으로 재사용하지 않는다. 최종본은 배분률이 0보다 큰 모든 참여자 이름과 RPS 금액(없으면 0)이 확정되어야 한다.

정산서 필수 표시 항목:

- 고객사, 입사자명, 입사일, 직책, 청구서 발행일
- 기준 연봉, 보증기간, 수수료율, 청구서 발행 금액
- 회사 25% 배분과 RPS 선결제 상태
- Account Manager와 Coworker 이름·배분률·배분액·3.3% 원천징수·세후 지급액
- 검수본 표식, 미입력 항목, 내부 정산 자료이며 세금계산서가 아니라는 고지

## 이메일 계약

- 기본 수신자: `sangmokang@valueconnect.kr`
- 기본 제목: `[밸류커넥트] 채용 수수료 인보이스 — {회사명} / {입사자명}`
- 본문은 회사명, 입사자명, 요청 수수료, 총 청구 금액, 납부 기한, 첨부 파일명을 간결하게 요약한다.

Python 렌더러에는 메일 전송 기능이 없다. `delivery` 값은 Codex·Claude 스킬이 연결된 Gmail 도구를 호출하기 전에 읽어 강제할 워크플로 계약이며, 렌더러 자체가 발송을 막는다고 주장하지 않는다.

발송 순서의 불변조건:

1. 최종 PDF의 `FEE_AUTHORITY_VERIFIED`, 렌더 검사와 시각 검수가 모두 통과해야 한다. `RENDER_VERDICT: PASS`만으로 업무 완료나 원격 저장 성공을 뜻하지 않는다.
2. 세금 기준이 확정되고 기계 계약의 `send_enabled`가 `true`여야 한다.
3. 스킬은 수신자, 제목, PDF 경로, PDF SHA-256, 요청 수수료, 총액, 납부 기한을 사용자에게 한 번에 보여준다.
4. 사용자가 그 구체적인 발송을 승인한 뒤에만 연결된 Gmail 발송 도구를 1회 호출한다. “PDF 만들어”, “검수본 보여줘”, 과거의 일반 발송 의향은 이 승인으로 세지 않는다.
5. 성공 응답의 Gmail 메시지 식별자를 다시 읽어 수신자와 첨부 유무를 확인한다. 도구가 없거나 확인이 안 되면 성공으로 보고하지 않는다.
6. 읽기 확인 뒤 문서 번호, 수신자, 제목, Gmail 메시지 ID, 발송 시각, 첨부 PDF SHA-256, 계약 버전·SHA-256을 `invoice_delivery_receipts`에 기록하고 Supabase 응답 ID를 확인한다.
7. 전달 기록 동기화가 실패해도 이미 보낸 메일을 자동 재발송하지 않는다. `GMAIL_SENT / DELIVERY_RECEIPT_PENDING`으로 구분하고 같은 payload로 기록 동기화만 재시도한다.
8. 같은 PDF SHA-256의 재발송은 새 사용자 승인이 필요하다.

Codex와 Claude의 Gmail 도구 이름이 달라도 위 계약은 같다. 연결된 Gmail 도구가 없는 플랫폼은 PDF와 메일 초안까지만 만들고 `BLOCKED`로 보고한다. SMTP 자격증명을 새로 요구하거나 소스에 저장하지 않는다.

## 상태 계약

- `RENDER_PASS`: 입력·계산·PDF·메타데이터 파일 검사가 통과함. 최종본은 별도로 `FEE_AUTHORITY_VERIFIED`가 필요함
- `FAIL`: 입력·계약·계산·렌더·시각 검사 중 하나가 위반됨
- `NOT_RUN`: 필수 실행을 시작하지 못했거나 결과를 읽지 못함
- `BLOCKED`: 최종 발송에 필요한 사용자 승인·세금 결정·Gmail 연결처럼 작업 권한 밖 조건이 없음
- `GMAIL_SENT / DELIVERY_RECEIPT_PENDING`: Gmail 읽기는 확인됐지만 Supabase 전달 영수증이 아직 확인되지 않음
- `SENT`: Gmail 읽기와 로컬 전달 기록이 일치하며, Supabase 전달 영수증까지 확인됨

`RENDER_PASS`인 검수본은 “메일 발송 완료”를 뜻하지 않는다. 생성, 원격 저장, 발송은 별도 상태로 보고한다.

## 2026-09-01 결정 기록

아래는 최초 예시 건의 결정 기록이며 새 거래의 입력값이나 번호를 공급하지 않는다.

1. 부가가치세: 비대상
2. 예금주: 밸류커넥트 주식회사
3. 회사 등록정보: 회사명만 표시하고 미제공 법정정보는 생략
4. 발송 대상: 두 입사자 각각 별도 PDF

인보이스 번호는 `VC-YYYYMMDD-NNN` 형식으로 제안하고, 발송 직전 정확한 요약 승인으로 확정한다. 당시 두 건은 서로 다른 번호를 사용했고 납부 기한 계산은 입사일+14일 규칙을 따랐다. 이 기록의 번호·날짜를 새 거래에 재사용하지 않는다.

당시 성사 배분 건은 참여자 이름이 입력 artifact에서 확정됐고 RPS 상태는 `deferred`였다. 이번 Term 공제 금액은 `0원`이며 `이번 Term에서 미공제, 추후 공제 예정`으로 표시했다. 실제 참여자와 입사자 이름은 이 추적 문서에 복사하지 않는다.

## 변경 절차

계산, 수수료 계약, 계좌, 수신자, 세금, 저장, 발송 승인 규칙을 바꿀 때는 문서와 JSON 계약, 데이터베이스 마이그레이션, 계산·렌더·저장 시험, Codex·Claude 두 스킬의 공통 계약 검사를 같은 변경에서 실행한다. 실제 후보자 자료는 근거 문서에 복사하지 않는다.
