## 2. REQ-0930 — AI Search 운영 v1 (2026-09-30)

출처: 사장님 첨부 `VALUEHIRE_V6_AI_SEARCH_OPERATIONS_SOT_v1.md` (원문 §번호를 괄호에 표기).

### 2.1 제품 성격 (원문 머리말)
"AI가 찾은 사람을 나열하는 페이지"가 아니라, AI 가 만든 검토 업무를 팀이 실제 제안·후보자 확보로 전환하는 과정을 증거 있는 기록으로 관리하는 운영 화면이다. 기술 실행 완료·내부 보고메일 발송·후보자 실제 제안·고객사 추천은 서로 다른 사건이다.

### 2.2 성공 조건 (§1.2)
- REQ-0930-S1 새 AI Search 결과는 구조화 DB 에 먼저 남고, 같은 저장 결과에서 웹 표시와 내부 보고메일이 만들어진다.
- REQ-0930-S2 사람인·잡코리아·LinkedIn 발송은 각각 증거와 관측 범위를 보여 준다. 확인 안 된 채널을 초록색 완료로 위장하지 않는다.
- REQ-0930-S3 전체 DB 를 대상으로 검색한다. 먼저 불러온 500개만 검색하지 않는다.
- REQ-0930-S4 재검색·재시도·메일 재수집이 후보자 수·업무량·발송 수를 부풀리지 않는다.
- REQ-0930-S5 카드·상세·그래프·위클리가 같은 정의와 같은 스냅샷을 쓴다.
- REQ-0930-S6 후보자 표는 짧고 읽기 쉽게, 근거·원문·전체 이력은 상세 패널에서 본다.
- REQ-0930-S7 이관 뒤에도 기존 기록을 보존하고, 증빙 없는 과거 기록을 신규 실적으로 바꾸지 않는다.

### 2.3 바꾸면 안 되는 규칙 (§2, 원문 그대로 번호 유지)
- R-01 `AI 결과 생성 ≠ 내부 보고 발송 ≠ 후보자 제안 ≠ 고객사 추천 ≠ 채용 성사`.
- R-02 운영 기록·웹/위클리 집계의 정본은 Supabase/Postgres. SQLite 는 로컬 원장·아웃박스·캐시다.
- R-03 결과 저장과 보고 발송 예약을 내구성 있게 처리한 뒤 부수효과를 수행한다. 메일 성공을 저장 성공으로 대신하지 않는다.
- R-04 자료 없음은 `null/unknown`. **미분석은 0점이 아니며, 이력 조회 실패는 미발송이 아니다.**
- R-05 외부 제안의 확인 상태를 LLM 설명·버튼 클릭·내부 메일·ClickUp 완료·크레딧 변화만으로 정하지 않는다.
- R-06 사람 수 / 후보자×포지션 업무 수 / 실제 제안 메시지-수신자 수를 분리한다.
- R-07 같은 입력·원천 사건 재수집은 같은 정체성. 실행 시각을 중복방지 키에 넣지 않는다.
- R-08 재평가·수정·제외·재개·발송 검증 취소의 이력을 보존한다.
- R-09 주간 = KST 일요일 00:00 이상 ~ 다음 일요일 00:00 미만, 사건의 실제 발생시각 기준.
- R-10 기존 인증·권한 경계 유지. UI 뿐 아니라 API·RPC·뷰·증빙 파일에도 적용.
- R-11 v4/v5 화면 동작·데이터는 필요한 부분만 이관한다(구형 전체 복사 금지).
- R-12 현재 승인된 평가 함수를 유지한다. 요약 표시 개선이 점수 재설계로 번지지 않게 한다.
- R-13 실제로 관측한 계정·기간·페이지·채널을 기록한다. 부분 수집을 전체 완료라 부르지 않는다.
- R-14 사용자 검토/발송과 시스템 중복정리/포지션 종료를 같은 생산성 실적으로 세지 않는다.
- R-15 레거시를 읽어왔다는 이유만으로 오늘의 처리대기 업무로 만들지 않는다.
- R-16 한 번에 한 원자 단위만 구현한다. 무관한 전역 정리를 끼워 넣지 않는다.

### 2.4 화면 (§3) — REQ-1014 가 바꾼 부분은 4절 참조
- 뷰: 처리할 후보(기본) / 전체 서치 기록 / 주간 성과 / 실행·동기화 상태(Fleet-job·ClickUp 을 진단 뷰로, 삭제 금지). 후보자 표의 칸반 컬럼은 제거(다른 메뉴 Kanban 은 유지). (§3.1)
- 상단 필터: 기간·담당자·포지션·원천·제안 채널·업무 상태·증거 상태·점수 범위. 소유자는 계정 ID 로 판정(표시 이름 금지). 카드에 단위를 명시(`제안 12건 · 10명 · 11매칭`). (§3.2)
- 표 고정 7컬럼: 후보자 / 서치 일시 / 제안 발송 / 프로필 요약 / 적합도·근거 / 매칭 포지션 / 담당·다음 행동. 이름이 없으면 원천 ID 로 표시하고 실명을 지어내지 않는다. (§3.3)
- 요약은 DB 의 검증된 구조화 자료로 만들고 LLM 이 학력·회사·기간을 보충하지 않는다. 화면을 열 때마다 LLM 을 부르지 않는다. 점수 0 은 유효한 평가의 실제 결과일 때만. 근거 미확인 레거시는 `레거시 100/100 · 근거 미확인`. (§3.4)
- 색만으로 상태를 구분하지 않는다(텍스트·아이콘 병기). 1024px 이하에서도 후보자·포지션·발송·다음 행동은 남긴다. (§3.5)
- 행 클릭 → 우측 상세 패널(URL 로 직접 접근 가능): 평가 버전·근거·리스크·타임라인·채널별 발송 증빙. `발송 완료로 표시` 버튼 금지. (§3.6)
- 검색: Supabase 권한 범위 전체 대상, Unicode 정규화·대소문자·공백 정리, **공백으로 나눈 검색어는 AND·각 검색어는 필드 간 OR**, `%`·`_`·따옴표는 사용자 문자열로 처리, q 최대 200자, 기본 page size 50(25/50/100), 안정 정렬+ID tie-breaker 페이지네이션. (§3.7)

### 2.5 범위 밖 (§1.3)
후보자 자동 대량 발송, 포털 로그인 우회·CAPTCHA 회피, 새 브라우저 자동화 프레임워크, 평가모델 교체·점수 가중치 변경, 새 ATS·CRM, 전면 디자인시스템 교체, Elasticsearch/벡터DB/Kafka 등 신규 인프라. 개발 시험이 실메일을 보내서는 안 된다.

### 4.2 해석 (요구 ID)
- **REQ-1014-T 개발 대상 변경:** 이 모듈의 구현은 **v4 저장소 코드**(운영 admin.valuehire.cc 를 배포하는 저장소)(`app/ai-search-list`, `/admin`)를 고친다. REQ-0930 머리의 "개발 대상 v6, v4 는 인수 대상"을 이 범위에서 대체한다. 요구 원장(이 문서)은 v6 에 둔다.
- **REQ-1014-P 속도:** `admin.valuehire.cc/admin` 과 관리자 화면 이동이 느리다. 코드 리팩토링으로 원인을 측정·확정하고, 화면을 그리는 속도를 최대한 빠르게 한다. 원인은 측정 없이 확정하지 않는다(서버 데이터 조회·RSC 전송량·클라이언트 렌더를 나눠 잰다).
- **REQ-1014-C1 후보자:** 모든 행에 이름이 나온다. 이름이 없으면 원천 ID 로 표시하되 실명을 지어내지 않는다(REQ-0930 §3.3 유지). 이름 누락 행 수를 측정해 0 이 되도록 저장 경로를 고친다.
- **REQ-1014-C2 점수 출처:** 점수 옆에 **누가(ChatGPT·Claude·Gemini·Codex 등) · 어떤 모델로 · 언제** 평가했는지 표시한다. 출처가 저장돼 있지 않은 과거 점수는 지어내지 않고 `평가자 미기록`으로 표시한다(R-04·§3.4).
- **REQ-1014-C3 프로필:** `대학교, 전공(YY.MM~YY.MM)` 한 줄 + `최근 회사 부서 직책 YY.MM~YY.MM` 최대 3줄. 자료가 없는 항목은 비우거나 `기간 미확인`으로 표시하고 추정하지 않는다(§3.4).
- **REQ-1014-C4 왜 잘 맞는지:** 불릿 목록. 리스트에서는 짧게, 후보자 상세 프로필에서는 근거를 풍부하게. 점수와 근거는 한 칸(REQ-0930 §3.3 ⑤ 유지).
- **REQ-1014-C5 매칭:** `회사-포지션` 표기는 현재대로 유지. 한 후보가 여러 포지션에 매칭되면 최신순으로 보여 주고, 많으면 `더 보기` → 상세 페이지에서 전체 목록.
- **REQ-1014-F Fleet-job 메뉴:** v6 에서 실제로 돌았던 AI Search 실행을 반영한다. **현재 정본은 Gmail** 로 도착하는 aisearch 결과 메일(제목 접두사 `[aisearch]claudecode`·`[aisearch]codex`, 레이블 `aisearch`)이며, 이 메일의 값을 Fleet-job 화면에 기록한다. 같은 메일을 다시 읽어도 실행이 두 번 세지지 않는다(R-07). 메일 본문의 후보자 개인정보는 기존 관리자 인증 경계 안에서만 보인다(R-10).
