최종 갱신: 2026-09-14. 소유 WU: HS-11.04a. 상태: 계약 검토 중, 제품·라이브 미구현.

## 결론

정확한 포지션의 기존 프로젝트가 하나면 재사용하고, 없으면 생성한다.
검색 실패·모호한 결과·생성 결과 유실은 새 프로젝트를 만드는 근거가 아니다.
프로젝트를 확보한 뒤 검색 조건을 적용하고 다시 읽어 일치해야 후보 검색을 시작한다.

필터값을 업데이트”라고 결정했다. 같은 세션의 실행 지시 v5는 이를 재확인하며
생성 여부를 다시 승인 질문으로 올리지 않도록 했다.
원문 회수 포인터: `/Users/kangsangmo/Desktop/hs-next-prompt-v5-20260914.md` §1·§6·§7.
이 경로는 승인 기록의 출처이며 제품의 실행 경로나 입력 기본값이 아니다.

이 결정은 포지션이 확정된 RPS 프로젝트 생성과 검색 소유 필터 업데이트에만 적용된다.

## 입력과 신뢰 경계

호출자는 다음 값을 명시한다. 누락을 기본 회사·포지션·프로젝트로 대체하지 않는다.

| position_id | ClickUp 포지션의 비어 있지 않은 안정 ID. 이름으로 대체 금지 |
| customer_id, customer_name | 원본 포지션과 연결된 고객 식별자·표시 이름 |
| position_title, jd_sha256 | 원문 포지션 이름, 필터를 도출한 JD의 SHA-256 |

| mapped_project_id | 같은 position_id/account_scope의 저장된 연결 또는 명시적 null |

형식상 유효한 호출자 주장만으로 조회가 완료됐다고 믿지 않는다. 관측과 사용권은 실행기가
같은 계정·대상·시점에 결합한다. 합성 관측은 합성 시험용이며 라이브 권한을 얻지 못한다.

프로젝트 관측은 실제 project_id, 보이는 고객·포지션 식별 근거, 조회 범위와 출처를 포함한다.
이름 유사도만으로 동일 프로젝트라고 판정하지 않는다. 기존 프로젝트에 안정 고객 ID가 없으면
실제로 관측한 고객사·포지션·기존 프로젝트 정보의 대응 근거를 보호 장부에 남긴다.
이 근거가 없거나 상충하면 해당 대상은 AMBIGUOUS다. 다른 확정 대상은 독립 진행할 수 있다.

필터는 실제 UI의 지원 필드·값·저장 범위를 확인한 채널 계약으로 검증한다.
South Korea, 경력의 단위·상하한·포함 경계, Boolean AND/OR·괄호는 정규화 규칙과 함께 비교한다.
미지원 필드·값·빈 Boolean 식·근거 없는 경력값은 INVALID_INPUT이며 임의 치환하지 않는다.
지원 값과 origin을 기억으로 하드코딩하지 않는다. 정확한 origin 목록은 HS-05.01이 소유한다.

## 프로젝트 확보 판정

다음 순서로 판정하며 결과는 아래 닫힌 상태 중 하나다.

1. 입력·계정·사용권·관측의 유효성을 검사한다. 실패하면 INVALID_INPUT 또는 BLOCKED다.
2. 조회 오류·페이지 누락·오래된 관측은 QUERY_FAILED다. 빈 성공 목록으로 변환하지 않는다.
3. 미확정 생성 의도가 있으면 RECONCILE_REQUIRED다. 다른 신규 생성에 앞서 복구한다.
4. 저장된 project_id가 있으면 그 ID를 직접 재조회하고 계정·포지션 연결을 검증한다.
   일치하면 REUSE, 사라짐·접근 거부·불일치면 MAPPING_CONFLICT다. 이름으로 새 연결을 덮지 않는다.
5. 매핑이 없으면 고객·포지션·기존 정보가 일치하는 서로 다른 project_id를 센다.
   정확히 하나면 REUSE, 둘 이상이면 AMBIGUOUS, 완전한 조회에서 0이면 CREATE_REQUIRED다.

CREATE_REQUIRED는 다음 쓰기 경계를 준비하는 결과이며 생성 성공이나 외부 실행 허가 자체가 아니다.
REUSE는 검증된 project_id를 공통 SQLite에 연결한 뒤 필터 단계로 넘긴다.
페이지 간 같은 ID 중복은 한 프로젝트로 합치되 내용이 충돌하면 QUERY_FAILED로 처리한다.
매핑 읽기·저장 실패는 STORAGE_FAILED이며 다음 단계로 넘어가지 않는다.

## 생성 쓰기와 복구

생성은 읽기 어댑터와 다른 명시적 메서드가 소유한다. 실행 전 대상 입력과 현재 권한을 재검증한다.

1. 공통 SQLite의 `(account_scope, position_id)` 고유 제약 아래 생성 의도를 먼저 기록한다.
   의도에는 요청 ID, 고객·포지션·JD 지문, 실행 ID, 사용권 증가 번호와 상태가 들어간다.
2. 저장 커밋을 확인한 뒤 생성 직전 프로젝트를 다시 조회한다. 타 실행 결과가 있으면 재사용한다.
3. 유효한 사용권에서 외부 생성 요청을 한 번 전송한다. 이미 전송된 요청을 자동 재전송하지 않는다.
4. 응답의 ID만 믿지 않고 프로젝트를 독립 재조회해 실제 ID와 대상 일치를 확인한다.
5. 확인된 연결과 의도 상태 CONFIRMED를 같은 SQLite 트랜잭션으로 기록한다.

응답 유실·클릭 뒤 STOP·프로세스 종료·재조회 실패는 UNCERTAIN이다.
다음 실행은 미확정 의도를 읽고 기존 결과부터 확인한다. 조회 0건만으로 새 생성을 재전송하지 않는다.
관측 지연과 이전 전송의 확정 실패를 구분할 증거가 없으면 RECONCILE_REQUIRED를 유지한다.
실제 API가 멱등키를 지원하는지는 미확인이다. 지원한다고 가정하지 않는다.
생성 성공 후 연결 저장 실패도 같은 복구 경계를 사용한다. 프로젝트 삭제로 복구하지 않는다.
STOP 이후 새 외부 호출 0과 이미 전송된 효과의 불확실성은 각각 기록한다.

## 기존·신규 필터 적용

프로젝트 확보 뒤 현재 필터를 읽어 이전값·저장 범위·관측 지문을 보존한다.
프로젝트 영구 설정인지 검색 세션 설정인지는 실제 UI에서 확인한다. 세션 설정을 영구 저장으로 보고하지 않는다.

업데이트는 requested_filters의 소유 필드에만 적용한다. 수동 설정·후보 상태·멤버·공유 권한은 보존한다.
같은 값이면 NO_CHANGE로 반환하여 불필요한 쓰기를 만들지 않는다.
쓰기 직전 현재값을 다시 읽고 보존한 이전값과 대조한다. 동시 변경이면 CONFLICT로 중단하며 덮어쓰지 않는다.
읽기와 쓰기 사이 서버 측 원자적 비교 기능이 없으면 경합 방지가 증명되지 않은 것으로 기록한다.
그 경우 충돌 가능한 라이브 쓰기는 BLOCKED이며 로컬 사용권만으로 외부 사용자까지 잠갔다고 주장하지 않는다.

변경 의도에는 이전값·요청값·관측 지문·소유 필드·실제 저장 범위가 들어간다.
적용 뒤 소유 필드 전량 및 보존 대상 필드를 독립 재조회해 요청과 대조한다.
완전 일치일 때만 FILTERS_CONFIRMED다. 일부 적용·저장 실패·읽기 실패는 RECOVERY_REQUIRED이며 검색 시작 0이다.
자동 되돌림도 현재값이 이번 쓰기의 결과와 일치한다고 증명할 때만 소유 필드에서 허용한다.
그 증거가 없으면 이전값·요청값·실제값을 보존하고 해당 대상의 검색을 멈춘다.
재실행은 현재 실제값부터 비교한다. 과거 성공 영수증만으로 검색을 허가하지 않는다.

## 저장·출력·오류 계약

후보·사용권·checkpoint와 같은 SQLite 원본을 사용한다. 별도 프로젝트용 원본 DB를 만들지 않는다.
실제 스키마·버전 마이그레이션은 HS-03.01 이후 HS-11.04c에서 추가한다.
DB에는 계정/포지션 연결 고유성, 의도 중복 방지, 사용권 증가 번호 검증이 필요하다.
운영 프로젝트 이름·필터·원문 지문과 관련 관측은 승인된 보호 저장 경계를 따른다.

상위 실행기에 반환하는 결과에는 상태, position_id, 확인된 project_id 또는 null,
조회/의도/필터 증거 참조, 재개 가능 여부, 오류 코드를 포함한다. 성공처럼 보이는 빈 ID는 금지한다.
일반 보고에는 상태·비민감 지문·호출 수만 쓴다. 후보 정보·계정 비밀·실 URL·검색 원문은 넣지 않는다.
INVALID_INPUT / QUERY_FAILED / AMBIGUOUS / MAPPING_CONFLICT / STORAGE_FAILED / CONFLICT /
RECONCILE_REQUIRED / RECOVERY_REQUIRED / BLOCKED는 검색 시작을 허가하지 않는다.

HS-11.04a 문서 인수는 모든 행의 입력·결과·담당이 빠짐없고 상충하지 않는지 독립 대조하는 것이다.

| A5 | If 입력·페이지·관측이 불완전하면 시스템은 생성 판정을 거부해야 한다 | 호출자가 complete만 참으로 주장 | b/d |
| A6 | When 두 실행이 같은 대상을 확보하면 시스템은 의도·연결을 하나만 기록해야 한다 | 별도 SQLite마다 한 행 | c |
| A7 | If 생성 후 응답이 유실되면 시스템은 결과부터 재조회해야 한다 | 재실행 신규 생성 클릭 | d |
| A8 | If 생성 성공 뒤 DB 저장이 실패하면 시스템은 미확정 의도를 보존해야 한다 | 실패를 새 대상처럼 처리 | c/d |
| A9 | When 신규 필터가 일치하면 시스템은 FILTERS_CONFIRMED여야 한다 | 입력 호출 수만으로 성공 | e |
| A10 | When 기존 소유 필터만 다르면 시스템은 그 필드만 갱신해야 한다 | 수동 설정·멤버 변경 | e |
| A11 | When 동일 필터를 재실행하면 시스템은 쓰기를 생략해야 한다 | 중복 설정 변경 | e |
| A12 | If 일부 적용·동시 변경·저장 실패면 시스템은 검색을 시작하지 않아야 한다 | 1개 필드 성공으로 전량 성공 | e/f |
| A13 | If STOP이면 시스템은 새 외부 호출을 하지 않아야 한다 | 과거 사용권으로 재전송 | d/e/f |
| A14 | When 읽기 어댑터를 호출하면 시스템은 생성·저장·발송하지 않아야 한다 | 읽기 안에 숨긴 생성 | d/f |
| A15 | When 화면의 저장 범위가 세션이면 시스템은 세션 적용으로 보고해야 한다 | 프로젝트 영구 저장 주장 | e |
| A16 | If 같은 이름이라도 고객·포지션 근거가 없으면 시스템은 모호 상태여야 한다 | 이름만으로 기존 연결 확정 | b |

→ 문서 대조와 합성 시험은 실제 RPS 생성·필터·반복 검색·후보 저장의 성공 증거가 아니다.

## 영향·되돌리기

무엇을 — 포지션에 귀속된 프로젝트 쓰기를 별도 경계로 정의한다.
왜 — 응답 유실 뒤 중복 생성과 관련 없는 수동 필터 덮어쓰기를 막기 위해서다.
버린 길 — 읽기 어댑터가 프로젝트를 알아서 만드는 방식은 의도·재시도 경계가 숨으므로 채택하지 않는다.
대가 — 조회의 완전성·필터 저장 범위·외부 경합 제어를 실제로 증명할 때까지 라이브 일부가 보류될 수 있다.
되돌리기 — 계약 커밋을 되돌리고 소비 WU를 중지한다. 이미 생성된 외부 프로젝트는 자동 삭제하지 않는다.
