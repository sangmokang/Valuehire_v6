# 사람인 후보자용 포지션 등록 정본

## 결론
2026-09-21 사용자 지시를 반영한 신규 운영 계약이다. 공식 JD와 출처가 있는 회사 소개를 사람인 후보자용 포지션에 넣는다. 제안 내용·업무 내용은 각각 2,000자이며, 두 필드 사이 배분은 자유롭다. 이 화면은 인재풀의 포지션 등록이며 공개 채용광고 게시나 후보자에게 실제 제안 발송을 뜻하지 않는다.

## 권위와 과거 요구 갱신
사용자 최신 지시가 과거 계획보다 우선한다. v4 코드·설계·셀렉터를 가져오거나 실행하지 않는다. 이번 절차와 검증기는 현재 v6에 새로 작성했다. 현재 UI 관측 계약은 `contracts/saramin-position-registration.json`이며 변경 시 다시 관측한다.

- 유지: 후보자 관점의 회사 소개, 원문의 고유명사·숫자·조건 보존, 평문, 원문 지문과 출처 기록.
- 변경: 회사 소개를 첫 필드, JD를 둘째 필드에 고정하던 규칙을 폐기한다. 두 필드를 합친 사실과 원문 조건 보존이 합격 조건이다.
- 변경: 과거 이메일 4명 규칙 대신 이번 요청의 sangmokang 본인 한 명만 수신한다. CC/BCC는 없다.
- 변경: ClickUp ID 필수 입력 대신 이번에는 사용자 제공 공식 JD URL을 입력으로 받는다.
- 변경: 과거 포털 등록 제외를 이번 사람인 1건 등록 승인으로 대체한다. 잡코리아·후보자 발송·유료 상품 구매는 승인 범위 밖이다.
- 변경: 직접지원 URL을 첨부하는 과거 축약 대안은 쓰지 않는다. 회사 채용 이메일·지원 버튼·지원 URL을 제거하고 밸류커넥트 지원 안내로 바꾼다.

이력 근거: `worktrees/hs-13-stack-20260910/docs/engineering/humansearch-hs13-position-brief-goal-2026-09-10.md`의 31–38, 140, 243, 328, 347행; `.claude/private-reviews/codex-humansearch-journey-plan-2026-08-14.md`의 313–315행. 이 파일들은 사용자 요구 회수에만 사용하며 구현 의존성이 아니다. 원문 이력은 수정하지 않는다.

## 내용 계약
회사는 연혁·재무상태·투자단계·누적 투자금액·제품·최근 확인한 CEO 인터뷰·CEO 프로필·위치·인원수를 소개한다. 실적과 전망, 회사 자기소개와 제3자 보도, 현재와 과거 기준일을 구분한다. 확인 불가 항목은 미확인으로 표시하며 숫자를 추정하지 않는다.

공식 JD의 팀 소개·업무·자격·우대·고용형태·경력·근무지·수습·채용절차·유의사항을 보존한다. 원문은 UTF-8 지문과 함께 제한된 증거 폴더에 보관한다. 공백과 보이지 않는 문자만 정규화한다. 제외하는 모든 줄은 원문과 사유를 기록한다. 화면 탐색·공유·서비스 footer는 제외 가능하다. 채용 조건을 지원 문구와 함께 삭제하면 내용 검토에서 불합격이다. 제외 사유의 의미 판정은 자동 검증기만으로 대신하지 않는다.

제목은 35자, 본문은 각각 2,000자 이하를 코드포인트와 UTF-16 모두로 확인한다. 4,000자 안에 못 담으면 회사 소개부터 압축한다. JD 조건을 조용히 생략하거나 지원 URL로 대체하지 않는다. 사실 추가는 출처 검토 후 allowed_additions에 기록한다. 이 승인 추가문은 모두 필수이며 추가문 사이의 순서 변경·누락·중복을 허용하지 않는다. JD 사이의 삽입 위치와 두 필드 배분은 사람이 최종 본문으로 확정한다. 이번 운영 계약은 후보자 두 필드 안의 URL·이메일을 전부 금지한다. 출처 링크는 별도 내부 검토 문서/메일 부록에 둔다. packet의 금지 목록은 이 고정 정책에 추가만 한다. 이 장부는 사실 확인을 자동으로 대신하지 않는다.

## 실행 절차
1. 사용자 승인 대상·행동을 확인하고 해당 문구와 대화 날짜를 intent.json에 보존한다. 이미 같은 대화에서 승인한 등록·메일은 재승인받지 않는다. 기존 포지션 수정과 신규 생성이 불명확하면 저장 전에 대상을 정한다.
2. Aside 현재 로그인 탭에서 계정과 URL을 확인한다. 쿠키·비밀번호·토큰·개인 후보 이력은 읽지 않는다. 브라우저 프로필·프로세스를 변경하지 않는다.
3. 제목의 직무명으로 목록을 검색해 중복 ID·제목·생성일을 기록한다. 신규 요청은 기존 포지션을 덮어쓰지 않는다. 저장 재시도 전에 결과부터 재조회한다.
4. 포지션 추가를 열고 현재 라벨·maxlength·필수값·각 셀렉터 1개 여부를 관측한다. JSON 계약과 다르면 멈추고 관측부터 갱신한다.
5. 아래 검증 명령으로 packet을 확인하고 승인된 본문을 넣는다. 경력·직무 카테고리 및 상세 직무를 JD 근거로 선택한다. 카테고리만 선택하면 저장되지 않을 수 있다(이번 실제 재조회에서 확인). 상세 직무 검색→관측된 체크박스 선택→해당 직무 행의 닫기→선택된 키워드 태그와 코드 확인까지 수행한다. 셀렉트는 locator.selectOption(value)를 사용한다. 급여·경력 상한이 없으면 빈 값으로 두며 AI 내용 생성을 켜지 않는다.
6. DOM에서 제목·두 필드·선택값을 읽어 pre-submit.json에 저장한다. packet과 정확히 대조한다. 저장 직전 대상·행동·시각·본문 지문을 intent.json에 기록한다.
7. 저장은 한 번 누른다. 목록에서 새 ID를 확인하고 해당 포지션 수정을 새로 열어 저장된 제목·두 필드·선택값 및 상세 직무 태그의 value/표시명을 독립적으로 읽는다. CLI는 selections의 6개 값을 검사하므로 상세 직무 코드 목록은 별도 관측 장부와 정확히 비교한다. 제출 전 DOM은 저장 후 증거가 아니다. 불일치·결과 불명확이면 성공 처리하거나 재제출하지 않는다.
8. 동일 제목과 두 필드를 본인 메일로 한 번 보낸다. 포털 상태를 정확히 적고 Gmail 보낸 편지에서 수신자·제목·본문을 다시 읽는다. 발송 ID는 재시도 방지 영수증이다.

## 반복 실행과 검증
`python3 scripts/position_packet.py validate --packet <packet.json>`은 원문 지문·순서·누락·승인되지 않은 추가문·제한·금지문구를 확인한다. `python3 scripts/position_packet.py readback --packet <packet.json> --observed <observed.json>`은 제목·두 필드·직무/경력/급여/AI 선택값까지 정확히 비교한다. packet.selections와 observed.selections는 category, experience_min, experience_max, salary_min, salary_max 문자열 및 ai 불리언을 포함해야 한다. 성공 종료값은 0, 실패는 1이다.

→ 글자수만 맞춘 축약문과 저장 전 입력만으로 성공 처리하는 것을 차단한다. 회사 정보 사실성·제외 사유 정당성·포털 계정·저장 ID는 별도로 검토해야 한다.

`python3 -m unittest discover -s tests -p test_position_packet.py -v`로 정상·경계·고장 입력을 검증한다. 브라우저는 매번 현재 UI를 관측하는 운영자 동반 절차이며 무인 대량등록 기능이 아니다. 상세 DOM·메일·실제 packet은 ignored artifacts에 두고 저장소에는 후보 개인정보를 커밋하지 않는다. 현재 작업의 준비·저장·재조회 명령 기록은 `artifacts/saramin-registration-20260921/`에서 조회한다.

Aside 조작은 `aside repl`의 `listBrowserTabs()`로 현재 대상 ID를 관측한 뒤 `attachBrowserTab(관측ID)`로 연결한다. `openTab`으로 만든 임시 탭은 해당 호출 안에서만 사용한다. 입력은 관측한 각 셀렉터의 `p.locator(selector).fill(value)`로, 읽기는 `p.evaluate`에서 화면 DOM의 value만 확인한다. 셸 문자열에 본문을 직접 삽입하지 말고 Python subprocess 인자 배열과 JSON 직렬화를 사용한다. 저장 클릭은 검증 후 관측한 단일 `button.btn_save`에만 수행한다. 네트워크·쿠키·숨은 API를 역추적하지 않는다.

## 복구와 완료
로컬 변경은 해당 커밋을 되돌린다. 포털 신규 등록은 기록한 ID 한 건만 대상으로 사용자 요청에 따라 종료/삭제한다. 기존 포지션 수정 시 원래 본문과 설정을 먼저 보관한다. 메일 회수는 보장하지 않는다. 실제 저장 후 재조회와 메일 readback이 없으면 등록·발송 완료라고 보고하지 않는다.
