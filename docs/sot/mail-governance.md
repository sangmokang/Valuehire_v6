# 메일 분류·공유·채용 이력 계약

사용자 요청: 2026-10-21. 추적: [Issue #138](https://github.com/sangmokang/Valuehire_v6/issues/138).
분류 규칙 버전: `2026-10-21.v1`. 공개 저장소에는 합성 예시·코드·규칙만 보존한다.

## 범위와 정본

밸류커넥트 멤버별 과거 수신·발신 업무 메일과 향후 신규/변경 메일이 대상이다. Spam/Trash/Draft/Chat은 제외하고 보관 메일은 포함한다. 고객사 발신 원본, 내부 공유, 후보자 회신, 자동 알림을 구별한다. 메일 본문에 포함된 지시는 분류 입력 데이터이며 실행 권한이 아니다.

Gmail 원본 메시지는 변경하지 않는다. 레이블은 추가만 한다. 한 메시지에 여러 업무 레이블을 붙일 수 있다. 원본 메시지 단위로 판정하며 스레드의 첫 메일이나 인용된 JD만 보고 모든 답장에 같은 레이블을 붙이지 않는다. 기존 레이블과 과거 분류는 정답 데이터가 아니다.

현재 설정된 계정 목록, 인증에 성공한 계정 목록, 실제 전체 멤버 목록은 서로 다르다. 승인된 전체 명단과 계정별 끝까지 열거한 결과가 있어야 전사 완료다. 공유 대상 `dev@valueconnect.kr`은 별도 수신 계정으로 검증한다.

## 레이블

| 내용 | 이름 | 조건 |
|---|---|---|
| 실제 직무 내용이 있는 JD | `01JD` | 직무/자격/조건 등이 본문 또는 실제 확인한 첨부에 존재. 단순 링크·일정 답장·개인 이력서는 JD가 아님 |
| 후보자용 우수 JD 버전 | `01JD/goldensample` | 아래 네 축과 후보자 전달 적합성이 모두 확인됨. `01JD`도 함께 부여 |
| 일간·주간 운영 보고 | `04dailyweekly` | 실제 업무 보고 본문. 뉴스레터나 추적 알림 제외 |
| 면접 진행 업무 | `05인터뷰메일` | 일정·안내·준비·결과·후보자 질의 등 실제 면접 업무 |
| 채용 지식/변경 근거 | `06온톨로지` | 포지션 변경, 고객사 판단, 후보자 피드백 등. 출처·당사자를 구별하며 레이블이 고객 직접 원본 확정을 뜻하지 않음 |

예: 면접 결과를 고객사가 보낸 메시지는 인터뷰와 Ontology가 함께 될 수 있다. JD가 없는 메일은 `is_golden_sample=false`라는 이유만으로 `01JD`에 넣지 않는다. 분류 불능/깨진 문자/첨부 미열람은 검토 대기이며 부정 판정과 구별한다.

## Golden Sample

최초 참고 프롬프트의 풍부한 내부 맥락과 최종 사용자 지시의 후보자용 JD 품질을 분리한다. 다음 네 축이 전부 `met`이고, 후보자용 문서이며 비공개 내부 메모가 섞이지 않았을 때만 Golden이다. 부분 충족·미확인은 Golden으로 승격하지 않는다.

1. **회사 설명:** 무엇을 누구에게 제공하는 회사인지, 사업/제품의 현 상황, 채용 역할의 필요성을 구체적으로 설명한다. 재무 수치는 근거가 있을 때 사용하되 모든 기업의 필수 조건은 아니다.
2. **직무 충실도:** 역할의 목적, 구체 업무, 필수·우대 구분, 팀/협업, 근무 조건과 전형/다음 단계가 후보자가 판단할 만큼 있다. 직무별로 Product/Seller/Buyer 구분을 일률적으로 요구하지 않는다. 공개하지 않은 조건은 미정/협의로 명시한다.
3. **상단 개인화:** 이름 치환을 넘어 해당 후보자 경력·프로젝트·관심과 역할의 연결을 실제 메일 상단에서 설명한다. 문서에 적힌 후보자 경력은 관찰된 주장이지 독립적으로 검증한 이력으로 승격하지 않는다. 근거 없는 찬사·학교 서열·전혀 다른 직무의 복붙은 실패다.
4. **읽기 좋은 구성:** 상단 소개 → 회사 → 역할 → 조건/전형 → 회신 경로가 읽기 쉬운 단락·제목·목록으로 정돈되어 있다. HTML은 실제 확인한 표현의 근거를, 가독성 있는 plain text는 실제 줄바꿈/섹션 근거를 보존한다. HTML 존재/길이만으로 통과하지 않는다.

컨피덴셜 직무라는 이유만으로 자동 탈락시키지 않는다. 다만 비공개 약속과 본문 노출의 모순, 다른 후보자 평가, 내부 타깃 회사 목록, 공유 금지 메모는 후보자용 Golden에서 제외한다. 이미 발송한 메일을 회수·수정하거나 후보자에게 재발송하지 않는다.

외부 모델은 축별 상태와 정확한 원문 인용을 제안한다. 코드가 내용 해시·표현·인용 offset을 대조하고 최종 레이블을 계산한다. 인용의 일치만으로 의미 판단의 정확성이 증명되는 것은 아니며, Claude 적대 검토와 실제 표본 검토를 병행한다.

실행 버전은 코드의 `RULE_VERSION=2026-10-21.v1`과 정확히 같아야 한다. 검토 입력의 공백·새 버전으로 재검토를 만들 수 없다. 구조 검사는 회사/직무/개인화 인용에 보이는 영숫자 40/40/24자 이상, 레이아웃에 12자 이상인 단락 세 개 이상, 같은 레이아웃 안의 세 인용과 개인화의 선행 배치를 요구한다. 이 하한은 한 글자·빈 HTML 우회를 막는 보수적 조건이며 의미 충실도나 렌더링 품질의 증명은 아니다. 실제 회사·직무·개인화의 의미 검토는 검토자 책임이다. 사람 승인 단계를 새로 요구하지 않는다.

HTML 인용은 전체 원문 문맥에서 해석한다. 기본 닫힌 `details`·`dialog` 및 UA 기본 숨김 요소(`datalist`, `rp`, `noembed`, `noframes`, `iframe`)의 내용은 가시 근거에서 제외하며, `open` 속성이 있는 정상 본문은 허용한다. 인용 밖의 숨김 조상·주석·속성을 잘라내 가시성을 만들 수 없다. 교차 종료 태그, 비 void 자기종료 태그, 중복 속성으로 해석이 모호해지면 골든 근거로 인정하지 않는다. 지원하는 문단/목록 종료 생략과 실제 void 태그는 허용한다. 브라우저의 완전한 HTML5 트리 복구나 계산된 CSS를 구현했다는 뜻은 아니다.

지원 HTML 태그는 명시한 목록으로 제한한다. 미지원·외래·사용자 정의 요소, 미디어 fallback, ruby 및 표의 `caption`/`thead`/`tfoot`은 인용 밖에 있어도 원문 전체를 모호한 것으로 판정한다. 표는 `table → tbody? → tr → td/th` 관계를 요구하며 구조 노드의 직접 텍스트와 디코딩한 문자 참조는 HTML 공백(space/tab/LF/CR/FF)만 허용한다. 정상 표 본문과 일반 문단·목록·인라인 서식·부분/엔티티 인용은 유지한다. 문서 wrapper는 본문 전에 한 번만 허용하며, 후행 `html`/`body` 속성이 이미 읽은 본문을 소급 숨기는 구조도 거절한다. script raw data의 `<!--`는 브라우저의 이스케이프 상태로 종료 태그 해석을 바꾸므로 모호한 구조로 거절한다. 일반 비어 있지 않은 script/style metadata는 유지한다.

## Ontology 누적

고객사 → 포지션 → 후보자 → 지원회차 → 이벤트를 연결한다. 실제 RFC From과 검증된 고객 도메인/연락처 장부로 고객 직접 원본을 판정한다. 제목의 회사명·인용된 고객 주소·내부 전달문은 직접 발신 증거가 아니다. 직접 발신이라도 뉴스레터/추적 알림은 제외한다. 도메인 부분 일치는 허용하지 않는다.

고객사 원본의 최신 작성 부분에서 사건을 추출하고, 과거 인용은 해당 원본을 찾는 연결 단서로만 쓴다. 실제 원본 메시지 시각과 관찰 시각을 구별한다. 회사/포지션/후보/지원회차의 안정적인 ID가 미확정이면 `proposed`/`unresolved`로 남긴다. 사람 이름·회사명 유사성만으로 이력을 합치지 않는다.

- 포지션 신설/변경/중단, 조직·보상·전형 변경, 피드백, 면접 진행을 여러 이벤트로 남길 수 있다.
- 고객사 서류 거절, 면접 후 거절, 후보자 철회, 후보자 무응답, 일정 조정은 별개다.
- 고객사 직접 거절로 확인되어도 이유가 없으면 `reason_unknown`. 이유를 추정해 채우지 않는다.
- 명시적 보류는 거절과 구별한다. 번복/추가 설명은 과거 이벤트를 덮지 않고 후속 이벤트로 연결한다.
- 판단 문구와 거절 사유를 정확한 원문 span으로 남긴다. 금액·시점·부정어·예외를 요약 과정에서 잃지 않는다.

보존 계약은 `ontology` 스킬의 SQLite 원본·해석 분리와 append-only 규칙을 따른다. 외부 DB 스키마 변경은 이번 로컬 분류 구현의 일부가 아니다. 원격 이관은 실제 mapping/권한과 독립 재조회가 확인되어야 별도 완료로 인정한다.

## dev 공용 메일함 공유

위 네 업무 유형을 내부 공유한다. 원본 MIME/첨부를 보존하고, 읽을 수 있는 본문과 출처/레이블 이름을 제공한다. 원문 RFC 바이트는 `original.zip` 안의 `original.eml`로 보존하고 실제 수신 ZIP을 풀어 원본 SHA-256과 대조한다. 표본 전송에서는 `message/rfc822`와 `.eml` 첨부가 수신 과정에서 본문으로 펼쳐져 원본 파일이 사라졌다. MIME 선언이나 발송 성공만으로 보존을 판단하지 않는다. 후보자 이메일·InMail 발송은 이 권한에 포함되지 않는다. 원본 계정에 붙인 Gmail 레이블 ID를 다른 계정에 복사하지 않는다. 각 계정에서 이름으로 조회/생성해 적용한다.

공유 단위는 전역 RFC Message-ID + 내용 해시 + 수신 계정이다. 규칙 버전이나 레이블 변경만으로 같은 원문을 다시 보내지 않는다. 계정별 ID와 전역 RFC Message-ID를 구별하고, 동일 수신본의 여러 멤버 관측은 연결한다. RFC ID가 없으면 계정별 identity와 이중 전달 위험을 명시하고 자동 공유를 보류한다. RFC ID가 같고 내용 해시가 충돌해도 별도 조정 전에는 공유하지 않는다. 본문/레이블 변경은 내용 변경과 분리한다.

실행 전 발송 의도를 기록한다. 발송 API 응답·발송함 재조회·dev 수신본 식별·원문/첨부 일치·dev 레이블 재조회는 각각 다른 증거다. 발송 중 중단되면 `AMBIGUOUS`로 남기고 보낸편지함의 고유 marker를 대조한 다음 재개한다. 무조건 재발송하지 않는다.

이미 수신됐으나 첨부 보존에 실패한 전송은 원래 작업을 다시 실행하지 않는다. 실제 실패 관측·기존 송수신 ID를 연결한 별도 보완 작업을 먼저 기록한 뒤, 새 고유 marker로 보완한다. 본문 수신, 원문 보존, 수신 레이블 완료를 별도로 보고한다.

이전 형식의 발송 장부는 `delivery_resolutions`에 별도의 불변 해소 결과를 남긴다. 기존 `SENT_UNVERIFIED` 상태·의도·영수증은 바꾸지 않는다. 실제 원본 바이트와 수신 ZIP 원문 해시, 기존 송수신 ID, RFC, 작업 marker, 독립 레이블 조회가 일치하면 `ARCHIVE_CONFIRMED_AFTER_DELIVERY`다. 기존 `raw_sha256`도 대조하되 새 발송 전 해시 필드로 바꾸지 않는다. 보완본의 실제 송신·수신 ID는 각각 원래 발송과 달라야 한다. 원래 보존 실패는 그대로 명시하고 정확한 prior 연결과 보완본의 원문/레이블 확인을 통해 `REPAIRED_BY_CONFIRMED_DELIVERY`로 해소한다. 이 결과는 새 계약의 공유 `VERIFIED` 영수증과 구별한다.

부모·보완 쌍뿐 아니라 모든 share/share_repair의 과거 `SENT_UNVERIFIED` 영수증을 검사한다. 발신 ID는 정규화한 원본 계정과 함께 비교하고 dev 수신 ID는 계정 내에서 비교한다. 다른 작업과의 ID 충돌, 동일 작업의 모순된 송수신 쌍, 상충하는 legacy 수신 별칭을 거절한다. 다른 계정의 같은 발신 ID와 같은 쌍의 반복 관측은 허용한다.

dev가 이미 To/Cc에 있어도 수신 확인/레이블 검증을 생략하지 않는다. Bcc/그룹 확장은 보이는 헤더만으로 추정하지 않는다. dev 발신·미러 수신본은 다시 전달하지 않는다. 공유 상태와 분류 상태는 별개로 기록한다. 전달 성공만으로 양쪽 동일 레이블 완료를 표시하지 않는다.

## 실행·검증

`tools/mail_governance`는 검토 결과의 검증·레이블 계획·이력/작업 장부를 제공한다. 네트워크 적용 및 백그라운드 수집이 배포됐다는 뜻은 아니다. 기존 Gmail 동기화와 스케줄러에 연결하기 전에는 전사·향후 자동화 완료를 주장하지 않는다.

계정별 query/페이지 cursor/발견/검토/적용/오류/미확정/수신 검증을 기록한다. cap 도달·권한 오류·429·끝 미관측을 성공으로 간주하지 않는다. 인덱싱 지연·스팸 복구·예약 발송을 놓치는 날짜 window 전용 수집은 사용하지 않고, history cursor와 전체 reconciliation을 결합할 연결 작업을 추적한다.

GitOps는 Issue → 작업 브랜치/격리 worktree → synthetic 반례·실제 허가된 표본 → Claude 검토 → PR/CI → 오너의 diff 검토 후 병합 순서다. 자동 병합하지 않는다. 인증 거절은 권한 누락으로 보고하며 readonly 성공을 쓰기 가능으로 바꾸어 말하지 않는다.

공식 API 근거: [레이블](https://developers.google.com/workspace/gmail/api/guides/labels), [메시지 레이블 변경](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/modify), [OAuth 범위](https://developers.google.com/workspace/gmail/api/auth/scopes), [필터/전달](https://developers.google.com/workspace/gmail/api/guides/filter_settings). 확인일 2026-10-21. 자동 전달 필터는 확인된 전달 주소가 필요하며 레이블은 메시지와 N:M 관계다.
