# 『Accelerate DevOps with GitHub』(깃허브로 구현하는 데브옵스) — 이 저장소에 실제로 필요한 주제 선별

작성: 2026-09-07
입력: 책 목차 전량(1~20장, 6부)
판정 기준: **"이 저장소의 현재 상태에서 지금 적용할 수 있고, 적용하면 실측 결함이 닫히는가"**
근거는 전부 이 저장소의 실행 확인값이다. 책의 권고를 그대로 옮긴 항목은 없다.

## 0. 이 저장소의 현재 좌표

- 운영 형태: 오너 1인 + LLM 에이전트 다수. 팀 조율 대상 없음.
- 강제 장치: `verify.sh` + `.github/workflows/verify.yml`(단일 job, 25스텝, 270줄) + `hooks/pre-commit`·`pre-push` + 인수 검사 34개.
- 원칙 정본: `docs/sot/coding-principles.md` P1~P24.
- **강점**: "검사가 무력화에 저항하는가"(P13⑥·P20·P23)는 책 어느 장보다 앞서 있다. 책 12·13·14장을 그대로 따르면 오히려 후퇴하는 영역이다.
- **공백**: 공급망(종속성·액션 핀·코드 스캔)과 **속도 측정**이 0이다. 책이 메울 곳은 정확히 여기다.

## 1. 즉시 적용 — 실측 결함이 열려 있는 것

### ① 14장 「코드 보안」 — 종속성 관리 및 Dependabot (p.381~394)

- **실측**: `.github/dependabot.yml` **없음**. `humansearch/uv.lock`·`humansearch/pyproject.toml`이 커밋되어 있으나 취약점 갱신을 보는 장치가 저장소 어디에도 없다.
- **왜 이 저장소에 필요한가**: P4·P22가 막는 것은 *우리가 쓴* 비밀이다. *남이 쓴 코드*의 취약점은 P1~P24 어디에도 없다. `verify.yml` 25스텝 전부가 초록인 상태로 취약한 의존성을 배송할 수 있다.
- **적용 형태**: `.github/dependabot.yml`(pip/uv + github-actions 두 ecosystem). 자동 머지는 금지 — `docs/sot/git-workflow.md`의 "자동 병합 금지"가 우선한다.

### ② 15장 「안전한 배포」 — 액션 보안 강화 (p.437)

- **실측**: `verify.yml:18` `uses: actions/checkout@v4` — **가변 태그**. `origin/task/checkout-v7-sha-pin-20260907` 브랜치가 이미 이 문제로 열려 있다(미병합).
- **왜**: 태그는 재지정 가능하다. 서드파티 액션 하나가 이 저장소의 **모든 게이트를 실행하는 러너**에서 임의 코드를 돌린다. P13⑥이 증명한 "스텝을 조용히 끄는" 공격면과 같은 계열이며, 그것보다 상위다 — 스텝을 끄는 게 아니라 스텝 자체를 바꾼다.
- **적용 형태**: 모든 `uses:`를 커밋 SHA로 고정. `permissions: contents: read`는 **이미 되어 있다**(책 권고 충족).
- **P23과의 정합**: "초록불은 SHA에 귀속된다"를 이미 원칙으로 쓰고 있으면서, 그 초록불을 만드는 액션은 태그로 당겨오고 있다.

### ③ 14장 「코드 스캔」 / CodeQL (p.395~420)

- **실측**: Python 59파일 + JS 1 + HTML 2. 코드 스캔 워크플로 **없음**.
- **왜**: 이 저장소의 인수 검사 34개는 전부 **"우리가 정한 규칙을 어겼는가"**를 본다. **"알려진 취약 패턴이 있는가"**를 보는 검사는 0이다. 다른 계층이므로 중복이 아니다.
- **주의**: CodeQL 도입 시 P20이 그대로 적용된다 — 스캔 대상 파일 수를 로그로 남기고 최소치 미만이면 FAIL. "0건 스캔 후 초록"은 이 저장소에서 합격이 아니다.

### ④ 1장 「메트릭이 핵심」 — DORA 4지표 · 리드타임 (p.045~074)

- **실측**: 원격 미병합 브랜치 **39개**. 최고령 `origin/task/hook-enforcement`(2026-08-07, **31일 방치**). `docs/sot/git-workflow.md`는 작업 브랜치 수명 **24~48시간 상한**을 규약으로 적고 있다 — 기계 강제가 없어 규약이 붕괴했고, **아무 게이트도 이를 빨갛게 만들지 않는다**.
- **왜 이 책의 1장인가**: 이 저장소는 "품질 게이트"를 극한까지 지었지만 **속도를 한 번도 측정하지 않았다**. 책의 지적 그대로다 — 속도와 품질은 상충하지 않으며, 측정하지 않는 쪽이 무너진다. v4의 "워크트리 77개·미병합 113개"가 이미 같은 방식으로 무너진 실측 사례로 SOT에 적혀 있는데, v6에서 39개까지 다시 왔다.
- **적용 형태(최소)**: 배포 대상이 없으므로 DORA 4개를 전부 쓰지 않는다. **리드타임(첫 커밋→main 머지)**과 **브랜치 최고령**만 센다. 임계 초과 시 CI 경고 → 이후 FAIL.
- **SPACE는 보류**: 1인 조직에서 만족도·활동 설문은 자기보고이며 P14("판정 수치는 코드가 만든다")와 직접 충돌한다.

### ⑤ 10장 「피처 플래그와 피처의 수명 주기」 (p.297~311)

- **실측**: `origin/task/admin-dashboard-shadow-ui`(8/17), `phase-d`(8/22), `position-cards-e1`(9/7) — 대시보드 한 기능이 **장수 브랜치 3개**로 갈라져 있다.
- **왜**: ④의 39개 브랜치는 "게으름"이 아니라 **미완성 코드를 main에 넣을 수단이 없기 때문**이다. SOT는 "장수 브랜치 + LLM 생성 코드 = 대형 충돌, LLM은 충돌을 코드를 새로 지어내서 해결한다(v4 자동로그인 6벌)"를 이미 원인으로 지목했다. 피처 플래그가 그 수단이다 — **11장(트렁크 기반)을 실제로 굴리기 위한 전제 조건**이지 부가 기능이 아니다.
- **함께 필요한 것**: 책이 말하는 **플래그의 수명 주기(제거)**. 만료 없는 플래그는 P13③의 "만료 없는 억제"와 동일 취급 → `suppressions.yaml`과 같은 expiry 규칙을 적용한다.

## 2. 다음 순번 — 지금 손댈 필요는 없으나 근거가 이미 있는 것

### ⑥ 6장 「워크플로 모범 사례」 — 잡 분리 · 재사용 워크플로 (p.180~192)

- **실측**: `verify.yml` 단일 job 25스텝 **순차**. 스텝 하나가 빨개지면 뒤 24개는 실행되지 않는다. 소요 시간은 **측정된 적이 없다**(④와 같은 공백).
- **적용**: `needs`로 독립 게이트(비밀 스캔 / 인수 검사 / invoice PostgreSQL)를 병렬 job으로 분리. 인수 검사 실행은 이미 `scripts/verify/run-acceptance.sh` 한 벌로 통일돼 있으므로 **composite action 화의 비용이 낮다**.
- **선행 조건**: P13⑥·`acceptance-ci-step-integrity.sh`가 워크플로를 YAML로 파싱한다. **잡 분리는 그 판정기가 job 경계를 아는지 먼저 확인한 뒤에** 한다 — 아니면 분리 자체가 검사를 우회하는 경로가 된다.

### ⑦ 12장 「테스트 자동화」 — 코드 커버리지 · 불안정한 테스트 제거 (p.313~318)

- **실측**: `humansearch/tests` 28파일, `tools/invoice/tests` 11파일. **커버리지 측정 없음.** 세션 시작 시점 RED 10/29.
- **왜 조건부인가**: 이 저장소는 P16(런타임 import 강제)·P13⑥(변조 시 반드시 빨개짐)으로 **커버리지보다 강한 지표를 이미 쓰고 있다**. 커버리지 숫자는 그 위에 얹는 보조지표일 뿐이며, 목표치로 삼으면 P14에 걸린다.
- **가져올 것은 커버리지 %가 아니라 "불안정한 테스트 제거"** — RED 10/29를 "환경 탓"으로 넘기지 않는 규율. 책의 이 절이 그 근거다.

### ⑧ 15장 「소스 코드 및 인프라 무결성」 — 커밋 서명 (p.429~433)

- **실측**: 커밋 저자가 오너·Claude·Codex 혼재. 서명 없음.
- **왜**: P17("증거는 만든 자가 쓸 수 없다")·P23(SHA 귀속)과 같은 축이다. **누가 이 SHA를 만들었는가**를 암호학적으로 고정하지 않으면 두 원칙 모두 저자 필드라는 위조 가능한 문자열 위에 서 있다.
- **SBOM(p.428)은 보류** — 배송 artifact가 아직 없다.

### ⑨ 3장 「코드 리뷰를 위한 모범 사례」 — 필수 리뷰 · 상태 검사 (p.129~142)

- **실측**: `docs/sot/git-workflow.md`가 **스스로** 적고 있다 — *"main 보호(직접 push 금지)는 기계 강제되어 있는지 실행으로 재확인 필요 — 미확인"*. 아직도 미확인이다.
- **적용**: 책의 "최소 2명 승인"은 1인 조직에 부적용. 가져올 것은 **required status checks + main 직접 push 차단** 한 줄뿐이다. P15③("판정 권한은 CI에 있다")이 GitHub 설정으로 강제되지 않으면 원칙이 아니라 문장이다.

## 5. 결론 — 순서

1. **액션 SHA 핀**(②) — 이미 브랜치가 열려 있다. 가장 싸고 가장 상위 공격면
2. **Dependabot**(①) — 파일 1개
3. **브랜치 최고령 · 리드타임 계측**(④) — 39개/31일이라는 실측이 이미 나와 있다
4. **피처 플래그 + 수명 주기**(⑤) — 3번의 원인을 닫는다
5. **CodeQL**(③) — P20 준수(스캔 대상 수 하한) 조건부

1~2는 각각 PR 1개. 3~5는 인수 기준을 따로 세워야 한다.

## 비범위

- 각 항목의 구현 설계·인수 기준은 이 문서에 없다. 채택이 결정된 항목별로 goal 문서를 따로 연다.
- 책 본문은 읽지 않았다. 판정 근거는 목차의 절 제목과 이 저장소의 실행 확인값이다.
