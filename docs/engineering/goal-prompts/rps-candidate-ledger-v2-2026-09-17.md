# LinkedIn Recruiter 후보 조사 실행 프롬프트 v2 — Single Ledger 구조 (2026-09-17)

**이 문서는 `rps-5position-email-followup-2026-09-17.md`를 대체한다.** 그 프롬프트대로 그대로 실행하지 마라 — Codex·Gemini 적대적 리뷰 양쪽이 공통으로 지적한 구조적 결함(레코드 파편화, 기컨택 미검증, 상태값 뭉뚱그리기)을 아직 반영하지 않은 버전이다.

## 왜 다시 쓰는가 (Codex + Gemini 공통 지적, 요약)

- **후보 레코드가 파편화됐다.** 이메일 CSV, 리포트, 컨택 큐가 각각 따로 존재해서 하나를 고치면 다른 하나가 낡은 채로 남는다. → **단일 원장(Single Ledger) 하나에서 모든 산출물을 생성**해야 한다.
- **"조회 안 됨"과 "이력 없음"을 구분 안 하고 있었다.** 제한된 범위에서 못 찾은 것을 "신규 컨택 가능"으로 넘기면 중복 제안 위험이 생긴다.
- **2촌이라 이메일 비공개일 것이라고 단정하지 마라.** 지난 조사에서 실제로 2촌 13명이 전부 막혔던 건 사실이지만, 그 패턴을 규칙으로 미리 가정하지 말고 **후보마다 실제로 시도하고 결과를 기록**해라. "구조적으로 불가능하다"는 결론도 매번 검증된 관찰이어야지, 지레짐작이면 안 된다.
- **점수만 있고 근거·확인 수준이 분리 안 됐다.** 적합도 점수와 "이 정보가 얼마나 확인됐는가"는 서로 다른 축이다. 필수 조건이 미확인이면 점수가 높아도 보완 대기로 둬야 한다.
- **기존 ChatGPT 답변·이전 세션 보고서는 정본이 아니라 검증할 가설이다.** 이번 작업에서 재확인 없이 "이미 확보됨"으로 넘기지 마라 — 이전 결과는 출발점(어디를 다시 볼지)으로만 쓰고, 필드 하나하나 다시 확인한다.
- **수정 요청은 PATCH가 아니라 FULL RECORD REBUILD.** 사용자가 필드 하나를 지적하면, 그 후보의 원장 레코드 전체를 프로필 재방문부터 다시 만든다.

## 핵심 원칙 — 후보자 1명 = 원장(ledger) 1행

아래 12개 항목이 하나의 완결된 레코드다. 하나라도 "확인 안 됨" 상태면 그 레코드는 **미완성**이고, 미완성 레코드를 완성된 것처럼 보고하거나 발송 대상에 넣지 않는다.

1. 이름
2. 현재 회사 / 현재 직책
3. LinkedIn 프로필 URL (`linkedin.com/in/...` 우선, 없으면 Recruiter `talent/profile/...`, 둘 다 있으면 둘 다)
4. 연결 차수 (1촌/2촌/3촌)
5. 이메일
6. 학력
7. 주요 경력
8. 해당 포지션과 잘 맞는 이유 (JD 요구조건과 후보 경력을 문장으로 직접 연결 — "경험 많아 적합함" 같은 일반론 금지)
9. 적합도 점수 (100점 만점, JD별 고정 가중치 기준)
10. 점수 근거 (2~4문장, 항목별 점수 내역 포함)
11. 과거 컨택 / InMail 이력
12. 추천 액션 (바로 컨택 / 검토 후 컨택 / 보류 / 제외)

### 필드마다 값과 별개로 "확인 상태"를 반드시 같이 적는다

값 하나만 적지 말고, 아래 4가지 상태 중 하나를 명시한다. 상태 없이 값만 있거나 "미확인"으로 뭉뚱그리는 것 자체가 결함이다.

- `확인됨` — 실제 값이 있음 (예: 이메일 hong@gmail.com)
- `확인 시도, 값 없음` — 접근은 됐지만 해당 정보 자체가 비공개/없음 (예: Contact info 열람했으나 이메일 칸이 비어있음)
- `접근 불가` — 구조적으로 열람 자체가 막힘, 왜 막혔는지 사유 포함 (예: 2촌이라 Add email 버튼만 뜸 — 인메일 발송 전에는 열람 불가)
- `조사 범위 밖` — 시간/범위 제약으로 아직 안 봄 (없다고 단정한 게 아니라 아직 안 본 것)

과거 컨택 이력은 특히: **"이력 없음"이라고 쓰려면 반드시 "어디를(프로필 메시지 탭 / 프로젝트 연결) 확인했는데 없었다"는 조사 범위를 같이 적는다.** 범위를 안 적은 "이력 없음"은 "조사 범위 밖"으로 처리한다.

## 점수 규칙

- 포지션(JD)마다 사전에 가중치 기준을 정하고(핵심 역량 항목별 배점), 그 기준 버전을 레코드에 같이 기록한다.
- 확인되지 않은 역량은 충족으로 계산하지 않는다 — 확인 안 된 항목은 0점 또는 "미확인이라 계산 제외"로 명시.
- **적합도 점수와 정보 확인 수준은 별개 축이다.** 점수가 90점이어도 이메일/연결차수/컨택이력 중 하나라도 `조사 범위 밖`이면 추천 액션은 자동으로 "검토 후 컨택" 이하로 낮추고, 필수 조건(예: 현재 실제 1촌 여부, 이메일 확보 가능성)이 미확인이면 점수와 무관하게 "보완 대기"로 둔다.

## 컨택 이력 처리

- 같은 포지션 또는 사실상 동일한 포지션으로 이미 컨택(contacted 상태)된 후보는 신규 추천에서 제외하고, 이력만 원장에 남긴다.
- 다른 포지션으로 컨택된 이력이 있는 후보는 자동 제외하지 않는다 — 어떤 포지션으로 언제 제안됐는지 기록하고, 현재 포지션 재제안 가치는 별도 판단 항목으로 남긴다(사용자 결정 대기).
- **발송 직전에는 반드시 재조회한다.** 조사 시점과 실제 발송 시점 사이에 상태가 바뀔 수 있으므로, 원장에 기록된 컨택 이력은 "조사 시점 스냅샷"임을 명시하고 발송 승인 전 재확인을 요구한다.

## 수정 요청 처리 — PATCH 금지, FULL RECORD REBUILD만

사용자가 "URL 빠졌어", "이메일 없잖아", "점수 근거 줘" 등 특정 필드를 지적하면:

1. 해당 후보를 원장에서 식별
2. 프로필을 다시 방문해서 12개 필드 전체를 재확인 (지적된 필드만 보지 않는다)
3. 원장의 해당 레코드를 통째로 교체
4. 완결성 체크(아래 §발송 전 검증)를 그 레코드에 대해 다시 실행
5. 지적된 필드만 답하지 말고, 전체 레코드를 다시 제시

## 검색 순서와 한도

- 포지션별로 1촌부터 탐색 → 충분히 탐색되면 2촌 → 이후 3촌.
- **무기한 탐색 금지.** 착수 전에 이번 조사의 시간 한도 또는 탐색 범위(예: 검색 페이지 N개, 후보 M명)를 정하고, 그 한도에 닿으면 "몇 명 중 어디까지 봤는지"를 원장 요약에 남기고 멈춘다. 인원수 목표를 먼저 채우려고 하지 말고 적합도 기준으로 계속 보되, 한도는 지킨다.
- 검색 결과 상단 몇 명만 보고 멈추지 않는다.

## 산출물 — 단일 원장에서 전부 생성

- 보고서·표·이메일 첨부는 전부 **하나의 원장 데이터**(예: 후보ID를 키로 한 표/CSV 한 장, 12개 필드 + 각 필드의 확인상태·출처·확인시각 컬럼 포함)에서 생성한다. 별도 CSV와 별도 리포트가 서로 다른 값을 가지면 안 된다.
- 최종 출력 형식(포지션별 섹션, 후보별 표기)은 기존 예시를 따르되, 각 필드 옆에 확인 상태를 괄호로 병기한다.

예:
```
이메일: hong@gmail.com (확인됨, Contact info, 2026-09-18 확인)
과거 컨택: 이력 없음 (조사범위: 프로필 메시지탭+프로젝트연결, 2026-09-18 확인)
연결 차수: 1촌 (확인됨, 2026-09-18 재확인 — 원 목록 라벨과 다를 수 있으므로 매번 재확인)
```

## 발송 전 강제 검증 (후보마다)

```
[ ] 이름
[ ] 현재 회사/직책
[ ] LinkedIn/Recruiter URL (실제 클릭 가능한 URL, "확인함" 같은 표현 금지)
[ ] 연결 차수 — 이번 조사에서 재확인한 값
[ ] 이메일 — 값 또는 명확한 미확보 사유
[ ] 학력
[ ] 주요 경력
[ ] 적합 이유 — JD 요구조건과 직접 연결된 문장
[ ] 적합도 점수 + 항목별 근거
[ ] 과거 컨택 이력 + 조사 범위
[ ] 추천 액션 — 점수와 정보 확인 수준을 모두 반영한 값
```
하나라도 `조사 범위 밖`이면 그 레코드는 **미완성**으로 표시하고 "보완 대기" 명단에 넣는다. 미완성 레코드는 신규 컨택 추천 목록·발송 대상에서 제외한다.

## 최종 상태 보고 (완료 시 반드시 이 숫자들을 포함)

- 조사 시도 후보 수
- 완결(12개 필드 전부 확인) 후보 수
- 보완 대기(필드 일부 `조사 범위 밖`) 후보 수
- 신규 추천 후보 수 (기컨택 제외 후)
- 확인된 1촌 수 / 2촌 수 / 3촌 수
- 이메일 확보 수 / 이메일 확인 시도했으나 값 없음 수 / 접근 불가 수
- 기컨택으로 제외한 수 (사유 포함)
- 0명인 항목이 있으면 0이라고 그대로 보고 — 없다고 숨기거나 뭉뚱그리지 않는다

**정상 완료 조건: "미완성" 레코드 수 = 0, 또는 보완 대기 명단으로 명시적으로 분리됨.**

## 발송·컨택 금지 원칙 (그대로 유지)

- 이번 작업은 검색 → 조사 → 원장 작성 → 사용자 보고까지다.
- 사용자가 명시적으로 지시하지 않는 한 LinkedIn 메시지·InMail·후보자 이메일 발송 0건.
- 내부 보고 이메일(사용자 앞)은 사용자가 지시한 경우에만 발송하며, 발송 전 위 완결성 체크를 통과한 레코드만 포함한다.
