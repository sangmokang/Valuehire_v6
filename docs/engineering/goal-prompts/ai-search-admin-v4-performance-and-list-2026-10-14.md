# 실행 프롬프트 — AI Search 운영 리스트와 관리자 화면 속도

## 목표

`https://admin.valuehire.cc/admin`의 로그인 상태 첫 표시와 메뉴 이동이 느린 원인을 계측해 v4 코드에서 개선한다. `https://admin.valuehire.cc/ai-search-list`는 2026-09-30 AI Search 운영 SOT와 2026-10-14 사용자의 추가 표시 요구에 맞춘다. Gmail로 오는 AI Search 내부 보고를 Fleet-job 진단에서 근거와 함께 조회할 수 있게 한다. 완료 선언은 코드·테스트·실제 배포 상태를 분리해 한다.

## 시작 전에 읽을 정본

1. v6 `docs/sot/ai-search-operations.md`와 링크된 `docs/engineering/ai-search-operations-original-2026-09-30.md` 전문. 원문 SHA-256은 `c5fa50e2d3b13c14c18cac7e4f4e0dd92270053e3b245aa312f40b57fc0eac2e`다. 최신 사용자 지시는 요약 SOT의 2026-10-14 절이다.
2. v4 `AGENTS.md`, `docs/engineering/admin-navigation-full-performance-audit-prompt-2026-07-22.md`, `app/ai-search-list/**`, `app/(admin)/admin/page.tsx`, 관리자 layout/middleware/auth, 현재 배포 브랜치와 PR #796의 실제 포함 여부. 로컬 main이 원격 main보다 뒤처질 수 있으므로 `git show`만으로 배포를 단정하지 않는다.
3. v6의 `task/ai-search-ops-wu00~03` 별도 작업 트리, 원본 WU-00~03의 구현/테스트/미검증 상태. 사용자의 다른 미커밋 변경을 건드리지 않는다.

## 작업 범위와 선행 조사

- **즉시 코드 변경 대상은 v4 관리자 화면과 리스트다.** v6는 Gmail/AI Search 정본·저장 경로와 실행 이력을 대조한다. v4 UI에서 v6 미구현 기능을 완료처럼 보이게 하지 않는다. 외부 시스템 연결이나 DB 객체가 실제로 없으면 원본 SOT WU 경계에 맞춰 필요한 로컬 구현과 검증을 진행하고, 운영 전환 필요 사항을 분리해 기록한다.
- 실제 `admin.valuehire.cc` 배포 SHA·v4/v6 소유 경계·Supabase 테이블/뷰/RLS·Gmail 수신 계정/레이블/메일 형식·기존 Fleet-job 저장소를 읽기 전용으로 확인한다. 이름이나 제목 유사성만으로 사건을 결합하지 않는다.
- 우선 현재 화면과 네트워크의 병목을 측정한다. 로그인한 실제 `/admin` 방문과 메뉴 클릭의 동일 경로를 변경 전·후 비교한다. 최초 HTML/TTFB, 서버 RSC, 외부 API·DB·파일 I/O, 클라이언트 bundle/hydration, cross-layout 전환, 핵심 내용 표시를 구분한다. `/admin` 비로그인 redirect 시간은 관리자 성능 증거로 쓰지 않는다. 브라우저 검증은 Aside를 쓴다.
- 근거 없는 전체 리팩터링을 하지 말고 측정에서 확인된 critical path를 우선 줄인다. 중복 조회 제거, 서버 대기 경로 정리, 필요한 병렬화/streaming, 적정 범위 쿼리·인덱스·캐시를 기존 패턴 안에서 검토한다. 숫자·오류·권한 검사를 제거하거나 실패를 0/빈 목록으로 바꿔 속도만 좋아 보이게 하지 않는다. 새 의존성은 추가하지 않는다.

## 리스트 인수 조건

1. **이름:** 원천에서 확인된 후보 이름을 목록에 보여 준다. 미확인 이름을 만들어내지 않는다. 동명이인은 ID/원천으로 분리한다.
2. **점수와 출처:** 점수의 평가 주체(ChatGPT/Claude/Gemini 등 실제 확인 값), 모델명/버전, 평가 시각, 점수 함수·평가/JD 버전과 근거 참조를 보여 준다. 근거가 없으면 `미확인`이라고 명시한다. 미분석/분석 실패/레거시 미검증/유효한 0점을 분리한다. 점수 계산식·가중치 변경은 범위 밖이다.
3. **프로필:** 대학·전공·`YY.MM~YY.MM`과 최근 경력 최대 3개의 회사·부서·직책·`YY.MM~YY.MM`을 목록에서 읽을 수 있게 한다. 확인되지 않은 값은 빈칸/미확인으로 남기고 없는 기간을 추정하지 않는다. 긴 원문과 전체 이력은 상세에 둔다.
4. **왜 잘 맞는지:** 목록은 짧은 bullet point, 상세는 원문과 연결된 풍부한 강점·위험·확인 필요 근거를 보여 준다. 목록 자르기로 저장된 근거를 잃지 않는다.
5. **매칭:** 회사–포지션 표시는 유지한다. 복수 모집 건은 최신 매칭 순으로 요약하고 `더 보기`와 상세 full version을 제공한다. 실제 모집 회차/ID가 다른 건을 제목만으로 병합하지 않는다.
6. 원본 §3.3의 서치 일시, 증거 기반 제안 발송, 담당·다음 행동 정보도 유지한다. 위 다섯 항목은 기존 7컬럼을 삭제하라는 뜻이 아니다. 점수와 적합 이유는 한 셀에 두더라도 시각적으로 구분한다. 목록 밀도와 키보드 접근성을 확인한다.
7. 검색은 권한 있는 **전체 DB**에서 수행하고 기본 50건/페이지, 선택 25/50/100, 안정적인 cursor/ID tie-breaker와 정확한 총수를 제공한다. 공백 단어는 AND, 각 단어의 필드는 OR이다. `%`, `_`, 따옴표는 리터럴로 검색한다. v4 PR #796의 검색 문자 삭제와 500건 출력 상한을 그대로 재사용하지 않는다. 기존 한글 이름 검색의 검증된 동작은 회귀시키지 않는다.
8. 사람인·잡코리아·LinkedIn의 발송 상태는 해당 계정·기간·페이지의 실제 증거로만 `확인됨`이 된다. 수집 실패, 미확인, 관측 범위 내 미발송은 구분한다. 내부 브리핑 메일과 ClickUp 완료는 제안 발송 증거가 아니다.
9. 주간 집계는 KST 일요일 00:00 포함~다음 일요일 00:00 미포함이며, 카드·그래프·드릴다운이 같은 스냅샷을 읽는다. 재검색·재평가·메일 재수집으로 사람/매칭/발송 건수가 늘지 않는다.

## Fleet-job과 Gmail

- Gmail 수신 메일이 내부 AI Search **보고**인지, 실제 후보 제안 이력인지 메시지 ID·발신/수신·본문 locator·원본 snapshot으로 판별한다. 내부 보고는 실발송 KPI를 0건 늘린다.
- 검증한 메일은 `source mailbox + message ID`를 기본 재수집 키로 기록하고, 보고 ID·후보/포지션 locator·받은 시각·원천 실행 시각(확인된 경우만)·연결 상태·파싱 오류를 보존한다. 동일 메일 재읽기는 같은 사건을 갱신/재확인한다.
- Fleet-job의 실행·동기화 뷰에 v6 기준 실행 상태, Gmail 보고 수집/연결 상태, 마지막 성공 시각, coverage와 오류를 표시한다. Gmail 메일을 Fleet 실행 성공이나 후보자 제안 완료로 자동 승격하지 않는다. 과거 메일의 포맷이 여러 개면 원본 WU-23대로 포맷별 검증 경계를 둔다. 실제 메일 발송 테스트를 하지 않는다.
- DB 저장→웹/내부 보고의 같은 snapshot 원칙, Supabase 웹 정본/SQLite outbox 관계, 실제 점수 함수 보존은 원본 SOT R-02/03/12를 따른다. 미구현 생산 경로를 새 UI만으로 해결됐다고 주장하지 않는다.

## 작업 순서와 검증

1. 현행 코드·배포/데이터 경로·변경 전 성능을 기록하고, 요구사항별 `충족/부분/미구현/확인불가` 표와 v4/v6 소유 파일을 만든다. PR #796에서 충족하는 부분은 재사용한다.
2. 병목별 작은 변경으로 `/admin`을 최적화하고, 같은 로그인 상태·경로·표본 수로 변경 전/후 p50/p95·오류율·핵심 내용 표시·메뉴 클릭 시간을 비교한다. 성능 수치가 없으면 빠르다고 보고하지 않는다.
3. 리스트 읽기/검색/페이지네이션, 이름·점수 provenance·프로필·근거·복수 매칭 UI, 상세, Fleet/Gmail 근거 투영을 의존 순서대로 구현한다. 물리 DB 변경이 필요하면 실제 스키마/RLS/백필/rollback을 먼저 검증한다. 운영 migration과 bulk 편입은 별도 실행 경계로 다룬다.
4. 집중 회귀시험: 501번째 이후와 10,000건 규모 검색, `김민수 토스` AND, `%`/`_`/따옴표 리터럴, 동명이인, 복수 포지션 최신순/더 보기, null/0/legacy 점수와 모델 provenance 부재, 학력·경력 날짜 누락, 근거 없는 bullet, 발송 미확인, Gmail 재수집, 일요일 KST 경계, 권한별 목록·총수·상세 누출, 실패한 외부 소스의 오류 표시. 테스트는 실제 데이터 조작 없이 합성/비식별 fixture를 쓴다.
5. v4의 관련 테스트·typecheck·lint/build와 v6의 관련 계약 테스트를 실행한다. 원본 §9.3의 합성 데이터 첫 50행 응답 p95 2초 목표를 측정 환경/반복 횟수와 함께 판정한다. 브라우저에서 관리자 페이지·리스트·상세·Fleet의 기능과 console/network 오류를 확인한다. 실제 배포 후 검증은 배포 SHA와 함께 별도 기록한다.
6. 결과 보고에는 바뀐 파일, 요구사항별 상태, 성능 before/after 측정값과 환경, 테스트 결과, 운영 미검증·승인 필요 작업, rollback을 명시한다. 로컬 통과와 운영 완료를 혼동하지 않는다.

## 실행 경계

로컬 조사·코드 편집·테스트·read-only 실측은 계속 진행한다. 외부 후보자 발송, 운영 DB bulk 쓰기, 실메일, scheduler 등록, 운영 배포처럼 외부 상태를 바꾸는 단계는 준비·검증을 마친 뒤 해당 승인 경계에서만 실행한다. 관련 없는 사용자 변경은 보존한다.
