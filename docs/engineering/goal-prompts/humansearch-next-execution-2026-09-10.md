# HumanSearch 작은 WU 실행 프롬프트 (2026-09-10)

## 결론

아래 지시문을 새 구현 세션에 붙여 넣으면 작은 작업부터 이어서 구현할 수 있다.
현재는 지시문을 저장했으며, 제품 구현과 온라인 작업 등록은 후속 실행에서 수행한다.

## 사용 자료

전체 Issue 명세는 [실행 장부](../humansearch-next-issues-wu-2026-09-10.md)에 있다.

```text
HumanSearch 다음 구현을 수행해라.

목표: 사람인 후보 1명을 검색→상세 열람→증거 저장·독립 재읽기→목록 복귀까지 완주한다.
그 뒤 Discord·ClickUp·Supabase, 잡코리아·LinkedIn, 반복 검색·평가를 순서대로 연결한다.

읽을 파일:
- AGENTS.md(세션에 주어진 지침 포함)
- docs/engineering/humansearch-next-issues-wu-2026-09-10.md
- docs/sot/git-workflow.md
- docs/sot/coding-principles.md
- docs/sot/verification-commands.md
- docs/sot/humansearch-browser-contract.md
- docs/sot/humansearch-l0-surface-contract.md

실행 범위:
1. 장부의 HS-00부터 미완료이며 선행 조건을 충족한 가장 작은 WU 하나를 고른다.
2. git status, 현재 main/원격 SHA, 관련 PR·Issue·worktree·소유 세션을 확인한다.
   01495b3 또는 예전 시험 수를 현재 사실로 고정하지 않는다. 같은 WU를 중복 구현하지 않는다.
   GitHub 조회 불가면 로컬 브랜치·커밋을 회수하되 원격·CI 상태는 NOT_RUN으로 남긴다.
3. Issue는 사업 결과 하나, WU는 검증 가능한 행동 하나로 관리한다.
   기존 Issue가 있으면 연결하고, 없으면 먼저 로컬 명세를 사용한다.
   GitHub 등록·push·PR까지 이 세션에 요청됐으면 중복 조회 뒤 실행한다.
4. WU 하나 = 작업 워크트리 하나 = 인수 기준 하나 = PR 하나.
   여러 외부 시스템을 동시에 연결하거나 3개 이상 행동이 붙으면 구현 전에 자식 WU로 나눈다.
   main에 직접 제품 코드를 쓰지 않는다. 남의 변경을 되돌리거나 브랜치를 삭제하지 않는다.

각 WU 카드:
- 사용자 결과, 포함/제외, 입력·출력·오류·경계·부작용
- 소유 파일, 선행 PR·SHA, 시험 명령 1개, 정상/음성 사례
- 상태, RED/GREEN SHA, 감사 지문·검토자, 적대 재현, 미검증, 복구 방법
예정 경로/명령은 아직 없다고 표시하고 해당 WU에서만 만든다.

각 WU의 필수 루프:
A. 최소 행동 시험을 실행해 실제 단언 실패를 확인한다.
   import 오류·수집 0·문법 오류는 RED가 아니다.
   독립 검토자가 시험과 요구의 일치를 확인한 뒤 시험·fixture RED 커밋.
B. 최소 제품 구현. 기존 RED 시험 기대값 변경 금지.
C. 정조준 시험. 순수 판정=속성 시험, 저장=실제 임시 SQLite,
   경쟁=장벽을 둔 재현, 외부 경계=실제 호출 경로와 네트워크 차단 시험.
D. 독립 Codeaudit: $codeaudit 스킬을 읽는 별도 검토 맥락에 카드·diff·시험을 제공한다.
   요구→계약→입력→처리→출력→시험이 연결되는지 읽기 전용으로 판정한다.
E. 별도 적대 검증: 정상 대조군 통과와 결함 주입 시 실패를 모두 실행한다.
   항상 허용/항상 거부/핵심 효과 생략, 경계·중복·중간 종료·오래된 증거 중 관련 사례를 공격한다.
   격리 사본에서만 변이를 실행한다. 검토 문구나 시험 개수만으로 PASS를 만들지 않는다.
F. 재현된 결함 수정→해당 시험·감사·적대 검증 반복.
   새 결함 시험은 새 회귀 파일·별도 RED 커밋. 관련 없는 결함은 별도 Issue로 분리.
G. diff 검사·정적 검사·회귀·비밀 스캔 후 감사받은 지문과 같은 제품 코드를 GREEN 커밋.
   높음 이상 미해결, AC 실패, 필수 적대 검증 NOT_RUN이면 GREEN 확정 금지.
H. 커밋 후 SHA·파일 지문 대조. 내용 변경 시 영향받는 검증을 갱신.
   원격 배송 요청이 있으면 push→draft PR→CI 조회→검증 SHA 확인까지 실행한다.
   로컬 커밋 완료와 VERIFIED·MERGED는 구분한다. 자동 merge는 하지 않는다.

Codeaudit에 넘길 프롬프트:
"$codeaudit. 이 WU 카드와 현재 diff를 읽기 전용으로 감사하라.
각 AC의 입력→처리→출력·부작용→시험 연결, 가짜 정상·항상 거부·누락 경계를 확인하라.
file:line과 재현 명령을 제시하고 구현 확인/부분 구현/불일치/검증 불충분을 구분하라.
현재 지문과 다른 옛 실행 결과를 승인 근거로 사용하지 마라. 직접 수정하지 마라."

적대 검증자에게 넘길 프롬프트:
"이 WU가 틀렸는데도 초록이 되는 최소 반례를 격리 사본에서 실행하라.
정상 대조군은 통과해야 한다. 관련 결함 하나를 주입하면 기존 시험이 실패해야 한다.
중복·빈값·경계·중간 종료·경쟁·외부 응답 유실·오래된 SHA 중 해당 부류를 공격하라.
mutation diff, 실행 명령·종료값·대상 지문, 살아남은 변이를 보고하라.
제품 워크트리·실제 포털·운영 DB에는 공격이나 변이를 실행하지 마라."

검증 도구:
- git diff --check
- cd humansearch && uv run --no-sync pytest -q tests/test_hs_XXYY.py
  (XXYY는 선택 WU의 실제 숫자로 바꾼다. 기존 시험이면 그 node ID를 카드에 적는다.)
- Python 변경: humansearch에서 uv run --no-sync ruff check src tests,
  uv run --no-sync mypy src tests
- 저장소 루트에서 bash verify.sh
- 원격 배송 시 bash scripts/verify/check-verified-sha.sh task/<실제-브랜치>
새 acceptance 스크립트가 꼭 필요하면 같은 WU에서 CI·명령 정본에 연결한다.
기존 pytest 수집으로 충분한 함수마다 별도 검사 프레임워크를 만들지 마라.

증거 경계:
독립 맥락 검토와 OS 권한 격리를 혼동하지 마라. HS-04.02/03 이전의 같은 UID 하위 에이전트
검토는 로컬 검토로 표시한다. P17 준비 전에는 최종 독립 영수증·라이브 검증 완료를 주장하지 마라.
구현자가 독립 판정/라이브 영수증을 쓰지 않는다. 필수 Claude V1/Codex V2는 실제 도구 실행과
출처가 있을 때만 표기한다. 불가하면 NOT_RUN, 사용할 수 있는 독립 검토의 범위는 정직하게 적는다.
정본·계약 개정은 영향·되돌리기·기존 결정 대체·필수 교차 검증·실제 승인 근거를 포함한다.
이미 기록된 사용자 결정을 반복해서 묻지 않는다. 새 권한이 실제 필요한 외부 작업만 분리한다.
HS-04.01/HS-05.01에서 L3 결정·승인 출처와 실제 미해제 조건을 대조한다.
브라우저 정본 끝의 '이 정본이 병합되기 전' D0 승인 대기는 PR #34 병합 전 역사 기록이다.
병합된 D0를 미승인으로 되돌리지 않는다. 최신 세션 지시와 기존 승인으로 덮이는 로컬 구현은 계속한다.
라이브 직전에는 §12 조건과 현재 승인 범위를 확인하며, 실제 미충족인 외부 행동만 NOT_RUN으로 둔다.

안전·범위:
3채널 Aside 정책과 v1~v5 코드 의존 0을 유지한다.
선택적인 Chrome 복귀 실증(HS-12.06)은 사람인 새 전용 프로필만 대상으로 한다. LinkedIn에 확대하지 않는다.
자동 로그인·비밀번호 입력·메시지 자동 발송을 구현하지 않는다.
실제 포털 관측은 저장·보존·권한·중단·독립 증거 선행 관문 뒤에만 한다.
현재 실행 세션이 승인받은 테스트 범위 밖 운영 쓰기·계정 변경·브라우저 재시작은 하지 않는다.
저장 실패는 순회 정지, STOP은 재개보다 우선, 목표 탭이 0/2개 이상이면 거부.
원본 이력서·세션 값·키는 Git·로그·PR·Issue에 남기지 않는다.

커밋은 Lore 형식: 왜 바꿨는지 첫 줄, Constraint/Rejected/Confidence/Scope-risk/Directive/
Tested/Not-tested 중 실제 의사결정에 필요한 trailer만 넣는다. 훅은 우회하지 않는다.
RED는 의도된 실패 시험 커밋, GREEN은 테스트·감사·적대 검증을 통과한 구현 커밋이다.

한 WU 완료 후 선행 조건을 충족한 다음 WU로 계속한다.
선행 PR 위 누적 브랜치는 base SHA를 밝히고, 라이브 선행 병합 조건은 우회하지 않는다.
복구 가능한 로컬 편집·시험·감사·커밋마다 재확인을 묻지 않는다.
막히면 그 WU의 원인·해제 조건을 기록하고 독립 WU만 계속한다. 실패를 완료로 바꾸지 않는다.

매 보고: 현재 Issue/WU, 실제 사용자 행동, 변경 파일, 시험 결과, Codeaudit/적대 판정,
RED/GREEN SHA, 원격·CI·병합 상태, 미검증, 다음 한 개를 짧게 적는다.
최종 완료는 모든 필수 WU 병합과 각 채널 실제 완주 증거가 있을 때만 선언한다.
```

→ 이 프롬프트는 작은 작업마다 시험·독립 검토·실패 주입·커밋을 반복하게 한다.
문서 저장 요청과 제품 실행 요청을 구분하며, 새 실행 세션에서는 가장 먼저 남은 WU부터 진행한다.
