> 다음 세션(Claude)이 그대로 읽고 실행하는 자율 프롬프트다. /strict 모드로 돈다.
> 위험 등급: **Phase 0(스펙 개정)은 L1+ 문서 작업**, **Phase 1~5(구현)는 L3 풀하네스** — 운영 배포체(Valuehire_v4, admin.valuehire.cc)의 데이터베이스·화면·발송 도구를 바꾸고 후보 개인정보를 다루기 때문이다.

## 결론 (사장님 브리핑 — 먼저 읽는 요약)

**무엇을 하는 지시서인가.** 오늘 감사에서 "그대로 만들면 안 된다"고 판명난 잔디밭 지도 설계서를 먼저 2판으로 고치고, 고친 설계서가 다시 적대 검증을 통과한 뒤에만 실제 화면·장부 구현에 들어가게 하는 작업 지시서입니다.

**왜 바로 구현하지 않는가.** 감사 결과, 현재 설계서는 다섯 색깔 중 세 개가 실제 저장된 데이터와 다른 기준 위에 서 있습니다. 이대로 만들면 "완성됐는데 지도가 온통 투명"이 됩니다. 설계서를 고치는 데는 하루가 들지만, 잘못 만든 뒤 다시 만드는 데는 일주일이 듭니다.

**서로 지지 않게 하는 장치.** 만드는 쪽(클로드)은 제출 전에 자기 결과물을 스스로 공격해 결함 목록을 먼저 내야 하고, 검증하는 쪽(codex)은 그 목록에 없는 결함을 새로 찾아야 제 몫을 한 것으로 칩니다. 매 단계 "누가 몇 건을 먼저 잡았나" 점수표를 남겨 양쪽 다 긴장을 유지합니다.

**사장님이 결정하실 것 세 가지.** ① 후보 개인정보(이름·프로필 주소)의 보관 기간, ② 계측 시작 전의 과거 발송 기록을 얼마나 소급해 채울지, ③ 운영 데이터베이스에 실제 변경을 적용하는 각 시점의 승인 — 이 지시서는 ③ 직전마다 반드시 멈추고 여쭙게 되어 있습니다.

## 판단 근거 (2층)

### 결정 A — 구현 전에 "스펙 v2 개정"을 별도 단계로 둔다
> **무엇을** — 반증된 v1을 고친 v2 문서를 만들고, v2가 적대 검증을 통과한 뒤에만 코드를 짠다.
> **왜** — 감사가 반증한 문서가 정본으로 남아 있으면 구현자가 어느 쪽을 따를지 모호해지고, 모호함은 반드시 "문서 반, 감사 반" 잡종 구현으로 이어진다.
> **버린 길** — "구현하면서 그때그때 고치기". 빠르지만 판정 기준표(T)가 사라져 검증자들이 채점할 기준이 없어진다.
> **대가** — 반나절~하루의 착공 지연.
> **되돌리기** — v2가 또 틀리면 같은 감사 절차로 v3. 문서 단계라 되돌림 비용이 가장 낮다.

### 결정 B — 검증 승부를 "선제 자기공격 + 신규 발견 점수제"로 절차화한다
> **무엇을** — 구현자는 산출물마다 자기공격 로그(스스로 찾은 결함·시도한 반증)를 먼저 내고, codex는 그 로그에 없는 신규 결함 발견으로만 성과를 인정받는다. 단계마다 [Claude 선제 발견 M / codex 신규 발견 N / 2차 검증 신규 발견 K] 점수표를 장부에 남긴다.
> **왜** — 사장님 지시("서로 지지 마라")의 실현. 반증 의무가 없는 검증은 동의·요약으로 끝나기 쉽다(§5 반증 의무의 배경 사고와 동일).
> **버린 길** — 지시 없는 자유 검증. 오늘 감사처럼 잘 되는 날도 있지만, 잘 되는 날에 의존하는 절차는 절차가 아니다.
> **대가** — 단계당 검증 왕복이 최소 1회 늘어난다.
> **되돌리기** — 점수 경쟁이 트집 잡기 소모전이 되면 사장님 승인 하에 표준 V1→V2 절차로 축소한다.

### 결정 C — 감사가 증명 못 한 것은 스펙 확정 전에 실측한다
> **무엇을** — 오늘 감사가 "저장소만 봐서는 모른다"고 남긴 운영 데이터 실값 3종을, v2 확정 전에 읽기 전용 조회로 직접 확인한다.
> **왜** — v1이 무너진 원인이 정확히 "스키마만 보고 실제 적재를 안 따라간 것"이었다. 같은 함정을 v2에서 반복하면 감사가 무의미해진다.
> **버린 길** — 구현하며 확인. 확인 결과가 스펙을 바꿀 수 있는데 그때는 이미 코드가 있다.
> **대가** — 운영 데이터베이스 읽기 접근 필요(쓰기는 금지).
> **되돌리기** — 실측 자체는 읽기 전용이라 되돌릴 것이 없다.

### §3 Phase 0 — 스펙 v2 개정 (L1+, 문서 + 읽기 전용 실측)

**0-1. 운영 실측 (전부 SELECT만 — 운영 데이터베이스에 쓰기 절대 금지):**

1. Postgres 버전 — 발송 원장의 중복 방지 방식 선택에 필요(15 이상이면 `UNIQUE NULLS NOT DISTINCT` 사용 가능, 미만이면 COALESCE 식 인덱스).
2. `position_batch_steps.position_id` 실값 5건 이상 ↔ `pipeline_position_cards`의 ClickUp task id 대조 — 감사 R8이 "형식 강제 없는 text"라고 반증한 조인 키의 실제 대응 여부.
3. `pipeline_candidates` 중 ClickUp 미러 유래 행의 `jd_id`·이름 관련 컬럼 실값 분포 — 감사 R5가 지적한 "매칭에 쓸 컬럼이 비어 있음"의 실제 비율.
4. `pipeline_candidates.stage` 실제 저장값 전수(distinct) — 감사 R4의 영문 키 집합을 눈이 아니라 쿼리로 확정.

실측 명령과 출력 전문을 v2 문서 3층에 그대로 붙인다. 개인정보가 섞이면 §8-1 민감정보 예외(가린 사실·원본 위치·지문 기재)를 따른다.

**0-3. 산출:** `docs/engineering/admin-position-map-spec-v2-<작성일>.md` (v6 저장소). v1의 유효 부분(§8 화면, §2 결정 1~3, §10 기계 인수 기준의 살아남는 항목)은 계승하고, 문서 맨 앞 사장님 브리핑(§1⑪)과 `## 적대 검증 로그` 절을 갖춘다. v1 상단의 개정 대기 표식을 "v2로 대체됨"으로 갱신한다.

### §4 Phase 1~5 — 구현 (Valuehire_v4, L3 풀하네스)

각 Phase = 독립 worktree(`task/<name>` 브랜치) + RED 시험 먼저 + 최소 구현 + 검증 + 자기공격 로그 + V1(codex) + V2(리셋 Claude) + PR. **머지 전까지 어떤 단계도 "완료"라 부르지 않는다.**

| Phase | 내용 | 핵심 RED (v2에서 AC로 상세화) |
|---|---|---|
| P0 | 미러 데이터 계약 복구(원본 상태 보존 + 전이 기록 + sync_state 연결) | 미러 dry-run에 상태 변경 fixture를 넣으면 전이 행이 계획되고, 원본 상태명이 보존 컬럼에 남는다. 기존 vitest 전부 초록 유지 |
| P1 | 발송 원장 + 판정 SQL 함수 | v2 §10 계승 항목 전수(색 우선순위·되감기·중복 방지·시각 없는 사건 제외·0건 시 실패) |

→ 표 해석: P0가 새로 생긴 것 말고는 v1 §9의 단계 구조를 계승한다. 순서를 바꾸지 말 것 — P1의 되감기 시험은 P0가 만드는 전이 기록을 전제한다.

**v4 게이트 명령은 추측하지 않는다.** 착수 시 v4 저장소에서 /strict §3의 3분기 판정(`make -n red-ledger` → `package.json` scripts → SOT 문서·`scripts/`·CI 워크플로 순서로 실행 확인)을 돌려 실제 명령을 확정하고, 그 결과 표를 첫 보고에 첨부한다.

**하드 멈춤점 (사장님 승인 없이 절대 넘지 않는다):**
1. 운영 Supabase에 마이그레이션·데이터 변경을 적용하기 직전 (Phase마다).
2. ClickUp에 쓰기가 발생하는 어떤 작업이든 그 직전.
3. cron 등 자동 반복 실행을 등록하기 직전.
4. 발송 도구 계측 코드를 실제 발송 경로에 병합하기 직전 (P2).

### §5 codex(V1) 호출 규칙 — 매 검증마다 그대로 지킨다

1. **Agent 도구, `subagent_type: "codex:codex-rescue"`, `name` 파라미터 금지**(이름을 주면 일반 Claude 서브에이전트가 도는 사고 — 2026-08-12 실측). 슬래시 명령 `/codex:rescue`는 해설 금지 규칙이라 쓰지 않는다(사장님이 직접 치시는 경우만 예외, 그때는 직후에 3층 해석을 별도로 드린다).
2. 판정을 **파일로 쓰게** 지시: 경로는 scratchpad 경유 후 즉시 `docs/engineering/verdicts/` 아래 추적 파일로 이동. 첫 줄은 `VERDICT: PASS|FAIL`. 읽기 전용이라 파일을 못 쓰면 화면 출력을 받은 쪽이 저장한다.
3. 프롬프트에 반드시 포함: ① 산출물+AC+계약+자기공격 로그(구현 추론 과정은 비전달 — 격리), ② 사장님 적대 지시 원문, ③ "자기공격 로그에 없는 신규 결함을 찾아라, 동의만 하면 실패", ④ 반증 의무("X를 Y로 깨려 했으나 실패" 기록), ⑤ /strict §8-7의 출력 형식 지시 블록 전문.
4. 판정 수신 후: **신분 확인**(subagent 기록에서 `codex-companion` Bash 실행 존재 여부 — 없으면 V1이 아니라 V2급으로 기록하고 V1 재실행) → 형식 검사(`brief-lint`) → 내가 정조준한 항목이 빠졌으면 전달 실패부터 의심 → 원문 100% 장부 보존 + 사장님 보고는 3층 번역(고정값: 판정 단어·결함 수·심각도·file:line + 결함별 원문 제목·원인·사업 영향 1:1 대응).
5. 재요청(`--resume`)은 이어받을 세션이 내 작업임을 확인할 수 없으면 쓰지 말고 새 검증을 돌린다.

### §6 v4 저장소 규칙 회수 (착수 첫 작업)
