# P03 — 포지션 명세와 시작 가능 관문

아래 내용을 새 Codex 작업의 첫 프롬프트로 그대로 사용한다.

## 목표

ClickUp 원문에서 추측하지 않고, 승인된 필수값이 모두 있을 때만 포지션을 `READY`로 판정한다.

## 선행조건

P00B·P01·P02 `CONTRACT_PASS`.

## 작업 소유 범위

`humansearch/src/humansearch/positions/spec.py`, `contracts/position_policy.schema.json`, 스키마·판정 함수, 합성 fixture와 단위시험.

경로가 현재 SOT와 충돌하면 임의로 다른 영역까지 고치지 말고 목표 문서에 충돌을 증거와 함께 기록해 이 프로젝트를 중단한다.

P03은 ClickUp 읽기 스냅샷 **필드 계약**만 합성 fixture와 주입 포트로 고정한다. 실제 ClickUp 읽기와 라이브 스냅샷 생성은 P05가 소유하므로 P03은 P05를 선행조건으로 요구하지 않는다.

## 비범위

ClickUp API 호출, 언어모델 최종 승인, 포지션 우선순위 계산.

## RED 먼저

정식 고객사·포지션 ID와 열린 상태, 표시 이름·직무기술서 원문 참조, 필수 경력·직무·산업·근무지·언어·자격, `target_eligible_candidate_count`, 허용·금지 채널, 중복 접촉 기간, 민감 기준 목록과 승인 근거, 후보 원문 보관기간, 접근권한 계약 버전, ClickUp 읽기 스냅샷 지문, 정책 버전·승인자·승인시각 중 필수값 하나가 빠져도 `READY`가 되는 실패 시험을 먼저 만든다. 민감 기준이 없다는 명시적 빈 목록은 유효하지만, 항목이 있으면 항목별 사람 승인 근거가 모두 있어야 한다.

## 구현 계약

`position_policy` 저장 기술을 하드코딩하지 않고 P00A 오너 결정과 P00B 데이터 책임 정본이 승인한 위치를 포트로 주입한다. 정식 포지션 ID는 `clickup:<workspace_id>:<position_task_id>`, 정식 고객사 ID는 승인된 ClickUp 관계 또는 승인된 정책이 가리키는 `clickup:<workspace_id>:<client_task_id>`로만 만든다. 고객사 이름 문자열 추측·대소문자/접미사 정규화로 ID를 만들지 않으며, 관계가 없거나 ClickUp 스냅샷과 정책의 고객사 ID가 다르면 `NEEDS_DECISION`이다.

필수 계약은 정식 고객사·포지션 ID와 열린 상태, 표시용 고객사·포지션명과 직무기술서 원문 참조, 필수 경력·직무·산업·근무지·언어·자격, `target_eligible_candidate_count`, 허용·금지 채널, 중복 접촉 기간, 민감 기준의 명시적 목록과 항목별 사람 승인 근거, 후보 원문 보관기간, 접근권한 계약 버전, ClickUp 읽기 스냅샷 지문, 정책 버전·승인자·승인시각이다. 민감 기준 목록은 빈 목록일 수 있지만 누락될 수 없고, 비어 있지 않으면 모든 항목에 승인 근거가 있어야 한다. `target_eligible_candidate_count`는 hard gate와 승인된 근거 완전성 기준을 통과해야 하는 고유 후보 목표 수이며 P06 우선순위와 P07 부족분이 같은 값을 그대로 소비한다. `target_pre_interview_count`는 선택적 사업 퍼널 목표이고 누락돼도 `READY`를 막지 않으며 우선순위·부족분의 분모로 쓰지 않는다. 후보 원문 자체는 이 계약에 저장하지 않는다. ClickUp 열린 상태나 지문이 달라지면 `READY`를 취소한다. 원문 참조와 입력 지문을 보존하고 `READY | NEEDS_DECISION | CLOSED`만 순수하게 계산하며 누락값·무효값·승인자를 필드별 사유로 반환한다.

## 가짜 합격을 깨는 시험

필수 계약 필드 각각의 누락, `target_eligible_candidate_count` 0/음수, `target_pre_interview_count`와 필드 교환, 선택값 누락, 닫힌 포지션, 알 수 없는 허용·금지 채널, 중복 접촉 기간 0/음수, 민감 기준 목록 누락·미승인 항목, 후보 원문 보관기간 누락·무효값, 접근권한 계약 버전 누락·낡은 값, 낡은 정책 버전, ClickUp 지문 누락·불일치, 고객사 관계 누락·불일치, 같은 이름의 서로 다른 고객사 ID, 다른 표기의 같은 고객사 ID, 같은 입력 키 순서 변경을 시험한다.

## 검증

표 기반 경계시험, 100회 결정 지문 동일성, 전용 인수 검사, `bash verify.sh`.

## 원자적 인수 기준

후속 구현은 `bash scripts/acceptance-ai-ra-p03.sh` 한 명령으로 위 필수 계약 필드 각각을 한 번씩 제거한 표 기반 시험이 모두 `NEEDS_DECISION`과 필드별 사유를 내고 작업 제안을 만들지 못하며, 전체 입력의 준비 상태와 지문은 100회 동일함을 검사해야 한다. P03의 출력 계약은 `target_eligible_candidate_count`와 선택값 `target_pre_interview_count`를 서로 다른 필드로 직렬화하고, 선택값이 없어도 `READY`가 될 수 있으며 두 값을 교환한 변조를 거부해야 한다. P06과 P07이 이 계약을 실제 계산 입력으로 소비하는 검증은 각 후속 프로젝트의 자기 인수 스크립트가 소유한다. 승인된 ClickUp 관계에서 정식 고객사·포지션 ID가 재현되고, 이름 표기가 달라도 같은 관계 ID면 같은 정식 ID이며 같은 이름이라도 관계 ID가 다르면 합치지 않아야 한다. 정상 실행은 `PASS AI_RA_P03 <실제 핵심 건수>`를 출력하되 실제 핵심 건수는 반드시 1 이상이고 종료값 0을 남겨야 하며, 핵심 차단을 한 줄 고장 낸 반대 시험은 0이 아닌 종료값이어야 한다. 이 프로젝트는 자기 인수 스크립트만 소유한다. P04가 소유한 `scripts/acceptance-ai-ra-all.sh`와 서버 workflow가 이름 규칙으로 자동 발견해야 하며, 이후 프로젝트는 공용 workflow를 직접 수정하지 않는다.

## 라이브 증거와 멈춤점

합성 포지션만 사용한다. ClickUp 실데이터는 읽지 않고 계약이 통과하면 멈춘다.

## 공통 strict 실행 지시

1. 기본 작업공간을 수정하지 말고 최신 기준 커밋에서 이 프로젝트 전용 worktree와 `task/` 브랜치를 만든다.
2. 코드보다 먼저 이 프로젝트 목표 문서를 작성하고 원자적 인수 기준 1개, 반대 시험, 비범위, 실제 검증 명령을 적는다.
3. `docs/sot/INDEX.md`, `coding-principles.md`, `git-workflow.md`, `hook-contracts.md`, `verification-commands.md`와 P00B 이후 새 정본을 전문으로 읽고 체크리스트를 목표 문서에 남긴다.
4. v4/v5 코드는 행동·실패 사례와 테스트 오라클만 참고한다. import, 복사, subprocess 호출, 런타임 의존성은 금지한다.
5. RED를 실제 런타임 시험으로 먼저 만들고 실패 출력을 목표 문서에 남긴다. 소스 문자열 검색만으로 기능을 증명하거나 테스트 0건을 PASS로 세지 않는다.
6. 최소 구현 뒤 대상 시험→자기 번호 인수 검사→P04 공용 `scripts/acceptance-ai-ra-all.sh`→`bash verify.sh` 순으로 실행한다. P04 전 프로젝트는 자기 스크립트만 만들고 P04가 공용 배관을 연결하며, P04 이후 프로젝트는 이름 규칙 자동 발견을 증명하고 `.github/workflows/verify.yml`을 직접 수정하지 않는다.
7. 비밀·후보 원문·인증정보를 터미널, fixture, 문서, 커밋에 남기지 않는다. 외부 쓰기·발송·운영 DB 변경·배포는 이 프롬프트가 명시적으로 허용하지 않으면 하지 않는다.
8. `claude -p` 1차 적대검토를 실행하고 각 지적을 Codex가 직접 명령으로 재현한다. 한 항목이라도 동의하면 수정 후 1차부터 다시 반복한다.
9. 완료 보고는 변경 파일, 실제 처리 건수, 테스트/인수 검사 종료 코드, `git diff --check`, 남은 `NOT_RUN`과 위험을 구분한다. 검사가 하나라도 빨갛거나 증거가 없으면 완료라고 하지 않는다.
