# P22 — 사람인 허용 범위 후보 1명 관찰

아래 내용을 새 Codex 작업의 첫 프롬프트로 그대로 사용한다.

## 목표

정책과 계약이 확인된 범위에서 사람인 검색 결과 후보 1명을 관찰하고 증거 영수증을 남기는 최소 실행기를 증명한다.

## 선행조건

P02 `CONTRACT_PASS`, P18·P19·P20·P21 `LIVE_PASS`, 사람인 서면/계약 허용 범위와 실제 계정 작업 승인.

## 작업 소유 범위

`humansearch/src/humansearch/browser/channels/saramin.py`, `contracts/saramin/markers.json`, 실제 화면에서 파생하고 개인정보 제거를 검증한 `humansearch/tests/fixtures/captures/saramin/` 자료, 한 후보 smoke 명령과 증거 스키마.

경로가 현재 SOT와 충돌하면 임의로 다른 영역까지 고치지 말고 목표 문서에 충돌을 증거와 함께 기록해 이 프로젝트를 중단한다.

## 비범위

대량 수집, 연락·제안 발송, CAPTCHA/2FA 우회, 속도·기기 분산을 통한 제한 회피.

## RED 먼저

정책 미확인·탭 불일치·사람 개입·표시 규약 변경에도 후보 읽기가 진행되거나, 전체 시나리오를 가짜 브라우저만으로 통과시키는 실패 시험을 먼저 만든다.

## 구현 계약

표시자는 코드가 아니라 `contracts/saramin/markers.json` 한 곳에 둔다. 사전 관문 전수 통과 뒤 후보 1명에서 허용된 최소 필드와 원문 위치 지문만 staged evidence로 만든다. 판정·배선·동작 시험을 분리하고 대상 0명은 PASS가 아니다.

## 가짜 합격을 깨는 시험

로그아웃, 보안문자, DOM/접근성 구조 변경, 중복 후보, 개입 경합, 계정 경고, stale lease를 시험한다.

## 검증

개인정보 제거 검사가 붙은 실캡처 파생 fixture로 판정·표시자 변화 RED/GREEN을 증명한다. 별도 오너 승인과 허용 근거가 있을 때만 라이브 후보 정확히 1명·외부 쓰기 0건·명령 전후 영수증을 기록하고 `bash verify.sh`를 실행한다. 가짜 브라우저 fixture는 주 증거가 될 수 없다.

## 원자적 인수 기준

후속 구현은 `bash scripts/acceptance-ai-ra-p22.sh` 한 명령으로 승인된 실제 화면에서 후보 정확히 1명·외부 쓰기 0건·명령 전후 영수증을 남기며 0명·가짜 화면은 합격이 아님을 검사해야 한다. 보안문자·2FA·로그아웃·계정 선택·계정 경고·정책 미확인 화면은 브라우저 명령 0건이고, 속도·기기·계정 분산에 의한 제한 우회 경로가 없음을 반대 시험으로 검증해야 한다. 정상 실행은 `PASS AI_RA_P22 <실제 핵심 건수>`를 출력하되 실제 핵심 건수는 반드시 1 이상이고 종료값 0을 남겨야 하며, 핵심 차단을 한 줄 고장 낸 반대 시험은 0이 아닌 종료값이어야 한다. 이 프로젝트는 자기 인수 스크립트만 소유한다. P04가 소유한 `scripts/acceptance-ai-ra-all.sh`와 서버 workflow가 이름 규칙으로 자동 발견해야 하며, 이후 프로젝트는 공용 workflow를 직접 수정하지 않는다.

## 라이브 증거와 멈춤점

허용 근거나 계정 승인이 하나라도 없으면 `BLOCKED_POLICY` 또는 `BLOCKED_AUTH`이며 프로젝트는 `LIVE_PASS`가 아니다. `NOT_RUN`을 준비 완료로 보고하지 않고 우회하지 않는다.

## 공통 strict 실행 지시

1. 기본 작업공간을 수정하지 말고 최신 기준 커밋에서 이 프로젝트 전용 worktree와 `task/` 브랜치를 만든다.
2. 코드보다 먼저 이 프로젝트 목표 문서를 작성하고 원자적 인수 기준 1개, 반대 시험, 비범위, 실제 검증 명령을 적는다.
3. `docs/sot/INDEX.md`, `coding-principles.md`, `git-workflow.md`, `hook-contracts.md`, `verification-commands.md`와 P00B 이후 새 정본을 전문으로 읽고 체크리스트를 목표 문서에 남긴다.
4. v4/v5 코드는 행동·실패 사례와 테스트 오라클만 참고한다. import, 복사, subprocess 호출, 런타임 의존성은 금지한다.
5. RED를 실제 런타임 시험으로 먼저 만들고 실패 출력을 목표 문서에 남긴다. 소스 문자열 검색만으로 기능을 증명하거나 테스트 0건을 PASS로 세지 않는다.
6. 최소 구현 뒤 대상 시험→자기 번호 인수 검사→P04 공용 `scripts/acceptance-ai-ra-all.sh`→`bash verify.sh` 순으로 실행한다. P04 전 프로젝트는 자기 스크립트만 만들고 P04가 공용 배관을 연결하며, P04 이후 프로젝트는 이름 규칙 자동 발견을 증명하고 `.github/workflows/verify.yml`을 직접 수정하지 않는다.
7. 비밀·후보 원문·인증정보를 터미널, fixture, 문서, 커밋에 남기지 않는다. 외부 쓰기·발송·운영 DB 변경·배포는 이 프롬프트가 명시적으로 허용하지 않으면 하지 않는다.
8. `claude -p` 1차 적대검토를 실행하고 각 지적을 Codex가 직접 명령으로 재현한다. 한 항목이라도 동의하면 수정 후 1차부터 다시 반복한다.
9. 완료 보고는 변경 파일, 실제 처리 건수, 테스트/인수 검사 종료 코드, `git diff --check`, 남은 `NOT_RUN`과 위험을 구분한다. 검사가 하나라도 빨갛거나 증거가 없으면 완료라고 하지 않는다.
