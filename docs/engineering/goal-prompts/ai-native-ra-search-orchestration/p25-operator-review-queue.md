# P25 — 운영자 후보 검토 큐와 판정 영수증

아래 내용을 새 Codex 작업의 첫 프롬프트로 그대로 사용한다.

## 목표

내부 매칭과 외부 staged evidence를 같은 검토 계약으로 보여주고 사람이 채택·기각·보류한 이유를 원자료와 연결한다.

## 선행조건

P12~P14·P17·P22~P24 `CONTRACT_PASS`.

## 작업 소유 범위

`humansearch/src/humansearch/review/operator_queue.py`, 검토 항목/판정 영수증 모델, 단위·통합시험, 읽기 전용 출력.

경로가 현재 SOT와 충돌하면 임의로 다른 영역까지 고치지 말고 목표 문서에 충돌을 증거와 함께 기록해 이 프로젝트를 중단한다.

## 비범위

웹 UI 미관, ClickUp 쓰기, 후보 연락, AI 자동 승인.

## RED 먼저

원문 위치·입력 지문·동일인 근거 없이 채택되거나 같은 후보가 중복 검토 항목으로 생기는 실패 시험을 먼저 만든다.

## 구현 계약

P22/P23의 채널별 staged evidence와 P24의 수동 영수증을 먼저 P12 동일인 입력 포트로 보내 `canonical_candidate_id`와 별칭 폐쇄 지문을 받는다. P12 결과가 `NEEDS_REVIEW`이거나 충돌이면 임의 ID를 만들거나 `ACCEPTED`하지 않고 `HOLD`·에스컬레이션한다. 동일인 경계를 통과한 자료만 공통 읽기 전용 검토 항목으로 변환하되 원문 위치 지문·표시자/계약 버전·채널·수집/수동 상태·외부쓰기 0건 증명을 보존한다. 적합 근거, 부족 근거, 동일인 근거, 출처, 정책 상태, 중복 접촉 상태를 표시하고 판정자·시각·이유·이전 판정을 불변 영수증으로 남긴다. 사람 `ACCEPTED`만 P12 공용 스키마의 외부+사람+`ACCEPTED` 영수증으로 내보내 P07 재계산 입력이 될 수 있고, `REJECTED | HOLD`는 적격 수에 포함할 수 없다.

## 가짜 합격을 깨는 시험

P22/P23/P24 스키마 불일치, 원문 위치/표시자 버전 누락, 근거 누락, stale 입력, 중복 출처, 판정 덮어쓰기, 삭제 요청 후보, hard gate 무시를 시험한다.

## 검증

합성 검토 10건에서 중복 0·근거 누락 채택 0, 영수증 append-only, `bash verify.sh`.

## 원자적 인수 기준

후속 구현은 `bash scripts/acceptance-ai-ra-p25.sh` 한 명령으로 P22/P23 staged evidence와 P24 수동 영수증이 P12 동일인 경계를 거쳐 원문 위치 지문·표시자/계약 버전·채널 상태를 잃지 않고 같은 검토 계약으로 변환되며, 운영자의 O/X·보류·에스컬레이션이 원자료와 분리 기록되고 승인 없는 다음 단계 쓰기가 0건임을 검사해야 한다. P12 `NEEDS_REVIEW`·충돌은 임의 ID 생성 없이 `HOLD` 1건이고, `ACCEPTED`만 P12 공용 스키마를 통과하는 외부 적격 영수증 1건을 만들며 `REJECTED | HOLD`는 0건이어야 한다. P07 중복 계수는 P07과 P26 인수 검사가 소유하며 P25가 그 모듈을 수정하지 않는다. 정상 실행은 `PASS AI_RA_P25 <실제 핵심 건수>`를 출력하되 실제 핵심 건수는 반드시 1 이상이고 종료값 0을 남겨야 하며, 핵심 차단을 한 줄 고장 낸 반대 시험은 0이 아닌 종료값이어야 한다. 이 프로젝트는 자기 인수 스크립트만 소유한다. P04가 소유한 `scripts/acceptance-ai-ra-all.sh`와 서버 workflow가 이름 규칙으로 자동 발견해야 하며, 이후 프로젝트는 공용 workflow를 직접 수정하지 않는다.

## 라이브 증거와 멈춤점

실제 후보자 화면이나 외부 쓰기 없이 CLI/구조 출력과 판정 계약에서 멈춘다.

## 공통 strict 실행 지시

1. 기본 작업공간을 수정하지 말고 최신 기준 커밋에서 이 프로젝트 전용 worktree와 `task/` 브랜치를 만든다.
2. 코드보다 먼저 이 프로젝트 목표 문서를 작성하고 원자적 인수 기준 1개, 반대 시험, 비범위, 실제 검증 명령을 적는다.
3. `docs/sot/INDEX.md`, `coding-principles.md`, `git-workflow.md`, `hook-contracts.md`, `verification-commands.md`와 P00B 이후 새 정본을 전문으로 읽고 체크리스트를 목표 문서에 남긴다.
4. v4/v5 코드는 행동·실패 사례와 테스트 오라클만 참고한다. import, 복사, subprocess 호출, 런타임 의존성은 금지한다.
5. RED를 실제 런타임 시험으로 먼저 만들고 실패 출력을 목표 문서에 남긴다. 소스 문자열 검색만으로 기능을 증명하거나 테스트 0건을 PASS로 세지 않는다.
6. 최소 구현 뒤 대상 시험→자기 번호 인수 검사→P04 공용 `scripts/acceptance-ai-ra-all.sh`→`bash verify.sh` 순으로 실행한다. P04 전 프로젝트는 자기 스크립트만 만들고 P04가 공용 배관을 연결하며, P04 이후 프로젝트는 이름 규칙 자동 발견을 증명하고 `.github/workflows/verify.yml`을 직접 수정하지 않는다.
7. 비밀·후보 원문·인증정보를 터미널, fixture, 문서, 커밋에 남기지 않는다. 외부 쓰기·발송·운영 DB 변경·배포는 이 프롬프트가 명시적으로 허용하지 않으면 하지 않는다.
8. `claude -p` 1차 적대검토를 실행하고 각 지적을 Codex가 직접 명령으로 재현한다. 한 항목이라도 동의하면 수정 후 1차부터 다시 반복한다.
9. 완료 보고는 변경 파일, 실제 처리 건수, 테스트/인수 검사 종료 코드, `git diff --check`, 남은 `NOT_RUN`과 위험을 구분한다. 검사가 하나라도 빨갛거나 증거가 없으면 완료라고 하지 않는다.
