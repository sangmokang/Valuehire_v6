## 결론 (사장님 브리핑 — 먼저 읽는 요약)

**결론.** 지금까지는 나쁜 코드를 막는 문지기(검사 장치)만 만들었습니다. 이 작업부터가 **진짜로 후보를 찾는 기능의 첫 조각**입니다. 첫 조각은 화면이나 로그인을 건드리지 않고, "지금 사람인 화면이 어떤 상태인지"(로그인 안 됨·사람이 로그인함·인증됨·보안문자 뜸·화면이 바뀜)를 판단하는 **뼈대**만 만듭니다. 결정하실 것은 없습니다 — 클린룸 계약에 이미 정해진 다섯 상태를 코드로 옮기는 일입니다.

**왜 이것부터인가.** 클린룸 계약이 "이 상태 뼈대(L0)가 완성되기 전에는 실제 사람인 화면 캡처를 시작하지 말라"고 못 박았습니다. 화면 계약과 상태 의미가 서로 물고 늘어지는 순환을 막기 위해서입니다. 그래서 이게 서치의 첫 착수점입니다.

**틀리면 뭐가 깨지나.** 상태 판단이 엉성하면, 나중에 "로그인 안 됐는데 인증됐다고 착각해서 계속 긁는" 사고(v5의 실제 실패)가 재발합니다. 그래서 이 뼈대는 "정의 안 된 상태 변화는 무조건 거부"하도록 짜고, 그걸 시험으로 증명합니다.

**선행 조건.** G3(PR #13)·500줄 게이트(PR #14)가 **병합된 뒤** 착수합니다. 두 문지기가 main에 들어가야 이 코드도 그 검사를 받습니다.

- 클린룸 계약 `:378-379`: *"L0가 병합되기 전에는 fresh portal capture를 시작하지 않는다"* — C(화면 캡처)의 선행.

### ② 근본 원인

실제 서치 코드가 아직 0줄이다. 그리고 상태 의미를 화면 요소(구체 셀렉터)에 묶으면 v5처럼 화면이 조금만 바뀌어도 전체가 무너진다 — 그래서 화면 요소 없이 상태 의미부터 고정해야 한다.

### ③ 인수 기준 (EARS + 검증 명령 + counter-AC)

**AC-L0-1 (상태 전이표 전수).** When 상태기계가 (현재 상태, 의미 신호) 쌍을 받으면, then 클린룸 계약이 정의한 전이표대로 다음 상태를 결정론적으로 반환해야 한다.
- 5개 상태: `UNKNOWN`(모름)·`HUMAN_AUTH`(사람 로그인 필요/진행중)·`AUTHENTICATED`(인증됨)·`CHALLENGE`(보안문자·2단계)·`DRIFTED`(화면 구조가 계약과 어긋남).
- 검증: 전이표의 모든 정의된 (상태, 신호) 쌍에 대해 기대 결과를 단언하는 단위 시험 전수 통과.
- counter-AC: 같은 입력이 실행마다 다른 상태를 내면(비결정론) 가짜. 시계·난수·네트워크에 의존하면 가짜.

**AC-L0-2 (잘못된 전이 거부 — property test).** If 전이표에 정의되지 않은 (상태, 신호) 쌍이 들어오면, then 시스템은 임의로 상태를 만들지 말고 명시적으로 거부(예외 또는 `illegal` 결과)해야 한다.
- 검증: 무작위로 생성한 (상태, 신호) 쌍 다수에 대해 "정의된 것은 전이표와 일치, 정의 안 된 것은 전부 거부"를 만족하는 성질 시험(property test — 특정 입력이 아니라 "모든 입력이 만족해야 할 성질"을 무작위 입력 다수로 검사).
- counter-AC: 정의 안 된 쌍에 아무 상태나(예: 조용히 `AUTHENTICATED`) 반환하면 가짜. 이게 v5의 "미로그인을 인증으로 착각" 사고 경로다.

**AC-L0-3 (빈 화면 신호 = 안전 방향).** When 화면에서 아무 의미 역할(role)도 읽히지 않으면(빈 locator fixture), then 상태는 `AUTHENTICATED`로 가지 않고 `UNKNOWN` 또는 `DRIFTED`로 판정해야 한다(fail-closed = 애매하면 통과가 아니라 안전한 쪽으로).
- 검증: 빈 role 집합을 넣은 fixture로 상태 판정 → 결과가 `AUTHENTICATED`가 아님을 단언.
- counter-AC: 빈 화면을 인증됨으로 보면 가짜.

**AC-L0-4 (화면 요소 비의존).** Where 상태 판정 로직이 구현되면, 구체 DOM 셀렉터(`#id`, `.class`, `querySelector` 등)나 특정 URL 문자열이 상태기계 코드에 존재하면 안 된다 — 의미 role 스키마(사람이 읽는 역할: "로그인폼", "인증배지", "보안문자입력" 등)만 소비한다.
- 검증: 상태기계 소스에 DOM 셀렉터·URL 리터럴 0건(grep). 이건 이미 G3 게이트가 잡는 규칙과 같은 방향 — G3 검사가 이 파일에도 걸리는지 확인.
- counter-AC: role 스키마인 척하면서 실제로는 셀렉터를 문자열로 박으면 가짜.

### ⑥ 계약 스펙 (입출력 — 손대기 전에 박는다)

```python
# 상태 (열거형)
State = Literal["UNKNOWN", "HUMAN_AUTH", "AUTHENTICATED", "CHALLENGE", "DRIFTED"]

# 의미 신호 — 화면에서 읽은 역할의 집합 (구체 셀렉터 아님).
# 정확한 role 이름 집합은 클린룸 계약의 role schema 정의를 정본으로 삼아 확정한다.
Signal = frozenset[str]   # 예: {"login_form"}, {"auth_badge"}, {"captcha_input"}, {} (빈 화면)

def transition(current: State, signal: Signal) -> State: ...
#   정의된 (current, signal) → 전이표대로. 정의 안 됨 → raise IllegalTransition (AC-L0-2).

def classify(roles: Signal) -> State: ...
#   화면 role 집합 → 상태. 빈 집합이면 AUTHENTICATED 금지 (AC-L0-3).
```
→ 이 계약이 시험(RED)과 검증자(V1)의 채점 기준표다. role 이름의 정확한 집합은 클린룸 계약의 role schema 절을 읽어 확정하고, 계약에 없으면 코드를 짜기 전에 사장님께 질문한다(추측 금지).
