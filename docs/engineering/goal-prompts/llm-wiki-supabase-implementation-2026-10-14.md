# 실행 프롬프트: ValueConnect LLM Wiki 최소 구축

당신은 ValueConnect의 기존 ValueHire v4/v6 코드와 운영 Supabase를 실사하여 **4명의 팀원이 10만 명 이상 후보자를 안전하게 공동 조회하고, AI Search 결과와 Gmail·ClickUp·Notion·Discord 근거를 후보자/포지션 이력으로 확인하는 최소 시스템**을 구축하는 담당자다. 새 플랫폼 설계보다 기존 기능 재사용, 관계 연결, 접근 권한, 검증 가능한 출처를 우선한다.

## 먼저 읽을 근거

1. `docs/engineering/llm-wiki-supabase-audit-2026-10-14.md`와 `docs/engineering/evidence/llm-wiki-supabase-fields-2026-10-14.tsv` (2026-10-14 API 노출 객체 222개, 필드 2,772개 전수 목록).
2. `docs/sot/ai-search-operations.md`와 `docs/engineering/ai-search-operations-original-2026-09-30.md`의 운영 SOT/원천·중복·조회 계약.
3. ValueHire v4/v6의 현재 인증·관리자 화면·Supabase 마이그레이션·ClickUp 동기화·Gmail 적재·AI Search 쓰기/읽기 코드. 로컬 문서가 운영 DB와 다르면 실제 DB/API와 실행 코드를 대조하고 차이를 명시한다.

## 조사에서 이미 확인한 사실

- 운영 `pipeline_candidates` 21,771건, `sourcing_results` 1,436건, `profile_archives` 21,651건, `gmail_messages` 35,504건, `gmail_derived_events` 21,791건, `clickup_comments` 11,658건, `notion_clients` 269건, `customer_ontology_sources` 5,008건이 있다. 중복된 대상과 별도 후보자 테이블이 있으므로 단순 합산 금지.
- `sourcing_results`에는 `candidate_id`가 없고, Gmail 파생 이벤트의 `candidate_id`/`position_id`/`company_id`는 모두 NULL이다. `candidate_activity_log`는 0건이다. 통합 후보자 이력 뷰 34,036건 중 후보자 ID가 채워진 행은 21,496건뿐이다. 지금 있는 뷰를 완성된 타임라인으로 간주하지 말 것.
- Discord 메시지 테이블은 공개 API 스키마에서 확인되지 않았다. 봇 임대/킬스위치 흔적만 있다. 웹훅·외부 저장소 여부는 별도 실사할 것.
- 벡터 컬럼과 관련 RPC가 있어도 조사한 주요 테이블의 임베딩은 채워진 행이 0건이다. 의미 검색이 이미 작동한다고 주장하지 말 것.
- **P0 보안:** 비로그인 `anon` 키로 Gmail 본문, 프로필 텍스트, 활성 후보자 이름, 통합 이력 본문의 실제 값이 반환됐다. 원인은 미확정이다. 새 사용자 조회 기능을 배포하기 전 관련 테이블·뷰·RPC의 GRANT/RLS/뷰 보안 특성을 조사하고, 익명 접근을 차단한 뒤 HTTP 수준에서 재검증해야 한다. 운영 권한 변경은 변경안·영향·롤백을 먼저 검토하고 승인된 배포 절차로 적용한다. 조사 결과에 개인정보 원문·토큰을 붙이지 말 것.

## 구현 계약

### 1. SOT를 객체/필드 단위로 확정

후보자 통합 ID·AI Search 검토 상태·확정된 내부 평가는 Supabase를 운영 SOT 후보로 삼되, 기존 `pipeline_candidates`/`candidates`/`sourcing_results` 간 작성 주체와 충돌을 확인해 하나의 쓰기 경로를 정한다. ClickUp 진행 단계, Gmail 커뮤니케이션, Notion 문서, Discord 논의의 원문 SOT는 각각 원천 시스템으로 둔다. DB에 필요한 식별자·시각·검색용 최소 사실·출처 링크·해시를 보존한다. 사람이 확정한 판단과 LLM 요약은 서로 다른 필드/상태로 표시하고, 원천과 충돌하면 자동 덮어쓰지 않는다. 특정 테이블/필드를 새로 만들기 전에 동일 역할의 기존 컬럼과 뷰를 목록으로 제시한다.

### 2. AI Search 결과 통합

현재 여러 저장 경로를 실사해 공통 결과 계약을 정한다: `run_id`, `position_id`, 원천 채널/원천 ID/URL, 수집 시각, 후보자 식별키, 점수와 평가 주체, 근거 URL, 검토 상태. `sourcing_results`와 이미 `pipeline_candidates`에 들어간 AI Search 결과를 함께 다룬다. 저장은 idempotent하며 재실행으로 동일 원천 결과가 중복 확정되지 않아야 한다. LinkedIn URL 등 안정적 ID 또는 확인된 이메일이 정확히 일치할 때만 자동 연결한다. 이름+현직장만 같은 경우는 검토 대상으로 남긴다. URL이 없는 결과도 유실하지 않고 별도 원천 식별자로 보존한다. 후보자 마스터 승격은 담당자의 명시적 검토 규칙에 따른다.

### 3. 후보자 목록·검색·이력

기존 관리자 인증/화면을 재사용해 팀원 4명이 같은 후보자 목록을 본다. 이름·회사·포지션·기술·연차·진행/추천 여부·최근 접촉일을 구조화 필터와 검증된 텍스트 검색으로 제공한다. 페이지네이션과 정렬 기준을 고정하고 API 응답이 사용자 권한에 맞게 필드를 제한해야 한다. Gmail/ClickUp/Notion/AI Search 이벤트는 후보자 또는 포지션에 **확인된 ID**로 연결한 것만 해당 타임라인에 표시하고, 미연결 항목은 별도 검토 목록에 둔다. 각 행에 발생 시각, 수집 시각, 원천, 원천 ID/링크, 사람이 확정했는지/AI가 생성했는지를 보인다. 원천 정정·삭제와 중복 이벤트도 처리한다.

### 4. LLM Wiki의 경계

고객사 인사이트·채용 전략·업무 지식은 기존 `customer_ontology_documents` 및 Notion 자료와 중복 여부를 검토해 한 곳의 사람이 확정한 문서를 SOT로 정한다. Git Markdown은 비민감 지식의 편집·버전 관리에 필요한 경우에만 사용한다. 10만 후보자의 원본 이력서, 메일 본문, 연락처, 운영 이력은 Git에 저장하지 않는다. LLM은 승인된 검색 API가 반환한 작은 결과 집합만 요약하며 문장 단위로 근거를 제공한다. 출처 없는 주장, 모순, 오래된 정보는 확인 필요로 표시한다. 자연어 검색에서 LLM에게 임의 SQL 또는 서비스 키를 주지 말고 허용된 필터 스키마로만 변환한다. 키워드 검색의 실제 실패 사례가 확보되기 전에는 전량 임베딩·별도 벡터 DB·MCP 서버를 만들지 않는다.

### 5. 네 채널의 연동 범위

Gmail·ClickUp·Notion은 이미 저장된 자료의 동기화 신선도, 중복, 삭제·수정 반영, 출처 링크 접근성을 먼저 확인한다. Discord는 채널 범위와 승인된 결정 기록만 작은 파일럿으로 추가한다. 원문 대량 복제와 양방향 상태 변경을 기본값으로 삼지 않는다. ClickUp 또는 Supabase 중 실제 진행 단계 쓰기 SOT는 운영 사용자 행동과 현재 동기화 코드를 근거로 한 곳만 결정한다.

## 작업 순서와 배포 문턱

1. **현행 실사:** 테이블/필드 매핑, RLS·GRANT·뷰·RPC 정책, 사용자 역할, 기존 조회 화면과 수집기, 실제 레코드 연결률, 데이터 보존/삭제 경로를 기록한다. API 전수 목록이 내부 PG 카탈로그 전수 조사가 아님을 명시한다.
2. **P0 권한 보정:** `anon`/로그인 팀원/서비스 역할 각각으로 민감 필드 조회 테스트를 작성하고 운영 배포 절차로 수정한다. 실패하면 새 Wiki/API 노출 중단. 서비스 키는 서버에서만 사용한다.
3. **첫 사용 가능 버전:** 기존 AI Search 결과와 파이프라인 후보자 목록을 연결하고, 팀 로그인 검색·페이지네이션·원천 링크·검토 상태를 제공한다. 후보자 자동 병합과 LLM 요약 없이도 유용해야 한다.
4. **연결 이력:** Gmail/ClickUp/Notion 원천 ID를 확정된 후보자·포지션 ID에 연결하고 미연결 큐·재처리·감사 로그를 만든다. 기존 이력 뷰와 활동 로그의 부족한 점을 고친다.
5. **지식·LLM·Discord:** 기존 고객사 지식을 연결하고, 출처 검증 가능한 요약을 추가한다. Discord는 허용 채널·보존 기간·권한 확인 후 붙인다.

## 수용 조건과 반례

- 비로그인 HTTP 클라이언트는 후보자 이름/연락처/프로필·Gmail 본문·이력 본문을 읽을 수 없다. RLS가 걸린 기본 테이블뿐 아니라 뷰와 RPC도 시험한다.
- 팀원 4명이 같은 승인된 후보자 목록을 조회하되 역할별 민감 필드가 새지 않는다. 조회/내보내기 권한과 감사 기록을 검증한다.
- 동일 AI Search 실행을 두 번 입력해도 결과·후보자·타임라인 수가 중복 증가하지 않는다. 동명이인, URL 변경, 이메일 중복, 원천 ID 없는 결과를 별도 반례로 시험한다.
- 후보자 상세에는 추천/접촉/피드백 이벤트의 출처 URL과 발생 시각이 있고, 잘못 연결된 항목은 표시되지 않는다. `candidate_id`가 비어 있는 Gmail/ClickUp/Notion 행을 자동으로 해당 인물의 사실로 취급하지 않는다.
- 실제 10만 명 합성 데이터와 동시 팀원 4명 조건에서 대표 검색의 `EXPLAIN ANALYZE`, p50/p95 응답시간, 권한 결과, 페이지네이션 정합성을 보고한다. 0.1초/5일/90% 해결 같은 근거 없는 수치를 성공 기준으로 미리 선언하지 않는다.
- 삭제·정정 요청 시 운영 DB, 요약/캐시, 백업·로그의 처리 경로와 남는 제한을 기록한다.

## 산출물

기존 자산 재사용표, 최소 스키마 변경과 마이그레이션/롤백, SOT·충돌 규칙, 권한 테스트 결과, AI Search 중복·연결 테스트, 10만 명 성능 측정표, 단계별 화면/동작 검증, 미구현 범위와 다음 결정 사항. 실사로 확인되지 않은 가정은 사실처럼 쓰지 말고 `미확인`으로 분리한다. 구현 범위는 수용 조건을 만족하는 최소 변경으로 유지한다.
