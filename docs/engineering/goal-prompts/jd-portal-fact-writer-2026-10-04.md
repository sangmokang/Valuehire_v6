# 포털별 JD 작성 프롬프트 — 사람인·잡코리아·LinkedIn + 후보자 발송용 (팩트 100%, Aside 브라우저) (2026-10-04)

> 사용법: 아래 `---` 사이 본문을 그대로 붙여 넣고, 맨 위 **입력** 칸만 채운다.
> 근거 SOT: `docs/sot/search-query-and-filter-rules.md` (2026-09-28 Aside 탭 재사용·숨김 탭·shadow DOM 규칙), `docs/sot/humansearch-browser-contract.md` (로그인·보안 확인 시 멈춤).

---

너는 Valuehire v6 저장소에서 **Aside 브라우저**로 한 포지션의 JD 원문을 모으고, 이를 근거로
(1) 사람인 (2) 잡코리아 (3) LinkedIn 채용공고 입력값과 (4) 후보자 발송용 JD를 작성한다.
**원문에 없는 내용은 한 글자도 만들지 않는다.** 문장을 다듬는 것은 되지만 사실을 더하거나, 추측하거나, 좋아 보이게 부풀리는 것은 안 된다.

## 입력 (사장님이 채움)

- 포지션: `<고객사명> / <포지션명>`
- ClickUp 태스크 URL: `<URL 또는 "없음">`
- Gmail 검색어 또는 스레드: `<예: from:hr@고객사.com "JD" 또는 스레드 URL, 없으면 "없음">`
- 고객사 채용페이지 URL: `<URL 또는 "없음">`
- 포털 공고에 회사명 공개: `<공개 / 비공개>` (비공개면 회사 소개는 원문에 적힌 사실만으로 익명 서술)
- 연봉 표기: `<원문 그대로 / 표기 안 함 / "협의">`
- 포털 폼까지 채울지: `<텍스트만 / 폼 입력까지(등록 버튼은 누르지 않음)>`

## 절대 규칙

1. **팩트 100%.** 출력의 모든 문장·숫자·기술명·연차·학력·근무지·근무형태·복지·전형 단계는 원문 한 곳 이상에 근거가 있어야 한다. 근거 없는 항목은 지우거나 `[확인 필요: 무엇]`으로 남긴다. 빈칸을 그럴듯한 문장으로 메우지 않는다.
2. **금지 표현:** 원문에 없는 "업계 최고 대우", "빠르게 성장 중", "유니콘", "시리즈 X", 투자 규모, 직원 수, 매출, "수평적 문화", "자율 출퇴근" 등. 원문에 있으면 원문 표현 그대로 쓴다.
3. **기술명·고유명사는 원문 표기 그대로.** (예: 원문이 `PyTorch`면 `Pytorch`/`파이토치`로 바꾸지 않는다. 포털 직무 태그 선택은 별개 — 아래 4단계.)
4. **원문끼리 다르면 고르지 말고 드러낸다.** 아래 "충돌 처리" 표대로 하고, 판단이 필요한 건은 사장님께 묻는다.
5. **발송·게시 0건.** 포털의 `등록`/`게시`/`Post job`/`결제` 버튼, Gmail `보내기`, LinkedIn InMail `Send`는 누르지 않는다. 임시저장은 폼에 그 버튼이 있을 때만 쓰고, 결제·공고권 차감 화면이 뜨면 즉시 멈춘다.
6. **로그인·캡차·2단계 인증·"다른 기기에서 로그인" 화면이 뜨면 멈추고 보고한다.** 비밀번호 입력, 다른 세션 로그아웃 금지.

## 브라우저 규칙 (Aside 특성 — 반드시 준수)

- **새 창·새 탭을 만들지 않는다.** 시작할 때 전 창의 탭 id·URL을 읽고, 이미 열린 ClickUp·Gmail·사람인·잡코리아·LinkedIn·고객사 탭을 재사용해 그 탭의 URL만 바꾼다. 쓸 만한 탭이 하나도 없을 때만 사장님께 한 줄 알리고 새 탭 1개를 연다.
- **탭은 순번이 아니라 탭 id로 지정한다.** 사장님이나 다른 세션이 탭을 옮기면 순번이 바뀐다. 다른 세션이 쓰는 탭(최근 1시간 산출물·실행 중 스크립트에 그 id가 있음)은 건드리지 않는다. 사장님 메인 창의 활성 탭을 바꾸지 않는다.
- Claude 확장이 붙어 있으면 claude-in-chrome MCP(`tabs_context_mcp, navigate, get_page_text, read_page, find, computer`)를 쓰고, 안 붙어 있으면 AppleScript `execute tab id ... javascript`로 조작한다. 창 id 숫자는 `osascript -e` 문자열에 직접 넣지 말고 인자로 넘긴다(실수형으로 바뀌어 실패).
- **숨김 탭 주의:** 창이 가려지거나 비활성 탭이면 `document.visibilityState=hidden`이 되어 타이머가 느려지고 지연 로딩 영역이 안 그려진다. 원문 읽기 결과가 짧거나 중간에서 끊기면 보이는 탭(자기 창의 활성 탭)에서 다시 읽는다. 폼 입력은 반드시 보이는 탭에서 한다.
- **원문 전체가 펼쳐졌는지 확인한다:** `더보기`·`펼치기`·아코디언·탭(`주요업무/자격요건/우대사항`)을 모두 연 뒤 읽고, 끝까지 스크롤해 지연 로딩을 끝낸다. 읽은 글자 수와 섹션 제목 목록을 기록한다.
- **텍스트로 안 읽히는 원문:**
  - 고객사 채용페이지가 그리팅·나인하이어·Greenhouse·Lever·Workday 등 외부 ATS면 iframe 안에 있다 → iframe의 원본 URL로 이동해 읽는다.
  - 닫힌 shadow DOM·캔버스·이미지 JD(사람인 상세 등) → 보이는 탭에서 창 단위 캡처(`screencapture -l <CGWindowID>`)로 읽고, 캡처 파일 경로를 근거로 남긴다. 이미지에서 읽은 숫자·고유명사는 한 번 더 확대 캡처해 확인한다.
  - PDF 첨부(Gmail·ClickUp) → 내려받아 텍스트를 추출해 읽는다.
- **ClickUp·Gmail은 MCP가 있으면 MCP가 먼저다.** ClickUp은 `clickup_get_task`(설명·커스텀 필드·첨부)와 `clickup_get_task_comments`(댓글의 수정 사항), Gmail은 `search_threads`/`get_thread`(스레드 전체, 첨부 포함)로 읽는다. MCP가 없거나 막히면 Aside 탭에서 읽는다(Gmail·ClickUp 작업에 Chrome 쓰지 않음).
- 사람 수준 속도로 움직인다: 같은 URL 연속 재접속 금지, 클릭 사이 간격을 둔다.

## 1단계 — 원문 수집 (출처별로 따로 저장)

출처마다 `원문 텍스트 + URL + 확인 시각 + 원문 작성/수정일(보이면)`을 저장한다.

| 출처 | 읽을 것 |
| --- | --- |
| ClickUp | 태스크 설명, 커스텀 필드(연봉 범위·근무지·수수료 등), 첨부 JD, **댓글의 변경 지시**(최신 댓글이 설명보다 우선일 수 있음 → 충돌로 표시) |
| Gmail | 고객사가 보낸 JD 메일 스레드 전체(답장 속 수정 포함), 첨부 JD 파일. 스레드 내 날짜순 변경 이력 정리 |
| 고객사 채용페이지 | 해당 포지션 공고 본문 전체, 게시일/마감일, 회사 소개(사실 문장만), 복지, 전형 절차 |

저장 위치: `artifacts/jd-<YYYYMMDD>/<고객사>-<포지션>/sources/{clickup,gmail,careers}.md` (+ 캡처 이미지)

## 2단계 — 사실 장부 만들기 (모든 출력의 유일한 재료)

원문을 항목별 사실로 쪼갠다. 한 줄에 사실 하나, 출처 표시 필수.

```
| # | 항목 | 내용(원문 표현) | 출처(ClickUp/Gmail/Careers + 위치) | 원문 날짜 |
```

항목: 포지션명·소속 조직·주요 업무·자격 요건·우대 사항·기술 스택·경력 연차·학력·고용 형태·근무지·근무 형태(재택/하이브리드)·근무 시간·연봉·복지·전형 절차·마감·회사 소개.

**충돌 처리**

| 상황 | 처리 |
| --- | --- |
| 같은 항목이 출처마다 다름 (예: 경력 5년↑ vs 7년↑) | 둘 다 장부에 남기고 `충돌` 표시. 출력에는 `[확인 필요: ClickUp 5년↑ / 채용페이지 7년↑]` |
| Gmail·ClickUp 댓글에 고객사의 **명시적 변경 지시**가 있음 ("자격요건 이렇게 바꿔주세요") | 그 지시를 최신으로 쓰고, 근거에 날짜·작성자 표기 |
| 한 출처에만 있음 | 그대로 쓴다(충돌 아님) |
| 채용페이지 공고가 마감·삭제됨 | 쓰지 말고 보고. 남은 출처로만 작성 |
| 내부 정보(수수료·내부 메모·고객사 담당자 연락처·연봉 상한 협상 메모) | 장부에는 `내부` 표시, **어떤 출력에도 넣지 않는다** |

## 3단계 — 출력 작성

공통: 사실 장부의 내용만 쓴다. 섹션 순서와 말투만 포털에 맞게 바꾼다. 원문에 없는 섹션은 만들지 말고 비워 둔다.

### (1) 사람인 / (2) 잡코리아 채용공고

- 폼 칸 이름을 **실제 등록 화면에서 읽어** 그 칸 단위로 값을 만든다(칸 구성이 바뀌어도 맞도록 기억에 의존하지 않는다). 일반적으로: 공고 제목, 모집 분야(직무 카테고리), 담당 업무, 자격 요건, 우대 사항, 경력, 학력, 고용 형태, 근무지, 급여, 복지, 전형 절차, 접수 기간.
- **직무 카테고리·키워드 태그·지역·경력·학력 같은 선택형 칸은 화면의 선택지 중에서만 고른다.** 원문과 정확히 맞는 선택지가 없으면 가장 가까운 후보 2~3개를 제시하고 `[선택 필요]`로 둔다.
- 글자 수 제한은 **입력 화면의 실시간 카운터**로 확인한다. 넘치면 줄이되 요건(숫자·기술명)은 지우지 않고 수식어부터 뺀다. 그래도 넘치면 보고한다.
- 공고 제목: `[회사명 또는 익명 서술] 포지션명 (경력 조건)` 형태, 원문 포지션명 유지.

### (3) LinkedIn 채용공고

- 입력값: Job title(원문 포지션명, 영문 원문이 있으면 영문), Company(공개 시), Workplace type(On-site/Hybrid/Remote — 원문 근거 없으면 `[확인 필요]`), Job location, Employment type, Description.
- Description: 원문이 영문이면 영문 원문 기준, 국문뿐이면 국문으로 쓰고 **번역은 사장님이 요청할 때만** 한다(번역 시 원문 대조표 첨부, 의미 추가 금지).
- Skills 선택은 LinkedIn 화면의 제안 목록 중 원문 기술명과 같은 것만.

### (4) 후보자 발송용 JD (메일·InMail·문자 공용)

- 순서: 한 줄 요약(포지션·조직·근무지) → 주요 업무 → 자격 요건 → 우대 사항 → 근무 조건(원문에 있는 것만) → 전형 절차.
- 회사명 공개 여부·연봉 표기는 **입력** 설정을 따른다.
- 후보자 개인 맞춤 문구(“귀하의 ○○ 경험이…”)는 넣지 않는다 — 이 프롬프트는 JD만 만든다.
- InMail용 짧은 버전도 함께 만든다(요약 + 핵심 요건 3개 + 상세 JD 링크 자리 `[링크]`).

## 4단계 — 포털 폼 입력 (입력이 "폼 입력까지"일 때만)

- 보이는 탭에서 이미 열린 사람인·잡코리아·LinkedIn 공고 작성 탭을 재사용한다.
- 리치 텍스트 에디터는 iframe·contenteditable인 경우가 많다. JS로 값을 넣었다면 **화면에 실제로 반영됐는지 다시 읽어 확인**한다(React 등은 `value`만 바꾸면 저장 시 빈 값이 된다 → 네이티브 setter + `input`/`change` 이벤트, 또는 붙여넣기 방식). 줄바꿈·글머리표가 깨지면 그 칸은 사람이 붙여넣도록 텍스트만 남긴다.
- 자동완성 칸(직무·지역·스킬)은 `click`만으로 안 붙는 경우가 있다 → `pointerdown → mousedown → mouseup → click` 순서로 보내고 칩이 생겼는지 확인한다.
- 칸마다 입력 후 화면 값을 다시 읽어 사실 장부와 대조한다. 끝나면 폼 전체를 캡처한다.
- **`등록`·`게시`·`Post`·결제 버튼은 누르지 않는다.** 마지막 상태로 두고 사장님께 넘긴다.

## 5단계 — 검증 (출력 전 필수)

1. **역추적:** 각 출력의 문장마다 사실 장부 번호를 붙여 본다. 번호를 못 붙이는 문장은 삭제하거나 `[확인 필요]`로 바꾼다.
2. **토큰 대조:** 출력에 나온 모든 숫자(연차·연봉·인원·날짜), 기술명, 학교/학위, 지명, 회사명이 원문 텍스트에 그대로 있는지 문자열 검색으로 확인한다. 없으면 오류.
3. **누락 대조:** 원문 자격 요건·우대 사항 항목이 출력에서 빠지지 않았는지(글자 수 때문에 뺀 것은 목록으로 보고).
4. **내부 정보 유출 검사:** 수수료·내부 메모·담당자 연락처·`내부` 표시 항목이 출력에 없는지.
5. 검증 결과를 `verification.md`에 남긴다: 문장 수 / 근거 연결 수 / 확인 필요 수 / 충돌 수 / 누락 수.
