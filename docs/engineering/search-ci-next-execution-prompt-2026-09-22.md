# 다음 실행 프롬프트: 수정된 여섯 경계의 재검증

## 결론

이번 수정 결과와 실제 변경 내용을 먼저 대조한 뒤 다음 개발의 출발점으로 사용할지를 판단한다. 광범위한 재설계나 반복 감사로 범위를 늘리지 않는다.

## 실행 프롬프트

아래 내용을 그대로 다음 작업에 사용한다.

---

$codeaudit $humanreview

Search Company Intelligence의 CI-01~CI-06 수정본을 대상으로 최종 변경분만 재검증하라. 먼저 `docs/engineering/search-ci-boundaries-review-2026-09-22.md`, 같은 날짜의 goal 문서, `docs/sot/company-intelligence.md`를 읽어라. 이전 보고서의 통과 수나 코드 지문을 현재 상태라고 가정하지 마라.

1. 현재 경로, HEAD, branch, git status, git diff를 확인한다. 수정이 별도 worktree에 있으면 그 경로에서 검사하며 원 저장소의 JD 관련 변경을 가져오지 않는다. 커밋되지 않은 수정은 HEAD만으로 식별할 수 없으므로 변경 파일 SHA256과 전체 diff를 함께 보존한다.
2. 기존 RED(수정 전 동작 때문에 실패한 시험) 로그와 GREEN(수정 후 통과) 로그를 대조한다. 오류가 import/문법 실패였거나 해당 단언까지 도달하지 않았다면 RED 증거로 인정하지 않는다.
3. 아래 계약만 독립 재현한다.
   - CI-01: 이름과 안정 프로필이 다른 관찰이 같은 raw ID이면 오류다. 서로 다른 ID + same_person_as + 근거의 명시적 병합은 성공한다. 이름 차이는 충돌로 남는다. 정확히 같은 캐시 관찰 재사용은 중복 생성하지 않는다. 같은 ID에 다른 내용을 넣으면 조용히 덮어쓰지 않는다.
   - CI-02: published_at의 잘못된 문자열, 빈 값, 잘못된 달력 날짜, 시간대 없는 시각을 차단한다. 날짜/연월/시간대 포함 시각은 지원한다. 무효 날짜가 조직 패턴과 검색어에 들어가지 않는지 확인한다.
   - CI-03: 미래 snapshot이 과거 as_of 실행에 들어가지 않는다. 미래 관찰 시각과 수집 시각도 차단한다. 정상적인 과거 캐시 재사용, 같은 입력 재실행, 이전 snapshot 바이트 보존을 함께 확인한다. 시각은 문자열 순서가 아니라 시간대가 반영된 실제 시각으로 비교한다.
   - CI-04: JD Backend Engineer, Python, large traffic과 조직 Go/commerce가 다르면 모든 채널에 JD 기본 검색어와 조직 확장 검색어가 개별적으로 남는다. 확장어가 많아도 JD 기본어를 밀어내지 않는다. internal key나 출신회사/학교를 자동 필수조건으로 바꾸지 않는다. 단일 확장 쿼리 실행을 전체 JD 검색 완료라고 보고하지 않는다.
   - CI-05: search/profile/snapshot에 없거나 공백뿐인 run_id는 브라우저 호출과 출력 파일 생성 전에 실패한다. local-only에도 동일하다. 유효한 run_id로 기존 동작과 trace가 유지된다. 로컬 JSON의 신규/덮어쓰기 권한도 확인한다.
   - CI-06: 잠정 인물+확정 재직, 오래된 인물+최근 재직, 패턴 필드가 없는 인물, 충돌 필드만 있는 인물의 표본 수가 실제 기여자와 섞이지 않는다.
4. 사용 가능한 기존 환경에서 다음 명령을 실행하고 명령·시각·종료값·전체 출력을 보존한다.
   - python3 -m unittest tests.test_company_intelligence tests.test_recruiting_browser tests.test_recruiting_archive
   - PYTHONPATH=humansearch/src <기존 가상환경 python> -m pytest humansearch/tests/test_recruiting_review.py
   - 관련 기존 변이 시험 및 CI-01~06별 검증을 끈 임시 사본 시험
   - git diff --check
   기존 환경에 의존성이 없으면 설치하지 말고 NOT_RUN과 원인을 기록한다. 변이는 임시 사본에서만 실행하며 실패 개수만 보지 말고 의도한 계약 단언으로 실패했는지 확인한다.
5. 원래 시험의 수정 사항을 확인한다. 중복 ID와 미래 시각을 정상 입력으로 쓴 예제, JD의 Python을 무조건 배제하던 예제의 수정이 새 계약과 일치하는지 대조한다. 단언 삭제·skip·xfail·넓은 예외 허용으로 통과시켰으면 반려한다.
6. 문제를 재현한 경우에만 해당 함수와 시험을 최소 수정하고 그 시험 및 관련 회귀만 다시 실행한다. 관찰되지 않은 위험을 이유로 새 서비스·DB·checker·ledger·framework를 만들지 않는다.

제한 사항:
- commit/push/PR/병합/이메일/후보 연락/라이브 채용사이트 조작/운영 SQLite·Supabase·외부 DB 쓰기를 하지 않는다.
- 이번 검증에 쓰는 합성 입력과 임시 파일을 실제 후보/운영 증빙으로 표시하지 않는다.
- 과거의 후보 서치·메일 증빙을 이번 수정본의 라이브 검증으로 재사용하지 않는다.
- 기존 파일 줄 수 한도 초과, 독립 엔진 미실행, 실제 브라우저 미실행 등 남은 항목을 기능 회귀 통과와 분리한다. 예외 승인이나 전체 Strict PASS를 만들어내지 않는다.

보고:
각 CI-01~06을 해결 확인/부분 해결/미해결/오탐 철회로 표시하고 근거 함수·입력·수정 전후 결과·실행 명령·종료값을 연결하라. 마지막에 ① 다음 개발 단계의 기준선 사용 가능 여부 ② 운영 서치 잔여 위험 ③ 기존 무관한 diff 혼입 여부를 별도로 답하라. 문제가 없으면 여섯 경계의 재검증으로 종료하며 추가 광범위 감사나 라이브 실행으로 자동 확대하지 마라.
