VERDICT: REBUT-PARTIAL

## 1) 결론

현재 제안된 업무 배분안을 그대로 승인하시면 안 됩니다. “가장 비싼 모델이 중요한 판단을 하고, 저렴한 모델이 반복 작업을 한다”는 큰 방향은 타당하지만, 발송 기록과 자동 반복 작업까지 중간 위험으로 묶은 판단은 실제 코드와 맞지 않습니다.

Sonnet은 화면 제작과 정해진 형식의 반복 작업에는 충분히 강합니다. 반면 과거 상태 복원, 외부 발송 기록, 자동 실행처럼 잘못되면 데이터·고객 경험을 되돌리기 어려운 작업은 Opus 이상이 맡아야 합니다.

“시험과 교차 검증이 있으니 구현 모델의 약점이 보완된다”는 말은 과장입니다. Valuehire 자체 기록에서 시험 통과 후 실제 운영이 실패했고, 독립 검증에서도 첫 제출의 53.8%가 반려되었습니다.

비용 절감 가능성은 실제로 있습니다. 다만 토큰 단가만으로 승인하지 말고, Valuehire 대표 작업에서 재작업·검토·사고 복구까지 합친 총비용을 먼저 측정해야 합니다.

## 2) 판단 근거

### 먼저 밝힐 확인 범위와 한계

- 웹 리서치는 가능했고, Anthropic 공식 자료, ICML·NeurIPS 논문, Google Research, GitHub 저장소를 확인했습니다.
- 현재 `Valuehire_v6`에는 제품 소스가 거의 없어, 실제 구현은 형제 저장소 `Valuehire_v4`의 현재 작업 트리와 v6의 감사 문서를 읽기 전용으로 대조했습니다. v4 확인 기준 커밋은 `79227565`이며, 관련 파일 중 `tools/position-batch/orchestrator.mjs`에는 미커밋 변경이 있어 핵심 근거로 사용하지 않았습니다.
- 운영 Supabase와 ClickUp 실데이터는 조회하지 않았습니다. 실제 단계 값 분포, 포지션 연결률, 과거 이력 보유량은 미확인입니다.
- Claude 주장에 버전이 없으므로 ※ `Opus=4.8`, `Sonnet=5`로 해석했습니다.
- Fable·Opus·Sonnet으로 동일한 Valuehire 작업을 재실행한 비교 실험은 없습니다. 따라서 아래 대안 배분은 외부 수치와 코드 위험을 결합한 판단이지, Valuehire에서 이미 입증된 최적안은 아닙니다.
- 정확히 같은 “ClickUp→Supabase 채용 미러+과거 시점 판정+발송 원장” 공개 저장소는 찾지 못했습니다. 부분적으로 유사한 사례만 사용했습니다.
- 저장소 자동 탐색 명령은 `cargo` 부재로 실패해 `rg` 검색과 파일별 직접 판독으로 대체했습니다.
- 내부 실패 보고서는 강한 프로젝트 내부 증거지만, 모든 원본 실행 기록을 제가 다시 재현한 독립 학술자료는 아닙니다.

### 주장별 판정

모델 라우팅(업무 성격에 따라 서로 다른 AI 모델에 일을 나누는 방식)과 TDD(실패하는 시험을 먼저 만든 뒤 구현하는 방식)를 다음처럼 판정했습니다.

| 클로드 주장 | 판정 | 심각도·사업 영향 | 핵심 이유 |
|---|---|---|---|
| Fable이 기획·설계·최종 판단 담당 | 대체로 타당 | 낮음 — 잘못된 설계를 구현 전에 잡을 가능성이 커집니다. | Valuehire의 스펙 감사와 외부 planner 연구가 모두 계획 품질의 중요성을 지지합니다. |
| 고위험 구현은 Opus | 부분 타당 | 높음 — 모델 능력보다 실제 데이터 확인과 구현 중 재설계 권한이 빠지면 재작업이 남습니다. | Opus는 충분히 강하지만, 과거 시점 SQL처럼 짧고 치명적인 부분은 Fable 직접 수행도 비용 대비 합리적입니다. |
| API 계측·React·cron은 모두 Sonnet | 과도한 묶음 | 치명 — 발송 중복이나 자동 실행 오류가 고객에게 직접 노출될 수 있습니다. | React 화면은 Sonnet으로 충분하지만, 외부 발송 계측과 무인 cron은 되돌리기 어려운 부작용이 있습니다. |
| 실제 실패는 전부 판단 오류 | 반박 | 치명 — 구현 결함을 판단 문제로만 분류하면 같은 사고의 방지 장치가 빠집니다. | 비밀값 노출, 셸 따옴표 오류, 널 문자 미처리, 잘못된 배포, 시험 기대값 약화는 구현·운영 결함입니다. |
| 계약+TDD+교차 검증이 구현자 약점을 보완 | 일부만 인정 | 치명 — 시험이 놓친 결함이 운영에 빠져나갈 수 있습니다. | Valuehire에서 시험 통과 후 라이브 실패가 있었고, 첫 제출의 53.8%가 교차 검증에서 반려됐습니다. |
| 토큰 비용이 절약됨 | 가능하지만 미입증 | 높음 — 재작업 한 번이 단가 절감분을 없앨 수 있습니다. | 외부 벤치마크는 혼합 모델의 절감 가능성을 지지하지만 Valuehire 총비용 측정은 없습니다. |

→ 뭘 했나: 주장을 전부 부정하지 않고, 방향·위험 분류·근거를 분리했습니다.  
→ 뭐가 나왔나: 큰 방향은 맞지만 “Sonnet 중위험 묶음”과 “게이트가 충분하다”는 결론은 승인 근거가 부족합니다.  
→ 좋은/나쁜 소식: 전면 폐기할 안은 아니며, 발송·cron을 상향 조정하면 살릴 수 있습니다.

### 왜 `REBUT-PARTIAL`인가

가장 강한 반박 지점은 “과거 실패가 전부 판단 오류였으므로 구현자는 낮은 모델이어도 된다”는 인과관계입니다.

“판단 오류”를 모든 잘못된 행동이라는 뜻으로 쓰면, 코딩 실수도 결국 잘못 판단한 것이므로 반박 불가능한 말이 됩니다. 그러나 그렇게 넓은 정의는 어느 모델을 구현에 써야 하는지 결정하는 근거로 사용할 수 없습니다.

반대로 판단 오류를 “스펙과 설계의 잘못”으로 좁히면 Valuehire 기록이 직접 반박합니다. 웹훅 비밀값 노출, 셸 명령의 따옴표 처리 실패, 널 문자 미정제, 잘못된 산출물 배포, 실제 동작 대신 문자열 존재만 확인한 시험은 설계서만 잘 쓴다고 사라지지 않는 구현·통합 결함입니다.

또한 현재 스펙 감사가 잡은 가장 큰 문제는 스키마가 아니라 적재 코드였습니다. “테이블이 있으니 데이터도 그렇게 쌓일 것”이라고 판단했지만, 실제 미러는 상태를 합치고 현재값만 덮어썼습니다. 이는 설계와 구현을 완전히 분리할 수 없다는 증거입니다.

### 버린 해석

- “Fable이 모든 코드를 직접 작성해야 안전하다”는 해석은 버렸습니다. Sonnet 5의 공개 코딩 성능이 높고, Anthropic도 Fable 조언자+Sonnet 실행자 구조의 비용 효율을 권장합니다.
- “Sonnet이면 Valuehire 전체가 충분하다”는 해석도 버렸습니다. 어려운 다중 파일 수정 시험에서 Fable과 Sonnet의 차이가 크고, Valuehire의 발송·과거 이력은 단순 화면 작업이 아닙니다.
- “멀티에이전트는 항상 나쁘다”는 해석은 버렸습니다. 병렬로 분리 가능한 조사에서는 큰 성능 향상이 측정됐습니다.
- “공개 벤치마크 점수가 곧 Valuehire 성공률이다”라는 해석도 버렸습니다. 공개 시험에는 ClickUp의 실제 데이터 모양, Gmail 발송 직후 장애, 한국 시간 경계 같은 Valuehire 조건이 없습니다.

### 이 판정이 틀렸을 때 깨지는 것

제가 지나치게 보수적이면 P0·P1·P2·P4의 모델 비용과 처리 시간이 늘어납니다. 이 손해는 사용량 기록을 보고 다음 작업부터 Sonnet으로 낮추면 되므로 비교적 쉽게 되돌릴 수 있습니다.

반대로 클로드 안이 지나치게 낙관적이면, 존재하지 않는 과거 이력이 화면에 표시되거나 동일 후보에게 발송이 중복되고, cron이 오류를 반복할 수 있습니다. 이 경우 데이터 정정, 고객 설명, 수동 대조가 필요하므로 손실이 비대칭적으로 큽니다.

전체 판정 확신도는 높음입니다. 다만 “정확히 어느 단계에서 몇 원을 절약하는가”는 Valuehire 실측이 없으므로 확신도 중간입니다.

## 3) 기술 상세·수치·출처 전문

### 3-1. 모델별 공개 코딩 수치

SWE-bench Verified(실제 공개 저장소의 결함 500개를 고치는 시험), SWE-bench Pro(더 크고 여러 파일에 걸친 어려운 결함 시험), Terminal-Bench 2.1(터미널에서 실제 도구를 사용해 작업을 끝내는 시험)의 Anthropic 공개 수치입니다.

| 모델 | SWE-bench Verified | SWE-bench Pro | Terminal-Bench 2.1 | API 단가: 입력/출력 100만 토큰 |
|---|---:|---:|---:|---:|
| Fable 5 | 95.0% | 80.0% | 84.3% | $10 / $50 |
| Opus 4.8 | 88.6% | 69.2% | 74.6% | $5 / $25 |
| Sonnet 5 | 85.2% | 63.2% | 80.4% | $2 / $10 |

→ 뭘 했나: 같은 회사가 공개한 현재 모델의 코딩·터미널 수치와 가격을 비교했습니다.  
→ 뭐가 나왔나: 어려운 다중 파일 시험에서 Fable–Sonnet 차이는 16.8%포인트지만, 터미널 시험에서는 Sonnet이 Opus보다 높았습니다.  
→ 좋은/나쁜 소식: Sonnet은 충분히 강하지만, “등급이 높으면 모든 작업에서 항상 우월하다”는 단순 서열도 틀립니다.

출처는 [Fable 5 시스템 카드](https://www-cdn.anthropic.com/2f9323abbcc4abe219577539efe19a623c9ca2bd/Claude%20Fable%205%20%26%20Claude%20Mythos%205%20System%20Card.pdf), [Opus 4.8 시스템 카드](https://www-cdn.anthropic.com/0b4915911bb0d19eca5b5ee635c80fef830a37ea.pdf), [Sonnet 5 시스템 카드](https://www-cdn.anthropic.com/73ad94ca3c0502e75e46637cc62c8bd9532a7f2c/Claude%20Sonnet%205%20System%20Card.pdf)입니다. 각 수치는 Anthropic 자체 측정이며 최대 노력 수준, 여러 차례 평균, 특정 실행 도구를 사용한 결과입니다.

여기서 나오는 결론은 두 가지입니다.

- [높음 — 사업 영향: 어려운 작업의 재작업률이 커질 수 있습니다.] Sonnet은 일반 구현자로 충분히 유력하지만, Fable과의 차이는 작업이 복잡해질수록 사라지지 않습니다. 특히 SWE-bench Pro의 16.8%포인트 차이는 “계획만 Fable이면 실행 품질은 동일하다”고 단정할 수 없게 합니다.
- [중간 — 사업 영향: 비싼 모델을 잘못 배치해 비용을 낭비할 수 있습니다.] Sonnet의 Terminal-Bench가 Opus보다 높다는 사실은 파일 종류만 보고 모델을 정하면 안 된다는 뜻입니다. 작업의 도구 사용 방식과 실행 환경도 함께 봐야 합니다.

가격만 보면 Fable은 Sonnet의 5배, Opus는 Sonnet의 2.5배입니다. 그러나 실제 총비용은 “첫 실행 토큰+검토 토큰+재작업+사람 확인+사고 복구”이므로, 토큰 단가만으로 절약을 증명할 수 없습니다.

또 하나의 운영 제약이 있습니다. Anthropic은 Fable 5 같은 Mythos급 모델 요청에 30일 보관 정책을 요구한다고 밝혔습니다. Valuehire가 후보자 개인정보를 프롬프트에 넣는다면 원문을 Fable에 넘기지 말고, 이름·연락처를 제거한 스키마와 집계만 제공해야 합니다. [Fable 5 발표와 보관 정책](https://www.anthropic.com/news/claude-fable-5-mythos-5)

### 3-2. 클로드 주장에 유리한 외부 증거

클로드 주장의 큰 방향은 공상은 아닙니다.

ICML 2025의 Plan-and-Act 연구는 planner–executor(계획 담당과 실행 담당을 분리하는 구조)를 시험했습니다. 기본 실행 모델에 고품질 동적 계획을 제공하자 성공률이 9.85%에서 44.24%로 34.39%포인트 개선됐습니다. 다만 연구진은 매 행동 뒤 재계획하는 방식이 느리고 비효율적이라고 직접 한계를 밝혔습니다. [Plan-and-Act 논문](https://proceedings.mlr.press/v267/erdogan25a.html)

Anthropic 역시 “Fable을 조언자, Sonnet을 실행자”로 쓰는 방식을 공식 교육에서 권장합니다. 동시에 자체 업무로 평가 세트를 먼저 만들고, 그 평가로 어느 일을 Fable에 올릴지 정하라고 안내합니다. 즉 Anthropic의 권고도 “위험 등급을 감으로 나눠 바로 전면 적용”이 아니라 “자기 업무 평가를 만든 뒤 배치”입니다. [Anthropic 모델 오케스트레이션 웨비나](https://www.anthropic.com/webinars/building-on-the-claude-platform-claude-fable-5-and-model-orchestration-patterns)

※ Anthropic 개발자 게시물을 전달한 2차 자료에서는 Sonnet 5+Fable 조언자가 SWE-bench Pro에서 Fable 단독 성능의 약 92%를 약 63% 비용으로 냈다고 보도합니다. 다만 공식 시스템 카드에 실린 표준 수치가 아니며 독립 재현도 확인하지 못했습니다. [보도 자료](https://pc.watch.impress.co.jp/docs/news/2123524.html)

#### 반증 시도 기록 1

“최상위 모델이 계획을 맡는 것이 실제로 도움이 되지 않는다”는 방향으로 클로드 주장을 깨려 했으나 실패했습니다. Plan-and-Act의 34.39%포인트 개선과 Valuehire의 스펙 v1 사전 반려 사례는 모두 계획 품질이 중요하다는 주장을 지지합니다.

#### 반증 시도 기록 2

“Sonnet은 이 정도 프로젝트 구현에 부족하다”는 방향으로도 깨려 했으나 실패했습니다. Sonnet 5는 SWE-bench Verified 85.2%, Terminal-Bench 80.4%이며, Anthropic은 고난도 실행 모델로 직접 권장합니다. 따라서 React 화면과 정해진 형식의 테스트·어댑터까지 상위 모델로 올리자는 주장은 근거가 없습니다.

그럼에도 최종적으로 `CONCEDE`가 아닌 이유는, 클로드 안이 Anthropic의 동적 조언 구조와 다르기 때문입니다. Valuehire 안은 Fable이 앞에서 스펙을 쓰고, 이후 단계별 모델이 분리 수행하고, 마지막에 다시 검토하는 구조입니다. 실행 중 발견된 데이터 불일치를 즉시 상위 판단에 돌려보내는 통로가 명확하지 않습니다.

### 3-3. 분업 구조의 실패와 전달 비용 연구

Google Research는 180개 에이전트 구성을 세 모델 계열과 여러 구조에서 비교했습니다. 병렬로 나눌 수 있는 금융 분석에서는 중앙 조정형 구조가 단일 모델보다 80.9% 좋아졌지만, 순서가 강하게 연결된 PlanCraft에서는 모든 다중 모델 구성이 39~70% 나빠졌습니다. 연구진은 전달 과정이 사고 흐름을 잘게 쪼개 실제 문제 해결에 쓸 자원을 줄였다고 설명합니다. [Google Research 요약](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/), [논문](https://arxiv.org/abs/2512.08296)

NeurIPS 2025의 MAST 연구는 7개 다중에이전트 프레임워크에서 1,600개가 넘는 실패 흔적을 분석했습니다. 실패는 시스템 설계, 모델 간 불일치, 검증 실패의 세 묶음과 14개 세부 유형으로 분류됐습니다. 즉 “최종 검토자가 있으므로 전달 오류가 해소된다”는 구조는 연구상 보장되지 않습니다. [NeurIPS 논문](https://proceedings.neurips.cc/paper_files/paper/2025/hash/b1041e52d3be19f0a9bc491657488e4a-Abstract-Datasets_and_Benchmarks_Track.html)

2026년 사전 공개 연구는 사고에 사용한 토큰 수를 같게 맞추자 여러 모델 구조보다 단일 모델이 여러 단계 추론에서 일관되게 같거나 더 좋았다고 보고했습니다. 아직 학회 확정 논문이 아닌 사전 공개본이므로 보조 근거로만 사용했습니다. [동일 토큰 비교 연구](https://arxiv.org/abs/2604.02460)

이 연구들이 Valuehire에서 멀티모델이 실패한다고 증명하는 것은 아닙니다. 그러나 P0의 이력 적재가 P1의 과거 판정을 결정하고, P1의 원장 구조가 P2 발송 계측을 결정하는 현재 작업은 병렬 조사보다 순차 연결 작업에 가깝습니다. 따라서 Google 연구의 “순차 작업 불이익”을 무시할 수 없습니다.

2. 이력 기록은 실패합니다.
3. API는 성공으로 응답합니다.
4. 나중의 과거 시점 화면은 존재하지 않는 이력을 기준으로 틀린 결과를 냅니다.

[적대 감사](/Users/kangsangmo/Desktop/Valuehire_v6/docs/engineering/admin-position-map-spec-v1-adversarial-audit-2026-08-17.md:31), [구현 킥오프](/Users/kangsangmo/Desktop/Valuehire_v6/docs/engineering/goal-prompts/admin-position-map-v2-impl-kickoff-2026-08-17.md:112)

실제 Gmail 도구는 Gmail API의 발송 요청이 성공하고 `SENT` 표시가 반환된 뒤에야 성공을 출력합니다. [send-offer-email.mjs](/Users/kangsangmo/Desktop/Valuehire_v4/tools/position-batch/send-offer-email.mjs:103)

1. Gmail 발송 성공
2. 프로세스 중단 또는 Supabase 쓰기 실패
3. 원장에는 미발송처럼 보임

[치명 — 사업 영향: 동일 후보에게 중복 제안이 발송되어 회사 신뢰가 직접 훼손될 수 있습니다.] 따라서 발송 계측은 React와 같은 중간 위험이 아니라 Opus급 구현과 장애 지점 강제 시험이 필요한 고위험 작업입니다.

[치명 — 사업 영향: 잘못된 동기화나 발송이 야간·주말에도 반복될 수 있습니다.] “코드가 짧다”거나 “정해진 명령 등록이다”라는 이유로 Sonnet 범주에 넣으면 안 됩니다.

### 3-6. 숨은 가정과 반박

**숨은 가정 A — 게이트가 구현 결함을 거의 모두 잡는다**

- 무엇을: 계약·시험·두 모델 검토가 있으면 구현 모델의 약점이 충분히 보완된다는 가정입니다.
- 왜: 심각도 치명 — Valuehire 내부 감사에서 첫 제출 106건 중 57건, 53.8%가 독립 검증에서 반려되어 사업상 거짓 완료 보고 위험이 이미 확인됐습니다. [내부 실패 감사](/Users/kangsangmo/Desktop/Valuehire_v6/docs/engineering/evidence-2026-08-06/llm-failure-cases.md:113)
- 버린 대안: 게이트를 없애자는 대안은 버렸습니다. 이 수치는 오히려 게이트가 필요하다는 강한 증거입니다.
- 대가: 게이트가 “필요하다”를 “충분하다”로 오해하면, 검토자가 보지 못한 통합 결함이 그대로 운영으로 나갑니다.
- 되돌리는 법: 모델 검토와 별도로 실제 데이터 그림자 실행, 장애 지점 강제 중단, 결과 대조 쿼리를 필수 영수증으로 둡니다.

**숨은 가정 B — 시험을 통과한 코드는 안전하다**

- 무엇을: 실패 시험을 먼저 쓰고 모두 통과하면 운영 안전성까지 증명된다는 가정입니다.
- 왜: 심각도 치명 — v4 시험의 `expect` 10,450개 중 3,037개, 29.1%가 문자열 포함 확인이었고, 361개 시험 파일 중 96개가 소스 텍스트를 읽어 검사했습니다. [내부 시험 감사](/Users/kangsangmo/Desktop/Valuehire_v6/docs/engineering/evidence-2026-08-06/llm-failure-cases.md:96)
- 버린 대안: 단위시험이 무가치하다는 해석은 버렸습니다. 순수 매핑과 React 동작에는 여전히 효과적입니다.
- 대가: 실제 ClickUp 응답, Supabase 제약, Gmail 성공 직후 장애, 한국 시간 경계를 시험하지 않으면 “57개 통과, 라이브 전멸”이 반복될 수 있습니다.
- 되돌리는 법: 각 단계에 단위시험 외 그림자 실행·통합시험·운영 전 읽기 전용 대조를 추가합니다.

**숨은 가정 C — 판단과 구현은 깔끔하게 분리된다**

- 무엇을: Fable이 스펙을 확정하면 실행자는 판단 없이 그대로 코딩할 수 있다는 가정입니다.
- 왜: 심각도 높음 — 기존 스펙의 치명 결함은 스키마가 아니라 미러가 데이터를 합치고 덮어쓰는 실제 구현을 끝까지 따라가지 않아 생겼습니다.
- 버린 대안: 한 모델이 전체를 독점하는 방식은 비용과 독립 검증 측면에서 버렸습니다.
- 대가: 실행 중 발견된 `NULL`, 시간 경계, API 응답 모양이 계획자에게 돌아가지 않으면 실행자가 임의로 설계를 바꾸거나 멈추게 됩니다.
- 되돌리는 법: 구현자가 계약 충돌을 발견하면 같은 세션에서 Fable 조언을 호출하고, 변경된 결정을 계약 문서와 시험에 동시에 반영하게 합니다.

**숨은 가정 D — 전달·재작업 비용이 토큰 절감보다 작다**

- 무엇을: Fable→Opus/Sonnet→Codex→리셋 Claude로 넘기는 추가 비용이 항상 절약분보다 작다는 가정입니다.
- 왜: 심각도 높음 — Google 연구에서 순차 작업의 다중 모델 구성은 단일 모델보다 39~70% 나빠졌고, Valuehire P0→P1→P2는 앞 단계 결과에 의존합니다.
- 버린 대안: 멀티모델을 전부 금지하는 해석은 버렸습니다. 서로 독립적인 조사·화면 구성은 병렬화할 가치가 있습니다.
- 대가: 같은 배경을 다시 읽고 잘못 전달된 결정을 수정하는 왕복이 생기면 2.5~5배의 단가 차이를 쉽게 상쇄할 수 있습니다.
- 되돌리는 법: 단계별 모델 비용이 아니라 첫 승인까지의 총 토큰, 경과시간, 반려 횟수, 사람 검토시간을 기록해 다음 배치를 조정합니다.

**숨은 가정 E — 과거 실패는 전부 설계 판단 오류였다**

- 무엇을: 구현 타이핑과 통합에는 문제가 없었고, 좋은 계획만 있었다면 사고가 사라졌다는 가정입니다.
- 왜: 심각도 치명 — 웹훅 비밀값 노출, 셸 명령치환으로 GitHub 이슈 21개 생성, 널 문자 미정제로 공고 유실, 잘못된 버전 배포는 구현·운영 결함입니다. [사고 목록](/Users/kangsangmo/Desktop/Valuehire_v6/docs/engineering/evidence-2026-08-06/llm-failure-cases.md:28)
- 버린 대안: 이 사고에 판단이 전혀 개입하지 않았다는 해석도 버렸습니다. 구현 중 안전하지 않은 선택 역시 판단 실패입니다.
- 대가: 모든 사고를 “기획 모델 문제”로만 분류하면 인용 안전, 입력 정제, 배포 후 화면 확인 같은 구체적 방어책이 빠집니다.
- 되돌리는 법: 사고를 설계·코딩·통합·운영·검증으로 다시 분류하고, 분류별 방지 영수증을 둡니다.

**숨은 가정 F — 같은 검토 자료를 본 두 모델은 충분히 독립적이다**

- 무엇을: Codex와 컨텍스트를 초기화한 Claude가 같은 계약·코드·시험을 보면 상관없는 두 번의 검증이 된다는 가정입니다.
- 왜: 심각도 높음 — 두 모델이 같은 불완전한 스펙과 같은 약한 시험을 근거로 삼으면 같은 결함을 공유할 수 있어 사업상 “두 번 확인”이라는 거짓 안심을 줍니다.
- 버린 대안: 교차 검증을 없애는 선택은 버렸습니다. v1 스펙 결함을 실제로 잡은 성과가 있습니다.
- 대가: 검토자 수만 늘고 새로운 증거가 추가되지 않으면 토큰만 늘며 신뢰도는 기대만큼 오르지 않습니다.
- 되돌리는 법: 두 번째 검토자에게 첫 검토 결론 대신 원본 계약과 코드만 주고, 별도로 그림자 실행 결과·DB 제약·장애 주입 결과를 요구합니다.

**숨은 가정 G — Fable에 모든 기획 문맥을 넘겨도 운영상 안전하다**

- 무엇을: 최상위 모델의 판단을 위해 후보자 원문과 운영 데이터를 그대로 제공해도 된다는 가정입니다.
- 왜: 심각도 높음 — Fable 5 트래픽에는 30일 보관 정책이 있어 개인정보 처리 조건과 충돌할 수 있습니다.
- 버린 대안: Fable을 아예 사용하지 않는 선택은 능력 손실이 커서 버렸습니다.
- 대가: 기술적 정확도를 얻으려다 개인정보 보관·계약 위험이 생길 수 있습니다.
- 되돌리는 법: 이름·이메일·회사별 민감값을 제거한 구조, 익명 표본, 집계 결과만 Fable에 전달합니다.
