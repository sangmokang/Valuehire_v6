## 3. Issue → PR → CI → Merge 사슬의 실제 상태

**붙어 있는 칸**: 이슈-PR 1:1 연결은 잘 된다. `#71→#74` · `#72→#77` · `#73→#75` · `#76→#78`.

**비어 있는 칸**:
- **required check 없음** — `gh api .../rulesets` 와 `.../branches/main/protection` 둘 다
  `HTTP 403 "Upgrade to GitHub Pro or make this repository public"`.
  **이것은 "구조적 제약"이 아니라 요금제 선택이다.** 403 메시지가 해제 조건 두 개
  (Pro 전환 / public 전환)를 직접 알려준다. "구조"라고 부르면 "돈으로 못 푸는 문제"로
  잘못 읽히고, 방어를 전부 로컬 훅에 의존하는 현 상태가 정당화된다.
- **merge = 사람 1명** — strict 계약 `USER_MERGE_ONLY`. 안전 규칙으로는 옳으나 현재 유일한 병목.
- **N-1 껍데기 CI 우회가 살아 있다** — `verify.yml:136` 의
  `if: github.ref == 'refs/heads/main'` 때문에 `인수 검사 0-5 (push · CI 연결)` 스텝이
  **병합 전 어떤 PR 에서도 돌지 않는다.** PR #79 의 두 실행(push·pull_request) 모두
  31스텝 중 이 1건이 `skipped`였다. main 에 들어간 **뒤에야** 돈다.
  → 기존 미해결 항목 `project_n1_shell_ci_bypass_open` 의 실물 증거.

**L3. 조정 조건을 산문으로 남기면 안 지켜진다.** 8/21 문서가 "워크트리 새로 파지 마라"고

**L4. 검증 산출물을 gitignore 에 넣는 순간 검증이 관측 불가능해진다.**

**L5. 요금제로 못 거는 게이트를 "구조적"이라 부르면 대체 방어를 안 만들게 된다.**
해제 조건은 403 메시지에 적혀 있다.

**L6. CI가 13시간 22분 죽었는데 아무도 몰랐다.** main 커밋에는 9/6의 옛 초록 체크가
그대로 붙어 화면상 안전해 보였다. 검사하는 기계를 검사하는 것이 없다.

**L7. "원시적"이라는 감각의 정체는 방법론의 오류가 아니라 실행체의 부재다.**
쪼개기·적대검증·게이트는 옳고 효과를 냈다(약 5배 축소). 빠진 것은 순서대로 호출하는 실행체다.

**L8. 세션 병렬 실행은 경계를 명시하지 않으면 중복을 만든다.** 2026-09-09 CI 장애를
두 세션이 각자 조사해 4분 간격으로 거의 동일한 메모리를 중복 생산했다(하나 폐기).
창마다 ①워크트리 이름 선점 ②`git stash` 금지(스택 공유) ③main 병합 권한 1창 독점
④공유 저장물 쓰기 전 중복 확인.

**L9. "전수 검색했다"는 주장일수록 그물코를 먼저 의심하라.** 이 문서 초안이 "오케스트레이터
0건"을 확장자 3종·depth 3·정규식 1줄로 단정했고, 셋 다 뚫렸다. 특히 정규식은
범위를 아무리 넓혀도 원리적으로 못 잡는 상태였다. **"없다"를 주장할 때는 그물이
알려진 양성 사례를 잡는지 먼저 시험하라(양성 대조군).**

**L10. 표본을 고르는 순간 결론의 부호까지 바뀔 수 있다.** 같은 데이터로 8월 대 9월 PR
