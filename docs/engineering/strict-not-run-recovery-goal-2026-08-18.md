# 결론

이전 저장소 상태 검사는 멈춘 것이 아니라 약 2분 동안 진행 상황을 보여주지 않았습니다. 이를 기다리지 않고 중단해 “실행 확인 못함”으로 남긴 것이 직접 원인이며, 엄격 모드가 필수 검사를 복구하지 않은 채 최종 보고에 남길 수 있게 한 절차가 근본 원인입니다.

이번 변경은 두 엄격 모드에 동일한 복구 규칙을 넣습니다. 필수 검사는 처음 실패하거나 끝나지 않은 그 검사가 성공해야 끝나며, 오래 걸리거나 아무 안내가 없는 경우에는 내부 단계를 좁혀 원인을 고친 뒤 처음 검사를 다시 실행해야 합니다.

## 판단 근거

- `bash scripts/session-status.sh`는 실제로 121초 뒤 종료됐습니다. 첫 하위 검사 `acceptance-0-2.sh`만 약 59~62초가 걸렸지만, 상위 스크립트는 하위 출력 전체를 버려 그동안 아무 진행 상황도 보이지 않았습니다.
- 현재 `RED 2/19`의 실패 두 건은 `acceptance-0-2.sh`의 도달 불가능한 Git 객체 236건과 `acceptance-0-5.sh`의 로컬 `main` 미업로드입니다. 이는 `NOT_RUN`과 별개인 실제 실패입니다.
- 기존 Codex strict는 보조 형식 검사에 대해서는 실행 불가를 허용하면서도, 필수 검사와 보조 검사의 상태 용어를 분리하지 않았습니다. Claude strict의 PR 계약도 `NOT_RUN`을 숨기지 말라고만 하고 해결 의무를 두지 않았습니다.
- 단순히 `NOT_RUN`을 보고하는 길은 버립니다. 대신 필수 검사는 복구하고, 선택 검사만 `SKIPPED`로 분리합니다. 외부 권한 때문에 복구할 수 없는 필수 검사는 `BLOCKED`로 승격해 완료를 차단합니다.

## ① 현재 상태

- `scripts/session-status.sh:42-64` — 19개 검사를 차례로 실행하면서 각 검사의 표준 출력과 오류 출력을 모두 폐기하고, 개별 제한 시간과 진행 표시가 없습니다.
- 변경 전 `~/.codex/skills/strict/SKILL.md:75,170,229` — 실행 불가 사실을 보고할 수는 있지만 필수 검사의 복구·원명령 재실행 계약이 없었습니다.
- 변경 전 `~/.claude/skills/strict/SKILL.md:239-260,474` — 마무리와 PR 보고에 미실행 사실을 적게 하지만 필수 검사의 `NOT_RUN`을 완료 차단 상태로 정의하지 않았습니다.

## ② 근본 원인

직접 원인은 장시간 무출력을 멈춤으로 오판한 조기 중단입니다. 근본 원인은 strict가 `NOT_RUN`을 상태 보고 항목으로만 취급하고, 하위 단위 재현·진단·수정·원명령 재실행을 의무화하지 않은 것입니다.

## ③ 인수 기준

### AC-1 — `NOT_RUN`은 필수 검사의 최종 상태가 아니다

- EARS: When 필수 검사가 실행되지 않거나 끝나지 않으면, 시스템은 이를 임시 `NOT_RUN`으로 기록하고 복구 절차를 시작해야 한다.
- 검증: 두 strict 파일에 `NOT_RUN 복구 게이트`와 `필수 게이트의 NOT_RUN 0건` 문구가 있어야 한다.
- counter-AC: 이유만 적고 작업을 완료로 보고하면 실패다.

### AC-2 — 무출력·멈춤은 가장 작은 단위로 진단한다

- EARS: When 검사가 무출력·제한 시간 초과·멈춤 상태면, 시스템은 하위 검사 이름을 드러내고 제한 시간을 둔 최소 단위로 다시 실행해야 한다.
- 검증: 두 strict 파일에 하위 프로세스 식별, 출력 비억제, 실행시간·마지막 출력 기록 규칙이 있어야 한다.
- counter-AC: 같은 상위 명령만 맹목적으로 반복하거나 즉시 중단하면 실패다.

### AC-3 — 대체 검사 통과는 원래 검사 통과가 아니다

- EARS: When 복구 후 검증할 때, 시스템은 원래 명령을 다시 실행해 종료값과 출력 계약을 모두 충족해야만 PASS로 기록해야 한다.
- 검증: 두 strict 파일에 대체 검사는 보조 증거이고 원명령의 종료값·출력 필드·실패 건수를 다시 판정한다는 규칙이 있어야 한다.
- counter-AC: `verify.sh`가 통과했다는 이유로 `session-status.sh`도 통과했다고 쓰면 실패다.
- counter-AC: `session-status.sh`가 종료값 0이어도 `RED: 2/19`를 출력했는데 PASS로 쓰면 실패다.

### AC-4 — 외부 차단과 선택 검사를 분리한다

- EARS: If 필수 검사가 권한·자격증명·외부 서비스 때문에 복구 불가능하면, 시스템은 `BLOCKED`로 승격하고 완료를 차단해야 한다; 선택 검사면 `SKIPPED`와 비차단 이유를 기록해야 한다.
- 검증: 두 strict 파일에 PASS/FAIL/NOT_RUN/BLOCKED/SKIPPED 상태표가 있어야 한다.
- counter-AC: 필수 검사를 `SKIPPED`로 낮추거나 선택 검사를 필수 실패로 과장하면 실패다.
- counter-AC: 이미 실패한 검사를 goal 비범위에 소급 추가해 `SKIPPED`로 바꾸면 실패다.
- counter-AC: 첫 실행 전 비범위였다는 선행 기록의 경로·시각 없이 `SKIPPED`라고 주장하면 실패다.

### AC-5 — 두 플랫폼의 공통 계약이 드리프트하지 않는다

- EARS: When 한쪽 strict의 공통 복구 계약이 바뀌면, 시스템은 다른 쪽에도 같은 의미의 계약을 반영해야 한다.
- 검증: 두 파일에서 표식 사이 공통 블록을 추출해 바이트 단위로 비교한다.
- counter-AC: Codex 쪽에만 복구 규칙이 있고 Claude 쪽에는 보고 규칙만 남으면 실패다.

## ④ Harness 게이트 진행

- 게이트 0: 원명령과 하위 검사를 재실행해 `NOT_RUN` 원인 및 실제 RED 2건을 분리한다.
- 게이트 1: 이 문서의 AC와 상태 계약을 확정한다.
- 게이트 2~3: 두 strict 파일에 동일한 공통 복구 블록을 삽입하고 기존 마무리·PR 계약을 정합화한다.
- 게이트 4: skill 구조 검사, 공통 블록 동치 검사, 문구 뮤테이션 성격의 부정 검사를 수행한다.
- 게이트 5~6: 홈 스킬 변경이므로 PR·머지 대상이 아니다. 원본 경로에서 재읽어 적용 여부를 확인한다.

## ⑤ 적대 검증 정조준

1. `NOT_RUN`을 이름만 `BLOCKED`로 바꾸고 실제 복구 없이 끝낼 수 있는가.
2. 대체 검사 PASS로 원명령 실패를 덮을 수 있는가.
3. 무한 재시도하거나 사용자에게 평범한 진단을 떠넘길 수 있는가.
4. 선택 보조 검사까지 완료를 영구 차단하는 과잉 규칙인가.
5. Codex와 Claude의 공통 계약이 같은 의미와 문구를 유지하는가.

- 저장소 SOT 수정: 없음. 이번 변경은 홈 디렉터리의 두 strict 실행 절차에 한정합니다.

## ⑦ 비범위

- `acceptance-0-2.sh`가 보고한 도달 불가능 객체 정리.
- 로컬 `main`과 `origin/main`의 차이 해소 또는 push.
- `scripts/session-status.sh` 자체의 진행 표시·제한 시간 구현.

## ⑧ 롤백 절차

두 strict 파일에서 `STRICT_NOT_RUN_RECOVERY:START/END` 사이 블록과 이에 연결된 마무리·PR 문구만 되돌립니다. 저장소 SOT와 실행 스크립트는 건드리지 않습니다.

## ⑨ 영향 반경

두 홈 스킬을 사용하는 모든 저장소의 `$strict`와 `/strict` 완료 판정에 영향을 줍니다. 규칙이 과하면 선택 검사 때문에 작업이 멈추고, 약하면 필수 검사를 실행하지 않은 채 완료로 보고할 수 있습니다.

## ⑩ 계약 스펙

입력 상태는 `PASS | FAIL | NOT_RUN | BLOCKED | SKIPPED`입니다. 출력은 `최종 상태`, `필수 여부`, `원명령`, `원인`, `복구 시도`, `원명령 재실행 증거`를 포함합니다. `PASS`는 원명령의 종료값과 SOT가 정한 출력 계약을 모두 충족할 때만 가능하고, 필수 검사의 `NOT_RUN | FAIL | BLOCKED`는 완료를 차단합니다.

## 적대 검증 로그

### 복구 과정

1. 기본 `claude -p` 검증은 5분 동안 판정 본문에 진입하지 못했습니다. 프로세스 트리에서 Claude 시작 훅의 `session-status.sh`와 플러그인 보조 서버 시작이 남아 있음을 확인하고 중단했습니다.
2. `--safe-mode --tools Read` 재실행은 저장소 안 문서만 읽고 홈 디렉터리의 두 skill 파일은 권한 거부되어 `VERDICT: BLOCKED`를 냈습니다. 이 판정이 지적한 “종료값 0이지만 RED가 남는 상태 보고기” 구멍을 두 skill에 반영했습니다.
3. `--add-dir`로 두 홈 skill 경로를 명시한 재실행은 PASS와 함께 5개 우회 가능성을 제시했습니다. `SKIPPED` 소급 세탁, 상태 보고기의 의미 충돌, 게이트 약화, Codex판 제3 레포 분기 누락, 전 등급 적용 모호성을 모두 수정했습니다.
4. 마지막 Claude 재검증은 선행 기록 증명까지 포함한 최종 파일을 읽고 PASS를 냈습니다.

### V2 — Codex 재공격

Claude 판정을 그대로 믿지 않고 다음을 다시 공격했습니다.

- Claude가 비차단으로 남긴 “첫 실행 전 비범위였다는 증명 수단 부재”를 실제 우회로로 승격하고, 첫 실행보다 앞선 사용자 지시·SOT·goal의 경로와 시각을 `SKIPPED` 장부에 요구했습니다.
- `hook-contracts.md`의 “상태 보고기 자체는 exit 0” 계약과 게이트 0의 “RED 0건이어야 시작 가능” 의미를 분리해, `RED: N/M`은 `N=0`, `M>0`, `UNKNOWN` 없음이 모두 필요함을 확인했습니다.
- 두 마커 블록을 셸 `diff`로 바이트 단위 비교하고, skill-creator의 원래 검사기를 격리 환경에서 두 번 실행했습니다.

최종 실행 출력:

```text
Skill is valid!
Skill is valid!
PASS: skill schema 2/2; common block byte-identical; recovery assertions 15/15
```

→ **무엇을 시켰나:** 두 skill의 앞부분 형식, 공통 복구 블록의 완전 동일성, 15개 필수 문구를 검사했습니다.
