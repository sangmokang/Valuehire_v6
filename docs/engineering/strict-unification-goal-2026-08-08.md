## ② 근본 원인 — 그리고 SOT 가 틀린 이유

### 겉보기 문제와 실제 문제가 다르다

겉보기: *"같은 규칙이 3벌이라 갈렸다."*
실제: **3벌 중 2벌은 애초에 호출되지 않고, 살아있는 2개가 다른 것은 결함이 아니라 의도된 설계다.**

```
~/.codex/skills/strict/SKILL.md:13
  ⚠️ Claude판과의 단 하나의 차이 = 적대검증 엔진이 뒤바뀐다.

~/.codex/skills/strict/SKILL.md:56
  구현자가 codex이므로 검증자는 반드시 다른 엔진(Claude)이다.
```

| | 구현자 | V1(1차 적대검증) | V2(재공격) |
|---|---|---|---|
| Claude 판 | Claude | **Codex** | Claude |
| Codex 판 | Codex | **Claude** | Codex |

핵심 불변식은 **"만든 사람 ≠ 검증하는 사람"**(§6.5)이다.
**심링크로 내용을 같게 만들면 Codex 가 자기 자신을 1차 검증자로 쓰게 되어 이 불변식이 붕괴한다.**

### 기술 층위와 설계 층위를 구분해야 한다

V1-surface 프로브 실측:

| 방식 | 결과 |
|---|---|
| SKILL.md **파일** 심링크 (절대/상대 모두) | **작동 안 함** — 스킬이 카탈로그에 아예 등재되지 않음 |
| **디렉토리** 통째 심링크 | **작동함** — Claude판 234줄 그대로 로드, frontmatter 스키마 호환 |

**"디렉토리 심링크는 기술적으로 되지만 채택하면 안 된다"**가 결론이다. 되는 것과 옳은 것이 다르다.

### 그래서 진짜 원인

**규칙 본문이 플랫폼별 파일 안에 통째로 들어 있다.** 그래서
- 공통 부분(위험등급·AC·배선·증거)이 2벌이 되어 갱신이 한쪽에만 반영됐고(Claude 06-24 / Codex 06-22),
- 달라야 하는 부분(검증자 배정)과 같아야 하는 부분이 **같은 파일에 섞여** 있어 "합칠지 말지"가 이분법이 됐다.

**분리하면 이분법이 사라진다** — 같아야 할 것은 코어에, 달라야 할 것은 어댑터에.

## ③ 인수 기준 (AC) — 실행 가능한 명령이 본체다

### AC-0 — SOT 의 틀린 지시를 먼저 고친다

- **검증**: `grep -c '심볼릭 링크로' docs/engineering/v6-coding-principles-goal-2026-08-06.md` → **`0`**
  그리고 0-8 항목에 코어+어댑터 방식과 **폐기 근거(역할 반전)**가 적혀 있을 것
- **EARS**: If SOT 의 지시가 실측과 충돌하면, then 시스템은 코드보다 SOT 를 먼저 고쳐야 한다.
- **counter-AC**: 문구만 바꾸고 **왜 폐기했는지**를 안 적으면 다음 사람이 같은 판단을 반복한다.

### AC-1 — 규칙 본문이 코어 한 곳에만 있다

- **검증**: 두 어댑터에 규칙 본문이 남아 있지 않을 것
```bash
# 어댑터에 위험등급표·게이트표·R2~R5 본문이 없어야 한다
for f in ~/.claude/skills/strict/SKILL.md ~/.codex/skills/strict/SKILL.md; do
  grep -cE 'L0~L3|게이트 [0-9]|R2 —|R5 —' "$f"      # → 각 0
done
# 코어에는 있어야 한다
grep -cE 'L0~L3|게이트 [0-9]|R2 —|R5 —' <코어경로>   # → > 0
```
- **counter-AC**: 어댑터에 본문을 **복사**해 두는 것은 가짜. 다음 갱신에서 또 갈린다.

### AC-2 — 검증자 배정은 어댑터마다 반대다

- **검증**:
```bash
grep -c 'V1.*Codex' ~/.claude/skills/strict/SKILL.md   # → ≥1
grep -c 'V1.*Claude' ~/.codex/skills/strict/SKILL.md   # → ≥1
```
- **EARS**: When 구현자가 X 이면, then 1차 적대검증자는 반드시 X 가 아닌 엔진이어야 한다.
- **counter-AC**: 두 어댑터가 **같은 검증자**를 지정하면 불변식 붕괴. 이것이 심링크안을 폐기한 이유 그 자체다.

### AC-3 — 저장소 하드코딩 0건

- **검증**: `grep -rc 'valuehire_v4\|Valuehire_v4\|sangmokang/' <대상 5파일>` → 전부 `0`
- **counter-AC**: `v4` → `v6` 치환은 **또 다른 하드코딩**. 저장소는 현재 작업 디렉터리에서 판별해야 한다.
  (정본 §0.5 가 이미 *"명령어·경로를 추측하지 않고 실행으로 확인한다"*고 규정)

### AC-4 — 활성 경로가 실제로 코어를 읽는다

- **검증**: 각 도구에서 strict 를 호출해 **코어 고유 문자열**(예: `counter-VERIFIER`)이 응답에 나타나는지
- **counter-AC**: 파일만 바꾸고 **실제 호출로 확인하지 않는 것**.
  2026-08-07 훅 작업의 교훈 — *"설치했다는 보고가 아니라 실물 동작으로."*
- **counter-VERIFIER**: 코어 읽기에 실패했을 때 도구가 **조용히 규칙 없이 진행**하면 그 자체가 fail-open 이다.
  실패 시 멈추는지 확인해야 하며, 멈추지 않으면 어댑터에 가드를 넣는다.

### AC-5 — 드리프트가 다시 생기면 잡힌다

- **검증**: 코어를 한 줄 바꾸고 어댑터를 그대로 둔 채 검사 → **실패**해야 함
- **counter-AC**: 검사를 만들어놓고 **아무 데서도 실행하지 않는 것**.
  전역 파일이라 CI 가 못 본다(§⑨ 참조) — 이 한계를 숨기지 않고 배치를 명시한다.

## ⑤ codex 적대검증 정조준 항목

1. **코어 읽기 실패 시 fail-open 여부** — 파일이 없거나 못 읽을 때 조용히 규칙 없이 진행하는가
