필수 불변식:
- I1: 승인된 본문·수신자와 현재 발송 대상이 다르면 발송 권한을 얻지 못한다. 실제 사용하는 자료에서 계산한 두 해시를 잠금 안에서 대조한다. 호출자가 임의로 제출한 해시만 믿지 않는다.
- I2: 재조회 검증이 실패한 발송은 어떤 공개 경로로도 VERIFIED가 되지 못한다. 검증과 기록을 같은 시도·패킷·본문·수신자·message_id에 결합한다. 검증 직후 변경과 다른 시도의 결과 재사용을 시험한다.
- I3: 새 시도는 자기 본문·수신자 해시를 기록한다. 이전 시도 정보를 무조건 복사하지 않는다.

함께 처리할 것:
- JD 영역 밖의 임의 조건 삽입, 본문의 packet-id 문구 삽입, 한 줄 입력에 개행 삽입을 재현·차단한다. 정상 회사 소개·후보 평가 문장을 과잉 거부하지 않는 양성 시험도 둔다.

- 수신자 비교는 to·cc를 구분하고 각 그룹의 순서는 무관하게 정규화한다. 중복 처리 계약과 그룹 변경 반례를 고정한다.

잡코리아 실증이 사람인 성공을 대신 증명한다고 기록하지 않는다. 공통 저장 경계는 재사용하되 잡코리아용 검색·상세·저장·복귀의 인수 기준과 실제 시험을 별도로 둔다. 이 순서 변경을 다시 선택 질문으로 올리지 않는다. 사람인 제한을 아직 실측하지 않았으므로 미리 “결제 때문에 실패”로 확정하지 않는다.

실제 잡코리아·RPS 접속 전 확인할 것:
- 필요한 브라우저 접속·중단 증명과 채널별 정확한 origin 목록이 현재 계약으로 확정·검증돼 있다.
- HS-03.04, HS-04, HS-05, HS-06 중 해당 행동에 필요한 조건이 충족됐다.
- LinkedIn 상세 저장에는 HS-11.03의 계약 개정이 선행한다. 9월 8일 상세 저장 결정을 근거로 개정하고, 저장 허용을 후보 발송 허용으로 확대하지 않는다.
- RPS 프로젝트 생성·기존 프로젝트 필터 업데이트에는 9월 14일 사용자 원문을 승인 근거로 연결한 계약 개정이 필요하다. 과거 HS-13 §2의 생성 비범위와 “프로젝트 생성 호출 0” 조건은 승인된 대상 밖 생성 0·재시도 중복 생성 0이라는 새 계약과 시험으로 대체한다. 문자열만 삭제해 검사를 약화하지 않는다.
- 장부가 필수 계약의 main 병합을 요구하면 실제 병합 SHA를 확인한다. LOCAL_COMMITTED 또는 AUDITED를 병합 대체로 사용하지 않는다.
- HS-13.11은 명시된 HS-05·HS-11.04~06 병합 조건을 충족한다. HS-13.12도 명시된 선행 병합 및 암호화 경계를 충족한다.
- 사용자 최신 결정으로 바뀐 옛 제한은 대체표에 반영한다. 이 지시가 모든 구현·검증·병합이 이미 끝났다는 뜻은 아니다.

미충족이면 해당 라이브는 NOT_RUN이다. 로컬 구현·합성 시험·문서 개정·PR 생성은 독립적으로 계속한다. 사용자만 병합하는 규칙 때문에 더 진행할 수 없으면 필요한 PR과 충족된 검증, 병합 뒤 가능한 동작을 구체적으로 보고한다. 임의 병합하거나 라이브 조건을 낮추지 않는다.

## 7. 트랙 C — 잡코리아와 RPS 실행 연결

잡코리아:
- HS-11.01→02→07→08→09→10: 채널 계약 → 검색 조건 적용 재조회 → 후보 식별·잠금 → 상세 열람 → 전체/부분 증거 암호화 저장·독립 재조회 → 목록 필터·위치 복귀 → 실제 1명 완주.
- 같은 후보 재실행 중복 열람 차단과 다른 후보 정상 진행을 함께 검증한다.

RPS:
- HS-11.03~06 및 11~13: 상세 저장 계약 개정 → 프로젝트 확보·필터 설정/업데이트 → 요청 간격·중단 → 후보 상세 읽기·저장·목록 복귀.
- 프로젝트 확보는 작은 WU로 나눈다. 이름만으로 동일 프로젝트라고 판단하지 말고 ClickUp 포지션 ID와 기존 RPS 프로젝트 ID의 연결을 우선한다. 매핑이 없으면 고객사·포지션·기존 프로젝트 정보를 대조한다. 기존 프로젝트가 정확히 하나면 재사용, 없으면 해당 포지션의 프로젝트를 생성, 여러 개면 그 대상만 모호 상태로 보류한다. 검색 오류를 “없음”으로 처리해 생성하지 않는다.
- 생성 전 의도를 기록하고 생성 뒤 실제 ID를 재조회해 로컬 포지션과 연결한다. 클릭 뒤 응답 유실·중단·재실행 시 기존 결과부터 재확인하고 중복 생성하지 않는다. 임의 테스트 프로젝트·다른 포지션 프로젝트·프로젝트 삭제는 범위 밖이다.
- 신규 프로젝트에는 JD에서 도출한 필터를 설정한다. 기존 프로젝트는 변경 전 필터를 보존하고 이번 서치가 소유하는 필드만 업데이트한다. South Korea·Boolean AND/OR·경력 등 실제 입력값과 적용 결과를 재조회해 대조한다. 같은 설정 재실행은 불필요한 변경을 만들지 않는다. 관련 없는 수동 설정·후보 상태·프로젝트 멤버·공유 권한은 유지한다. 필터의 저장 범위가 프로젝트인지 검색 세션인지 실제 UI로 확인하고 과장하지 않는다.
- 필터 일부만 적용되거나 저장 실패하면 검색을 시작하지 않는다. 이전값·요청값·실제값을 기록해 복구 가능하게 하고 동시 변경은 덮어쓰지 않는다. 생성/업데이트 기능은 별도 명시적 쓰기 경계로 두고, 읽기 어댑터가 몰래 프로젝트를 생성하지 않게 한다.
- HS-13.11의 기존 “저장·발송 호출 0”은 읽기 어댑터의 책임 경계로 유지한다. 상세 저장은 HS-11.11과 공통 저장 계층이 담당하고 상위 실행 흐름에서 연결한다. 프로젝트 쓰기는 위 신규 WU로 연결한다. 해당 계약을 바꿔야 하면 사용자 승인 근거·입출력·반례를 포함해 개정한다.
- South Korea와 해당 포지션 필터를 실제 화면의 적용 결과로 확인하고, HS-13.07의 Boolean 검색식 변형을 이용한 반복 순회를 연결한다. 한 페이지 읽기는 중간 실증이며 반복 검색 완료가 아니다.
- 읽은 후보의 출처 URL·매칭 이유·학력·경력·관측된 연락처·근거 기반 점수를 기존 패킷에 연결한다. LLM이 만든 숫자를 점수로 사용하지 않는다. 1촌의 표시된 연락처만 취득하고 보이지 않는 주소를 추정하지 않는다.
- HS-13.12로 패킷→SQLite 저장·중복 방지·재조회·암호화 경계를 완성한다. 파일 저장을 DB 통합 완료로 표현하지 않는다.

사람인:
- 라이브 조건 충족 뒤 현재 계정의 목록·검색·상세 접근 가능 범위를 확인한다. 로그인 문제·상품 권한·화면 변경·제어 도구 부재를 구분한다.
- 실제 막힌 카드만 이유·해제 조건과 함께 보류한다. 사람인 카드·회귀시험·장기 목표는 삭제하지 않는다.

## 8. 전체 제품 목표와 검증

ClickUp·Gmail 포지션 파악, 회사 조사·인재 구성 파악, 원문에 충실한 JD 3버전, 편집하기 쉬운 팀 메일, 후보별 InMail 초안, Discord 멤버 명령, Supabase·ClickUp 결과 연동, 반복 검색·재개를 요구 대응표에서 유지한다. 이번에 구현하는 항목과 기존 구현 재사용, 후속 항목을 구분한다. 회사 조사나 발송이 외부 도구에 의존하면 순수 코드가 모든 운영을 자동 수행한다고 표현하지 않는다.

각 WU는 입력·출력·오류·경계·부작용·DB/API 계약·타입·counter-AC를 고정한다. 실패 시험 → 최소 구현 → 관련 회귀 → 독립 Codeaudit → 격리 사본의 결함 주입 → 필수 검사 → 커밋 → PR → 현재 SHA의 CI 순서로 검증한다. 독립 검토를 위해 미검증 제품을 GREEN 완료로 커밋하지 않는다. 검토 도구가 커밋을 요구하면 후보/WIP와 검증 완료를 구분한다.

기존 9월 12일 HS-13 수정은 기존 PR 소유 범위에서 이어가고, 새 작업은 WU 1개·워크트리 1개·PR 1개로 작게 나눈다. 문서·계약·검사기 변경은 현재 저장소의 변경 절차와 코드량 예산을 따른다. 훅을 우회하지 않는다. 커밋은 Lore 형식을 사용하며 실제 기여자만 표시한다.

필수 검사는 실제 존재하는 해당 WU 시험, 영향받는 회귀, Ruff·mypy, git diff --check, bash verify.sh 및 적용되는 acceptance다. 로케일 관련 변경은 UTF-8과 LC_ALL=C를 모두 검증한다. 검사 개수나 PASS 문구만으로 성공을 판단하지 않는다. 관련 없는 검사 반복으로 제품 작업을 무한히 지연시키지 않는다.

원본 이력서·세션 값·키·후보 개인정보를 Git·PR·일반 로그에 넣지 않는다. 저장과 라이브의 증거는 계약상 보호 위치에 두고 보고에는 비민감 지문·결과만 사용한다.
