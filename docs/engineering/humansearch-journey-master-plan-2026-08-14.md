## 결론 (사장님 브리핑 — 1층)

사장님이 그리신 여정(고객 메일 접수 → 회사 조사 → 4개 채널 등록 → 인공지능이 후보를 미리 모아 헤드헌터에게 밑거름 제공 → 디스코드에서 명령)은 방향이 맞습니다. 다만 지금 이 저장소에 이미 확정돼 있는 설계 약속 세 가지와 정면으로 부딪히는 지점이 세 곳 있어, 사장님이 결정을 내려주셔야 다음 단계로 갈 수 있습니다.

갈림길 세 곳을 여쭈었고, **사장님이 2026-08-14 세 건 모두 결정하셨습니다.** 결정 내용과 그에 따라 이 문서가 어떻게 바뀌는지입니다.

1. **디스코드 원격 명령 → 완전 무인으로 확정** ("사람이 누르는 게 있으면 모든 게 도루묵"). 이에 따라 브라우저 접속 방식을 재설계했습니다 — 사람이 버튼을 눌러 권한을 넘기는 기존 확정 설계를 버리고, **채널별 전용 브라우저를 항상 켜 두고 상주 프로그램이 명령 즉시 붙는 구조**로 갑니다. 이 구조는 v5가 수백 번 실패 끝에 도달해 실제로 돌던 방식과 같은 뼈대이며(코드는 새로 짓습니다), 사람이 필요한 순간은 로그인 만료·2단계 인증·보안문자뿐입니다 — 그때만 창을 앞으로 띄우고 디스코드로 한 번 알린 뒤, 사람이 로그인하면 자동으로 재개합니다. 기존 확정 문서의 브라우저 장(章)을 공식으로 고치는 승인 문서 1건이 함께 갑니다.
2. **저장은 SQLite(이 컴퓨터의 원본 장부) 1차 → Supabase로 순차 배치 전송으로 결정.** 권고안 그대로이며 설계 변경 없이 확정입니다.
3. **사람인·잡코리아에 한해, 높은 점수 매칭이면 부분 자동 발송을 실험하기로 결정.** 이는 기존 확정 문서의 "발송은 어떤 경우에도 자동으로 누르지 않는다"는 약속에 예외를 만드는 결정이므로, 예외의 범위(두 채널만, 점수 기준, 하루 발송 상한, 중복 접촉 차단 통과 필수)를 못 박은 실험 트랙(E4)을 신설하고 그 약속 문서 자체도 같이 고칩니다. LinkedIn과 Gmail은 종전대로 초안까지만 자동입니다.

남은 결정 사항은 실험의 숫자 두 개뿐입니다 — **자동 발송 점수 기준(제안: 85점 이상)과 하루 발송 상한(제안: 채널당 10건)**. 이 둘만 정해주시면 나머지는 결정 없이 진행 가능합니다. 코드 한 파일이 500줄을 넘지 못하게 하는 요구는 문서 약속이 아니라 **자동 검사로 강제**하도록 설계에 넣었습니다.

## 왜 이렇게 판단했나 (2층)

### 여정 전체를 하나의 공장으로 보면 다섯 정거장이다

사장님 말씀을 순서대로 늘어놓으면 일감은 다섯 정거장을 지납니다. 각 정거장은 독립된 부품이고, 앞 정거장의 출력이 뒷 정거장의 입력입니다. 이렇게 쪼개는 이유는 두 가지입니다 — ① 한 정거장이 고장 나도 나머지가 멈추지 않고, ② 각 정거장을 500줄 이하의 작은 부품 여러 개로 만들 수 있기 때문입니다.

| 정거장 | 하는 일 | 지금 상태 |
|---|---|---|
| ST-1 접수 | Gmail의 비정형 JD 요청 → 구조화된 포지션 명세 → ClickUp 등록 | [포지션] 메일→ClickUp 자동 등록은 이미 돌고 있음(사장님 확인). 비정형→구조화가 새 일 |
| ST-2 조사 | 회사 공식 URL로 매출·인원·투자·제품·뉴스 조사 카드 생성 | v5 스킬들이 반자동으로 수행 중. v6에는 없음 |
| ST-3 등록 | 포지션 명세 1개 → 4개 채널 본문(글자수 규격 자동 검증) → 각 사이트 등록 | v5 스킬(position-batch 등)이 현역. v6에는 없음 |
| ST-4 서치 | JD 조건으로 채용 사이트를 사람처럼 순회, 증거와 함께 후보 수집·채점 | **v6 본진.** 클린룸 계약 확정, G1·G2 병합 완료, 다음 G3 |
| ST-5 보고 | 합격 후보를 ClickUp·Discord·Supabase에 알리고, 개인화 메일 초안 생성 | 계약상 "선택적 어댑터"로 이미 자리 있음. 구현은 없음 |

→ 이 표의 의미: **다섯 정거장 전부를 v6에서 새로 만듭니다**(사장님 지시 2026-08-14: *"v5를 절대 의존하지 마라, 여기서 모든 것을 새롭게 다시 만든다"*). v5 칸은 "무엇이 이미 존재하니 참고하라"가 아니라 "무엇을 대체해야 끝나는가"의 목록입니다. 착공 순서만 ST-4(서치)가 먼저인데, 그 이유는 ST-4가 유일하게 설계 계약과 검사 장치(G1·G2)까지 깔린 트랙이라 가장 빨리 완성돼 대체 1호가 될 수 있기 때문입니다.

### 갈림길 세 곳 — 왜 이 답을 권하나

**결정 카드 ① 무인 실행 — 상주 세션 모델로 재설계 (사장님 확정 2026-08-14)**

> **무엇을** — 사람 클릭 0회. 채널별 전용 브라우저(사장님 실제 프로필)를 원격 진단 포트(브라우저가 외부 프로그램의 접속을 허락하는 공식 문)를 켠 채 상시 실행해 두고, 로컬 상주 프로그램이 디스코드 예약을 받는 즉시 그 브라우저의 기존 탭에 붙어 순회를 시작한다. 사람 개입은 로그인 만료·2단계 인증·보안문자 세 경우뿐 — 그때만 창 전면화 + 디스코드 알림 1건 + 정지, 사람이 로그인하면 자동 재개한다.
> **왜** — 사장님 지시: "사람이 누르는 게 있으면 모든 게 도루묵." 클릭 1회 모델은 이 여정의 핵심 가치(원격 지휘)를 무너뜨린다. 또한 상주 브라우저+진단 포트 접속은 2026-07-19 사장님이 직접 지정하신 목표 아키텍처이고(창립 스펙 §1-A: "브라우저 식별자는 CDP 포트로 통일, 머신별 전용 Chrome 상시 실행"), v5 말기에 라이브로 검증된 구조다.
> **버린 길** — ① 확장 버튼 클릭 모델(클린룸 계약 §4-1의 Active Tab Bridge): 무인 불가라 폐기. ② 확장에 광역 권한을 줘 클릭 없이 탭을 잡게 하기: 확장이 흉내내는 가짜 클릭·입력이 채용 사이트에 안 먹히는 것이 v5 실측이다(창립 스펙 §4-4: 화면 요소 직접 클릭은 무시되고 진단 포트 수준의 진짜 입력만 반영됨). 결국 진단 포트 권한까지 얹어야 해서 두 방식의 단점만 합쳐진다.
> **대가** — ⑴ 기존 클린룸 계약의 브라우저 접속 장(Phase B: B1~B5)을 개정하는 설계 변경 기록 문서(위험이 큰 약속을 바꿀 때 "무엇을 왜 바꿨고 누가 승인했는가"를 남기는 공식 문서 — 사장님의 2026-08-14 지시가 그 승인이다) 1건이 선행돼야 한다. ⑵ 전용 브라우저가 꺼지면 사람이 다시 띄울 때까지 그 채널은 정지다(상주 감시로 완화). ⑶ "엉뚱한 창을 잡는" 사고를 막던 사람 클릭 장치가 사라지므로, 접속 대상 검증(살아있는 포트 자동 탐지 + 화면 구조 검증 + 도메인 대조 + 목표 탭 1개만 접속)을 전부 코드로 강화해야 한다 — v5가 이 검증 없이 수백 건 실패했던 바로 그 지점이다.
> **되돌리기** — 상주 프로그램을 끄면 수동 모드로 복귀 가능. 큐·상태기계·증거·채점은 접속 방식과 무관하게 재사용된다.

**결정 카드 ② Supabase(클라우드 DB) 위치**

> **무엇을** — 이 컴퓨터의 SQLite(파일 하나짜리 로컬 데이터베이스)를 유일한 원본으로 유지하고, Supabase는 원본을 한 방향으로 복사해 내보내는 사본으로 둔다.
> **왜** — v5는 저장을 3벌(로컬+파일+Supabase)로 흩어서 "저장했는데 안 보인다" 사고를 냈고, 창립 스펙 §5가 이를 이유로 "SQLite 1개가 유일한 정본, 클라우드는 읽기 전용 파생"으로 확정했다. 사장님의 "Supabase에 저장 필요" 요구는 내보내기 어댑터로 충족된다 — 기존 테이블에 이미 쌓인 인재 데이터와의 대조(중복 확인)도 이 어댑터가 조회로 수행한다.
> **버린 길** — Supabase를 원본으로: 네트워크·외부 서비스 장애가 곧 서치 실패가 되고(v5 실증), 증거 파일(스크린샷 등)과 장부가 분리된다.
> **대가** — 클라우드에는 약간의 지연(내보내기 주기만큼)이 생기고, 내보내기 실패 감시가 하나 더 필요하다.
> **되돌리기** — 어댑터 방향만 바꾸면 되므로 스키마 재설계 없이 전환 가능.
> **판단 필요:** 없음(권고안이 사장님 요구를 전부 충족한다고 판단). 반대 의견이 있으시면 말씀만 주시면 된다.

**결정 카드 ③ 자동 발송 — 사람인·잡코리아 한정 실험 (사장님 확정 2026-08-14)**

> **무엇을** — 사람인·잡코리아 두 채널에서만, 높은 점수(제안: 85점 이상)로 매칭된 후보에 한해 이직 제안 발송을 자동으로 실험한다. 안전장치: 하루 발송 상한(제안: 채널당 10건), 중복 접촉 차단 관문 통과 필수, 발송 1건 = 장부 영수증 1건. LinkedIn 인메일과 Gmail 개인화 메일은 종전대로 초안까지만 자동이고 발송은 사람이 한다.
> **왜** — 사장님 판단: 사람인·잡코리아는 개인화 여지가 적어(정형화된 제안 양식) 자동 발송의 오발송 리스크가 상대적으로 낮고, 실험 가치가 있다. 반면 LinkedIn·Gmail은 개인화 품질이 곧 회사 인상이라 사람 검토를 유지한다.
> **버린 길** — ① 전 채널 발송 금지 유지(원래 권고): 편의성 손실이 커서 사장님이 기각. ② 전 채널 자동 발송: 개인화 채널의 오발송 1건이 고객사·후보 양쪽 신뢰를 깎아 기각.
> **대가** — 기존 확정 문서(창립 스펙 §2-1 "발송 자동 클릭 0회")에 예외가 생긴다 — 문서와 코드가 어긋나지 않도록 그 조항을 고치는 변경이 같은 작업(E4)에 묶여야 한다. 자동 발송된 제안의 품질 사고는 사후에만 발견된다(피드백 루프 §5가 감시 장치).
> **되돌리기** — 실험 채널·점수 기준·상한은 설정 파일 한 곳에 있어 언제든 끄거나 조일 수 있다. 확대(다른 채널·기준 완화)는 채택률 실측을 근거로 별도 결정한다.
>
> **단계적 실행 (codex 지적 5번 반영 — 85점·10건은 "상한"이지 즉시 실행량이 아니다):** 점수는 후보 적합도일 뿐, 수신자·공고·중복·문구·화면을 재확인하지 못한다. 그래서 3단계로 켠다 — ⑴ **무발송 관찰**(초안만 생성, 헤드헌터가 초안 품질 확인) → ⑵ **하루 1건 승인 시험**(사람이 발송 직전 승인) → ⑶ 채택률 지표 충족 시에만 **자동 상한 10건까지 확대**. 85점은 하드 하한, 10건은 하드 상한으로 설정에 **확정**한다(미확정 아님 — codex A-02 반영).

### 사장님 기획의 빈틈 — 제가 찾은 것 (비판)

1. **"정확도가 높아지면"을 잴 자가 없다.** 헤드헌터가 AI 수집 후보를 채택했는지/버렸는지 기록하는 칸이 여정에 없다. 이 라벨이 없으면 정확도는 영원히 느낌으로만 남고, 자동 발송 전환 조건도 판정 불가다. → 해소: ClickUp 후보 태스크에 채택/기각 상태를 두고, 그 결과를 장부로 회수하는 피드백 루프를 ST-5에 넣는다(§5).
2. **같은 후보에게 중복 접촉하는 사고 경로가 열려 있다.** 상시 오픈 포지션은 반복 순회하므로, 지난주에 본 후보를 이번 주에 또 열고, 서로 다른 포지션으로 같은 사람에게 두 번 제안하는 일이 생긴다. → 해소: 순회 전 기존 장부(로컬+Supabase 기존 인재 테이블) 대조를 관문으로 넣고, "재열람 금지 기간"을 설정값으로 둔다.
3. **Aside 브라우저 진단 포트 — 실측 완료(2026-08-14, 사장님 지시로 즉시 실행).** 절차: 열린 탭 9개 백업(`.claude/aside-tabs-backup-2026-08-14.txt`) → Aside 정상 종료 → 같은 프로필로 `--remote-debugging-port=45111` 재시작 → 접속 확인. **결과: 성공.** 진단 문(`/json/version`)이 응답했고(내부 엔진 Chrome 151), 탭 8개가 복원됐으며, 개별 탭마다 접속 주소가 발급된다 — 즉 Aside를 무인 상주 브라우저로 쓸 수 있다. 단 사이트별 편차: Gmail 받은편지함·ClickUp·LinkedIn 일반 화면은 로그인 유지, **잡코리아는 로그인 화면으로, LinkedIn 리크루터는 계약 선택 화면으로 복원**됐다(재시작 탓인지 원래 만료였는지는 단정 불가 ※). 이 편차가 바로 "미로그인이면 정지하고 사람을 부른다"는 관문이 반드시 필요한 이유다. 현재 Aside는 포트 45111이 켜진 상태로 떠 있다 — 재부팅 후에도 이 상태로 뜨게 하는 자동 기동은 D1의 일이다.
4. **검색어(Boolean) 자동 입력이 무인 결정으로 범위 안에 들어왔다.** 기존 확정 계약은 "사람이 걸어둔 검색을 순회한다"였는데, 사람 클릭 0회가 확정되면 검색을 걸 사람도 없다. 검색 조건 자동 입력은 v5에서 실패가 잦았던 영역(이전 검색 필터 잔재, 자동완성 미적용 등)이라, 창립 스펙 §4의 검증된 규칙(입력 전 필터 리셋, 진짜 입력, 적용된 조건 칩을 증거로 요구)을 v6 계약으로 새로 구현하는 AC를 D3~X 사이에 넣는다. 그전까지의 과도기(수직 슬라이스 검증 단계)에는 사람이 걸어둔 검색 탭을 쓴다.
   **★ 실측으로 검증된 핵심 결론 (2026-08-14):** 자동 로그인(저장된 자격증명을 코드가 입력)은 **실패**했고, 사장님이 브라우저에서 직접 로그인 버튼을 누른 것은 **성공**했으며, 그 성공한 세션을 **자동화가 접속 포트로 그대로 읽어냈다**(사람인: `hiring.saramin.co.kr/home`, 로그인 상태 True 확인). 이는 오늘 확정된 클린룸 계약 §4-3의 결정 — "자동 자격증명 입력을 코어에서 제거하고, 사람이 같은 탭에서 로그인한다" — 이 옳다는 실전 증거다. 컴퓨터에 따로 저장돼 있던 자격증명은 낡아서 안 맞았고(사람인·잡코리아 둘 다), 브라우저가 기억하는 로그인은 맞았다. **따라서 v6 무인 흐름의 로그인은 "코드가 비밀번호를 입력"이 아니라 "브라우저에 살아있는 사람 세션을 이어받고, 없으면 멈춰 사람을 부른다"로 확정한다.** 자동 자격증명 입력 기능은 코어에서 뺀다(비밀번호 유출 경로도 함께 사라진다).

   **LinkedIn 리크루터(RPS)의 검색은 구조가 다르다 (사장님 확정 2026-08-14):** RPS는 검색 페이지에 바로 가는 게 아니라 **포지션마다 프로젝트를 만들고 그 안에 필터를 걸어두는 준비 업무가 선행**된다. 따라서 ⑴ ClickUp에 포지션이 등록되면 RPS 프로젝트 생성+기본 필터 세팅까지가 등록(ST-3) 업무에 포함되고, ⑵ 서치 태스크가 생기면 그 프로젝트로 가서 **기본 세팅된 필터를 먼저 순회하고, 결과가 없으면 키워드 불린 값을 바꿔 재순회**한다. 이 두 단계를 각각 AC로 만든다(프로젝트·필터 준비 = U 트랙, 필터 순회·키워드 교체 = X2 확장).
5. **개인정보가 클라우드로 나갈 때의 규칙이 없다.** 클린룸 계약은 로컬 캡처에 보존기간·삭제 영수증을 강제하는데, Supabase로 내보내는 순간 같은 규칙이 클라우드에도 필요하다. → 해소: 내보내기 어댑터에 "내보낼 수 있는 필드 목록(화이트리스트)"과 보존기간을 계약으로 박는다. 스크린샷 원본은 내보내지 않는다.
6. **채용 사이트 계정 잠금 리스크는 0이 되지 않는다.** 사람 페이스 모방·재시도 금지·캡차 즉시 정지가 다 있어도, 사이트 약관상 자동화 접근이라는 사실은 남는다. 기업회원(서치펌) 정상 사용 범위의 열람량을 지키는 것으로 리스크를 낮출 뿐 제거하지는 못한다 — 이건 사업 리스크로 정직하게 안고 간다.
7. **상시 포지션의 재순회 주기가 미정이다.** "긴 시간 열어두는 포지션"을 언제 다시 도는지, 새 후보만 볼지 전체를 다시 볼지 규칙이 없다. → 해소: 포지션 명세에 `recurrence`(재순회 주기)와 `dedupe_window`(재열람 금지 기간) 필드를 넣는다(§3).

### 이 여정이 서치펌에 최선인가 — 제 판단

**방향은 최선에 가깝습니다.** 근거: ① 상시·반복 포지션은 "거의 확정된 일감"인데 병목이 헤드헌터의 서치 노동이라는 진단은 v5 운영 기록과 일치합니다. ② 후보 수집→검토 밑거름 모델은 발송 자동화보다 리스크가 낮으면서 시간 절약 효과는 큽니다.

다만 **순서에 대한 반례를 하나 스스로 찾았습니다(규칙 R3의 반례 1회):** "상류(접수·조사·등록)부터 v6로 다 만들고 서치를 나중에" 하는 대안도 성립합니다. 상류가 매일 반복되는 노동이기 때문입니다. 그런데 이 대안을 버린 이유는 — 서치는 v5에서 3개월간 실패한 가장 어려운 구간이라 유일하게 정본 계약과 검사 장치(G1·G2)까지 깔아 두었고, 여기서 방향을 틀면 그 트랙이 다시 멈추면서 v5의 "다 벌려놓고 아무것도 병합 안 됨" 병리가 재현되기 때문입니다. **v6는 서치 수직 슬라이스(사람인 1명 완주)를 먼저 끝내고, 곧바로 상류 재건(U 트랙)으로 넘어가 v5 의존을 구간별로 끊어냅니다**(사장님 지시: v5 의존 금지, 전부 새로 제작).

## 3층 — 기술 상세

## §1. 전체 아키텍처 지도

```text
[ST-1 접수]  Gmail → intake 파서 → PositionSpec(JSON) → ClickUp 초안 → 사람 승인
                                       │
[ST-2 조사]  회사 도메인 → CompanyCard(JSON, 캐시) ─┤
                                       ▼
[ST-3 등록]  PositionSpec + CompanyCard → 채널 렌더러 4종(순수 함수+글자수 검증)
             → (v6 렌더러가 직접 등록. v5 스킬 사용 안 함 — 사장님 v5 의존 금지)
                                       │
[지휘부]     Discord Bot → 명령 검증 → SQLite 작업 큐 → 상주 러너가 즉시 착수(사람 클릭 0회) ← 결정 카드 ①
                                       ▼
[ST-4 서치]  채널별 전용 브라우저(실프로필, 진단 포트 켠 채 상시 실행)의 기존 탭에 러너가 접속
             → 프리플라이트(로그인·보안문자·화면 검증, 하나라도 실패면 정지) → 순회 → 증거·채점·게이트
             → 예외(미로그인·2FA·보안문자·세션충돌): 창 전면화 + Discord 알림 1건 + 정지, 사람 로그인 후 자동 재개
             → 사장님이 그 브라우저를 직접 쓰면 즉시 양보, 손 떼면 재개(v5 검증 규칙 계승)
                                       ▼
[ST-5 보고]  SQLite(정본) → 어댑터: ClickUp(901818680208) · Discord · Supabase(순차 배치 내보내기)
             → 사람인·잡코리아 고점수 자동 발송 실험(상한·영수증) / LinkedIn·Gmail은 초안까지 ← 결정 카드 ②③
             → 헤드헌터 채택/기각 라벨 회수(피드백 루프)
```

→ **그림이 말하는 것:** 여정 전체가 한 줄 파이프입니다. 디스코드 명령이 들어오면 사람 없이 곧장 순회가 시작되고, 사람이 등장하는 지점은 로그인·2단계 인증·보안문자 세 곳뿐입니다. 결정 카드 ①②③이 각각 어느 이음새에 걸리는지 표시했습니다.

- 지휘부(Discord)와 ST-5 어댑터는 전부 **꺼도 파이프라인이 완결**되는 선택 부품이다(클린룸 계약 §5 RunResult가 이미 이 구조).
- 무인 결정(결정 카드 ①)으로 기존 클린룸 로드맵 중 **브라우저 접속 방식(Phase B)만 교체**된다. 나머지 — 상태기계(L0), 화면 계약(C), 로그인 판정(L1), 수직 슬라이스(V), 채점·게이트(S), SQLite 정본, 증거·PII 규칙 — 는 접속 방식과 무관하게 전부 유지된다.

## §3. 입출력 계약 (핵심 2개)

**PositionSpec** — 여정 전체가 공유하는 포지션 명세. ST-1이 생산, ST-3·ST-4가 소비.

```jsonc
{
  "position_ref": "clickup task id",
  "company": { "name": "", "official_url": "", "domain": "" },
  "title": "", "jd_official_text": "",
  "requirements": { "years_min": 0, "years_max": 0, "skills_core": [], "education_min": "" },
  "urgency": "recent|evergreen",          // 최근 등록=시급 / 상시 오픈
  "recurrence_days": 7,                    // evergreen 재순회 주기
  "dedupe_window_days": 90,                // 같은 후보 재열람 금지 기간
  "channels": ["saramin","jobkorea","linkedin_rps","gmail"]
}
```

→ **이 명세가 말하는 것:** 포지션 1건에 대해 "얼마나 급한가, 얼마 주기로 다시 돌 것인가, 같은 후보를 언제까지 다시 열지 않을 것인가"까지 처음부터 데이터로 박습니다. 상시 오픈 포지션(코드잇 강사 등)의 반복 순회와 중복 접촉 방지가 이 두 필드(recurrence_days, dedupe_window_days)에서 나옵니다.

**RunCommand** — Discord 명령이 큐에 남기는 예약. ST-4의 RunRequest(클린룸 계약 §5)와 다르다 — RunRequest의 `tab_lease_id`는 사람 클릭 후에만 생기므로, 예약 단계에는 존재하지 않는다.

```jsonc
{
  "command_id": "uuid", "issued_by": "discord user id(허용 목록 대조)",
  "position_ref": "", "channel": "saramin|jobkorea|linkedin_rps",
  "issued_at": "", "status": "queued|claimed|running|done|expired",
  "expires_at": ""                         // 클릭 없이 방치되면 만료(조용한 영구 대기 금지)
}
```

## §11. 구현 명세 — Phase별 인수기준·입출력·실패모드 (codex FAIL 반영, 구현 문서화)

### D-SAFE — 무인 안전 계약 (신설, 무인 실행보다 먼저) ★codex CRITICAL 반영

완전 무인은 이 Phase 없이 착수 금지. codex가 "계정잠금·봇탐지·세션충돌·포트보안·명령재전송 상태전이 없음"을 CRITICAL로 지목.

| 항목 | 계약 |
|---|---|
| **입력** | RunCommand(큐), 채널, 대상 탭 origin |
| **출력** | `preflight_receipt{live:bool, challenge:bool, session_conflict:bool, port_bound:'127.0.0.1', reason}` |
| **RED 인수기준** | ⑴ 미로그인 화면 fixture 주입 → 순회 코드 **실행 0회**, STOP + Discord 알림 1건. ⑵ 캡차/2FA 문구 fixture → 재시도 0회, terminal. ⑶ 같은 명령 2회 수신(idempotency_key 동일) → 외부행동 1회만. ⑷ 포트가 0.0.0.0 바인딩이면 exit 1(127.0.0.1만 허용). ⑸ 세션충돌 마커 → AUTH_CONFLICT terminal. |
| **실패모드** | 로그인만료→park+알림, 캡차→terminal STOP, 세션충돌→terminal, 포트노출→기동거부, 명령중복→기존결과 readback |
| **배선** | Discord명령 → run_queue → **D-SAFE 프리플라이트(여기)** → 통과 시에만 traverse 호출. 프리플라이트 실패는 순회 진입 자체를 막는다. |

→ **이 표가 말하는 것:** 무인 자동화가 계정을 건드리기 전 통과해야 할 5개 시험이다. 하나라도 실패하면 순회 코드가 실행되지 않는다 — codex가 지목한 무인 안전 공백을 이 관문이 메운다.
