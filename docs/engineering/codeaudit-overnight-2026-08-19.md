## 3. 핵심 해설

### 3-1. 무엇을 확인했나 (읽는 법)

이 세션은 "코딩 원칙 32개가 실제로 지켜지는지 자동으로 확인하는 장치"와 "검증하다가 실수로 다른 파일을 건드리지 못하게 막는 안전장치" 두 가지를 만들었다고 주장했습니다. 저는 이 둘을 **직접 실행**해서 확인했습니다 — 코드를 읽기만 한 게 아니라, 일부러 값을 조작해서(뮤테이션 시험: 원칙 이름을 몰래 바꾸거나 문서 형식을 깨뜨려 봄) 검사기가 실제로 잡아내는지, 그리고 파일 잠금 스크립트를 실제로 잠갔다 풀었다 해서 진짜로 쓰기가 막히는지 시험했습니다.

### 3-2. 진입점 → 핵심 로직 → 결과

**진입점**: `scripts/acceptance-principles-check.sh`는 `hooks/pre-push`(사장님이 `git push`를 누르는 순간 자동 실행되는 검사 목록)에 이름 패턴(`acceptance-*.sh`)만으로 자동 편입됩니다. 제가 직접 이 훅을 실행해봤더니 실제로 19개 검사 중 하나로 `scripts/acceptance-principles-check.sh`가 돌아서 `ok`가 찍혔습니다.

```text
pre-push: 검사 19개 실행
  ...
  ok  ./scripts/acceptance-principles-check.sh
  ...
  ok  ./verify.sh
```
→ 뭘 시켰나: 이 세션이 만든 검사 스크립트가 실제로 "매번 push할 때 자동 실행된다"는 PR 본문 주장을 그대로 재현. / 뭐가 나왔나: 19개 검사 전부 `ok`, 새 검사도 포함됨. / 좋은 소식인가 나쁜 소식인가: 좋은 소식 — 이름만 걸어두고 실제 실행선(hooks/pre-push, CI)에 안 끼워 넣는 흔한 함정(이 저장소 자체의 과거 사고 이력, `hooks/pre-push:69-72` 주석 참조)에 걸리지 않았습니다.

**핵심 로직(D1~D3)**: id 집합 검사(`scripts/acceptance-principles-check.sh:96-100`, id 32개의 정확한 이름 목록과 실제 파일 내용을 대조 — 이름 하나만 몰래 바꿔도 잡음), 따옴표 무결성(`:41,47-52`, 값이 큰따옴표로 완전히 감싸여 있는지 정규식으로 전체 대조), 회귀 검사(`:122-186`, `git fetch`로 서버 최신 상태를 강제로 내려받은 뒤 그것과 비교 — 로컬에 남아있는 오래된 사본과 비교하지 않음)를 각각 코드로 확인했고, 앞의 둘은 실제로 값을 조작해 잡히는 것까지 봤습니다. 세 번째(회귀 검사)는 코드는 정확하지만, 실제로 "서버가 앞서있는데 fetch 안 해서 놓치는" 상황을 재현하려면 이 저장소의 공유 원격 설정을 일시적으로 망가뜨려야 해서(30개 넘는 다른 워크트리가 같은 설정을 공유) 위험 대비 이득이 낮아 **재현은 생략**했습니다.

**안전장치(guard-global-skill-files.sh)**: 제가 직접 `lock` → `~/.claude/skills/strict/SKILL.md`에 글자 추가 시도 → `permission denied`(권한 없음, 실제 OS가 거부) → `check` → `PASS` → `unlock` → 권한이 원래대로(644) 돌아왔는지 확인까지 전 과정을 실행했습니다. 프롬프트로 "쓰지 마라"고 부탁하는 게 아니라 컴퓨터 파일 권한으로 물리적으로 막는다는 주장이 사실이었습니다.

**출력/부작용**: `docs/sot/principles.yaml`은 실제 코드가 아니라 "현재 어느 원칙이 얼마나 지켜지는지"를 기록한 데이터 파일입니다. 새로운 기능을 만든 게 아니라 **현황을 정직하게 기록**하는 작업이었고, 그 기록 자체(완전 6/부분 12/없음 5/해당없음 4/미확인 5, 합계 32)는 실측과 일치했습니다.

### 3-3. 문제가 발견된 지점

세 가지 실측 불일치를 발견했습니다(위 표 R14~R16).

1. **PR #31 본문의 숫자 오류(R14)**: 사장님이 병합 여부를 결정할 때 가장 먼저 보시는 문서(PR 본문)에 "8개만 완전"이라 적혀 있는데, 제가 `docs/sot/principles.yaml`을 직접 세어보니 6개입니다. 흥미롭게도 로드맵 문서(내부 기록용, `docs/engineering/strict-verify-codeaudit-roadmap-goal-2026-08-19.md:48`)에는 "완전 6"이라고 **정확하게** 적혀 있습니다 — 즉 정확한 숫자를 이미 알고 있었는데, 사장님이 보실 PR 본문에만 잘못 옮겨 적힌 것입니다.
2. **근거 문서 브랜치 불일치(R15)**: `principles.yaml` 맨 위 주석이 "이 파일의 실측 근거는 `docs/engineering/strict-principles-yaml-goal-2026-08-19.md`다"라고 적어놨는데, 정작 그 파일은 PR #31이 속한 작업 브랜치에는 없고 `main` 브랜치에만 있습니다(그것도 다른 커밋에서, 아래 3번과 같은 사고로). 사장님이 GitHub에서 PR #31만 열어서 "그 실측 근거를 좀 보자" 하시면 파일을 찾을 수 없습니다.
3. **메인 작업 공간 직접 수정(R16)**: 로드맵 문서를 만든 커밋 2개(`cf633bb`, `7bd3298`)는 워크트리(격리된 작업 공간) 없이 메인 저장소 폴더에서 바로 만들어져서 곧바로 origin/main에 올라갔습니다. `docs/sot/principles.yaml` 작업은 올바르게 `worktrees/strict-principles-yaml/`이라는 별도 폴더에서 하고 PR로 올렸는데, 같은 날 밤 로드맵 문서 작업만 이 절차를 건너뛰었습니다. 사장님 CLAUDE.md가 "이건 예외 없이 지킨다"고 못 박은 최상위 규칙이라 코드 위험이 낮아도 원칙 위반입니다.

## 4. 놓친 더 나은 답

원래 요구(§8 브리핑 계약, "사장님이 읽을 수 있게")를 기준으로 보면, 이 세션의 보고 자체는 형식은 잘 지켰지만(3층 구조, 결정 카드, 브리핑 이메일 존댓말 등) **숫자 하나를 스스로 대조하지 않고 넘어간 것**이 가장 아쉽습니다. `/strict` §8-2가 이미 "판정 원문과 사장님께 드리는 요약을 직접 대조하는 습관을 명시한다(2026-08-19)"는 문구를 이 세션 스스로 추가했는데, 정작 자신의 PR 본문 숫자는 그 습관대로 대조하지 않았습니다. 더 나은 답은: PR 본문을 쓰기 직전에 `grep '완전' docs/sot/principles.yaml | wc -l` 같은 명령을 한 번 더 돌려 로드맵 문서의 숫자와 일치하는지 기계적으로 재확인하는 단계였을 것입니다.

또한 "완료됐다"고 말할 수 있는 시점 자체가 아직 오지 않았습니다 — 세 번째 이메일(R13)이 스스로 밝히듯 이 세션은 지금 이 감사 결과를 기다리는 중입니다. 즉 이 감사 보고서가 나가야 비로소 사장님께 드릴 "최종" 보고가 완성됩니다.

## 5. 적대 반박

**가장 강한 반론**: "PR 본문 숫자 오류(8 vs 6)는 사소한 오타이고, 실제 데이터(`principles.yaml`)는 정확하니 실질적 피해가 없다"는 반론이 가능합니다. 실제로 병합 여부를 결정하는 사장님이 데이터 파일 자체를 열어 32줄을 다시 세신다면 문제가 안 됩니다.

**반박에 대한 재반박**: 그러나 PR 본문은 정확히 "사장님이 매번 파일을 직접 열어 세지 않아도 되게 하려고" 요약한 문서입니다(PR 본문 스스로 "판단이 필요한 이유"·"승인 기준"을 안내). 요약이 틀리면 요약을 만든 목적 자체가 무너집니다. 또한 이 오류가 우연이 아니라 **같은 날 세션이 스스로 정한 새 규칙(원문-요약 대조, §8-2)을 자신에게 적용 안 한 사례**라는 점에서, "사소한 오타"가 아니라 "방금 만든 안전장치를 자기 자신에게는 안 쓴 것"으로 봐야 합니다.

**반박 후 남는 결론**: 실질 피해는 낮지만(원본 데이터가 정확하므로 사장님이 데이터를 열면 바로 알 수 있음), 신뢰도 측면에서는 중간 심각도로 유지합니다 — "이 세션이 스스로 세운 규칙을 스스로 지켰는가"가 이 감사의 핵심 질문 중 하나였고, 여기서 한 번 어긋났기 때문입니다.
