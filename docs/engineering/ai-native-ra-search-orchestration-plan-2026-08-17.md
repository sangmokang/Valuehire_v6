# AI 시대 리서치 운영체계 통합 기획서 — 2026-08-17

## 1층 — 결론

권고안은 “한 사람이 모든 일을 지시하는 방식”을 “일감이 스스로 정렬되고, 여러 컴퓨터가 안전하게 나눠 처리하며, 사람은 승인과 예외만 보는 방식”으로 바꾸는 것입니다. 다만 지금 6세대 저장소에는 실제 제품이 없으므로, 바로 큰 공장을 만들기보다 28개의 작은 작업으로 나눠 한 개씩 증명해야 합니다.

지금 바로 실행할 수 있는 것은 안전검사와 개발 시험 기반뿐입니다. 브라우저 연결 기록, 여러 컴퓨터 작업 큐, Gmail 첨부 매칭은 과거 사례이거나 일부 진단 기록이라서 실행 기능으로 재사용하지 않고 새 시험의 기준으로만 씁니다. 지금 바로 운영에 쓸 수 있는 6세대 사업 기능은 없습니다.

ClickUp에서 포지션을 자동으로 고르는 기능은 만들 수 있습니다. 먼저 내부 후보 자료에서 다시 찾고, 그래도 부족한 수만큼만 외부 서치를 만들며, 각 컴퓨터는 자기 계정과 자기 브라우저에서 허용된 일만 수행하게 합니다. LinkedIn 사이트 안의 자동 수집과 자동 메시지는 공식 정책 때문에 제외하고 사람이 수행합니다.

사장님이 이번에 판단할 것은 두 가지입니다. 첫째, 여러 컴퓨터의 작업 상태를 Supabase에 두되 후보 원문은 별도 보호 장부에 두는 경계를 승인할지입니다. 둘째, 실제 서치를 열기 전에 개인정보 보관기간·삭제 방식·채널별 허용 범위를 먼저 확정할지입니다. 권고는 둘 다 승인입니다.

## 2층 — 판단 근거

### 왜 이 순서인가

현재 병목은 후보자를 찾는 기술 하나가 아닙니다. 어떤 포지션을 먼저 할지, 기존 후보가 충분한지, 어느 컴퓨터와 어느 계정이 지금 안전한지, 결과가 중복인지, 사람이 개입했는지를 한 장부에서 판단하지 못하는 것이 근본 병목입니다. 이 바닥을 먼저 만들지 않고 브라우저 자동화를 붙이면 컴퓨터 수만큼 중복·오조작·차단 위험도 늘어납니다.

반대로 모든 기능이 완성될 때까지 기다릴 필요도 없습니다. ClickUp 읽기, 순수 우선순위 계산, 내부 자료 목록화, 작업 큐, Aside 탭 확인은 서로 분리해 증명할 수 있습니다. 각 단계가 실제 처리 건수와 실패 사유를 남기면 중간부터 사람이 운영에 활용할 수 있습니다.

### 준비 수준 요약

| 영역 | 현재 준비 수준 | 실제로 있는 것 | 아직 없는 것 |
|---|---|---|---|
| 6세대 안전 기반 | 높음 | 비밀·개인정보 노출 검사, 클린룸 경계, 시험 배관, 작업 공간 규칙 | 이번 기능 전용 검사와 운영 코드 |
| Aside 연결 | 낮음~중간 | 로컬 진단 주소와 페이지 탭 노출 확인 기록 | 재부팅 복구, 정확한 탭 선택, 후보 한 명 완주, 사람 개입 양보 |
| 여러 컴퓨터 지휘 | 6세대는 없음 | 5세대에 작업 큐·생존 신호·사용권의 과거 구현 | 6세대 독립 구현과 실제 여러 컴퓨터 시험 |
| ClickUp 선정 | 낮음 | 읽기 전용 목록·상태 확인 기록, 포지션/AI Search 목록 구조 문서 | 우선순위 계산, 부족분 계산, 큐 생성, 결과 반영 |
| 내부 후보 재매칭 | 6세대는 없음 | 4세대 Gmail 첨부 매칭, 후보 합치기, 5세대 SQLite→Supabase 내보내기 사례 | 6세대 입력 어댑터·사람 식별·통합 점수·보관 계약 |
| 운영 보고 | 계획 수준 | 주간 대시보드·원자료 추적 계약 | 실제 숫자 계산과 화면 |

→ “설계가 많다”와 “제품이 준비됐다”를 구분한 표입니다. 안전 기반과 과거 사례는 강하지만 6세대 사업 기능은 새로 만들어야 합니다.

### 핵심 설계 결정

#### 결정 1 — ClickUp은 일감, Supabase는 여러 컴퓨터 상태, 보호 장부는 후보 근거를 책임집니다

> **무엇을** — ClickUp은 포지션의 실제 운영 상태와 사람의 채택·기각 결정을 책임집니다. Supabase는 여러 컴퓨터의 작업 큐, 생존 상태, 사용권, 실행 영수증처럼 필요한 최소 운영 정보만 책임집니다. 후보 원문·화면·이력서 근거는 보관정책이 적용되는 보호 장부가 책임집니다.
>
> **왜** — 여러 컴퓨터가 같은 파일을 직접 공유하면 손상과 잠금 문제가 생기고, ClickUp 하나로 동시 실행권까지 안전하게 다루기 어렵습니다. 반면 후보 원문 전체를 공유 큐에 넣을 필요는 없습니다.
>
> **버린 길** — 네트워크 폴더의 SQLite 공동 쓰기, ClickUp을 작업 큐로 겸용, 후보 원문 전체를 공개 Supabase 표에 저장하는 길을 버립니다.
>
> **대가** — 장부가 나뉘므로 모든 외부 반영에 고유 중복 열쇠와 다시 읽어 확인하는 절차가 필요합니다.
>
> **되돌리기** — Supabase 작업 큐를 끄면 한 컴퓨터 수동 실행으로 돌아갑니다. 후보 보호 장부와 ClickUp의 기존 데이터는 바꾸지 않습니다.

#### 결정 2 — 내부 후보 재매칭을 모든 외부 서치의 0단계로 둡니다

> **무엇을** — P01 개인정보 계약과 P02 채널 계약이 통과하고 P03이 포지션을 `READY`로 판정한 뒤에만 Supabase 과거 후보, 로컬 SQLite 아카이브, Gmail 이력서 첨부 목록을 먼저 대조합니다. 강한 동일인 근거와 포지션 적합 근거가 있는 후보를 먼저 검토하고, 목표 인원에서 모자란 부분만 외부 서치 작업으로 만듭니다.
>
> **왜** — 이미 보유한 후보를 다시 찾는 비용과 계정 사용량을 줄이고, 외부 플랫폼 의존도를 낮춥니다.
>
> **버린 길** — 이름·회사만 비슷하면 자동 병합하는 방식과, 모든 원문을 먼저 한 곳으로 복제하는 방식을 버립니다.
>
> **대가** — 동일인 근거가 약하면 사람 확인이 늘고, 보수적인 초기에 자동으로 합쳐지는 비율은 낮습니다.
>
> **되돌리기** — 자동 후보 제안 기능을 끄고 목록화 결과만 사람이 보게 합니다. 원천 자료를 수정하지 않으므로 연결만 제거하면 됩니다.

#### 결정 3 — LinkedIn은 자동 실행 대상에서 제외합니다

> **무엇을** — 제품은 LinkedIn용 프로젝트명·검색식·필터 준비표와 사람이 실행한 결과를 기록할 영수증만 만듭니다. 사이트 안의 후보 순회, 수집, 연결, 메시지는 사람이 수행합니다.
>
> **왜** — LinkedIn 공식 계약과 도움말은 봇·스크립트·확장기능을 이용한 수집과 활동 자동화를 금지합니다. 계정 제한 위험을 여러 기기나 네트워크로 분산하는 것은 제품 전략이 아니라 차단 회피가 됩니다.
>
> **버린 길** — Aside를 이용한 LinkedIn 무인 순회, 계정·기기·네트워크 회전, 자동 메시지를 버립니다.
>
> **대가** — LinkedIn 채널에는 사람이 계속 필요합니다. 대신 준비·중복확인·결과 기록은 자동화해 사람 시간이 후보 판단에 쓰이게 합니다.
>
> **되돌리기** — 공식 파트너 권한이나 서면 허용 범위가 생기면 별도 변경 기록과 시험을 거쳐 허용된 API만 추가합니다.

#### 결정 4 — 여러 컴퓨터는 속도를 늘리는 장치가 아니라 책임을 나누는 장치입니다

> **무엇을** — 컴퓨터마다 고정된 실행자 번호, 허용 채널, 계정 참조, Aside 상태, 제품 버전을 등록합니다. 작업은 허용 채널이 맞고 생존 신호가 최신이며 계정 사용권을 얻은 컴퓨터만 가져갑니다.
>
> **왜** — 같은 계정의 동시 사용과 오래된 실행자의 뒤늦은 결과 덮어쓰기를 막아야 컴퓨터를 늘리는 효과가 납니다.
>
> **버린 길** — 처리량이 모자라면 한 컴퓨터의 클릭 속도를 높이는 방식, 작업을 모든 컴퓨터에 뿌리고 먼저 끝난 결과만 쓰는 방식을 버립니다.
>
> **대가** — 작업 큐·생존 신호·만료·증가 번호를 관리해야 하며, 지휘 장부 장애 시 새 일 배분이 멈춥니다.
>
> **되돌리기** — 실행자 수를 한 대로 줄여도 같은 계약이 동작하도록 설계합니다.

## 3층 — 기술 상세

## 1. 전체 구조

```text
ClickUp 포지션 읽기
  → 개인정보·채널 계약 확인 + 포지션 READY 관문
  → 내부 후보 재매칭
  → 후보 목표 대비 부족분 계산
  → 포지션·채널별 작업 우선순위 계산
  → Supabase 공유 작업 큐
  → 머신별 로컬 실행기
      ├─ 사람인/잡코리아: 허용 계약이 확인된 범위만 Aside 로컬 조작
      └─ LinkedIn: 준비표 생성 + 사람 실행 + 결과 영수증
  → 후보 증거·중복 대조·검토 대기
  → 사람 승인
  → ClickUp 결과 반영(별도 쓰기 승인 뒤)
  → 주간 지표와 다음 부족분 재계산
```

→ 일감 선택부터 결과 재계산까지의 한 바퀴입니다. 외부 사이트 쓰기와 후보 발송은 사람 승인 뒤의 별도 단계이며, LinkedIn은 사이트 안 자동화가 없습니다.

### 1-1. 제어 영역과 후보 자료 영역 분리

| 영역 | 저장 내용 | 금지 내용 | 책임 장소 |
|---|---|---|---|
| 사업 일감 | 포지션 참조, 상태, 사람의 채택·기각·보류 | 원문 이력서 전체를 설명란에 복제 | ClickUp |
| 공유 제어 | 승인된 `position_policy`, 작업 번호, 우선순위 입력 지문, 실행자, 만료, `queue_lease_epoch`, `account_fencing_token`, `local_reservation_epoch`, 상태, 요약 영수증 | 이력서 원문, 화면 이미지, 인증정보 | Supabase 비공개 표/큐 |
| 후보 근거 | 원문 참조, 내용 지문, 화면·본문 위치, 파싱된 사실, 동일인 검토 | 승인 없는 외부 전송 | 보호 장부와 보호 저장소 |
| 머신 임시 상태 | 전송 대기 묶음, 마지막 확인 위치, 재시도 사유 | 최종 사업 판정 | 각 머신 로컬 SQLite |

→ 여러 컴퓨터가 함께 봐야 하는 최소 정보와 개인정보를 분리합니다. 로컬 SQLite는 전송 대기와 복구용이며 네트워크 공유 파일로 사용하지 않습니다.

## 2. ClickUp 일감 선정

### 2-1. 읽기 범위

1. 실제 포지션 목록에서 열린 포지션만 읽습니다.
2. 상태명·태그·설명·담당자·생성일·마감일·우선도 관련 필드를 원문 그대로 저장하지 않고 필요한 구조값과 원문 지문을 남깁니다.
3. 목록·상태·필드 구조의 지문이 이전 값과 다르면 선정은 멈추고 계약 변경으로 분류합니다.
4. 모든 페이지를 끝까지 읽지 못하면 포지션 0개가 아니라 `NOT_RUN`, 즉 시험하지 못한 상태입니다.

현재 읽기 전용 관찰에서는 AI Search 목록과 포지션 목록의 커스텀 필드가 비어 있었다는 문서 기록이 있습니다. 따라서 초기 자동 우선순위에 필요한 `target_eligible_candidate_count`·사업가치 구간·긴급도·허용 채널·마감은 ClickUp 설명에서 추측하지 않습니다. 권고안은 오너가 승인한 `position_policy`를 Supabase 비공개 제어 영역의 단일 정본으로 두는 것이지만, 실제 책임 장소는 P00A 오너 결정과 P00B 정본을 따릅니다. 어느 장소가 승인되든 ClickUp 작업 식별자·읽기 스냅샷 지문·정책 버전·승인자·승인시각을 함께 저장하고 후보 원문은 금지합니다. ClickUp은 포지션의 열린 상태와 사업 원문을 계속 책임지고, 두 참조 지문이 다르면 `READY`가 취소됩니다. 정식 포지션 ID는 `clickup:<workspace_id>:<position_task_id>`, 정식 고객사 ID는 승인된 ClickUp 관계 또는 승인 정책이 가리키는 `clickup:<workspace_id>:<client_task_id>`로 고정합니다. 고객사 이름 문자열을 정규화해 ID를 추측하지 않으며, 관계가 없거나 ClickUp 스냅샷과 정책의 고객사 ID가 다르면 `NEEDS_DECISION`입니다.

### 2-2. 시작 가능 조건

다음 값이 모두 있어야 `READY`가 됩니다.

- 정식 ClickUp 고객사·포지션 ID, 포지션의 현재 열린 상태.
- 고객사·포지션명·직무기술서 원문 참조. 이 이름은 표시용이며 중복 방지 키가 아닙니다.
- 필수 경력·직무·산업·근무지·언어·자격.
- `target_eligible_candidate_count`: hard gate와 승인된 근거 완전성 기준을 통과해야 하는 고유 후보 목표 수.
- 허용 채널, 금지 채널, 중복 접촉 기간.
- 학교·짧은 이직·프리랜서 같은 민감하거나 오해하기 쉬운 기준의 명시적 목록과 항목별 사람 승인 근거. 기준이 없으면 명시적 빈 목록을 남깁니다.
- 후보 원문 보관기간과 접근권한 계약 버전.
- ClickUp 읽기 스냅샷 지문.
- 정책 버전·승인자·승인시각.

위 필수값이 하나라도 없으면 `NEEDS_DECISION`이며 자동 서치에 들어가지 않습니다. `target_pre_interview_count`는 별도 사업 퍼널의 선택값이라 누락돼도 `READY`를 막지 않고 우선순위·부족분의 분모로 쓰지 않습니다.

### 2-3. 우선순위 계산

언어모델은 원문에서 구조값 초안을 만들 수 있지만 점수를 쓰지 못합니다. 사람이 승인한 입력만 순수 함수가 계산합니다.

`position_priority_v1`은 0~100을 다음처럼 계산합니다. `target_eligible_candidate_count`가 0 이하이거나 승인 채널이 0개면 계산하지 않고 `NEEDS_DECISION`입니다.

| 항목 | 범위 | 계산 의미 |
|---|---:|---|
| 고객 마감·운영 긴급도 | 0~25 | 승인 긴급등급 0~5의 5배와 마감 잔여일 구간(3일 이하 25, 7일 이하 20, 14일 이하 15, 30일 이하 10, 그 밖 5) 중 큰 값 |
| 사업 가치 | 0~20 | 오너가 승인한 가치등급 0~4의 5배; 금액 원문은 저장하지 않음 |
| 후보 부족률 | 0~25 | `25 × max(target_eligible_candidate_count-current_eligible_unique_candidate_count, 0) / target_eligible_candidate_count` |
| 마지막 유효 서치 이후 경과 | 0~15 | 0일 0, 7일 이하 3, 14일 이하 6, 30일 이하 9, 60일 이하 12, 60일 초과 또는 기록 없음 15 |
| 채널 빠짐 | 0~10 | `10 × 최신 유효 완주 영수증이 없는 승인 채널 수 / 승인 채널 수`; 최신 기간은 `position_policy` 버전에 고정 |
| 내부 후보 즉시 검토 가능 | 0~5 | 강한 동일인 근거와 충분한 이력서 근거가 있는 내부 후보가 1명 이상이면 5, 아니면 0 |

→ 합계가 높을수록 먼저 처리합니다. 계정 경고·로그인 불확실·정책 미확인·원문 보관 미승인은 숫자 감점이 아니라 해당 채널 또는 포지션을 후보 목록에서 제외하는 절대 차단입니다. 같은 점수는 마감일, 포지션 생성일, ClickUp 식별자 순으로 고정 정렬합니다.

반드시 저장할 재현 정보는 `input_hash`, `policy_version`, 항목별 원점수, 최종점수, 선택/제외 사유, 계산시각입니다.

필드 계약의 검증 책임도 순서대로 나눕니다. P03은 두 목표 필드를 별도 직렬화하고 선택값 누락과 교환 변조를 검증합니다. P06과 P07은 P03 완료 뒤 각자 `target_eligible_candidate_count`를 실제 계산에 소비하며, `target_pre_interview_count`를 대신 넣은 교환 변조가 자기 원자 게이트를 통과하지 못하게 합니다. P03이 아직 존재하지 않는 후속 런타임을 미리 검사하지 않습니다.

## 3. 부족한 서치 계산

### 3-1. 숫자 부족과 구성 부족을 분리

단순 후보 수만 세면 같은 배경의 후보만 잔뜩 모아도 “충분”으로 오판합니다. 부족분은 두 층으로 계산합니다.

1. 수량 부족: `target_eligible_candidate_count`에서 P13의 `ELIGIBLE` 내부 영수증과 P25의 사람 `ACCEPTED` 외부 영수증을 `canonical_candidate_id`로 합집합한 `current_eligible_unique_candidate_count`를 뺍니다. P25 이전 최초 계산에서 외부 영수증 집합은 빈 값입니다.
2. 구성 부족: 필수 경력, 산업, 기술, 지역, 연차, 회사군, 허용 채널별로 근거가 비어 있는 정도를 계산합니다.

`search_gap`은 포지션·채널·검색식 버전·필터 버전마다 다음을 가집니다.

- 표시된 전체 결과 수와 실제 열람 수.
- 새 고유 후보 수와 이미 아는 후보 수.
- 적격·보류·제외·확인불가 수.
- 페이지/커서 완주 여부.
- 마지막 신규 후보가 나온 위치.
- 다음에 시험할 검색식과 그 근거.
- 중단 사유와 재개 조건.

### 3-2. 다음 서치를 만드는 규칙

- P13의 hard gate·근거 완전성·동일인 기준을 모두 통과한 `ELIGIBLE` 내부 후보가 목표를 채우면 외부 서치 작업을 만들지 않습니다. `REVIEW_REQUIRED | INELIGIBLE`은 수에 넣지 않습니다.
- 수량은 충분하지만 필수 구성 하나가 비면 그 구성만 겨냥한 작업을 만듭니다.
- 검색 결과 0명은 필터·페이지 완주 영수증이 있을 때만 정상 0명입니다.
- 같은 검색식에서 신규 후보 0명이 연속 두 번 나오고 완주 영수증이 있으면 해당 검색식은 소진으로 표시합니다.
- 계정 경고·보안문자·2단계 인증·정책 미확인은 재시도가 아니라 중단입니다.
- 채널별 시간·페이지·비용 상한을 넘으면 부분 결과를 보존하고 멈춥니다.

## 4. 내부 후보 재매칭

### 4-1. 입력원

| 입력원 | 1단계에서 읽는 것 | 1단계에서 하지 않는 것 |
|---|---|---|
| Supabase | 허용된 기존 후보·서치 결과 스키마, 고유키, 최신시각, 원문 참조 | 공개 표에 새 원문 복제, 권한 우회 |
| SQLite | 프로필 주소, 원문 지문, 수집 시각, 포지션 연결, 점수 근거 | 네트워크 폴더 공유, 원본 행 수정 |
| Gmail 첨부 | 메시지/첨부 식별자, 파일명·형식·크기·자료표 지문, 보관 권리 상태 | 보관 승인 전 첨부 본문 호출·내용 지문 생성·영구 저장 |

→ 첫 프로젝트들은 내용 이동이 아니라 “어디에 무엇이 있는가”를 안전하게 목록화합니다. 자료표 지문은 메시지·첨부 식별자와 파일명·형식·크기만으로 만들고, 실제 첨부 내용 지문과 원문 파싱은 보관정책과 접근권한이 확정된 뒤 별도 프로젝트로 엽니다.

### 4-2. 동일인 판정

자동 병합을 허용하는 강한 근거는 승인된 프로필 주소 일치, 검증된 이메일 일치, 동일 이력서 내용 지문, 한 출처가 다른 출처의 공개 자기 링크를 명시한 경우입니다. 이름+회사+직함만 같은 경우는 `NEEDS_REVIEW`이며 자동 병합하지 않습니다.

동일인 판정은 원천 행을 합치지 않고 `candidate_entity_link`라는 연결 사건을 추가합니다. 최초 동일인 클러스터를 만들 때 원천 ID와 값 공간이 겹치지 않는 새 불변 `canonical_candidate_id`를 발급합니다. 이미 정식 ID를 가진 두 클러스터를 연결할 때는 두 `canonical_candidate_id` 중 생성 사건이 더 오래된 것을 유지하고 다른 정식 ID를 영구 별칭으로 남겨 어느 과거 정식 ID에서도 현재 ID와 사건 이력을 찾을 수 있게 합니다. 생성시각이 같으면 정식 ID 바이트 오름차순으로 결정하며, 원천 ID를 정식 ID로 재사용하지 않습니다. 잘못된 연결도 행을 지우지 않고 해제 사건을 뒤에 남깁니다. 해제하면 기준 구성요소는 기존 ID를 유지하고 분리된 구성요소는 재사용하지 않은 새 ID를 받습니다. 분리 전 접촉금지 보호는 양쪽에 보수적으로 승계하며 명시적 사람 검토 사건 없이는 제거하지 않습니다. 연결·해제 모두 대상, 근거 종류, 사유, 검토자, 시각, 앞 사건 지문을 기록합니다. 이 동일인 입력 포트는 내부 세 입력원뿐 아니라 후속 채널 staged evidence에도 재사용합니다. 충돌하거나 강한 근거가 없으면 P25는 임의 ID를 만들지 않고 `HOLD`로 보냅니다.

P12는 `contracts/candidate_eligibility_receipt.schema.json`과 공용 집합 지문 함수를 소유합니다. 영수증은 정식 후보 ID·별칭 폐쇄 지문·입력원 종류·결정 주체·결정 상태·근거/정책/사건 지문과 시각만 담고 원문을 금지합니다. 내부 자료는 규칙엔진의 `ELIGIBLE | REVIEW_REQUIRED | INELIGIBLE`, 외부 staged evidence는 사람의 `ACCEPTED | REJECTED | HOLD` 조합만 허용합니다. 현재 정식 ID·origin별 유효 결정 한 건을 고정 필드로 추출하고 정렬한 공백 없는 정규 JSON UTF-8의 SHA-256을 `candidate_eligibility_receipt_set_hash=sha256:<64hex>`로 만듭니다. P06·P07은 이 함수를 불러 쓰고 재구현하지 않습니다. P13과 P25가 각 결정을 만들고 P07이 계수하므로 미래 프로젝트가 서로의 모듈이나 스키마를 소유권 밖에서 고치지 않습니다.

### 4-3. 포지션 매칭

최종 후보 판단을 한 숫자로 뭉치지 않습니다.

- `fit_score`: 직무·산업·기술·성과·필수조건 적합도.
- `contact_priority`: 이직 의사 공개, 현재 회사 재직기간, 마지막 접촉 시각처럼 연락 순서를 정하는 값.
- `evidence_completeness`: 원문 근거가 얼마나 완전하고 검토 가능한지.
- `hard_gate`: 법적 자격, 포지션별 승인된 제외 조건, 중복 접촉 금지, 원문 근거 부재.

언어모델은 근거 구간과 구조값 초안만 내며, 최종 계산은 입력 지문과 규칙 버전을 가진 코드가 수행합니다. 과거 점수 코드는 직접 불러 쓰지 않고 6세대 정본 계약을 새 시험으로 재작성합니다.

P13은 P12의 별칭 폐쇄 뒤 `canonical_candidate_id`마다 `gap_eligibility=ELIGIBLE | REVIEW_REQUIRED | INELIGIBLE`을 한 번만 계산합니다. `ELIGIBLE`만 내부 적격 영수증을 만들어 P06 우선순위와 P07 부족분에 들어갑니다. 새 외부 후보는 P25에서 사람이 `ACCEPTED`한 뒤에만 외부 적격 영수증이 되어 P07 재계산에 들어가며, 같은 정식 후보 ID의 내부·외부 출처는 한 명으로 셉니다.

## 5. 여러 컴퓨터 작업 큐

### 5-1. 실행자 등록

`machine_registry` 최소 필드는 실행자 번호, 운영체제, 제품 버전, Aside 버전, 허용 채널, 계정 참조 지문, 마지막 생존 시각, 사람 사용 상태, 상태 신호 출처·관측시각·만료시각, `local_reservation_epoch`, 정책 모드, 중단 스위치 상태입니다. 비밀번호·세션 쿠키·원문 인증정보는 저장하지 않습니다. `local_reservation_epoch`은 사람의 로컬 제어 동작만 새로 발급·증가시키며 중앙 스케줄러는 읽고 배정에 결합할 뿐 만들지 못합니다. 사람 사용 상태는 `IDLE_CONFIRMED | HUMAN_ACTIVE | HUMAN_UNKNOWN`으로 고정하며, 신호가 없거나 오래되면 `HUMAN_UNKNOWN`이고 작업을 받지 못합니다. P16은 이 값과 생존·버전·중단·예약 조건을 결합해 `READY | STALE | HUMAN_ACTIVE | HUMAN_UNKNOWN | STOPPED | VERSION_BLOCKED`를 반환하고, `READY`는 유효한 `IDLE_CONFIRMED`일 때만 가능합니다.

### 5-2. 작업 상태

`DISCOVERED → NEEDS_DECISION → READY → QUEUED → LEASED → RUNNING → EVIDENCE_STAGED → REVIEW_REQUIRED → ACCEPTED | REJECTED | EXHAUSTED`를 정상 흐름으로 둡니다. `PAUSED_FOR_HUMAN`, `BLOCKED_POLICY`, `BLOCKED_AUTH`, `FAILED_RETRYABLE`, `FAILED_TERMINAL`, `NOT_RUN`을 별도 상태로 둡니다. `FAILED_RETRYABLE`은 일시 네트워크 오류와 서버가 명시한 지연 응답에만 허용하고, 정책·인증·사람 개입은 자동 재시도하지 않습니다. `delivery_attempt`는 개별 `work_id + delivery_policy_version`의 전송 재시도만 세며 기본 상한은 3회, 기본 지연은 30초·2분·15분이고 서버 `Retry-After`가 더 길면 그 값을 따릅니다. 각 예정시각을 저장하고 3회 실패 뒤 `EXHAUSTED`와 `exhaustion_reason=DELIVERY_RETRY_LIMIT`을 남깁니다. 모든 작업권 교체 세대인 `queue_lease_epoch`은 자동 장애 회수와 사람 pause 모두에서 증가할 수 있습니다. 별도 `machine_recovery_attempts`는 개별 `work_id + recovery_policy_version`에서 자동 DB 만료 회수만 세고 사람 pause·명시적 재개·전송 재시도는 세지 않습니다. `machine_recovery_limit` 기본값은 3회이고 이미 3이면 다음 자동 회수 요청은 카운터 증가와 재배정 없이 `EXHAUSTED`·`exhaustion_reason=MACHINE_RECOVERY_LIMIT`·사람 에스컬레이션을 남기며 새 정책 버전·새 작업 ID 없이는 재개하지 않습니다. `account_fencing_token`은 채널·계정 사용권의 획득 세대이고 `local_reservation_epoch`은 사람의 로컬 예약 세대라 서로 다른 필드입니다. 세 카운터·세대는 서로의 상한을 소진하지 않습니다. 정책 버전이 다른 재시도 규칙은 새 작업으로 취급합니다.

### 5-3. 중복 방지

- 작업 고유키: 포지션 참조 + 채널 + 검색식 버전 + 필터 버전 + 범위 버전.
- 채널 사용권: 계정 참조 + 채널마다 한 개.
- claim 적격성: P16의 판정·규칙 버전·머신 ID·상태 스냅샷 지문·관측/만료시각을 담은 증명이 현재 등록과 일치해야 함. P16 판정 `READY`와 근거 P15 사람 상태 `IDLE_CONFIRMED`가 둘 다 필요함. 증명 누락·만료·재사용·지문 불일치, `STALE | HUMAN_ACTIVE | HUMAN_UNKNOWN | STOPPED | VERSION_BLOCKED`는 상태 전이 없이 claim 거부.
- 세대·토큰: P17 작업의 `queue_lease_epoch`, P18 계정 사용권의 `account_fencing_token`, P15에서 사람의 로컬 제어 동작이 발급하고 P16→P17→P19가 전달하는 `local_reservation_epoch`을 분리. 완료 결과는 세 현재값이 모두 같을 때만 수락.
- 만료 회수: 데이터베이스 시각 기준으로 만료된 `LEASED | RUNNING`을 짧은 조건부 갱신 한 번으로 `QUEUED`에 되돌리고 `delivery_attempt`는 유지한 채 `queue_lease_epoch`과 `machine_recovery_attempts`를 각각 1 올림. 단, 같은 `work_id + recovery_policy_version`의 장애 횟수가 이미 상한이면 두 값을 올리거나 재배정하지 않고 `EXHAUSTED`와 `exhaustion_reason=MACHINE_RECOVERY_LIMIT`으로 전이. 새 머신의 성공한 계정 사용권 획득에서 P18이 새 `account_fencing_token`을 발급하고, P19는 새 머신의 현재 `local_reservation_epoch`을 배정에 결합하되 만들거나 증가시키지 않음. 이미 갱신됐거나 사람·정책·인증 중단인 작업은 자동 회수하지 않음.
- 작업 가져오기: Supabase Queues 또는 짧은 잠금 거래를 사용하고 긴 데이터베이스 연결을 잡아두지 않음.
- 실행 전 의도 기록, 실행 후 결과 다시 읽기, 원문 지문 대조.

공식 문서상 Supabase Queues는 Postgres 기반 지속 큐와 보이지 않는 기간을 제공하며, 서비스 역할 키는 브라우저에 노출하면 안 됩니다. 따라서 큐 접근은 머신 로컬 서버 실행기만 갖고, Aside 페이지 코드에는 키가 들어가지 않습니다.

## 6. Aside 브라우저 실행 계약

### 6-1. 중앙에서 브라우저를 원격 조작하지 않습니다

각 컴퓨터의 로컬 실행기가 자기 컴퓨터의 `127.0.0.1` 진단 주소에만 연결합니다. 중앙 지휘자는 작업 설명과 고유키만 보내고 브라우저 진단 포트에 직접 접속하지 않습니다. 진단 포트를 외부 네트워크에 열면 실행을 거부합니다.

### 6-2. 시작 전 관문

1. 실행자·채널·계정 결합이 등록값과 같은가.
2. Aside 제품 버전과 진단 규약 버전이 승인 범위인가.
3. 허용된 주소의 목표 탭이 정확히 한 개인가.
4. 현재 화면이 로그인 완료이며 보안문자·2단계 인증·계정 선택 화면이 아닌가.
5. 로컬 자동화 예약 번호가 유효하고, 사람 사용 상태가 `IDLE_CONFIRMED`이며, 신호 출처·관측시각·만료시각이 현재 계약과 맞는가.
6. 작업의 포지션·검색식·필터 버전이 화면과 같은가.
7. 채널 정책이 자동 실행을 허용하는가.

하나라도 불확실하면 브라우저 명령 0건으로 멈춥니다.

### 6-3. 사람 개입

사람 개입 신호는 최소한 로컬 제어 화면의 `TAKE_OVER` 동작, 로컬 중단 단축키, 보안문자·로그아웃·계정 선택 화면 감지를 포함합니다. 각 신호는 `machine_id`·사람이 로컬에서 발급한 `local_reservation_epoch`·단조 사건 번호·관측시각을 가진 사건으로 로컬 실행기에 들어옵니다. P20이 Aside 또는 운영체제에서 신뢰할 수 있는 실제 사람 입력 신호를 발견하지 못하면 이를 자동으로 추정하지 않습니다. 그 경우 해당 머신은 전용 자동화 예약 중 사람이 브라우저를 만지지 않는 운영만 허용하고, 공유 대화형 운영은 `BLOCKED_POLICY`입니다.

사람 개입 사건이 들어오면 현재 드라이버 권한 객체를 원자적으로 폐기해 이후 클릭·입력·스크롤 함수를 호출할 수 없게 합니다. 이 권한 객체는 `queue_lease_epoch`·`account_fencing_token`·`local_reservation_epoch`과 큐 lease의 데이터베이스 만료시각에 대응하는 로컬 단조시계 마감에 함께 묶습니다. 모든 브라우저 명령 직전에 세 값과 로컬 마감을 다시 검사하고, 회수/재배정으로 값이 바뀌거나 통지가 끊긴 채 마감이 지나면 사람 개입 여부와 관계없이 명령 0건으로 권한을 폐기합니다. 신호 출처가 없거나 오래됐거나 로컬 예약 번호가 다르면 `HUMAN_UNKNOWN`으로 보고 명령 0건으로 멈춥니다. 개입 통지가 제어 장부에 닿으면 P19가 현재 세 값을 조건부 대조해 `RUNNING→PAUSED_FOR_HUMAN`, P18 계정 사용권 해제, `queue_lease_epoch` 증가를 한 영수증으로 남깁니다. 사람이 손을 뗀 뒤에는 P15 로컬 제어에서 새 `local_reservation_epoch`을 만들고 `PAUSED_FOR_HUMAN→QUEUED` 전이와 P18 사용권 재획득으로 새 `account_fencing_token`을 받은 다음 새 작업권·새 로그인 영수증·같은 탭·같은 포지션을 확인해야 처음 발견 단계부터 재개합니다. 개입 통지가 장부에 닿지 않으면 재개하지 않고 로컬 마감과 자동 만료 회수 경로를 따릅니다.

### 6-4. 채널 정책

| 채널 | 기획 기본값 | 자동 실행을 열 조건 |
|---|---|---|
| 사람인 | 계약 확인 전 관찰·수동 | 계정 계약·허용 범위 확인, 후보 1명 완주, 중단선 시험 |
| 잡코리아 | 계약 확인 전 관찰·수동 | 사람인과 별도 계약·화면 시험 통과 |
| LinkedIn Recruiter/RPS | 사이트 안 자동화 금지 | 공식 API/파트너 권한과 서면 허용 범위가 생긴 뒤 별도 설계 |
| ChatGPT 등 보조 조사 | 공개 자료·정책 허용 범위만 | 후보자 개인정보 입력 금지, 결과는 후보 근거가 아니라 조사 보조 |

→ 기기 수를 늘리는 것이 이용제한 회피 수단이 되지 않게 채널별 허용 상태가 모든 작업보다 먼저 판정됩니다.

## 7. 외부 서비스별 구현 제약

### ClickUp

ClickUp 공식 문서에 따르면 요금제에 따라 토큰별 분당 요청 상한이 다르고 초과 시 429 응답과 남은 한도 헤더가 옵니다. 상태 변경과 커스텀필드 값 변경은 다른 요청입니다. 따라서 읽기 스냅샷, 쓰기 의도, 상태 쓰기, 필드 쓰기, 다시 읽기 확인을 각각 기록하고 속도 제한을 중앙에서 관리합니다. 웹훅은 `webhook_id + history_item_id`를 중복 열쇠로 사용합니다.

근거: [ClickUp rate limits](https://developer.clickup.com/docs/rate-limits), [Update Task](https://developer.clickup.com/reference/updatetask), [Set Custom Field Value](https://developer.clickup.com/reference/setcustomfieldvalue), [Webhooks](https://developer.clickup.com/docs/webhooks).

### Gmail

Gmail 공식 문서에 따르면 메시지 목록은 기본 100개·최대 500개이며 다음 페이지 표식을 따라가야 합니다. 목록에는 메시지 본문이 없어서 개별 메시지 조회가 필요하고, 큰 첨부는 별도 첨부 조회가 필요합니다. 사용자별 요청 한도와 시간 기반 제한에 맞춘 지연 재시도가 필요합니다.

근거: [Gmail messages.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list), [Gmail attachments.get](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages.attachments/get), [Gmail usage limits](https://developers.google.com/workspace/gmail/api/reference/quota).

### Supabase와 PostgreSQL

공유 작업 큐는 [Supabase Queues](https://supabase.com/docs/guides/queues) 또는 짧은 `FOR UPDATE SKIP LOCKED` 방식으로 구현합니다. 공개되는 모든 표는 [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)에 따라 행 접근 정책을 켜고, 서비스 역할 키는 로컬 서버 실행기에만 둡니다. 긴 작업 동안 데이터베이스 잠금을 유지하지 않고 만료형 작업권으로 바꿉니다.

### SQLite

[SQLite 네트워크 사용 안내](https://sqlite.org/useovernet.html)와 [WAL 안내](https://www.sqlite.org/wal.html)는 여러 컴퓨터가 네트워크 파일을 함께 읽고 쓸 때 잠금·동기화 실패로 손상될 수 있고, WAL 방식은 같은 호스트의 프로세스만 지원한다고 설명합니다. 따라서 각 머신 로컬 대기 장부 또는 단일 호스트 보호 장부로만 사용합니다.

### Chrome 계열 진단 포트와 LinkedIn

[Chrome 원격 진단 변경](https://developer.chrome.com/blog/remote-debugging-port)은 Chrome 136부터 기본 사용자 자료 폴더에 진단 포트를 붙이는 방식을 제한합니다. Aside가 같은 제약을 따르는지는 별도 실증 대상이며, 기본 Chrome 프로필로 조용히 대체하지 않습니다. [LinkedIn User Agreement](https://www.linkedin.com/legal/user-agreement), [금지 소프트웨어 안내](https://www.linkedin.com/help/linkedin/answer/a1341387), [자동 활동 안내](https://www.linkedin.com/help/linkedin/answer/a1340567)는 수집·활동 자동화를 금지하므로 수동 경로만 둡니다.

## 8. 운영자 검토 화면

운영자는 다음 순서로 봅니다.

1. 오늘 자동 선정된 포지션과 선정 이유.
2. 내부 후보만으로 채워진 수와 외부 서치가 필요한 부족 수.
3. 머신별 생존, 허용 채널, 현재 작업, 사람 개입/인증/정책 중단.
4. 후보 검토 대기: 적합 근거, 부족 근거, 동일인 연결 근거, 원문 위치.
5. 외부 반영 대기: ClickUp에 무엇을 쓸지와 다시 읽어 확인할 값.
6. 계정 건강: 경고·차단·보안문자 0이 아니면 다른 성과보다 먼저 표시.

자동화가 추천한 우선순위는 사람이 바꿀 수 있지만, 변경 이유와 이전 순서를 기록합니다. 조용한 수동 덮어쓰기는 금지합니다.

## 9. 북극성과 퍼널

북극성은 “대표 캘린더의 주간 사전 인터뷰 수”로 둡니다. 제품 지표는 이를 만드는 원자료로만 사용합니다.

- 열린 포지션 수, 시작 가능/결정 필요 수.
- 내부 재매칭 적격 후보 수와 검토 승인률.
- 외부 서치 작업 수, 채널별 완주율, 신규 후보율.
- 후보 검토→승인→연락 준비→사전 인터뷰 전환.
- 실행자 1시간당 검토 가능한 후보 수.
- 중복 방지로 절약한 외부 서치 수.
- 계정 경고·보안문자·세션충돌·정책 차단 수.
- 자료 보관 만료·삭제 실패·접근 거부 수.

첫 한 달 실험의 권고 성공 기준은 제품 구현 뒤 실제 기준선을 측정한 다음 확정합니다. 현재 “이력서 30건·사전 인터뷰 6건”은 사업 가설이지 코드 인수 기준으로 쓰지 않습니다.

## 10. 프로젝트 분해와 선후관계

각 번호는 작업 공간 1개, 인수 기준 1개, 검토 요청 1개입니다. 상세 실행문은 `docs/engineering/goal-prompts/ai-native-ra-search-orchestration/`에 별도 파일로 두고, 각 파일은 자기 번호에 맞는 단일 `scripts/acceptance-ai-ra-<번호>.sh` 명령과 기대 출력까지 고정합니다.

| 묶음 | 프로젝트 | 끝났다고 부르는 조건 |
|---|---|---|
| A 계약 | P00A→P00B, P01~P04 | 오너가 책임 장소를 승인한 뒤 개인정보·채널 허용·포지션 입력·검사 기반이 기본 브랜치에서 강제됨 |
| B ClickUp·판단 | P05~P08 | P05 `LIVE_PASS` 실제 읽기 스냅샷과 C 묶음 P13의 내부 적격 영수증을 받은 뒤 P06~P08 `CONTRACT_PASS` 우선순위·부족분·작업 제안이 읽기 전용으로 동작 |
| C 내부 재매칭 | P09~P14 | P09~P11 `LIVE_PASS`로 세 실제 입력원을 안전하게 목록화하고 P12~P14 `CONTRACT_PASS`로 동일인·매칭·연락중복을 재현 가능하게 계산 |
| D 여러 컴퓨터 | P15~P19 | P15~P16 `CONTRACT_PASS`, P17~P19 `LIVE_PASS`로 실제 공유 큐·사용권과 두 실행자 장애 승계를 증명 |
| E 브라우저 | P20~P24 | P20~P21 `LIVE_PASS`로 Aside 진단·사람 개입 차단을 증명하고, 자동 실행에 포함할 사람인/잡코리아는 P22/P23 해당 `LIVE_PASS`, LinkedIn은 P24 `CONTRACT_PASS` 수동 준비표·영수증만 허용 |
| F 통합 | P25~P26 | 운영자 검토 큐가 원자료를 보존하고, 내부 후보→부족분→큐→결과→재계산의 읽기 전용 한 바퀴와 장애 복구가 실증됨 |

→ 큰 기능 하나를 28개 검토 단위로 쪼갰습니다. 표의 묶음은 완료 보고 단위이지 묶음 전체의 강제 직렬 장벽이 아닙니다. 각 프로젝트는 자기 파일의 명시적 선행조건이 실제 합격한 뒤 시작하며, 같은 선행조건만 요구하는 P05와 P09~P11 같은 프로젝트는 서로 다른 묶음이어도 병렬로 진행할 수 있습니다. F 통합 묶음은 요구된 모든 선행 프로젝트가 끝난 뒤에만 시작합니다. `NOT_RUN`이나 권한 대기는 합격 증거가 아닙니다.

4. P03 포지션 명세, P04 기획 묶음 검사 기반.
5. P05 ClickUp 읽기와 P09~P11 세 입력원 목록화를 병렬 진행.
6. P09~P11 뒤 P12 동일인, 이어 P13 내부 매칭. P14 중복 접촉은 P12 뒤 별도로 진행.
7. P13 뒤 P05 스냅샷과 같은 후보 영수증 합집합으로 P06 우선순위를, P03 목표와 그 합집합으로 P07 부족분을 병렬 계산한 다음 P08이 `position_priority_decision_hash`·부족분 지문·`candidate_eligibility_receipt_set_hash`가 같은 P03·P05·후보·정책 세대를 가리킬 때만 읽기 전용 작업 제안으로 결합.
8. P15~P19 여러 컴퓨터 제어.
9. P20 Aside 발견, P21 사람 개입 차단, P22 사람인, P23 잡코리아, P24 LinkedIn 수동 경로.
10. P25 운영자 검토 큐, P26 통합 그림자 운영.

## 11. 공통 중단 조건

- 기본 브랜치 시작 검사 실패를 숨기거나 우회해야 하는 경우.
- 개인정보 보관기간·삭제·접근권한이 없는 원문 이동.
- 외부 서비스 구조가 저장된 계약과 다름.
- 작업 대상 0건을 성공으로 세는 경우.
- 언어모델이 우선순위·적합도·동일인 여부를 최종 확정하는 경우.
- 같은 계정 사용권이 둘 이상이거나 `queue_lease_epoch`·`account_fencing_token`·`local_reservation_epoch` 중 하나라도 다른 결과가 들어오는 경우.
- 사람 개입 뒤 브라우저 명령이 한 건이라도 발생한 경우.
- 어떤 채널이든 봇 탐지·보안문자·속도·기기·계정·네트워크 제한을 숨기거나 우회해야 하는 경우.
- LinkedIn 사이트 안 자동 실행이 필요한 경우.
- ClickUp·메일·포털 쓰기 승인이 없는 경우.
- 실제 처리 건수·다시 읽기 확인·원문 지문이 없는 완료 주장.

## 12. 검증 전략

### 12-1. 판정 상태

| 상태 | 뜻 | 후속 선행조건 충족 여부 |
|---|---|---|
| `DECISION_APPROVED` | 오너가 버전·선택지·대가·되돌리기를 기록하고 승인 | 결정이 필요한 프로젝트에만 충족 |
| `CONTRACT_PASS` | 합성·실캡처 파생 자료·동시성 시험과 서버 검사가 통과 | 순수 계산과 다음 계약 프로젝트에만 충족 |
| `LIVE_PASS` | 허용된 실제 경계 한 건과 기계 영수증까지 통과 | 외부 의존 통합·배송 선행조건 충족 |
| `BLOCKED_OWNER` / `BLOCKED_AUTH` / `BLOCKED_POLICY` | 필요한 결정·권한·정책 근거가 없음 | 불충족 |
| `NOT_RUN` | 검증을 시도하지 않았거나 결과를 확보하지 못함 | 항상 불충족 |
| `FAIL` | 실행한 검증이 실패 | 항상 불충족 |

→ `NOT_RUN`을 “코드는 준비됨”으로 순화하지 않습니다. 각 후속 프롬프트는 필요한 합격 수준을 선행조건에 직접 적고, 외부 경계 프로젝트는 `LIVE_PASS` 없이는 완료가 아닙니다.

### 12-2. 프로젝트 유형별 필수 증거

모든 프로젝트는 실패하는 시험과 자기 번호의 단일 인수 명령을 먼저 만듭니다. 그 밖의 증거는 프로젝트 유형에 따라 다음처럼 다릅니다.

| 유형 | 대상 | 반드시 남길 증거 | 요구하지 않는 증거 |
|---|---|---|---|
| 오너 결정 | P00A | 선택지·대가·되돌리기·오너 원문 참조·서명 지문, 빈 결정 변조 거부 | 작업 큐 동시성·머신 장애·외부 데이터 읽기 |
| 정본·순수 계약 | P00B~P04, P06~P08, P12~P16, P24~P25 | 같은 입력 반복 지문 1종, 핵심 차단 변조 실패, 서버 검사 연결 | 실제 외부 쓰기; 동시성은 해당 계약이 소유할 때만 |
| 외부 읽기 경계 | P05, P09~P11, P20~P23 | 합성/실캡처 파생 계약시험과 허용된 실제 읽기 1건, 처리 건수, 쓰기 0건, 다시 읽기 영수증 | 권한·정책이 없을 때의 라이브 실행 |
| 공유 동시 실행 | P17~P19 | 두 실행자 승자 1명, 만료 회수, 오래된 결과 거부, 장애 승계, 서버 검사 연결 | 후보 원문과 외부 사이트 조작 |
| 통합 그림자 운영 | P26 | 요구된 모든 `LIVE_PASS`, 읽기 전용 한 바퀴, 두 실행자 장애 복구, 외부 쓰기 0건 | 승인 없는 ClickUp·메일·포털 쓰기 |

→ 오너 결정에 머신 장애 시험을 억지로 붙이지 않고, 실제 시스템을 읽는 프로젝트를 합성 자료만으로 완료하지도 않습니다. LinkedIn은 사이트 자동 실행 대상이 아니며 P24 준비표 한 건과 사람이 입력한 결과 영수증 연결만 검증합니다.

## 13. 현재 확인하지 못한 것

- 현재 ClickUp의 전체 열린 포지션과 우선순위에 필요한 값의 실제 충족률.
- Aside 재부팅 복구, 정확한 탭 선택, 후보 한 명 완주, 사람 개입 뒤 명령 0건.
- 사람인·잡코리아 계약상 허용되는 자동화 범위.
- 운영 Supabase의 실제 행 접근 정책과 후보 테이블 최신 구조.
- Gmail 첨부파일의 보관 권리와 삭제 요청 전파 범위.
- 여러 컴퓨터에서 작업 큐를 동시에 돌린 실제 장애 복구.

이 항목은 추정으로 채우지 않고 각각 독립 프로젝트의 시작 관문으로 둡니다.
