## §4. GitHub 전략

> **2026-08-08 이관**: "결론/규약" 부분의 정본은 `docs/sot/git-workflow.md`로 이동했다("CI가 강제할 것" 매핑표는 여기 그대로 남는다).

### 결론: Trunk-based + 수명 짧은 worktree 브랜치 + 태그 릴리스

**GitFlow REJECT.** develop/release/hotfix 분기는 여러 팀의 병렬 릴리스 트레인을 조율하는 장치다.
1인에게는 조율 대상이 없어 순수 오버헤드이며, 더 나쁜 것은 **장수 브랜치 + LLM 생성 코드 = 대형 충돌**이고
**LLM은 충돌을 "코드를 새로 지어내서" 해결한다. v4의 자동로그인 6벌이 그 산물이다.**

**worktree는 브랜치 전략이 아니라 작업 공간 격리 메커니즘**이며 trunk-based와 결합된다.
작업 1개 = worktree 1개 = 브랜치 1개 = 인수 기준 1개.

### 규약

- `main` 보호. 직접 push 금지. **오너 본인도 예외 없음**
- 작업 브랜치 `task/<name>`, 위치 `worktrees/<name>/`, **수명 24~48시간 상한**. 초과 = 인수 기준이 너무 크다는 신호(v4: 워크트리 77개·미병합 브랜치 113개가 방치된 실측 사례)
- PR = 인수 기준 1개. **squash merge**, 머지 후 브랜치 삭제
- 릴리스 = `main` 의 어노테이트 태그 `v6.YYYY.MM.DD-N` → CI가 artifact 빌드 → digest 산출 → `releases/<digest>/` 설치
- **자동 병합 금지.** 오너가 diff를 실제로 읽는 것이 P11(코드 예산)의 존재 이유

## §7. 가장 큰 위험과 그 처방

두 검증이 서로 다른 경로로 같은 지점에 도달했다.

- **속도(V1 Codex)**: 27개를 전부 지키면 하루 2~4 PR. 인수 기준 150개면 40~75 작업일.
  v5(하루 18커밋) 대비 기능당 **5~10배 느림**. 2주차에 게이트 이탈이 시작되고,
  그 순간 27개는 v5의 테스트 3,100개와 **같은 지위**(존재하지만 현실과 무관한 초록불)가 된다.
- **인지 한계(G Claude)**: §3의 지시 예산 초과. 과잉 준수로 성공률이 오히려 하락.

**처방은 규율 완화가 아니라 ① 범위 축소(Phase 3의 범위 정지 규칙) ② 문서 → 기계 이전(§3 3계층)이다.**

### 그리고 이탈은 게이트를 건너뛰는 형태로 오지 않는다 — 게이트를 **약화시키는** 형태로 온다

§0-C가 이것을 실측으로 보여준다. v4·v5 실패 9건 중 **5건이 검사 무력화**였다(A·B·C②·C③·E).
아무도 "게이트를 건너뛰겠다"고 선언하지 않았다. 대신 검사를 한 칸씩 느슨하게 했고
(`실제 경로 확인 → 저장소 파일 확인`, `무결성 검사 → 없으면 skip`, `결함 5건 → 실패해도 됨`),
그때마다 **CI는 여전히 초록이었다.**

**따라서 P13이 P1 다음으로 중요하다.** P1이 "원칙은 기계여야 한다"면,
P13은 "그 기계를 끌 수 없어야 한다"이다. 둘 중 하나만 있으면 나머지 원칙은 언제든 무력화된다.

### 세 번째 유형 — 장치는 있는데 안 쓰는 것 (§0-D D-3에서 새로 확인)

A~G와는 결이 다른 세 번째 실패 유형이 오늘 확인됐다. `/strict`는 검사를 "약화"시킨 적이 없다 —
계약 자체는 06-20 도입 이후 한 번도 느슨해지지 않았다. 그런데도 **적대검증 첨부율이 41.7%→14.5%로 떨어졌다.**
장치를 끄지 않고도, 그냥 **속도가 이행을 앞질러서** 장치가 비어버렸다. 이건 P13(약화 금지)만으로는 안 잡힌다 —
"검사 파일 diff"가 없기 때문이다. 그래서 P13 ⑤(첨부율 자체를 CI가 확인)와 P20(0건 처리를 의심)을 오늘 추가했다.
**장치가 존재하는 것과, 장치가 매번 쓰이는 것 사이의 간극이 세 번째 위험이다.**

### 업계 정설과의 차이 — 정직한 자기 비판

DORA 4대 지표 중 2개가 복구에 관한 것이다. 업계 정설의 목표는 **"안 틀리게 하기"가 아니라 "빨리 되돌리기"**다.
오너 원본 27개에는 **롤백이 한 줄도 없었다**(24번에 promotion만 있고 demotion 없음). 이것이 가장 큰 구조적 차이다.

다만 그 편향에는 정당한 근거가 있다 — v5에서 **틀린 것을 몇 주 동안 몰랐기** 때문에 되돌리기가 무의미했다.
그러나 그 경우 처방은 검증을 두껍게 하는 것이 아니라 **결과를 매일 보이게 하는 것**이다(P10).
뼈대 지시서 P13이 이미 그렇게 진단했다 — *"틀렸다는 걸 알려주는 숫자가 없었다."*

| 쟁점 | 오너 | 업계 정설 | 판정 |
|---|---|---|---|
| 리뷰어 부재 대응 | CI를 리뷰어로 | 팀 리뷰 | **오너가 맞음** — 1인에겐 이것이 정답 |
| 테스트 신뢰도 | 불신 | 신뢰 | **오너가 맞음** — v5 3,100개와 v4 테스트-결함 양의상관(+0.764)이 근거 |
| 원칙의 양 | 문서 27개 | 원칙 적게, 도구 많이 | **정설이 맞음** — ETH 연구가 수치로 확인 |
| 피드백 속도 | 하루 2~4 PR | 하루 여러 번 | **정설이 맞음** — 느린 루프는 2주 뒤 붕괴 |
| 목표 설정 | 100% 정확 | 빠른 복구(MTTR) | **정설이 맞음** — P7 신설로 보정 |
| PR 크기 규제 | 300줄 등 일률 제한 | 크기보다 리드타임 | **정설이 맞음** — v4 313개 데이터가 크기-결함 곡선 부재를 실증(§0-D) |

**달성 가능한 목표의 재정의**: 100% 정확한 코드를 보장하는 방법은 없다.
그러나 **틀렸을 때 그날 안에 드러나게 만드는 것**은 기계 장치로 100% 달성 가능하다.
이것이 되면 실패는 하루치 손실로 끝나고, 안 되면 v5처럼 30일치가 한꺼번에 무너진다.
