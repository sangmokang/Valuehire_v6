# P13 자가승인·커버리지·인덱스 결함 종결 — 착수 문서 (2026-09-11)

VERDICT: 진행 중 (Codex 적대검증 2라운드 needs-attention · 높음 3건 전부 재현됨)

## 결론 (1층)

검사를 지우지 못하게 만든 잠금장치를, **지우는 사람이 스스로 열 수 있습니다.** 그리고 비밀값을 잡는 규칙 25개 중 21개는 "줄어들었는지" 아무도 보지 않습니다. 세 번째로, 줄어든 것을 보는 장치가 **커밋될 내용이 아니라 화면에 열린 파일**을 읽어서, 지운 것을 올려놓고 화면만 되돌리면 통과합니다.

세 가지 모두 제가 만든 방어에 있는 구멍이고, 오늘 격리된 사본에서 직접 뚫어 확인했습니다. 사장님이 결정하실 것은 **2번 항목의 범위**입니다 — 규칙 25개 전부에 카나리를 붙일지, 아니면 의미가 겹치는 규칙을 묶어 더 적은 수로 덮을지.

## 2층 판단 근거

### 왜 세 건이 한 묶음인가

셋은 같은 구조적 실수입니다 — **검사기는 보호하면서 그 검사기가 기대는 것을 보호하지 않았습니다.**

| 결함 | 검사기가 기대는 것 | 보호 안 된 부분 |
|---|---|---|
| C1 | `suppressions.yaml` 의 은퇴 승인 | 승인을 **누가 언제** 썼는지 |
| C2 | 카나리가 규칙을 대표한다 | **어떤 규칙을** 대표하는지 |
| C3 | 카나리 파일 내용 | **어느 트리**의 내용인지 |

→ 세 줄을 나란히 놓으면 같은 실수임이 보입니다. 검사기 본체는 지켰는데 그것이 **읽는 대상**을 안 지켰습니다. 하나씩 고치면 네 번째가 또 나옵니다.

하나씩 고치면 네 번째가 또 나옵니다. 세 건을 같은 작업 단위로 묶는 이유입니다.

### 버린 길

**`.secret-patterns.default` 를 아예 수정 금지로 잠그는 안** — 기각했습니다. 규칙은 오탐이 나면 고쳐야 하고, 잠그면 우회 경로(로컬 `.secret-patterns` 로 덮어쓰기)가 생깁니다. "수정은 되되 탐지력이 줄면 막는다"가 유지보수 가능한 경계입니다.

**승인자를 사람 이름 허용목록으로 두는 안** — 부분 채택합니다. 허용목록만으로는 삭제자가 그 이름을 적으면 됩니다. **승인이 기준 브랜치에 이미 있었는가**(선재성)가 핵심이고, 허용목록은 보조입니다.

### 틀리면 깨지는 것

C1을 잘못 고치면 검사를 **영원히 은퇴시키지 못하는 벽**이 됩니다. 정당한 은퇴 경로(승인을 먼저 병합한 뒤 다음 커밋에서 삭제)가 반드시 통과해야 합니다.

## 결정 카드

### 카드 1 — 승인 선재성을 핵심 축으로 둔다

> **무엇을** — 은퇴 승인은 기준 브랜치(HEAD)에 이미 있던 것만 인정한다.
> **왜** — 같은 커밋에서 쓴 승인은 삭제자의 자기 서명이다. 실측으로 통과했다.
> **버린 길** — owner 허용목록만 두는 안. 삭제자가 그 이름을 적으면 그만이라 기각했다. 보조로만 쓴다.
> **대가** — 은퇴가 두 커밋으로 나뉜다(승인 병합 → 삭제). 한 번에 끝내던 흐름이 느려진다.
> **되돌리기** — `check-workflow-deletion.sh` 의 선재성 검사 블록을 지우면 즉시 옛 동작으로 돌아간다.

### 카드 2 — 카나리를 규칙이 아니라 capability 에 건다

> **무엇을** — 규칙 25개를 의미 단위(capability)로 묶고, 묶음마다 최소 하나의 카나리를 manifest 로 연결한다.
> **왜** — 규칙 1:1 로 25개 카나리를 만들면 규칙을 고칠 때마다 카나리가 깨져 유지가 안 된다. 의미가 겹치는 규칙이 실제로 있다.
> **버린 길** — 규칙 25개 = 카나리 25개 강제. 유지비가 너무 크고, 중복 규칙에 중복 카나리가 생긴다.
> **대가** — 묶는 판단이 사람 몫이라 **묶음이 잘못되면 구멍이 남는다.** 그래서 묶은 근거를 manifest 에 적고, 묶인 규칙 전부가 그 카나리로 실제 매칭되는지 실행으로 확인한다.
> **되돌리기** — manifest 를 1:1 로 펼치면 된다. 검사기 로직은 그대로다.

### 카드 3 — 독립 oracle 은 "완전 분리"가 아니라 "교차 대조"로 한다

> **무엇을** — 회귀 검사기가 `verify.sh` 와 별도 경로로도 판정하고, 두 판정을 대조한다.
> **왜** — 파싱을 복제하면 둘이 같이 틀릴 수 있다(공통모드). 실제로 첫 구현에서 정제 방식이 갈려 정규식이 깨졌다.
> **버린 길** — 완전히 다른 파서를 새로 쓰는 안. 그러면 "어느 쪽이 맞나"가 새 분쟁이 되고, 실제 스캔과 다른 규칙 집합을 보게 된다.
> **대가** — 둘이 **같은 방식으로 틀리면 이 검사도 못 본다.** 그 한계를 문서에 적는다.
> **되돌리기** — `--oracle-selftest` 경로만 제거하면 된다.

## 인수 기준 — EARS 단언 + 실행 명령

AC 마다 ① 명령 ② 기대 출력 ③ 양성/음성 ④ 최소 건수를 적는다. 산문 AC 는 금지다.

### AC-1 (C1) 선재하지 않은 승인은 거부한다

> When 보호된 검사 스크립트와 그 CI 실행 줄이 같은 커밋에서 사라지고 그 은퇴 승인이 **기준 브랜치(HEAD)에 존재하지 않으면**, 시스템은 커밋을 차단해야 한다.

```bash
bash scripts/acceptance-p13-deletion.sh
```
→ 시킬 것: 은퇴 차단 인수 검사. 볼 것: 시연 13건 이상이 전부 합격인지. 지금은 11건이고 자가승인 시연이 없습니다.

기대 출력: `RESULT: 합격`, `CHECKED:` 13 이상, 종료값 0.
- 양성 ≥2: ① 같은 커밋 자가 승인 → 차단 ② 승인 없는 삭제 → 차단
- 음성 ≥2: ① **승인이 HEAD 에 선재**하고 다음 커밋에서 삭제 → 통과 ② 무관한 파일 삭제 → 통과
- 승인 파싱은 문자열 포함이 아니라 **항목 단위 스키마**(check·owner·reason·expiry 네 필드가 한 항목 안에 모두 존재, expiry 는 YYYY-MM-DD 이고 오늘 이후, owner·reason 은 공백 아님)로 검증한다.

### AC-2 (C2) 모든 규칙이 최소 하나의 카나리로 덮인다

> While 비밀 규칙 파일에 규칙이 존재하는 동안, 시스템은 각 규칙이 최소 하나의 양성 카나리에 연결되어 있음을 보장해야 한다.

```bash
bash scripts/verify/check-secret-canary-coverage.sh
```
→ 시킬 것: 규칙 하나하나가 카나리에 연결됐는지. 볼 것: 숫자가 25/25 인지. 지금은 이 검사기 자체가 없습니다.

기대 출력: `PASS: 규칙 N개 전부 카나리로 덮임 (N=25)`, 종료값 0.
- 양성 ≥3: ① 규칙 1개 추가하고 카나리 없음 → 차단 ② 기존 규칙을 match-never(`THIS_WILL_NEVER_MATCH`)로 변경 → 차단 ③ 임의 규칙 1개 삭제 → 차단
- 음성 ≥2: ① 규칙과 그 카나리를 함께 정리 → 통과 ② 카나리를 추가만 → 통과
- 커버리지 관계는 **manifest** 로 명시한다: `capability → positive canary → 이를 잡아야 하는 규칙`. manifest 와 실제 파일이 어긋나면 차단한다.
- 규칙 25개 = 카나리 25개일 필요는 없다. 의미가 겹치는 규칙을 하나의 capability 로 묶되, **묶은 근거를 manifest 에 적고** 묶인 규칙 전부가 그 카나리로 실제 매칭되는지 실행으로 확인한다.

### AC-3 (C3) 판정 입력은 커밋될 내용이다

> If 카나리 고정물이 스테이징되었으면, 시스템은 작업트리가 아니라 **인덱스의 내용**으로 판정해야 한다.

```bash
bash scripts/acceptance-secret-detection-regression.sh
```
→ 시킬 것: 탐지력 축소 차단 인수 검사. 볼 것: 시연 10건 이상 합격. 지금은 7건이고 stage/worktree 미끼 시연이 없습니다.

기대 출력: `RESULT: 합격`, `CHECKED:` 10 이상, 종료값 0.
- 양성 ≥3: ① 카나리 삭제를 stage 하고 worktree 복원 → 차단 ② 기준 대비 카나리 감소(4→3) → 하한과 무관하게 차단 ③ manifest 매핑 손실 → 차단
- 음성 ≥1: 규칙과 카나리와 manifest 를 함께 줄임 → 통과
- 읽기 방식은 `git show HEAD:<path>` 와 `git show :<path>` 로 고정한다. 작업트리 직접 읽기는 금지한다.

### AC-4 독립 oracle 확보 (Codex P13-R4)

> Where 회귀 검사기가 비밀 규칙을 해석하는 경우, 시스템은 `verify.sh` 와 **독립적으로** 판정할 수 있어야 한다.

```bash
bash scripts/verify/check-secret-canary-coverage.sh --oracle-selftest
```
→ 시킬 것: 두 구현이 같은 입력에 같은 판정을 내는지. 볼 것: 일치 건수. 어긋나면 둘 중 하나가 규칙을 잘못 읽고 있다는 뜻입니다.

기대 출력: `PASS: 독립 oracle 일치 N/N`, 종료값 0.
- 같은 입력에 대해 두 구현(`verify.sh` 경로 / 검사기 자체 경로)의 판정이 일치하는지 대조한다. 어긋나면 차단한다.
- 목적은 파싱 복제로 인한 **공통모드 실패**를 드러내는 것이다. 둘이 같은 방식으로 틀리면 이 검사가 그것을 볼 수 없다는 한계를 문서에 남긴다.

## counter-AC — 가짜 합격 시나리오

1. manifest 를 만들되 커버리지 검사를 워크플로에 배선하지 않는다 → 배선 확인 시연 필수
2. 카나리를 늘리되 전부 같은 규칙에 매칭시킨다 → capability 별 매칭 실행 확인 필수
3. 승인 선재성을 `git log` 문자열 검색으로 확인한다 → `git show HEAD:suppressions.yaml` 항목 파싱으로 고정
4. 검사기는 고치되 그 검사기의 fixture·manifest·호출부를 보호 대상에서 뺀다 → **순환 우회 시연** 필수
5. mktemp 거부 환경에서 `exit 2` 를 "차단됨"으로 계수한다 → 실행 불가(126·127·2)와 판정 실패를 가르는 시연 필수

## 필수 mutation 목록 (8단계)

Codex·ChatGPT 권고를 합쳐 최소 13종. 각 항목은 **적용 여부를 diff 로 확인**한 뒤 결과를 센다.

```
1  protected script 삭제                     8  broad suppression 추가
2  protected script rename                   9  suppression expiry 제거
3  workflow 호출만 삭제                      10 expiry 과거 날짜
4  script 는 남기고 exit 0 으로 치환         11 owner 공백·없는 형식
5  .secret-patterns.default 전체 삭제        12 canary fixture 자체 삭제
6  한 개 pattern 삭제                        13 regression checker 를 workflow 에서 제거
7  pattern 을 match-never 로 변경
```

→ 13종을 다 돌리는 이유는 "하나를 막으면 다른 하나가 열린다"를 이미 네 번 겪었기 때문입니다. 적용 여부를 diff 로 먼저 확인해야 합니다 — 변조가 안 걸린 채 "생존"으로 세는 사고가 이번 세션에만 두 번 났습니다.

### 계약에 없던 결함 3건 (작업 중 발견해 함께 고침)

### 한계 — 이 변경이 막지 못하는 것

1. **로컬에서 커밋을 둘로 나누는 은퇴.** 승인 선재성은 "한 커밋 안에서의 자기 서명"만
   없앱니다. 승인을 먼저 커밋하고 다음 커밋에서 지우는 것은 통과하며, 그것을 거르는 것은
   PR 리뷰의 몫입니다.
2. **두 판정기가 같은 방식으로 틀리는 경우.** 독립 oracle 은 적재·정제·배관의 차이만
   드러냅니다. 같은 정규식 엔진과 같은 규칙 파일을 쓰므로, 규칙 자체가 틀렸으면 둘 다
   놓칩니다.
3. **capability 묶음의 판단.** 어떤 규칙을 한 묶음으로 볼지는 사람이 정합니다. 묶음이
   잘못되어도 각 규칙이 카나리로 매칭되는지는 실행으로 확인하므로 커버리지 구멍은 생기지
   않지만, 묶음의 의미가 흐려질 수는 있습니다.
4. **커버리지 검사기만 지우는 커밋.** 훅 트리거는 규칙·고정물이 스테이징될 때만 돕니다.
   검사기만 지우는 커밋은 훅을 안 건드리며, 그 구멍은 장치 명부가 막습니다(pre-push·CI).
