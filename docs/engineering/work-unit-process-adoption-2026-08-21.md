## 1층 결론

**채택하시는 게 맞습니다. 이 제안은 "새 검사를 늘리자"가 아니라 "이미 우리가 정해 둔 규칙을 지킬 수 있는 크기로 일을 자르자"입니다.**

- 저희 원칙 P11③은 **"3,000줄 넘는 변경 요청은 절대 금지"**(두 달 뒤 원인 추적 불가)인데, 지금 그 선을 넘은 것이 **5건**입니다. 최대 15,080줄, 최장 8일째 열려 있습니다.

→ 즉 저희가 막힌 지점은 "검사 종류가 부족해서"가 아니라 **한 덩어리가 너무 커서 끝을 못 내고 있어서**입니다. 제안이 정확히 그 지점을 칩니다.

### 다만 그대로 쓰면 안 되고 3가지를 조정해야 합니다

1. **각 Work Unit 안에서는 "실패하는 시험 먼저"를 유지합니다.** 제안의 순서는 `구현 → 검증`인데, 저희 규칙(게이트 2)은 **실패하는 시험을 먼저 커밋**하는 것입니다. 이 순서를 버리면 "구현을 복사한 시험"이 들어옵니다(P5·P16이 막으려던 바로 그것).
2. **Work Unit마다 작업 폴더를 새로 파지 않습니다.** 지금도 43개가 쌓여 있습니다. **한 이슈 = 한 작업 폴더, 그 안에서 Work Unit마다 커밋**으로 합니다.
3. **"위험한 Work Unit" 목록은 사람이 지키는 규칙이 아니라 검사기가 판정하게 합니다.** 규칙만 적어 두면 P13(`weakens-check` 라벨)처럼 배선 0건으로 남습니다.

> **되돌리기** — 쪼갠 뒤에도 하나로 합치는 건 언제든 가능합니다. 반대는 어렵습니다.

## 2층 판단 근거

### 이미 있는 것 vs 새로 얻는 것

| 제안 항목 | 저희 현재 상태 | 판정 |
|---|---|---|
| 한 작업 = 인수 기준 1개 | 하네스 게이트 1에 이미 있음 | **이미 있음** |
| 작업 폴더 격리 | 이미 씀(43개) | **이미 있음** (오히려 과다) |
| 실패 시험 먼저 | 게이트 2에 이미 있음 | **이미 있음 · 제안보다 강함** |
| strict·codeaudit·적대검증을 마지막 관문으로 | 지금도 마지막에 함 | **이미 있음** |
| **Work Unit마다 커밋 = 증명 경계** | 없음. 한 PR에 47파일이 섞임 | **새로 얻음 · 핵심** |
| **Work Unit마다 작은 반증 1~3개** | 없음. 반증은 마지막에 한 번 | **새로 얻음 · 핵심** |
| **위험 파일이면 강화 경로** | 없음. 모든 변경이 같은 절차 | **새로 얻음** |
| 이슈 → Work Unit → 커밋 → PR 연결 | 이슈 8건이 PR과 느슨하게 연결 | **새로 얻음** |

→ 표 해석: 제안의 8가지 중 4가지는 이미 저희 규칙에 있고, **나머지 4가지가 진짜 새로 얻는 것**입니다. 그래서 "완전히 갈아엎을 필요 없다"는 제안자의 판단은 정확합니다.

### 왜 "작은 반증"이 마지막 적대검증을 대체하지 못하는가 (제안의 검사 구분에 동의하는 이유)

어제~오늘 실측이 이 구분을 그대로 증명합니다.

- **Work Unit 검증**(약속 하나가 되는가): `bash scripts/acceptance-principles-check.sh` → `VERDICT: PASS`. 이건 한 단위 안에서 몇 초면 끝납니다.
- **Work Unit 반증**(어떻게 속일 수 있나): 검사 실행 줄을 `echo`로 바꿔 보는 것 — **23줄 중 15줄이 안 잡혔습니다.** 이건 단위별로 해야 잡힙니다.
- **최종 적대검증**(조합했을 때 뚫리나): 잠금 장치의 **동시 실행 경합** — `lock` 하나만 봐도, `recover` 하나만 봐도 정상인데 둘이 겹치면 "성공"이라 하면서 복구 기록이 사라집니다. **단위 검사로는 원리적으로 안 잡힙니다.**

→ 제안이 말한 "WU1 정상 + WU2 정상 → 조합하면 경합"이 저희 저장소에서 실제로 관측된 사례입니다. 그러므로 마지막 통합 관문을 없애면 안 됩니다.

## 3층 — 앞으로 이렇게 진행합니다 (실제 시나리오)

지금 열려 있는 **PR #35**를 Work Unit 방식으로 다시 짠다면 이렇게 됩니다. 파일명·명령은 모두 실재하는 것입니다.

### 0단계 — 이슈 하나로 약속을 고정

**아래 이슈 번호는 예시입니다. 2026-08-21 03:05 기준 실제 최신 이슈는 #33이며 #36은 발행하지 않았습니다.**

```
Issue #36(예시)  검사의 존재가 아니라 의미를 검증한다
  AC1  CI 실행 줄을 `echo bash …`로 바꾸면 검사가 실패해야 한다
  AC2  CI 스텝에 `if: ${{ false }}`를 넣으면 검사가 실패해야 한다
  AC3  acceptance 스크립트 본문을 `exit 0`으로 비우면 상위 검증이 실패해야 한다
  AC4  히스토리 비밀 스캔이 큰 파일에서 비밀을 찾으면 반드시 실패해야 한다
```

→ 인수 기준 1개 = Work Unit 1개입니다. 4개면 Work Unit 4개입니다.

### 1단계 — 작업 폴더는 이슈당 하나

```bash

```

→ Work Unit마다 새로 파지 않습니다. 이 폴더 하나에서 커밋 4개를 만듭니다.

### 2단계 — Work Unit 하나의 완전한 사이클 (WU-01 = AC1)

사장님이 실제로 타이핑하실 문장:

```
WU-01만 해. AC1(echo 치환 탐지)만이다. AC2~AC4는 건드리지 마.
실패하는 검사 먼저 커밋하고, 그다음 통과시켜라.
```

제가 하는 일과 그 증거:

```bash
# ① RED — 아직 없는 동작 때문에 실패하는 검사를 먼저 만든다
bash scripts/acceptance-ci-step-integrity.sh   # 기대: FAIL (echo 치환을 못 잡음)
git commit -m "test: CI 실행 줄 echo 치환을 잡지 못하는 것을 고정한다"

# ② GREEN — 최소 변경으로 통과시킨다
bash scripts/acceptance-ci-step-integrity.sh   # 기대: VERDICT: PASS
```

```bash
# ③ 작은 반증 3개 — "이 약속을 어떻게 속여서 통과하나"
#   무력화 형태를 하나씩 넣어 보고, 전부 빨개져야 한다
echo bash …        → 실패해야 함
if: false          → 실패해야 함
if: ${{ false }}   → 실패해야 함   ← 지금 저희가 뚫려 있는 형태
```

```bash
git commit -m "fix: CI 실행 줄 무력화 3종을 탐지한다 (AC1)"
```

→ 여기까지가 Work Unit 1개입니다. 커밋 2개(RED·GREEN)로 끝나고, **다음 단위로 넘어가기 전에 이 단위는 증명이 끝난 상태**가 됩니다.

### 3단계 — WU-02·03·04 반복

```
commit a1  test: echo 치환 미탐지를 고정한다
commit a2  fix: CI 실행 줄 무력화 3종을 탐지한다 (AC1)
commit b1  test: 조건 비활성화 미탐지를 고정한다
commit b2  fix: if 조건 비활성화를 탐지한다 (AC2)
commit c1  test: 본문 비우기 미탐지를 고정한다
commit c2  fix: acceptance 본문 치환 시 상위 검증이 실패한다 (AC3)
commit d1  test: 큰 파일 비밀이 통과하는 것을 고정한다
commit d2  fix: 히스토리 스캔을 실패 방향으로 뒤집는다 (AC4)
```

→ 나중에 문제가 나면 "a2 문제냐 c2 문제냐"를 바로 가릅니다. 지금 PR #35처럼 47파일 5,481줄 한 덩어리면 다시 전부 읽어야 합니다.

### 4단계 — 여기서부터가 기존 절차 그대로 (마지막 통합 관문)

```bash

/strict                              # 원칙 계약 + 게이트 전수

```

→ 제안대로 **strict·codeaudit·적대검증은 없애지 않고 마지막 관문으로 승격**합니다. 다만 이제 그 관문이 보는 대상이 "5,481줄 덩어리"가 아니라 "이미 각자 증명이 끝난 단위 4개의 조합"입니다.

## 도입 비용과 되돌리기

- **비용**: PR 개수가 늘어 CI 대기가 늘어납니다(1건 수 분). 커밋 메시지를 단위별로 정확히 써야 합니다.
- **얻는 것**: 원인 추적 가능, 하나가 막혀도 나머지가 나갑니다, P11③을 실제로 지킬 수 있게 됩니다.
- **되돌리기**: 절차 규칙일 뿐이므로 언제든 원래대로 큰 덩어리로 돌아갈 수 있습니다. 이미 쪼개 놓은 커밋은 그대로 남습니다.
