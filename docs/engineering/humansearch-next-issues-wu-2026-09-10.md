## 2. Issue와 WU의 크기

Issue는 사용자가 얻는 결과 하나다. WU(작업 단위)는 독립적으로 실패를 재현하고 되돌릴 수 있는 행동 하나다.
**WU 1개 = 인수 기준 1개 = 소유 워크트리 1개 = PR 1개**. RED/GREEN은 그 PR 안의 분리된 커밋이다.
한 WU에서 외부 시스템 두 개를 새로 연결하거나, 저장·브라우저·봇을 동시에 구현하지 않는다.
표의 정상·실패 사례는 하나의 인수 기준을 증명하는 입력 분할이다.

목표 크기는 제품 코드 1~3파일이다. 이는 분할 신호이지 새 절대 줄수 규칙이 아니다.
파일·함수·PR 예산은 P11을 따른다. 넘칠 조짐이면 쓰기 전에 `.a`, `.b`로 나누고 의존성과 검사를 갱신한다.
공유 계약·마이그레이션·CI는 한 번에 한 WU만 소유한다. 다른 세션의 작업은 덮거나 되돌리지 않는다.
현재 작업이 소유된 기존 WU면 상태를 인계받고, 이미 같은 결과가 있으면 새 구현을 만들지 않는다.

상태는 `PLANNED → RED → IMPLEMENTED → AUDITED → LOCAL_COMMITTED → PR_OPEN → VERIFIED → MERGED`다.
`BLOCKED`와 `NOT_RUN`은 이유·해제 조건을 기록한다. 로컬 커밋을 CI 검증이나 병합으로 표현하지 않는다.
상위 Issue는 모든 필수 WU가 병합되고 Issue의 실제 성공 사례가 입증돼야 닫는다.
초기값은 아래 WU 전부 PLANNED다. 기존 부분 작업은 위 기준 기록을 회수해 재평가한다.

## 3. 공통 시험·감사·커밋 계약

1. WU 카드에 입력·출력·오류·경계·부작용·수정 파일·선행 SHA·복구 방법을 적는다.
   인수 명령은 실행 가능한 한 개의 정조준 명령으로 확정한다. 시험 개수만으로 합격시키지 않는다.
2. **RED:** 실제 행동 단언이 실패하는 시험을 먼저 실행한다. import 실패·수집 0·문법 오류는 RED가 아니다.
   신규 API면 호출 가능한 최소 경계부터 준비하되, 성공 반환을 하드코딩하지 않는다.
   독립 검토자가 시험이 AC를 표현하는지 확인한 뒤 시험·fixture만 RED 커밋한다.
3. **GREEN 후보:** 제품 코드를 최소 구현한다. RED 이후 기존 시험의 기대값·단언·skip은 바꾸지 않는다.
   새 결함에는 새 회귀 파일과 별도 RED 커밋을 추가한다. 시험 계약 자체 정정은 별도 검토·커밋으로 한다.
4. **정조준 검사:** 아래 명령으로 해당 WU 시험을 실행하고 실제 분기·부작용·회귀를 확인한다.
   순수 판정은 Hypothesis, 저장은 실제 임시 SQLite, 경쟁은 동기화 장벽을 써서 검사한다.
5. **Codeaudit:** 구현자와 다른 읽기 전용 맥락에서 사용자 요구→계약→입력→처리→출력→시험을 대조한다.
   현재 diff와 원본 시험 출력을 제공한다. 판정 파일 존재나 `VERDICT: PASS` 문구만으로 통과시키지 않는다.
6. **적대 검증:** 감사와 별도로 결함을 실제 주입한다. 정상 대조군 통과 + 해당 결함군 음성 대조군 실패를 증명한다.
   항상 허용·항상 거부·핵심 저장/호출 생략 중 해당되는 변이를 쓰고, 비해당은 이유를 적는다.
   항상 거부되는 가짜 구현은 정상 사례가 잡아야 한다. 남의 워크트리에 변이를 주입하지 않는다.
7. 재현된 지적을 고치고 해당 검사·감사·영향받는 적대 검증을 다시 수행한다.
   필수 AC 실패·높음 이상 미해결·필수 검증 NOT_RUN이면 GREEN 확정 금지다.
   관련 없는 기존 실패는 재현 근거와 별도 Issue로 기록하고 현재 검사의 실패를 숨기지 않는다.
8. **커밋 전:** `git diff --check`, 변경에 맞는 정적 검사·회귀 검사, `bash verify.sh`를 실행한다.
   Python 변경은 `cd humansearch && uv run --no-sync ruff check src tests`와
   `uv run --no-sync mypy src tests`를 실행한다. 필요한 환경은 pyproject/lock 기준으로 준비한다.
   현재 GREEN 후보가 감사 대상 지문과 같을 때만 제품 코드 GREEN 커밋을 만든다.
9. **커밋 후:** 커밋 SHA와 파일 지문을 대조한다. 내용이 바뀌면 영향받는 검사와 검토를 다시 실행한다.
   push/PR까지 실행하는 세션은 같은 SHA의 CI를 확인하고
   `bash scripts/verify/check-verified-sha.sh task/<branch>`가 VERIFIED인지 읽는다.
   조회 불가·이전 SHA 결과·작업트리 변경이 있으면 VERIFIED가 아니다. 자동 merge 금지.

→ 시험의 의도된 실패를 남기는 RED와, 구현·감사를 통과한 GREEN을 구분한다.
CI는 커밋 뒤에 실행되므로 커밋 전 CI 성공을 요구하는 순환 조건을 만들지 않는다.

신규 Python WU `HS-02.02`의 예정 시험 경로는 `humansearch/tests/test_hs_0202.py`다.
해당 WU 인수 명령은 `cd humansearch && uv run --no-sync pytest -q tests/test_hs_0202.py`다.
아래 모든 Python WU에 같은 ID→파일 규칙을 쓴다. 파일은 해당 RED 단계에서 만들 대상이다.
문서·셸·라이브 WU는 카드에 실제 명령을 확정한다. 아직 없는 명령은 `PLANNED`라고 표시한다.
기존 시험으로 증명되면 새 파일을 만들지 않고 실제 node ID를 카드에 적는다.

새 `scripts/acceptance-*.sh`가 필요한 경우에만 추가한다. 그 WU에서 CI와 검사 명령 표를 함께 연결한다.
기존 pytest 수집으로 충분한 내부 함수마다 새 검사 실행기·검증 프레임워크를 만들지 않는다.
외부 어댑터에는 실제 요청 경로의 네트워크 차단 시험이 필요하다. mock 정상 성공과 라이브 성공을 구분한다.
라이브 효과가 필수인 WU는 실제 1건과 독립 readback까지 없으면 VERIFIED로 올리지 않는다.
중립 브라우저 시험은 채용 포털 성공 증거가 아니다. 라이브 선행 계약을 생략하는 명분으로 쓰지 않는다.

검토 증거에는 WU ID, base SHA, 후보 diff 지문, 시험 파일 지문, 명령·종료값·시각, 검토자 종류,
발견→재현→조치→재검증, 미검증 범위를 남긴다. 구현자가 독립 판정이나 라이브 영수증을 작성하지 않는다.
P17 권한 분리 미구현 상태의 같은 사용자 하위 에이전트는 독립 맥락 검토일 뿐 권한 격리 증거가 아니다.
권한 분리 전에는 제품 감사 출력을 출처와 함께 임시 기록하고 로컬 진척으로만 보고한다.
P17이 준비돼야 그 실행기가 판정·라이브 영수증을 보존하고 제품 WU의 최종 검증 증거로 사용할 수 있다.
Claude를 실제 실행하지 않았으면 Claude V1이라고 쓰지 않는다. 사용 가능 여부를 확인하고 필수 교차 검증이
불가능하면 NOT_RUN으로 남긴다. 내부 문서 검토에 채용 데이터나 외부 서비스 쓰기를 요구하지 않는다.

## 5. 순서·Issue 본문·진척 보고

주 경로: **HS-00.01 → HS-02.01·HS-01 → HS-04.02/03 → HS-02.02/03 → HS-03/04 → HS-05/06 → HS-07**.
그 다음 HS-08/09 → HS-10/11/12. HS-04.01을 HS-03.03보다 먼저, HS-06.01을 HS-05.07보다 먼저 수행한다.
이 장부는 작은 WU로 재분할하면서 기존 선형 순서를 의존성 순서로 바꾼다. 라이브 선행 관문은 유지한다.
독립 작업은 병렬화할 수 있지만 구현자 1명은 WU 1개만 맡는다. 검토자는 같은 코드를 고치지 않는다.
실제 포털 첫 관측은 필요한 정본·저장·권한 경계가 병합된 뒤다.

선행 PR이 열렸지만 미병합이면 순수 내부 작업은 검토된 선행 SHA 위에 쌓을 수 있다.
base PR·SHA를 명시하고 선행 변경 후 재검증한다. main에 선행 파일이 있다고 가정하지 않는다.
라이브·운영 정책에 필요한 병합 조건은 누적 브랜치로 우회하지 않는다.
장시간 CI나 계정 권한에 막히면 의존하지 않는 준비 작업만 계속하고 실패 WU를 완료로 바꾸지 않는다.

Issue 본문에는 해당 절의 성공 기준·선행 조건·WU 행·검증 한계와 아래 항목을 복사한다.
WU 분할 시 부모와 자식 ID를 연결하고 기존 ID는 삭제하지 않는다. 등록 전 같은 제목/목표 Issue를 조회한다.

```text
Issue: HS-xx / GitHub 번호(등록 뒤에만)
사업 결과 / 성공 사례:
필수 WU / 선택 WU:
선행 Issue·PR·SHA:
WU별 상태 / 담당 / 워크트리 / RED SHA / GREEN SHA / PR:
AC 명령·결과 / Codeaudit / 적대 검증 / live·CI·SHA 상태:
막힌 이유 / 해제 조건 / 다음 한 개:
```

→ 숫자 하나의 전체 진행률 대신 검증·병합된 WU 수와 실제 사용자 여정 성공 여부를 함께 보고한다.
GitHub Issue 등록은 별도 게시 작업이다. 이 로컬 문서 저장만으로 등록됐다고 말하지 않는다.
