# Production-first Strict 전환 Goal — 2026-09-04

## 결론

제품 기능은 로컬 구현을 쌓은 뒤 마지막에 배포하지 않는다. 첫 작업 단위에서 최소 운영 경로를 먼저 열고, 이후 기능을 그 경로에 하나씩 연결한다.

다만 빈 페이지 공개를 제품 완료로 세지 않는다. 운영 주소, 인증, 환경 설정, 데이터 저장·재조회, 배포 버전, 되돌리기를 증명한 뒤 실제 업무 한 건까지 끝나야 제품 완료다.

## 현재 상태와 근본 원인

- `~/.codex/skills/strict/SKILL.md`의 사용자 단계는 `PLAN → BUILD → AUDIT → CHECKPOINT → SHIP`이어서 운영 환경을 마지막에 만난다.
- `docs/sot/coding-principles.md`의 P6·P7·P19와 V-3는 실행 환경, 롤백, 라이브 검증을 요구하지만 최초 기능보다 배포 경로를 먼저 닫으라는 순서는 고정하지 않는다.
- `scripts/acceptance-principles-check.sh`는 현재 P1~P24와 V-1~V-5 등 34개 계약의 존재와 배선을 검사한다.

근본 원인은 라이브 검증의 존재 여부는 요구하지만, 개발 첫 단위에서 운영 골격을 만들고 배송 성숙도를 구분하는 계약이 없다는 점이다.

## 사용자 요구

1. 배포를 마지막 단계가 아니라 제품 기능 개발의 첫 작업 단위로 둔다.
2. 첫 배포는 운영 주소, 인증, 환경 설정, DB 연결, 배포 버전, 상태 확인과 롤백을 포함한 최소 골격이어야 한다.
3. 이후 기능은 이미 작동하는 배포 경로 위에 작은 단위로 추가한다.
4. 로컬 성공을 제품 완료로 보고하지 않는다.
5. 운영 주소에서 실제 데이터를 쓰고 다시 읽으며, 사용자가 실제 업무 한 건을 끝낸 상태를 제품 완료로 삼는다.
6. 개인정보와 운영 변경 승인은 기존 안전 경계를 유지한다.
7. 기능 구현 전에 운영에서 성공을 판정할 최소 검증 경로를 먼저 만든다.
8. DB 스키마는 버전 관리되는 마이그레이션으로만 변경하고 데이터 정합성은 가능한 한 DB 제약으로 강제한다.
9. 같은 사업 지표의 계산 정의는 한 곳에만 두고 모든 화면은 그 결과를 소비한다.
10. 운영 오류는 빈 결과로 숨기지 않고 부팅 검증·명시적 실패·외부 관측으로 드러낸다.

## 계약

### 배송 상태

검사 결과인 `PASS / FAIL / NOT_RUN / BLOCKED / SKIPPED`와 섞지 않고 다음 상태를 별도로 사용한다.

- `NOT_APPLICABLE`: 문서·내부 도구처럼 운영 제품 배송과 무관하며 근거가 기록됨
- `LOCAL_ONLY`: 로컬 실행만 확인됨
- `PREVIEW_VERIFIED`: 격리된 미리보기 배포에서 확인됨
- `PRODUCTION_REACHABLE`: 운영 주소·인증·환경·DB 연결·배포 버전 확인됨
- `PRODUCTION_VERIFIED`: 운영에서 승인된 실제 데이터의 쓰기와 재조회가 확인됨
- `BUSINESS_USED`: 사용자가 운영 주소에서 실제 업무 한 건을 끝내고 영수증이 남음

상태는 순서대로만 올라간다. 낮은 상태를 높은 상태처럼 부르거나 미실행을 성공으로 접지 않는다.

## 인수 기준

- AC-1: 제품 표면을 새로 만들거나 교체할 때 시스템은 첫 작업 단위를 최소 운영 골격으로 정의해야 한다.
- AC-2: 제품 변경을 보고할 때 시스템은 검사 결과와 별도로 배송 상태를 명시해야 한다.
- AC-3: 배송 상태를 `PRODUCTION_REACHABLE` 이상으로 주장할 때 시스템은 운영 주소, 배포 버전, 인증 경계, 환경 설정, DB 연결과 상태 확인의 재현 가능한 증거를 가져야 한다.
- AC-4: 배송 상태를 `PRODUCTION_VERIFIED`로 주장할 때 시스템은 승인된 실제 데이터 쓰기와 독립 재조회 증거를 가져야 한다.
- AC-5: 배송 상태를 `BUSINESS_USED`로 주장할 때 시스템은 사용자 업무 한 건의 결과 영수증을 가져야 한다.
- AC-6: 운영 배포·운영 쓰기 권한이 없을 때 시스템은 `LOCAL_ONLY` 또는 `PREVIEW_VERIFIED`를 정직하게 보고하고 완료를 선언하지 않아야 한다.
- AC-7: 문서·내부 검사처럼 배포가 무관한 작업은 시스템이 근거와 함께 `NOT_APPLICABLE`로 분류해야 한다.
- AC-8: 새 제품 골격을 만들 때 시스템은 구현 전에 로그인, 승인된 실제 데이터 조회, 저장 후 새 세션 재조회의 운영 smoke를 실패하는 검증으로 먼저 고정해야 한다.
- AC-9: DB 스키마를 변경할 때 시스템은 저장소의 마이그레이션만 사용하고 운영 스키마와 마이그레이션 이력의 차이를 배포 전에 실패로 판정해야 한다.
- AC-10: 필수값·동일성·관계·허용 범위를 DB가 표현할 수 있을 때 시스템은 `NOT NULL / UNIQUE / FOREIGN KEY / CHECK` 상당 제약으로 강제해야 한다.
- AC-11: 동일 지표를 여러 화면이 사용할 때 시스템은 한 개의 버전 관리된 DB view/function 또는 동등한 단일 계산 authority에서 값을 제공해야 한다.
- AC-12: 필수 환경변수가 없을 때 시스템은 부팅 단계에서 실패해야 하며, 운영 예외를 빈 배열·null·성공 상태로 바꾸지 않고 비밀값 없는 외부 관측 신호를 남겨야 한다.

## counter-AC

- 빈 페이지 HTTP 200만으로 `PRODUCTION_VERIFIED`를 주장한다.
- fixture나 seed를 실제 업무 데이터라고 부른다.
- Preview 성공을 운영 성공으로 부른다.
- 배포 URL은 열리지만 인증 우회, 환경변수 누락, DB 쓰기 실패 또는 옛 SHA 실행을 놓친다.
- 모든 오타·문서·순수 내부 로직 변경에 운영 배포를 강제해 개발을 마비시킨다.
- 후보자 개인정보를 저장소, CI 로그 또는 공개 미리보기에 노출한다.
- 일반적인 원칙 문구를 모든 미래 운영 배포에 대한 포괄 승인으로 해석한다.
- 운영 검증이 구현과 같은 잘못된 가정을 복사해 실제 장애를 놓친다.
- Supabase 대시보드에서 손으로 스키마를 바꿔 저장소 마이그레이션과 운영 DB가 갈라진다.
- 앱 코드에서만 중복·필수값을 검사해 다른 입력 경로가 제약을 우회한다.
- 화면마다 같은 지표를 따로 계산해 서로 다른 숫자를 표시한다.
- 환경변수 누락이나 DB 오류를 빈 목록으로 바꿔 정상 화면처럼 보이게 한다.

## 영향 반경과 롤백

- 영향: 저장소 코딩 원칙, 기계 장부, 원칙 검사기, Codex·Claude strict 작업 순서와 완료 보고.
- 롤백: P25 장부와 strict의 production-first 블록을 함께 되돌리고 검사기의 기대 ID·개수를 P1~P24/34로 복구한다.
- 데이터 안전: 이번 변경은 운영 배포나 실제 후보자 DB 쓰기를 수행하지 않는다.

## 오너 실행 프롬프트

```text
$strict

이 기능은 구현부터 시작하지 말고 production-first로 진행하라.

먼저 이 기능이 제품 배송과 관련 있는지 분류하고 배송 상태를 선언하라.
제품 표면을 새로 만들거나 교체하는 작업이면 첫 작업 단위로 최소 운영 골격을 만든다.
최소 운영 골격은 운영 URL, 내 계정 인증, 환경변수 로딩, DB 연결, health check,
배포 SHA 표시, 한 명령 롤백을 포함해야 한다.

그 다음 가장 작은 실제 업무 한 건이 운영 경로를 끝까지 통과하도록 기능을 하나씩 얹어라.
Preview 성공을 운영 성공으로 부르지 말고, 실제 데이터 쓰기 뒤 독립 readback을 수행하라.
내가 운영 화면에서 업무 한 건을 끝낸 영수증이 없으면 BUSINESS_USED 또는 제품 완료를 선언하지 마라.

기능 코드보다 먼저 배포 후 smoke test를 만들어라. 최소 여정은 로그인, 승인된 실제 데이터 조회,
한 건 저장, 새 세션 또는 새로고침 뒤 재조회다. 구현과 같은 가정을 복사한 테스트는 금지한다.

DB 스키마는 저장소의 마이그레이션 파일로만 변경하고 운영 스키마 drift를 배포 전에 검사하라.
필수값·중복·관계·허용 범위는 가능한 한 DB 제약으로 강제하고, 타입은 DB 스키마에서 생성하라.
같은 지표 계산은 버전 관리되는 DB view/function 또는 동등한 단일 authority 한 곳에만 둬라.

필수 환경변수는 부팅 시 검증하고, 운영 오류를 빈 배열·null·성공 상태로 삼키지 마라.
비밀값과 개인정보를 제외한 오류가 자동으로 관측되게 하되 특정 벤더나 소요 시간을 가정하지 마라.

운영 배포·운영 쓰기는 내가 이번 요청에서 정확한 대상과 행동을 승인한 범위에서만 수행하고,
후보자 개인정보를 저장소·CI 로그·공개 Preview에 남기지 마라.

최종 보고에는 검사 결과와 별도로 다음 중 하나를 반드시 적어라:
NOT_APPLICABLE / LOCAL_ONLY / PREVIEW_VERIFIED / PRODUCTION_REACHABLE /
PRODUCTION_VERIFIED / BUSINESS_USED.
```
