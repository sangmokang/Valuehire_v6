## 결론

사람인·잡코리아는 디스코드에서 명령하면 평소에는 사람의 추가 클릭 없이 일을 시작하게 만드는 방향이 맞습니다. 다만 로그인이 풀리거나 보안 확인이 뜬 순간까지 사람 없이 밀어붙이면 계정과 고객 신뢰를 함께 위험에 빠뜨리므로, 그 세 경우에는 멈추고 사람을 부르는 구조가 필요합니다. LinkedIn은 허용 근거가 확인되기 전까지 사이트 안 작업을 사람이 합니다.

후보 장부는 이 컴퓨터 한 곳을 원본으로 두고, 수파베이스·클릭업·디스코드는 결과를 받아 보는 창구로만 두는 것이 맞습니다. 어느 창구가 잠시 고장 나도 서치 자체는 끝까지 진행돼야 합니다.

사람인·잡코리아의 자동 발송 실험은 가능성이 있지만, 85점이라는 숫자만으로 곧바로 하루 10건을 보내는 안에는 반대합니다. 먼저 “보낼 뻔한 메시지”를 사람이 검토해 사고율을 재고, 그 다음 하루 1건의 소량 시험을 거친 뒤 늘려야 합니다.

후보 기준은 사장님의 다섯 가지 원칙을 반영하되, 학교·이직 횟수·글쓰기 모양을 사람의 능력과 동일시하지 않도록 역할을 나눕니다. 학교와 이직 이력은 고객사와 포지션에 맞춘 조건으로 쓰고, 글의 구조는 적합도나 사실 신뢰도가 아니라 정보가 얼마나 검토하기 좋게 정리됐는지를 판단하는 데 씁니다.

이 문서는 대안 초안 작성과 문서 검증을 마쳤습니다. 제품 구현, 완전 무인 순회, 자동 발송, 클릭업 필드 추가는 아직 끝나지 않았으며 이 문서도 그렇게 주장하지 않습니다.

## 판단 근거

기존 기획의 큰 방향은 맞습니다. 고객 요청 접수부터 회사 조사, 채널 준비, 후보 수집, 검토, 결과 회수까지를 하나의 여정으로 연결하면 헤드헌터가 반복해서 하던 일을 크게 줄일 수 있습니다. 특히 디스코드에서 시작하고, 로컬 장부에 먼저 남기며, 결과를 여러 서비스로 나중에 내보내는 구조는 편의성과 복구 가능성을 함께 높입니다.

문제는 “사업 목표”, “현재 계약”, “실측으로 확인된 사실”, “아직 해보지 않은 제안”이 섞였다는 점입니다. Aside 브라우저의 진단 주소가 열리고 탭 목록이 보였다는 사실은 확인됐지만, 재부팅 뒤 자동 기동·후보 한 명 완주·사람 개입 시 양보·로그인 복구까지 확인된 것은 아닙니다. 따라서 이를 곧바로 “무인 운영 성공”이라고 부르면 구현자가 가장 위험한 시험을 건너뛸 수 있습니다.

자동 발송도 같은 문제입니다. 85점은 후보와 포지션이 잘 맞는지를 나타내는 수치일 뿐, 수신자·회사·포지션·문구가 정확하고 중복 발송이 없다는 보증이 아닙니다. 그래서 매칭 점수와 발송 안전성을 분리해 측정해야 합니다.

또한 최신 클린룸 검토 문서는 사람이 선택한 현재 탭만 자동화에 맡기는 구조이고 발송 버튼 자동 클릭을 금지합니다. 이 문서는 별도 작업 폴더에 있는 계약 후보이며 기본 브랜치의 정본은 아니지만, 오너가 채택 여부를 정하기 전까지 권한 확대의 안전 기준으로 취급합니다. 사장님의 최신 지시는 정상 상황에서 사람 클릭을 없애고 사람인·잡코리아의 제한적 자동 발송을 시험하는 것입니다. 최신 사업 지시를 따르려면 기존 문서를 없는 것으로 취급할 것이 아니라, 무엇을 왜 바꾸는지 별도 변경 기록으로 먼저 승인해야 합니다.

## 3. 정본과 충돌 처리 순서

1. `docs/sot/`의 확정 원칙이 코드와 검증 방식의 최상위 기준입니다.
2. 오너의 최신 사업 결정은 제품 목표를 정하지만, 기존 안전 계약과 충돌하면 별도 변경 기록을 거쳐야 합니다.
3. 클린룸 후속 문서는 최신 검토 계약 후보입니다. 현재 브라우저·로그인·저장 경계의 안전 기준으로 참고하되, 아직 기본 브랜치의 정본은 아니므로 오너 채택 여부와 버전을 먼저 명시해야 합니다.
4. 창립 지시서는 과거 사고와 사업 규칙의 근거입니다. 더 최신 계약과 충돌하는 구현 방식은 그대로 계승하지 않습니다.
5. 기존 두 기획서는 제안과 검토 자료이며, 그 자체가 제품 사실이나 정본은 아닙니다.

## 4. 결정 카드

### 결정 1 — 평소에는 사람 클릭 없이 시작하되, 인증 예외에는 사람을 부릅니다

> **무엇을** — 1차 대상인 사람인·잡코리아에서 디스코드의 정상 명령은 추가 클릭 없이 로컬 작업 큐에 들어가고, 상주 실행기가 전용 브라우저의 정확한 채널 탭을 확인한 뒤 시작합니다. 로그아웃·보안문자·2단계 인증에서는 즉시 멈추고 알립니다. LinkedIn은 허용 근거 확인 전까지 사이트 안의 전 과정을 사람이 수행합니다.
>
> **왜** — 원격 지휘의 편의성을 살리면서도 자동 로그인 재시도와 잘못된 탭 조작을 막을 수 있습니다.
>
> **버린 길** — 매번 확장 버튼을 누르는 방식은 핵심 편의성을 잃어 기각합니다. 반대로 어떤 예외에도 사람을 부르지 않는 완전 무인은 계정 잠금과 오조작을 피할 수 없어 기각합니다.
>
> **대가** — 현 클린룸 계약의 브라우저 장을 바꾸는 최고 위험 변경 기록이 먼저 필요합니다. 전용 브라우저가 꺼졌거나 인증이 풀리면 사람이 한 번 복구해야 합니다. 사람인·잡코리아도 사이트당 한 좌석이므로 전용 프로필 로그인과 기존 사람 세션이 서로 밀어내는지 별도 실증해야 합니다.
>
> **되돌리기** — 무인 연결을 끄면 기존의 사람 선택 탭 방식으로 돌아갈 수 있게 작업 큐·증거·채점과 브라우저 연결부를 분리합니다.

**권고 상태: 제안.** 1차 무인 연결 범위는 사람인·잡코리아입니다. 구현 착수 조건은 “사람인 후보 1명 열기→증거 저장→목록 복귀→사람 개입 시 양보→재개” 실증과 계약 변경 승인입니다.

### 결정 2 — SQLite를 유일한 원본으로 둡니다

> **무엇을** — SQLite(한 파일 안에 표와 거래 기록을 보관하는 로컬 데이터베이스)를 후보·증거·점수·검토·발송 의도의 유일한 원본으로 둡니다. Supabase(클라우드 데이터베이스), ClickUp, Discord는 나중에 결과를 받는 사본 또는 알림 창구입니다.
>
> **왜** — 외부 서비스 장애가 서치 실패가 되는 것을 막고, 어느 곳의 정보가 맞는지 다투는 상황을 없앱니다.
>
> **버린 길** — SQLite와 Supabase에 동시에 원본을 쓰는 방식은 둘 중 하나만 성공했을 때 상태가 갈라져 기각합니다.
>
> **대가** — 다른 서비스에서 내용을 고쳐도 로컬 원본에는 자동 반영되지 않습니다. 필요한 피드백은 명시적인 회수 작업으로만 가져와야 합니다.
>
> **되돌리기** — 장차 클라우드를 원본으로 바꾸려면 별도 데이터 이전 계획과 양방향 충돌 규칙을 새로 승인합니다.

**권고 상태: 제안.** 현재 저장 계약 후보와도 일치합니다.

### 결정 3 — 자동 발송은 관찰, 소량 시험, 제한 운영의 세 단계로 엽니다

> **무엇을** — 사람인·잡코리아에서만 자동 발송 가능성을 시험하되, 처음에는 실제로 보내지 않고 “보낼 뻔한 메시지”를 만들어 사람이 검토합니다. 기준을 통과한 뒤 하루 채널당 1건, 그 다음 최대 5건으로 늘립니다.
>
> **왜** — 매칭 점수와 발송 정확도는 다른 문제입니다. 실제 수신자·회사·포지션·문구·중복 여부를 따로 재야 합니다.
>
> **버린 길** — 85점 이상이면 바로 하루 10건을 보내는 안은 오발송 데이터가 없는 상태에서 피해가 먼저 발생하므로 기각합니다. 영구 수동 발송도 절감 효과를 검증할 기회를 잃어 기각합니다.
>
> **대가** — 자동 발송까지 시간이 더 걸리고 초기에 사람 검토가 남습니다.
>
> **되돌리기** — 한 번에 끄는 중단 스위치, 채널별 상한, 발송 전 의도 기록, 발송 후 화면 재확인을 둡니다. 중대한 오류 1건이면 즉시 관찰 단계로 돌아갑니다.

**권고 상태: 현재 금지.** 단계형 예외는 제안이며, 기존 발송 금지 계약을 고치기 전에는 관찰 단계까지만 허용합니다.

### 결정 4 — v1~v5는 실행·복사·운영 의존을 모두 금지합니다

> **무엇을** — 과거 버전의 코드, 실행 파일, 함수 모양, 화면 선택 규칙, 운영 스킬을 v6가 불러 쓰지 않습니다. 과거 사고 목록은 새 시험 문제로만 사용합니다.
>
> **왜** — 과거 구조의 숨은 결함과 운영 전제가 새 제품으로 들어오는 것을 막기 위해서입니다.
>
> **버린 길** — 코드만 새로 쓰고 v5 운영 스킬을 임시로 이어 쓰는 안은 “의존 0”과 모순되므로 기각합니다.
>
> **대가** — 다섯 정거장을 새로 만들어야 하므로 단기 개발량이 늘어납니다.
>
> **되돌리기** — 되돌리지 않습니다. 사업 연속성이 필요하면 v5를 별도 운영할 수 있지만 v6 실행 경로에는 연결하지 않습니다.

**권고 상태: 제안.** 현재 1단계 클린룸 경계 검사는 경로·불러오기·실행 참조 일부만 막으므로, “완전히 기계로 증명됐다”고 표현하지 않습니다.

### 결정 5 — LinkedIn Recruiter는 프로젝트 준비와 후보 순회를 분리합니다

> **무엇을** — ClickUp에 포지션이 생기면 LinkedIn Recruiter(링크드인의 유료 인재 검색 도구)에 포지션용 프로젝트와 기본 필터를 준비합니다. 서치 때는 기본 필터를 먼저 돌고, 결과가 0명이라는 증거가 있을 때만 키워드 조합을 다음 버전으로 바꿉니다.
>
> **왜** — 프로젝트 준비와 후보 순회를 한 동작으로 섞으면 실패 원인과 재실행 기준을 알 수 없습니다.
>
> **버린 길** — 매번 검색 화면에서 처음부터 필터를 새로 만드는 방식은 설정 잔재와 자동완성 실패를 반복하므로 기각합니다.
>
> **대가** — 프로젝트 번호, 필터 버전, 적용된 조건 화면을 별도 영수증으로 남겨야 합니다. LinkedIn 정책과 계약상 허용 범위가 확인되기 전에는 실제 자동 순회를 켤 수 없습니다. 과거 자동화 전용 프로필이 봇 차단에 걸린 기록이 있어 프로필 전략도 별도로 다시 실증해야 합니다.
>
> **되돌리기** — 자동 순회를 끄고 프로젝트·검색식 준비 자료만 사람이 사용하는 방식으로 낮출 수 있습니다.

**권고 상태: 제안.** 자동 순회는 미확인이며, LinkedIn은 자동 수집 도구를 제한한다고 공식 안내하므로 라이브 사용 전 계약·계정 권한 검토가 필요합니다.

### 결정 6 — 파일 상한은 현재 600줄을 따르고, 500줄은 새 변경으로 따로 제안합니다

> **무엇을** — 현재 확정된 절대 상한은 파일 600줄, 함수 100줄입니다. 새 제품은 파일 300줄 안팎을 목표로 하고, 500줄을 새 절대 상한으로 바꾸려면 정본과 서버 검사를 같은 변경에서 고칩니다.
>
> **왜** — 존재하지 않는 검사를 “이미 강제된다”고 쓰지 않기 위해서입니다.
>
> **버린 길** — 문서에 500줄이라고만 적는 안과 로컬 검사만 추가하는 안은 서버에서 우회되므로 기각합니다.
>
> **대가** — 500줄 확정 전에는 501~600줄 파일도 현 정본상 합격할 수 있습니다.
>
> **되돌리기** — 새 500줄 검사가 과도하면 근거와 만료일을 가진 예외 또는 기존 600줄 기준으로 복귀합니다.

**권고 상태: 결정 필요.** 이 대안 문서는 현재 정본 600줄을 사실로 기록하고, 500줄은 구현 단계의 별도 결정으로 남깁니다.

### 결정 7 — 후보 기준은 적합도, 접촉 우선순위, 정보 완성도로 나눕니다

> **무엇을** — 학교·경력·필수 기술은 포지션 적합도에, 이직 의사 공개와 현 직장 재직기간은 접촉 우선순위에, 구조적인 글쓰기는 정보 완성도에 반영합니다. 프리랜서 제외와 짧은 이직 즉시 탈락은 포지션별 승인 조건으로 둡니다.
>
> **왜** — “서울권 대학을 중요하게”, “이직이 잦으면 크게 감점”, “2년 이상 위주”라는 사장님 의도를 살리면서도 이를 임의의 전체 후보 탈락 규칙으로 과장하지 않기 위해서입니다.
>
> **버린 길** — 학교 목록·12개월·24개월을 모든 포지션의 고정 탈락선으로 박는 안은 고객사 요구와 예외 경력을 무시하므로 기각합니다. 글을 잘 썼다는 이유로 사실 신뢰도를 올리는 안도 기각합니다.
>
> **대가** — 포지션을 시작할 때 학교 범위, 짧은 이직 기준, 프리랜서 범위를 한 번 더 정해야 합니다. 기준이 없는 포지션은 자동 서치를 시작할 수 없습니다.
>
> **되돌리기** — 점수 규칙 버전을 보존해 이전 규칙으로 재계산할 수 있게 하고, 채택률·회신률·면접률이 나빠지면 가중치를 원복합니다.

**권고 상태: 제안.** 포지션별 결정이 필요하며, 학교 선호는 고객사 근거와 필요 시 공정성·법률 검토를 남기고 사용합니다.

## 5. 전체 여정

**상태: 제안.** 네 등록 채널의 정확한 목록과 LinkedIn 허용 범위가 결정되기 전에는 운영 확정이 아닙니다.

~~~text
[고객 메일·로컬 접수]
        ↓
[포지션 명세 확정] → [회사 근거 조사] → [채널별 공고·검색 준비 묶음]
        ↓                                      ↓
[ClickUp 포지션 연결]           [LinkedIn Recruiter 프로젝트·기본 필터 준비]
        ↓                                      ↓
[네 채널 실제 등록 → 각 채널에서 등록 결과 다시 확인]
        ↓
[Discord 명령] → [SQLite 작업 큐] → [정확한 채널 탭 사전 확인]
                                                ↓
                               [기본 필터 순회 → 0명 증거 → 다음 검색식]
                                                ↓
                               [후보 증거 → 중복 차단 → 규칙 점수]
                                                ↓
                               [헤드헌터 채택·기각·사유]
                                                ↓
                       [ClickUp·Discord·Supabase로 순차 내보내기]
                                                ↓
                               [발송 초안·관찰 → 승인된 소량 시험]
~~~

→ 운영 여정에서는 네 채널 등록과 등록 결과 확인이 서치보다 먼저입니다. 디스코드 명령부터 후보 검토까지의 클릭 0회 목표는 1차로 사람인·잡코리아에만 적용하며, LinkedIn은 허용 근거 확인 전까지 로컬 준비만 자동이고 사이트 안 작업은 사람이 합니다. ClickUp·Discord·Supabase 중 하나가 꺼져도 로컬 수집 결과는 사라지지 않습니다.

Discord가 고장 났을 때는 컴퓨터의 로컬 명령창이 같은 형식의 작업 요청을 만들 수 있어야 합니다. 두 진입로는 같은 중복 열쇠와 만료 규칙을 사용하며, Discord 복구 뒤 같은 요청이 두 번 실행되지 않아야 합니다.

## 6. 포지션 명세

**상태: 제안.** 실제 학교 목록·짧은 이직·프리랜서 범위는 포지션별 결정이 필요합니다.

포지션마다 아래 내용을 먼저 확정해야 서치가 시작됩니다. 빠진 항목이 있으면 추측해 채우지 않고 `결정 필요`로 멈춥니다.

| 묶음 | 필수 내용 |
|---|---|
| 기본 정보 | 고객사, 포지션명, 담당자, 원문 직무기술서, 공식 회사 주소 |
| 필수 조건 | 경력 범위, 직무·산업, 근무지, 언어, 자격, 고용 형태 |
| 학교 기준 | “서울권”의 정확한 학교 목록, 사용 이유, 높은 가중치 또는 필수 여부 |
| 이직 기준 | 짧은 재직의 기준 개월 수, 감점 폭, 회사 합병·사명 변경·계약직 예외 |
| 프리랜서 기준 | 현재 프리랜서만 제외인지, 과거 경험도 제외인지 |
| 이직 의사 | Open to Work 우선, Non-Open to Work는 현 직장 24개월 이상을 우선 정렬하되 자동 제외하지 않음 |
| 검색 계획 | 채널별 기본 필터, 키워드 조합 순서, 종료 조건, 재순회 주기 |
| 접촉 정책 | 허용 채널, 중복 금지 기간, 발송 가능 여부, 하루 상한 |

→ 기존 기획은 “인서울”과 “서울권”을 같은 말처럼 썼습니다. 이 문서는 목록이 확정되기 전에는 둘을 같다고 보지 않습니다. 이직 “감점”과 “즉시 제외”도 별도 선택으로 둡니다.

## 7. 후보 판정 기준

**상태: 제안.** 사용자의 다섯 원칙을 구현 가능한 계약으로 번역한 것이며 점수·탈락선은 아직 승인되지 않았습니다.

창립 지시서는 프리랜서 전면 제외, 12개월 미만 재직 2회 이상 즉시 제외, 일부 채널의 전문대 기준을 기본값으로 적었습니다. 이 대안은 프리랜서와 짧은 이직을 포지션별 결정으로 바꾸고, 전문대 일괄 기준은 사용자의 최신 “서울권 대학을 중요하게” 지시와 같은 뜻으로 보지 않아 자동 계승하지 않습니다. 즉 기존 확정값을 조용히 유지하는 것이 아니라 **바꾸자는 제안**이며 오너 승인이 필요합니다.

후보 판정은 세 층으로 나눕니다. 언어 모델은 근거 문장을 뽑을 수 있지만 숫자를 직접 쓰지 않습니다. 최종 숫자는 버전이 남는 코드 규칙이 계산합니다.

### 7-1. 즉시 제외

- 포지션 명세에서 프리랜서를 명시적으로 제외했고, 후보가 현재 프리랜서임이 근거로 확인됨
- 법적·계약상 필수 자격이 없음
- 중복 접촉 금지 기간 안에 같은 후보·같은 포지션·같은 채널 기록이 있음
- 필수 증거가 없거나 프로필 주소가 원본과 다름

### 7-2. 적합도 점수

- 포지션·산업·업무 경험
- 필수 기술과 성과
- 고객이 승인한 학교 선호: **높은 가중치는 가능하지만 기본 하드 제외는 아님**
- 재직 안정성: 회사 단위로 묶어 계산하고 합병·사명 변경·승진·내부 이동은 이직으로 세지 않음
- 이직 의사 상태는 `공개 / 비공개 / 확인 불가` 세 가지로 기록

### 7-3. 접촉 우선순위

- Open to Work(이직 의사를 공개한 상태) 후보를 우선 정렬
- Non-Open to Work(이직 의사를 공개하지 않은 상태)는 현재 회사 24개월 이상인 후보를 우선 정렬
- 표시가 없는 채널은 `확인 불가`로 두며 비공개로 추정하지 않음
- 이 값은 적합도 점수에 더하거나 빼지 않음

### 7-4. 정보 완성도

- 역할·기간·성과가 구조적으로 정리돼 있는가
- 빈칸·복사 문구·과장 표현이 많은가
- 서로 다른 출처의 사실이 일치하는지는 별도 증거 대조로 판단

구조적인 글쓰기는 “일을 잘한다”거나 “사실을 더 믿을 수 있다”는 점수에 직접 더하지 않습니다. 정보가 검토하기 좋게 정리됐는지와 추가 확인이 얼마나 필요한지를 표시합니다. 이 구분이 없으면 글을 잘 쓰는 사람을 실제 적합도가 높거나 더 정직한 사람으로 오판할 수 있습니다.

## 8. 브라우저 실행 계약 제안

**상태: 결정 필요.** 정상 상황의 사람 클릭 0회는 사업 목표이고, 실제 연결 방식은 계약 변경과 라이브 한 명 실증 전까지 구현 권한이 없습니다.

### 정상 흐름

1. 사람인·잡코리아는 채널별 전용 브라우저와 전용 프로필을 제안합니다. LinkedIn은 과거 자동화 전용 프로필이 봇 차단에 걸린 기록이 있어 같은 전략을 전제하지 않습니다.
2. SQLite에서 채널당 한 작업만 얻는 사용권을 잡습니다. 사용권에는 만료 시각과 이전 실행의 명령을 무효화하는 증가 번호를 둡니다.
3. 작업 시작 전 허용된 도메인, 로그인 상태, 포지션 또는 프로젝트 번호, 목표 탭이 정확히 1개인지 확인합니다.
4. 하나라도 맞지 않으면 시작하지 않습니다.
5. 사람이 같은 채용사이트를 직접 사용하기 시작하면 자동화 권한을 즉시 회수합니다.
6. 사람이 손을 뗀 뒤 같은 작업과 같은 탭임을 다시 확인하고 재개합니다.
7. 자동화는 사람이 로그인한 탭을 닫거나 브라우저를 종료하지 않습니다.

### 사람이 필요한 예외

- 로그인 만료 또는 계정 선택 화면
- 보안문자
- 2단계 인증
- LinkedIn 좌석 또는 세션 충돌
- 사람인·잡코리아의 전용 프로필과 기존 사람 세션 충돌
- 목표 탭이 0개 또는 2개 이상
- 예상한 화면 구조와 실제 화면이 다름

### Aside 실증의 올바른 해석

현재 확인된 것은 Aside가 로컬 진단 주소를 열고 페이지 탭을 노출한다는 사실입니다. 이것은 기술 가능성의 첫 관문 통과입니다. 다음 항목은 별도 시험 전까지 미확인입니다.

- 컴퓨터 재부팅 뒤 자동 기동
- 실제 프로필의 세션 장기 유지
- 사람인·잡코리아 각각 후보 한 명 완주, LinkedIn Recruiter는 허용 근거 확인 시 별도 완주
- 목표 탭 오선택 0건
- 사람 개입 감지 뒤 브라우저 명령 0건
- 인증 복구 후 같은 작업 자동 재개
- 브라우저 업데이트 뒤 호환성

Chrome의 공식 안내에 따르면 최신 Chrome은 기본 사용자 자료 폴더에 진단 포트를 붙이는 방식을 제한합니다. 따라서 “Aside가 안 되면 같은 실프로필 Chrome으로 바꾸면 된다”를 자동 대안으로 두지 않습니다. Chrome을 쓰려면 별도 사용자 자료 폴더와 세션 운영 방식을 다시 실증해야 합니다.

사람인·잡코리아에서 기본 필터를 적용하고 결과가 없을 때 검색어를 바꾸는 기능은 기존 클린룸 범위 밖입니다. 이 기능은 무인 목표에 필요하지만 자동 계승하지 않고, P0의 별도 범위 변경으로 승인합니다. 입력 전 기존 필터 제거, 입력 뒤 실제 적용 조건 재확인, 결과 0명 증거가 없으면 다음 검색식으로 이동 금지를 함께 계약합니다. LinkedIn 안의 검색어·필터 적용은 허용 근거 전까지 사람이 합니다.

## 9. LinkedIn Recruiter 계약

**상태: 제안.** 로컬 준비표는 만들 수 있지만 LinkedIn 안에서의 프로젝트 생성·필터 적용·후보 순회 자동화는 허용 근거 확인 전까지 현재 금지입니다.

### 등록 단계

1. 로컬 자동화가 ClickUp 포지션 참조, 제안 프로젝트명, 기본 필터 준비표를 만듭니다.
2. 허용 근거 확인 전에는 사람이 LinkedIn Recruiter에서 프로젝트를 만들고 필터를 적용합니다.
3. 허용 근거가 확인된 뒤에만 자동 적용 실험을 별도 승인합니다.
4. 허용 전에는 사람이, 허용 뒤에는 승인된 실행기가 실제 프로젝트 번호, 필터 버전, 적용 시각, 증거 위치를 SQLite에 기록합니다.

### 서치 단계

허용 근거 전에는 아래 네 단계를 사람이 수행합니다. 허용 뒤에는 별도 승인된 실행기만 수행할 수 있습니다.

1. 기본 필터 결과를 끝까지 순회합니다.
2. 결과가 0명 또는 신규 후보 0명이라는 증거가 있을 때만 다음 키워드 조합으로 이동합니다.
3. 키워드 변경 전 기존 필터 잔재를 지우고, 변경 후 실제 적용된 조건을 다시 읽습니다.
4. 같은 프로젝트·필터 버전·후보 조합은 다시 수집하지 않습니다.

### 정책 중단선

LinkedIn의 공식 도움말은 제삼자 프로그램이 프로필을 수집하거나 활동을 자동화하는 것을 금지한다고 안내합니다. 계약·계정 권한상 허용 근거가 확인되기 전에는 로컬 프로젝트명·검색식·필터 준비표까지만 만들고, LinkedIn 안에서 프로젝트를 만들거나 필터를 적용하거나 후보를 순회하는 자동화는 모두 끕니다. 이 문서는 법률 판단을 대신하지 않으며, 실제 운영 전 사업 오너의 서면 위험 수용과 필요 시 법률 검토가 필요합니다.

## 10. 저장과 외부 내보내기

**상태: 제안.** SQLite 원본 원칙과 표 구조를 권고하지만 보존기간·외부 필드는 미확인입니다. 개인정보 보관 계약이 승인되고 시험되기 전에는 실제 후보 화면을 저장하지 않습니다.

SQLite에는 최소한 다음 기록이 있어야 합니다.

| 기록 | 역할 |
|---|---|
| position | 확정된 포지션 명세와 버전 |
| search_plan | 채널별 프로젝트·필터·키워드 순서 |
| run | 명령, 시작·종료·중단 사유 |
| browser_lease | 채널별 단일 사용권, 만료 시각, 이전 권한을 무효화하는 증가 번호 |
| evidence | 후보 원문·화면 증거의 위치와 내용 지문 |
| candidate | 정규화된 후보 식별 정보 |
| assessment | 규칙 버전과 근거별 점수 |
| review_decision | 헤드헌터 채택·기각·보류와 사유 |
| contact_intent | 발송 전 대상·채널·문구·중복 검사 결과 |
| contact_receipt | 실제 발송 뒤 화면 재확인 결과 |
| outbox | 외부 서비스로 내보낼 대기 기록과 재시도 상태 |

→ `contact_intent`는 “보내려고 했다”, `contact_receipt`는 “화면에서 실제 결과를 다시 확인했다”는 서로 다른 기록입니다. 둘을 하나로 합치면 클릭했지만 실패한 발송을 성공으로 오판할 수 있습니다.

실제 후보 화면을 처음 저장하기 전에 다음 개인정보 계약을 먼저 통과해야 합니다.

- 저장 위치는 Git 밖의 암호화된 전용 폴더
- 폴더는 실행 계정만 접근, 파일은 실행 계정만 읽고 쓰기
- 채널별 보존기간과 삭제 시각
- 만료 파일을 지우는 예약 작업
- 삭제한 파일 수·시각·실패 수를 남기는 영수증
- 저장소에는 후보 원문이 아니라 위치 참조와 내용 지문만 기록

이 조건 중 하나라도 시험되지 않으면 후보 원문·화면 캡처 단계는 `NOT_RUN`, 즉 시험하지 못한 상태로 멈춥니다.

외부 내보내기는 다음 순서를 따릅니다.

1. 로컬 거래 완료
2. 내보낼 필드 허용 목록 검사
3. 외부 서비스별 고유 중복 열쇠 생성
4. 한 서비스씩 전송
5. 외부 화면 또는 응답을 다시 읽어 확인
6. 실패는 해당 외부 서비스의 로컬 대기열에 남기고, 다른 서비스와 로컬 서치 완료 상태는 되돌리지 않음

스크린샷 원본, 로그인 정보, 보안 토큰은 Supabase·ClickUp·Discord로 내보내지 않습니다. 보존기간과 삭제 영수증은 Supabase 실제 표와 권한을 확인한 뒤 계약에 넣습니다.

## 11. ClickUp 피드백

**상태: 미확인.** 현재 필드 존재 여부는 미확인이고, SQLite를 원본으로 두는 피드백 구조는 제안입니다.

채택·기각 칸이 현재 ClickUp에 없다는 주장은 원본 조회 증거가 없으므로 미확인입니다. 구현 전에 두 리스트와 예시 태스크를 읽기 전용으로 조회하고 다음을 저장소 밖의 접근 제한 증거로 남깁니다.

- 리스트 번호와 이름
- 상태·사용자 정의 필드·태그·하위 작업 구조
- 예시 태스크의 필드 값
- 조회 시각과 응답 내용 지문

권고 구조는 SQLite의 `review_decision`이 원본이고 ClickUp은 입력 화면입니다. ClickUp에 새 필드를 만든다면 `채택 / 기각 / 보류`, 기각 사유, 검토자, 검토 시각을 받으며, 동기화 작업이 이를 SQLite로 회수합니다. ClickUp 필드가 삭제돼도 기존 결정 기록이 사라지지 않아야 합니다.

## 12. 자동 발송 실험 계약

**상태: 현재 금지.** 관찰 설계는 제안이며, 아래 표본 수는 안전을 증명하는 확정 숫자가 아니라 첫 관찰을 위한 권고값입니다.

### 단계 0 — 관찰만, 실제 발송 없음

- 대상: 사람인·잡코리아
- 조건: 매칭 점수 85점 이상은 **검토 대상 자격**일 뿐 발송 허가가 아님
- 산출물: 수신 후보, 포지션, 회사, 문구, 중복 검사, “보낼 뻔한 시각”
- 사람 검토: 그대로 승인 / 수정 후 승인 / 기각 / 잘못된 대상
- 최소 표본 권고: 채널별 50건 이상, 총 100건 이상, 30일 이상
- 통과 권고: 잘못된 후보·회사·포지션 0건, 중복 0건, 필수 수정률 5% 이하
- 85점 미만 후보도 일부 무작위 검토해 놓친 좋은 후보 비율을 측정

### 단계 1 — 하루 채널당 1건 소량 시험

- 별도 발송 예외 계약과 오너 승인 뒤 시작
- 시작 전 중단 스위치 작동 시험
- 총 20건을 초과하지 않음
- 발송 직후 화면 재확인과 Discord 알림
- 중대한 오류 1건, 중복 1건, 계정 경고 1건이면 즉시 중단
- 20건 무사고는 희귀 사고가 없다는 증명이 아니라 다음 검토를 열 수 있는 최소 관찰 자료일 뿐임

### 단계 2 — 하루 채널당 최대 5건

- 단계 1의 20건에서 중대한 오류 0건
- 후보의 부정 회신·수신 거부·민원과 헤드헌터 평가를 함께 검토
- 매주 오너 보고 뒤 유지 또는 축소
- 하루 10건은 최소 100건의 제한 운영 자료가 쌓인 뒤 새 결정

단계별 표본 수는 오너가 허용할 최대 사고율과 필요한 확신 수준을 정한 뒤 다시 계산합니다. 위 권고 수치는 그 계산을 대신하지 않습니다.

LinkedIn 인메일과 Gmail 메일은 이 실험에서 제외하고 초안까지만 만듭니다.

## 13. 단계별 구축 순서

**상태: 제안.** 아래 P는 구축 단계 번호이며, 단계별 시작·종료 조건이 승인되기 전에는 일정 확정이 아닙니다.

| 단계 | 결과 | 시작 조건 | 끝났다고 부르는 조건 |
|---|---|---|---|
| P0 계약 정리 | 브라우저·검색어·필터·발송·LinkedIn·개인정보 변경 기록 | 이 대안안 검토 | 오너·날짜·되돌리기 조건 포함 승인 |
| P1 저장소 상태 정리 | 3단계 포털 상수 작업의 검증 판정 채택 여부 확정 | P0와 독립 가능 | 기본 브랜치 포함 커밋과 실제 검사 결과 |
| P2 접수·회사 조사 | Gmail 또는 로컬 입력→포지션 명세→회사 근거 카드 | 입력·출력 계약 승인 | 같은 입력 재실행 중복 0, 근거 없는 회사 사실 0 |
| P3 네 채널 준비 | 채널별 공고 본문·검색식·필터 준비표 | 네 채널의 정확한 목록과 글자 수 확인 | 채널별 결과 4벌과 원문 추적 가능 |
| P4 개인정보 보관 | 암호화 저장·권한·보존기간·삭제 작업·삭제 영수증 | P0 개인정보 계약 | 만료 표본 삭제와 실패 영수증 시험 통과 |
| P5 네 채널 등록 | 포지션을 각 채널에 등록하고 결과를 다시 읽음 | P3, 채널별 등록 권한과 계약 | 채널별 라이브 1건, 잘못된 위치 등록 0; LinkedIn 사이트 작업은 허용 근거 전 사람 수행 |
| P6 사람인 1명 완주 | 정확한 탭→후보→증거→복귀 | 브라우저 계약·P4·P5 통과 | 라이브 1명, 증거 누락 0, 창 닫기 0 |
| P7 잡코리아 1명 완주 | P6와 같은 계약 | P6 통과 | 라이브 1명과 채널별 화면 계약 |
| P8 채점·검토 | 후보 근거와 헤드헌터 결정 | P6 또는 P7 | 규칙 재계산 일치, 근거 없는 점수 0 |
| P9 외부 내보내기 | ClickUp→Discord→Supabase 순차 연결 | 실제 스키마 확인 | 각 서비스 꺼짐 시험과 중복 0 |
| P10 LinkedIn 준비 | 로컬 프로젝트명·필터·검색식 준비표 | 정책·계정 검토 | 로컬 준비표 1건; 실제 LinkedIn 조작은 사람 수행 |
| P11 사람인·잡코리아 무인 정상 흐름 | Discord 명령 뒤 정상 상황 클릭 0회 | P6~P9 핵심 관문 | 정상 세션 10회, 오선택·미기록 0, 채널당 동시 실행 1개 이하 |
| P12 독립 감시 | 명령 서비스와 다른 실패 영역에서 하루 결과 감시 | P11 | 24시간 처리 0건 또는 영수증 누락 자동 알림 실증 |
| P13 발송 관찰 | 실제 발송 없는 100건 평가 | P8·P9 | 단계 0 권고 기준과 놓친 후보 검토 완료 |
| P14 소량 발송 | 하루 1건 제한 시험 | 별도 예외 계약과 표본 수 재계산 | 권고 20건 검토, 중대한 오류 0; 자동 확대 금지 |

→ 가장 먼저 증명할 것은 “브라우저에 붙을 수 있다”가 아니라 “정확한 후보 한 명을 안전하게 끝까지 처리한다”입니다. 자동 발송은 데이터가 쌓이는 마지막 단계입니다.

## 14. 공통 중단 조건

**상태: 제안.** 실제 화면 계약과 외부 서비스 응답을 확인한 뒤 채널별 조건을 더 좁혀야 합니다.

다음 중 하나가 발생하면 재시도하지 않고 작업을 멈춥니다.

- 보안문자·2단계 인증·계정 잠금 경고
- LinkedIn 세션 충돌
- 허용 도메인과 현재 주소 불일치
- 목표 탭이 없거나 둘 이상
- 포지션·프로젝트 번호 불일치
- 화면 구조 판정 불가
- 후보 증거 저장 실패
- 중복 후보 또는 중복 접촉 가능성
- 사람이 같은 채용사이트를 직접 사용 중
- 외부 내보내기 재확인 실패 — 해당 외부 연결만 중단하고 로컬 서치 완료는 유지
- 발송 중단 스위치 상태를 확인할 수 없음

“검색 결과 0명”은 성공도 실패도 아닙니다. 적용된 필터와 끝까지 순회한 증거가 있을 때만 정상적인 0명 결과로 기록합니다.

## 15. 구현 인수 기준

**상태: 제안.** 정본 원칙을 요약했으며, 실제 검사 명령은 각 단계 작업에서 만들고 서버 검사에 연결해야 합니다.

이 절의 명령은 아직 만들지 않은 검사 이름을 꾸며 쓰지 않습니다. 각 단계의 첫 작업은 실패하는 시험과 실제 검사 명령을 추가하고, 그 명령을 `docs/sot/verification-commands.md`와 서버 검사 양쪽에 연결하는 것입니다.

1. 모든 판정은 `PASS / FAIL / NOT_RUN`, 즉 합격·불합격·시험하지 못함의 세 상태를 냅니다. 시험할 대상이 0개면 `NOT_RUN`이고, 하나라도 `NOT_RUN`이면 전체 완료나 `PASS`로 판정할 수 없습니다.
2. 외부 효과는 실행 전 의도 기록, 실행 후 재확인, 고유 중복 열쇠를 모두 가져야 합니다.
3. 브라우저 명령은 사람 개입 신호 뒤 구조적으로 호출할 수 없어야 합니다.
4. 로그인 정보 입력·읽기 기능은 코어 제품에 넣지 않습니다.
5. 후보 원문·화면 증거가 없으면 점수·등록·발송 의도를 만들 수 없습니다.
6. v1~v5 경로·불러오기·실행 참조 검사를 유지하고, 별도 유사도 검사는 복사 탐지의 보조 수단으로만 씁니다.
7. 파일은 현 정본의 600줄 절대 상한과 함수 100줄 절대 상한을 지킵니다. 500줄 변경이 승인되면 정본과 서버 검사를 함께 바꿉니다.
8. 외부 사이트를 건드리는 단계는 실제 한 건 증거 없이는 완료가 아닙니다.
