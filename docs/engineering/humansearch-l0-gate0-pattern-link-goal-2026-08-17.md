# HumanSearch L0 시작 검사 연결 수리 목표 (2026-08-17)

## 1층 — 결론

새 작업 공간을 만들면 시작 검사에 필요한 로컬 규칙이 따라오지 않아 구현을 시작할 수 없습니다.
이미 있는 안전한 연결 기능을 실행 순서에 넣고, 연결이 실제로 맞는지 다시 확인한 뒤에만 검사를
시작하도록 수리합니다.

사장님이 지금 결정하실 것은 없습니다. 실제 채용 사이트, 로그인, 후보자 정보, 세 변경 요청의 합치기,
제품 분류기 구현은 이번 수리에서 하지 않습니다.

## 2층 — 판단 근거

검사 규칙에는 저장소에 함께 넣을 수 없는 실제 값이 포함되므로 새 작업 공간에 복사하거나 변경 기록에
넣으면 안 됩니다. 저장소에는 이미 기본 작업 공간의 로컬 규칙을 새 작업 공간에서 가리키게 하는 기능이
있습니다. 문제는 HumanSearch 실행 지시서가 새 작업 공간을 만든 뒤 이 기능을 실행하지 않고 곧바로
시작 검사를 부른다는 점입니다.

검사를 약하게 만들어 로컬 규칙 없이도 통과시키는 길은 버립니다. 실제 값을 복사하는 길도 유출 위험과
중복 관리 때문에 버립니다. 기존 연결 기능을 호출하고, 연결 대상이 기본 작업 공간의 파일과 정확히
같은지, 변경 기록에 포함되지 않는지, 빈 파일이 아닌지를 다시 읽어 확인하는 길을 택합니다.

이 판단이 틀리면 두 방향으로 깨집니다. 연결 확인이 느슨하면 다른 파일을 검사 규칙으로 오인할 수 있고,
지시가 과도하면 정상적인 새 작업 공간도 계속 시작하지 못합니다. 따라서 기존 연결 기능은 재사용하되
실패를 통과시키지 않는 확인 절차를 바로 뒤에 둡니다.

### 결정 카드

**무엇을** — 새 작업 공간을 만든 뒤 기존 로컬 규칙 연결기를 실행하고, 연결 대상·내용 존재·변경 기록
제외를 확인한 다음 시작 검사를 실행합니다.
**왜** — 연결 기능은 이미 구현돼 있지만 HumanSearch 지시서의 실제 실행 순서에서 호출되지 않아 시작
검사가 실행 불가로 끝나기 때문입니다.
**버린 길** — 검사를 약하게 만드는 길과 실제 규칙을 복사하는 길을 버렸습니다. 전자는 검출력을
낮추고, 후자는 민감한 값을 불필요하게 복제합니다.
**대가** — 새 작업 공간을 시작할 때 연결 확인 단계가 추가되고, 기본 작업 공간에 로컬 규칙이 없으면
계속 중단됩니다. 이는 검사 결과를 꾸며 통과시키지 않기 위해 감수하는 제한입니다.
**되돌리기** — 이번 지시서 변경만 되돌리면 됩니다. 연결은 변경 기록 밖의 로컬 파일 하나이므로 잘못된
연결은 해당 작업 공간에서 제거하고 기존 지시서 상태로 돌아갈 수 있습니다.

### 2. 근본 원인

저장소의 연결 기능과 HumanSearch 실행 지시서가 따로 존재하며, 지시서의 새 작업 공간 생성 경로가 연결
기능을 호출하지 않습니다. “기능이 있다”는 사실을 “실제 실행 경로에 연결됐다”로 잘못 본 것이
근본 원인입니다.

### 3. 단일 인수 기준

**AC-L0-G0-LINK.** HumanSearch 실행 지시서가 새 작업 공간을 생성하거나 기존 작업 공간을 재개하면,
기본 작업 공간의 로컬 비밀 검사 규칙을 기존 설치기로 연결하고 다음 네 조건을 모두 직접 확인한 뒤에만
시작 검사를 실행해야 합니다.

1. 연결 원본은 기본 작업 공간의 `.secret-patterns`와 정확히 같습니다.
2. 연결된 파일은 존재하고 비어 있지 않습니다.
3. `.secret-patterns`는 Git 변경 기록에 포함되지 않습니다.
4. `bash scripts/session-status.sh`의 실패 수는 정확히 0입니다.

다음 중 하나라도 가능하면 가짜 합격입니다.

- 설치기를 호출하지 않고 시작 검사부터 실행합니다.
- `.secret-patterns.default`만으로 로컬 전용 검사를 통과한 것으로 셉니다.
- 실제 규칙 파일을 복사하거나 Git에 추가합니다.
- 연결 대상이 다른데 파일이 존재한다는 이유만으로 통과합니다.
- 시작 검사 결과가 실행 불가이거나 실패 1건 이상인데 다음 단계로 갑니다.

## 결론

이번 수리 문서는 "검사 규칙이 없는 새 작업 공간에서 시작 검사가 실행 자체를 못 하는 문제"를 고치겠다는 목표를 실제로 달성하고 있습니다. 새 작업 공간을 만들 때나 기존 작업을 이어받을 때나 똑같이, 먼저 검사 규칙을 안전하게 연결하고 그 연결이 맞는지 네 가지 기준으로 다시 확인한 뒤에만 시작 검사를 실행하도록 순서가 고정돼 있습니다. 연결 규칙을 담은 파일을 실제로 복사하지 않고, 실패 메시지에도 규칙의 실제 내용은 나오지 않습니다. 앞선 세 작업(PR #13·14·15)이 실제로 합쳐지지 않으면 코드를 만들지 않는다는 원칙도 지켜지고 있고, 이번 수리 자체도 별도의 선행 작업(PR #21)이 먼저 합쳐져야 한다는 사실을 감추지 않고 정직하게 적어 두었습니다.

다만 두 가지는 고쳐두시는 것을 권합니다. 첫째, 연결 규칙에 대한 공식 계약 문서가 실제 동작의 일부를 빠뜨리고 있어서, 나중에 다른 사람이 이 문서만 보고 코드를 손대면 이번에 고친 안전장치가 모르는 사이에 없어질 위험이 있습니다. 둘째, 검사 스크립트 한 군데에 오류 발생 시 자동으로 멈추는 안전장치가 빠져 있어서, 아주 드문 상황에서 검사가 "통과"로 잘못 읽힐 여지가 이론적으로 남아 있습니다. 두 문제 모두 지금 당장 나쁜 결과를 내지는 않지만, 방치하면 나중에 원인을 찾기 어려운 문제로 이어질 수 있습니다.

## 판단 근거

이번 검토에서 가장 중요하게 본 것은 "검사를 통과시키기 위해 검사 자체를 느슨하게 만들지 않았는가"였습니다. 코드를 그대로 읽어본 결과, 실패 방향은 전부 안전한 쪽(작업을 막는 쪽)으로 기울어 있었습니다. 즉 연결 대상이 다르거나, 규칙 파일이 비어 있거나, 실수로 저장소에 포함되거나, 무시 규칙이 빠졌거나 하면 예외 없이 작업을 멈추게 되어 있고, 반대로 "확인 못 했는데 통과시키는" 경로는 찾지 못했습니다. 이 판단이 틀렸다면, 즉 제가 놓친 경로가 있어 실제로는 검증 없이 통과하는 틈이 있다면, HumanSearch 실행 지시서가 검사 규칙 없이도 코드를 만들기 시작할 수 있게 되어 민감한 값이 저장소에 실수로 들어가는 사고로 이어질 수 있습니다. 그래서 이 부분을 가장 꼼꼼히 대조했습니다.

두 번째로 중요하게 본 것은 "새로 시작하는 경우"와 "하던 작업을 이어받는 경우"가 실제로 같은 절차를 타는가였습니다. 문서 구조상 두 경우로 갈라지는 부분(작업 공간을 새로 만들거나, 기존 것을 재사용하거나) 뒤에 연결·확인·시작 검사 절차가 공통으로 한 번만 적혀 있어서, 어느 경로로 들어와도 같은 확인을 거치는 구조로 되어 있었습니다. 이 부분이 갈라져 있었다면 "재개할 때만 검사를 건너뛴다" 같은 구멍이 생길 수 있었는데, 그런 구멍은 없었습니다.

세 번째로 본 것은 "계약 문서가 실제 코드와 같은 말을 하고 있는가"입니다. 여기서 실제 차이를 발견했습니다. 공식 계약 문서(`docs/sot/hook-contracts.md`)는 설치기가 "훅 경로 설정과 실행 권한 부여만 한다"고만 적혀 있고, 실제 설치기가 하는 "작업 공간 간 규칙 파일 연결" 동작은 전혀 언급하지 않습니다. 그런데 이번 수리 문서는 스스로 이 계약 문서를 "확인했다"고 체크리스트에 적어 두었습니다. 실제로는 계약 문서가 이 부분을 다루지 않으므로, 이 확인 표시는 다소 과장된 것입니다. 코드 자체는 옳게 작동하지만, "문서만 보고 판단해도 된다"는 이 저장소의 원칙에는 어긋납니다.

### 1. 새 작업/재개 공통 경로 확인 — 통과

`docs/engineering/goal-prompts/codex-humansearch-l0-surface-classifier-v2-2026-08-16.md:253-306`에서, 작업 공간을 새로 만드는 경우(1번)와 branch만 있어 다시 연결하는 경우(3번), 이미 둘 다 있어 재개하는 경우(2번) 모두 이후에 이어지는 단일 코드 블록(`cd "$TARGET_ROOT"` 이하)을 공통으로 거칩니다. 이 블록 안에서 `scripts/install-hooks.sh`를 먼저 실행하고, 그 결과를 검증한 뒤에만(`exit 22` 아니면 통과) 다음 단계인 시작 검사(`scripts/session-status.sh`, 315행)로 넘어갑니다.

```text
INSTALL_LINE=279
STATUS_LINE=315
PROMPT_ORDER_EXIT=0
```
→ 무엇을 확인했나: 설치기 호출 줄과 시작 검사 호출 줄의 순서. 결과가 나쁜 소식인가 좋은 소식인가: 좋은 소식입니다. 실제 파일을 읽어 279행·315행이 맞다는 것도 직접 확인했습니다.

### 2. 잘못된 기존 파일을 설치기가 덮지 않는지, 뒤이은 검증이 확실히 막는지 — 통과

`scripts/install-hooks.sh:32`의 조건문 `[ ! -e .secret-patterns ]`는 해당 이름의 무언가(파일이든 잘못된 심볼릭 링크든)가 이미 있으면 새로 연결하지 않고 그냥 넘어갑니다. 즉 설치기는 절대 기존 것을 덮어쓰지 않습니다. 대신 뒤이어 실행되는 검증 블록(`codex-humansearch-l0-surface-classifier-v2-2026-08-16.md:288-299`)이 다음 조건을 전부 확인합니다.

```text
[ ! -L .secret-patterns ]           # 심볼릭 링크가 맞는가
[ "$linked_patterns" != "$expected_patterns" ]  # 연결 대상이 정확한가
[ ! -s "$expected_patterns" ]       # 원본이 비어 있지 않은가
[ ! -s .secret-patterns ]           # 연결된 파일 내용이 비어 있지 않은가
[ "$tracked_count" -ne 0 ]          # Git에 실수로 등록되지 않았는가
[ "$ignored_rc" -ne 0 ]             # 무시 규칙이 실제로 적용되는가
```
→ 이 조건들 중 어느 하나라도 걸리면 22번 성적으로 실행을 멈춥니다. 잘못된 기존 파일(엉뚱한 일반 파일, 다른 곳을 가리키는 심볼릭 링크 등)이 남아 있어도 이 검사가 그것을 잡아냅니다. 좋은 소식입니다.

### 3. `readlink` 절대 경로 비교와 실제 설치기 계약의 불일치 — MEDIUM, 문서 신뢰도 저하

```text
docs/sot/hook-contracts.md 안 "secret-patterns|워크트리|worktree" 검색 결과: 없음
```
→ 무엇을 확인했나: 계약 문서가 이 링크 동작을 규정하는지. 나쁜 소식입니다. 계약 문서에는 이 동작이 전혀 적혀 있지 않은데, `scripts/install-hooks.sh:4`는 자신의 계약처가 이 문서라고 스스로 적어 놓았고, `docs/sot/hook-contracts.md:71`은 "이 5개 파일 자체가 시행 지점이며, 문서와 실제 구현이 항상 같다"고 주장합니다. 실제로는 이번 사례에서 그 주장이 맞지 않습니다.

**심각도**: MEDIUM. **그대로 두면 생기는 일**: 나중에 다른 작업자가 계약 문서만 보고 `install-hooks.sh`를 "정리"하다가 21~35행의 워크트리 연결 로직을 실수로 지울 수 있습니다. 지금 구조는 실패 방향이 안전(작업 중단)이라 당장 정보가 새지는 않지만, 원인 모를 반복 중단이 생기거나 최악에는 향후 수정에서 검증 없이 규칙이 사라지는 계기가 될 수 있습니다.

- **무엇을**: `docs/sot/hook-contracts.md`의 `install-hooks.sh` 절에 `.secret-patterns` 심볼릭 링크 동작을 추가해야 합니다.

### 4. `check-ignore` 성적 해석 — 통과

```bash
ignored_rc=0
git check-ignore -q -- .secret-patterns || ignored_rc=$?
```
→ `git check-ignore`는 "무시 대상이다"일 때 0을, 아니거나 오류일 때 0이 아닌 값을 냅니다. 코드는 `ignored_rc`가 0이 아니면 그대로 중단시키므로 해석이 맞습니다(`codex-...-v2-2026-08-16.md:286,294`). 다만 `.secret-patterns`가 실제 `.gitignore`에 등록돼 있다는 사실 자체는 이번에 지정된 파일 목록 밖이라 직접 읽지 못했습니다(※). `install-hooks.sh:23`의 주석("gitignore 대상이라 메인 작업트리에만 존재")이 간접 근거입니다.

### 5. primary root 계산의 worktree 목록 순서 의존 — LOW, 안전한 방향으로만 실패

```bash
PRIMARY_ROOT="$(git worktree list --porcelain | sed -n '1s/^worktree //p')"
```
→ `git worktree list`는 항상 메인 작업 공간을 첫 줄에 낸다는 것이 Git의 공식 동작이므로, 이 가정 자체는 근거가 있습니다. 다만 이 값(`PRIMARY_ROOT`)과 `scripts/install-hooks.sh:30-31`이 계산하는 `main_root`(`git rev-parse --git-common-dir` 기반)는 서로 다른 두 방법으로 각각 계산되고, 서로 같은지 맞대어 확인하는 코드는 없습니다.

**심각도**: LOW. **사업 영향**: 두 값이 어떤 특이한 환경(심볼릭 링크가 낀 경로 등)에서 다르게 계산되면, 연결은 정상인데도 경로 문자열만 달라 보여 작업이 멈출 수 있습니다. 실패 방향이 항상 "중단"이라 잘못된 통과는 없지만, 원인 파악에 시간이 들 수 있습니다.

- **무엇을**: 두 계산값이 실제로 같은지 확인하는 한 줄을 추가할 수 있습니다.
- **왜**: 지금은 우연히 같다는 전제에 기대고 있습니다.
- **버린 대안**: 이번 검토에서는 코드를 고치지 않았습니다.
- **대가**: 없음(추가 안전장치일 뿐).
- **되돌리기**: 해당 한 줄만 지우면 원상 복구됩니다.

### 6. 파이프라인 오류 무시 가능성 — LOW

```text
tracked_count="$(git ls-files -- .secret-patterns | awk 'NF{c++} END{print c+0}')"
```
