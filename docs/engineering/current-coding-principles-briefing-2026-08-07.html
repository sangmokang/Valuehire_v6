핵심 결론

이 저장소의 중심 원칙은 “테스트가 초록이면 완료”가 아닙니다. 검사가 실제로 실행됐는지, 검사 자체가 약화·면제되지 않았는지, 결과가 실제 동작을 증명하는지까지 확인하는 것입니다.

정본 문서는 P1~P22의 설계와 목표를 담습니다. 다만 모든 원칙이 이미 CI로 구현된 것은 아닙니다. 이 문서는 원칙(목표)과 훅·CI(현재 강제)를 의도적으로 분리합니다.

P1~P22 요약

범위원칙
P1~P5기계 장치 없는 원칙은 삭제(P1), 인수 기준은 실행 명령(P2), PASS/FAIL/NOT_RUN 3상태(P3), 가짜 외부효과 구현 금지(P4), 테스트 변경으로 통과시키기 금지(P5).
P6~P10실행 환경도 제품(P6), 한 명령 롤백(P7), 단일 계정은 lease(P8), 외부효과는 멱등키·readback(P9), 사업 결과를 외부 감시자에게 매일 보고(P10).
P11~P15파일·함수 크기 예산과 만료되는 예외(P11), 고아 코드·숨은 산출물·세션 상태 회수(P12), 검사 약화·자기 면제 금지(P13), LLM 숫자를 판정값으로 사용 금지(P14), 더러운 작업트리와 검증 우회 차단(P15).
P16~P22런타임 동작 테스트(P16), 증거 작성 권한 분리(P17), 위험 능력 자체 제거(P18), 외부 경계 변경 시 라이브 스모크(P19), 0건 처리 PASS 금지(P20), 대용량 데이터 Git 금지(P21), 하드코딩·자격증명 금지(P22).

P12 — 회수

P12는 새 기능을 만들기 전에 이미 있는 구현·고아 모듈·미참조 export를 찾고 회수하라는 원칙입니다. private-reviews/, artifacts/, .harness/처럼 gitignore된 결과물도 범위에 넣습니다. 또 긴 세션에서는 시작 당시 HEAD를 기준으로 보고하지 말고, 보고·판단 직전에 HEAD를 다시 확인하라고 규정합니다.

현재 구현된 SessionStart 훅은 세션 시작 때 HEAD와 origin 상태를 보여 줍니다. 그러나 “최종 보고 직전 재확인” 자체를 자동 강제하는 장치는 아직 확인되지 않았습니다. 문서 원칙은 존재하지만 이 부분의 강제력은 절차 의존입니다.

P13 — 검사는 약화될 수 없다

검사기에 skip, continue-on-error, || true, 자기 제외 같은 틈이 생기면, CI는 초록이어도 검증이 사라집니다. P13은 이런 약화 탐지, 예외의 소유자·사유·만료일 기록, 검사기의 자기 면제 금지를 요구합니다.

현재 실제 강제 구조

커밋 전
  pre-commit
    ├─ index 기준 비밀 스캔
    ├─ 검사기의 자기 제외 탐지
    ├─ 검사 약화 패턴 탐지
    ├─ suppressions.yaml 만료 검사
    ├─ LLM 출력 → 판정 수치 변환 탐지
    └─ 외부효과 코드인데 네트워크 호출 0건 탐지

push 전
  pre-push
    ├─ 미커밋/미추적 파일이면 차단
    ├─ 로컬 검사 재실행
    └─ CI 이관 검사가 workflow에 남았는지 확인

push / PR 후
  GitHub Actions
    ├─ verify.sh 비밀 스캔
    ├─ 도달 가능한 Git history blob 전량 스캔
    ├─ 구 가짜 검증 스크립트 제거 검사
    ├─ 훅이 위반 6종을 실제 차단하는지 시연
    └─ 억제 만료·훅 실행권한·셸 문법 검사

현재 core.hooksPath는 hooks로 설정돼 있고, hooks/pre-commit과 hooks/pre-push가 추적돼 있습니다.

확인 실행 결과: bash verify.sh 및 bash scripts/acceptance-0-6.sh는 통과했습니다. 반면 bash scripts/session-status.sh는 RED: 1/4를 보고했으므로, 현재 미해결 검사 하나가 있습니다. 이 요약 출력만으로 어느 검사인지는 단정하지 않습니다.

Strict — 변경 작업의 엄격 모드

Strict는 CI가 아니라 Codex의 작업 방식입니다. 코드·스크래퍼·파이프라인·기능을 수정할 때 “수정 후 테스트” 이상을 요구합니다.

  1. 수정 전에 현재 상태·근본 원인·인수 기준·비범위를 담은 goal 문서를 남깁니다.
  2. 기존 구현과 실제 프로덕션 호출 경로를 먼저 추적해 고아·부분 배선을 찾습니다.
  3. Harness 게이트로 RED → 최소 GREEN → 실행 증거 → PR 순서를 지킵니다.
  4. 저장소 SOT를 먼저 읽고 충돌 시 SOT를 우선합니다.
  5. Claude의 1차 적대 검증 후, Codex가 그 판정과 증거를 재현·반박하는 2차 검증을 합니다.
  6. goal 문서, 실행 출력, 호출 배선, 라이브 증거, 적대 검증 로그가 있어야 완료를 주장합니다.

관계: Strict는 개발 절차, Verify는 변경 후 검사 절차, CI/훅은 기계적 강제 장치입니다. Strict가 켜져 있다고 CI가 자동으로 강해지는 것은 아닙니다.

Verify — 4단계 변경 검증

단계내용판정 원칙
1타입·린트·테스트·빌드·npm auditlocal-checks.sh를 실제 실행
2구조·복잡도·리팩터링 검토실제 서브에이전트 결과를 요약
3보안 검토실제 보안 서브에이전트 결과를 보고
4GPT 적대 리뷰--gpt일 때만 실행; 미실행이면 통과가 아니라 스킵

Verify의 핵심은 실행하지 않은 단계를 ✅로 포장하지 않는 것입니다. 현재 이 저장소에는 package.json이 없으므로 1단계는 “자동 검증 대상 아님”으로 스킵하고 exit 0을 반환합니다. 따라서 이 저장소에서 품질을 실질적으로 강제하는 주체는 Verify의 1단계가 아니라 verify.sh, 훅, CI입니다.

codeaudit — 읽기 전용 공격 감사

codeaudit은 코드를 수정하지 않습니다. 보고서, AI 답변, 운영 문서, 현재 코드를 대조해 “정말 구현됐는가 / 이 설명을 믿어도 되는가”를 검증합니다.

요구사항·주장 분해
  → SOT·계약 확인
  → 입력이 실제로 들어오는지 확인
  → 호출·처리 경로 추적
  → 실제 출력·부작용 확인
  → 테스트가 해당 경로를 실행하는지 확인
  → 우회·반례·거짓 정상 공격

판정은 구현 확인, 부분 구현, 미구현, 불일치, 검증 불충분, 미확인 중 하나입니다. 함수 이름이 존재하거나 mock 테스트가 통과했다는 사실만으로는 “구현 확인”이 되지 않습니다.

적합한 질문: “이 보고서 믿어도 돼?”, “요구사항과 코드가 맞아?”, “이 테스트가 진짜 버그를 잡아?”, “AI 설명의 근거가 뭐야?”
