# PR 전수 리뷰 프롬프트 — Aside 웹 모델 + 로컬 코드 검증

아래를 이 저장소를 읽을 수 있는 Codex/Claude 셸 세션에 붙여 넣고 `<PR_NUMBER>`만 바꾼다. 웹 모델에 보낼 자료는 이 세션이 준비한다. 브라우저는 Aside만 사용한다.

```text
PR #<PR_NUMBER>를 현재 HEAD 기준으로 전수 리뷰하라. 목적은 (1) 실제 코드 결함, (2) 승인된 사업 의도와의 불일치, (3) 불필요한 복잡성을 구분해 병합 전 판정을 내리는 것이다. 읽기 전용으로 진행한다. 코드·PR·라벨·댓글·브랜치·외부 서비스는 변경하지 말고, 유료 API를 호출하지 않는다.

1. 기준 고정
- `gh pr view`로 headRefOid, baseRefOid, 변경 파일, Draft/스택 여부, 최신 검사 결과를 기록한다. 원격 base를 갱신하고 PR HEAD와 로컬 검토 SHA가 같음을 확인한다. 다르면 중단한다. 과거 리뷰와 CI 성공은 현재 SHA의 증거가 아니다.
- PR 본문과 변경 목적, 해당 기능의 goal/AC·counter-AC, `docs/sot/`, ADR, 최신 사용자 결정을 찾아 원자적인 요구사항 목록으로 만든다. 서로 모순되면 출처·날짜·결정권을 적고 임의로 하나를 선택하지 않는다. 사업 의도가 문서에서 확인되지 않는 부분은 `의도 미확인`으로 둔다.

2. 빠짐없는 인벤토리
- base...HEAD의 변경 파일과 추가·삭제 줄 수를 기계로 뽑는다. 파일별로 전체 HEAD 원문, diff, 호출자·피호출자, 관련 테스트를 읽는다. 파일을 봤다는 사실과 동작을 검증했다는 사실을 별도 칸에 기록한다.
- 변경 파일마다 `REVIEWED(전체 원문 확인)` / `PARTIAL(확인 범위)` / `GENERATED(생성물 정합성 검증)`을 표시한다. 경계(API↔서비스, 서비스↔DB, 설정↔런타임, 권한↔데이터, 실패↔재시도, 테스트↔구현)도 ID를 붙여 목록화한다. 변경 파일이 0건이거나 인벤토리와 누락·중복이 생기면 완료로 보고하지 않는다. 경계가 0건이면 단일 파일 변경 등 그 이유를 기록하고 셸에서 확인한다.
- 큰 PR은 관련 파일을 묶어 한 단위의 변경 원문이 대략 300~500줄을 넘지 않게 분할한다. 한 파일이 크면 함수·호출 경계로 나누되 파일 전체의 어느 줄을 누가 확인했는지 남긴다. 삭제 줄과 변경 전 동작도 살핀다.

3. Aside 웹 독립 리뷰
- Aside의 ChatGPT.com과 Claude.ai를 각각 새 대화에서 사용한다. 저장소 연결이 없다면 줄번호가 붙은 파일 원문·diff·요구사항·경계 목록을 첨부한다. 연결을 새로 승인하거나 로그인·결제 화면을 통과하지 않는다. 비밀값·후보자 개인정보는 첨부 전에 제외한다.
- 같은 리뷰 단위와 같은 질문을 두 모델에 주되, 서로의 결론은 보여 주지 않는다. 각 모델에 이 파일의 `웹 리뷰어용 지시문`을 보낸다. 답변 원문과 사용한 묶음의 SHA·파일 목록·끝 줄번호를 로컬 비공개 폴더에 저장한다.
- 웹 답변의 `읽은 줄 수`, `PASS`, 테스트 실행 주장은 자기신고다. 묶음 생성 실패·전송 누락·마지막 줄 표식 누락·응답 잘림은 `NOT_RUN`으로 기록한다. 모델의 지적은 셸 검증 전에는 `미재현 의견`이다.

4. 셸 독립 검증
- 셸에서 실제 코드의 입력→검증→상태 변화→출력·외부효과→실패 경로를 한 줄씩 추적한다. 웹 지적마다 정확한 file:line, 재현 입력, 예상/실제 결과, 반대 증거를 확인한다. 새롭거나 위험한 SDK 동작은 공식 문서 또는 실제 고정 버전 코드로 확인한다.
- 가장 작은 관련 테스트를 현재 체크아웃에서 새로 실행하고 종료값을 기록한다. 중요한 검사는 원본 밖 임시 공간에서 금지 입력·누락 파일·실패 응답·검사기 무력화 같은 반례를 넣어 실제로 실패하는지 확인한다. 실행하지 않은 것은 `NOT_RUN`이라고 쓴다. 외부 전송, 운영 DB 변경, 메일 발송, 유료 호출은 하지 않는다.
- 두 웹 모델이 같은 말을 해도 근거로 승격하지 않는다. 재현된 결함만 `CONFIRMED`; 코드·테스트의 반대 증거가 있으면 `REFUTED`; 환경·권한·외부 응답이 없으면 `NOT_TESTED`로 둔다.

5. 사업 적합성과 과잉 설계
- 각 핵심 설계 선택에 대해 `어떤 사업 결과/AC를 지키는가`, `현재 코드·기존 유틸리티로 더 작은 방법이 있는가`, `새 상태·의존성·운영 작업·실패 경로가 몇 개 늘었는가`, `지금 필요한가`를 근거와 함께 답한다.
- 복잡성이 법적·보안·정확성·복구 계약을 지킨다면 필요하다고 인정한다. 기능과 연결되지 않는 추상화·일반화·미래 가정은 `삭제/단순화 후보`로 적고, 동일한 AC를 만족하는 최소 대안을 제시한다. 단순한 코드라는 이유만으로 기존 요구사항을 약화하지 않는다.

6. 최종 판정
- `APPROVE`는 현재 SHA의 모든 변경 파일·핵심 경계가 검토되고 필수 검증이 실행됐으며 재현된 중대 결함이 없을 때만. 재현 결함·사업 AC 위반·거짓 완료는 `REQUEST_CHANGES`; 자료·접근·실행 증거가 부족하면 `NOT_RUN`이다. 판정은 자동 병합 권한이 아니다.
- 한국어로 아래 순서로 보고한다: PR 번호/현재 SHA/기준 SHA/작업트리 상태 → 사업 목표와 요구사항별 판정 → 파일 N/N·경계 N/N 장부 → 심각도순 결함(file:line, 재현, 영향, 최소 수정) → 웹 모델별 의견과 셸 재현 결과 → 테스트 명령·종료값·반례 → 과잉 설계 후보와 최소 대안 → 미검증·잔여 위험 → 병합 전 판정. 웹 사용 여부와 추가 API 비용도 적는다.
```

## 웹 리뷰어용 지시문

각 Aside 대화에는 아래를 넣고, 셸 세션이 만든 **한 단위의 자료 묶음**을 첨부한다.

```text
당신은 PR 코드의 독립 리뷰어다. 첨부에 있는 요구사항·diff·줄번호 붙은 HEAD 파일과 호출 경계만 근거로 삼아라. 저장소에 접근할 수 있다고 가정하지 말고, 명령을 실행했다고 주장하지 마라. 첨부가 잘렸거나 끝 줄번호가 없으면 `TRUNCATED`라고 적고 멈춰라.

각 변경 줄과 그 주변 호출 경로에서 입력, 출력, 오류, 상태 변화, 재시도, 권한, 데이터 저장·전송, 테스트의 실제 검증력을 따져라. PR 설명과 기존 테스트 성공은 검증할 주장이다. 결함 후보마다 file:line, 조건, 예상 결과, 코드상 실제 결과, 사업 영향, 최소 반례, 반대 증거를 적어라. 확인하지 못한 경로는 `NOT_CHECKED`로 남겨라.

사업 의도는 첨부된 goal/AC·SOT·최신 결정에만 연결하라. 각 새 추상화·의존성·상태에 대해 지금 필요한 요구사항과 더 작은 대안을 비교하라. 근거가 없는 일반화는 과잉 설계 후보로 표시하되, 보안·정확성·복구 요구를 위해 필요한 복잡성은 유지하라.

마지막에 이 단위의 파일별 확인 범위와 끝 줄번호, 경계 ID별 VERIFIED/ISSUE/NOT_CHECKED, 결함 후보의 확신도, 실행하지 않은 검증을 표로 적어라. 당신의 PASS나 읽은 줄 수 자기신고는 최종 검증이 아님을 명시하라.
```
