# 비밀 탐지 카나리 (detection-regression fixture)

`.secret-patterns.default` 의 **탐지력이 줄었는지**를 판정하는 데 쓴다.

## 왜 필요한가 (2026-09-10 Codex 적대검증)

P13 약화 탐지는 diff 의 **추가된 줄**을 일반 약화 리터럴(`|| true` 등) 목록과 대조한다.
비밀 규칙 파일에는 그 방식이 통하지 않는다:

- 규칙 **삭제**는 추가된 줄이 없으므로 입력에 들어오지도 않는다
- 수량 하한을 `{16}` → `{99}` 로 올리는 **수정**은 어떤 약화 리터럴과도 일치하지 않는다

실측: `AKIA[0-9A-Z]{16}` 줄을 지운 커밋이 통과했고, **바로 다음 커밋에서 실제 AWS 키가
든 파일이 그대로 통과했다**. 규칙을 정하는 파일이 "무엇을 잡는가"로 지켜지지 않으면
문법 검사는 의미가 없다.

## 계약

- `positive.txt` — 각 줄은 **반드시 잡혀야 하는** 값이다. 하나라도 안 잡히면 탐지력이 줄었다.
- `negative.txt` — 각 줄은 **잡히면 안 되는** 값이다. 새로 잡히면 오탐이 늘었다.
- 판정은 `scripts/verify/check-secret-detection-regression.sh` 가 한다.
  기준(HEAD)의 패턴과 커밋될(인덱스) 패턴으로 각각 돌려 **집합을 비교**한다.
- 규칙을 정당하게 줄일 때는 이 파일에서 해당 양성 줄도 함께 지운다. 그 삭제는 diff 에 남고
  리뷰에서 보인다 — 조용한 축소만 막는 것이 목적이다.

## 이 파일 자체가 비밀 스캔에 걸리지 않는가

걸린다. 실제로 2026-09-11 에 두 번 걸렸다:

1. `-----BEGIN \tRSA PRIVATE KEY-----` — 개인키 패턴의 `[[:space:]]+` 가 **구분자 탭을
   삼켜서** 조립 전에도 매칭됐다. 쪼갠 위치가 패턴의 공백 허용 구간이면 분할이 무의미하다.
   그래서 `-----BEG` / `IN RSA PRIVATE KEY-----` 처럼 **글자 중간에서** 끊는다.
2. 훅 쪽 변수명 `SECRET_REG_CHECKER=...` 가 키워드 규칙(`*SECRET*=값`)에 걸렸다.
   검사기를 부르는 코드가 자기 검사에 걸린 것이다 — 변수명에서 그 키워드를 뺐다.

그래서 값은 **조립해서** 쓴다(`verify.sh` 가 읽을 때 한 줄로 완성되지 않도록
접두사와 본문을 분리해 두었다). 카나리 러너가 실행 시점에 조립한다.

## manifest.txt — 어떤 카나리가 어떤 규칙을 대표하는가

`positive.txt` 만으로는 **카나리가 어떤 규칙을 대표하는지** 아무도 적어 두지 않는다.
2026-09-11 Codex 적대검증 실측: 규칙 25개 중 카나리에 연결된 것은 4개뿐이었고,
나머지 21개는 통째로 사라져도 검출 집합이 안 변해 탐지 회귀 검사가 초록이었다.

`manifest.txt` 가 그 대응을 정본으로 고정한다. 탭 네 칸이다:

```
<capability>	<카나리 설명>	<규칙 id 쉼표목록>	<묶은 근거>
```

- **카나리 설명**은 `positive.txt` 의 첫 칸과 글자 그대로 같아야 한다. 그것이 키다.
- **규칙 id** 는 `.secret-patterns.default` 의 규칙 줄 **바로 앞** `# @id: <슬러그>` 주석에서 온다.
  주석은 스캔에서 걸러지므로 탐지 집합에는 영향이 없다.
- **capability** 는 같은 위협을 막는 규칙들의 묶음이다. 규칙 25개 = 카나리 25개일 필요는
  없지만, 벤더 키처럼 접두사가 규칙마다 다른 묶음은 한 값으로 여러 규칙을 만족시킬 수
  없어 결과적으로 1:1 이 된다.

판정은 `scripts/verify/check-secret-canary-coverage.sh` 가 한다. **적어 두기만 해서는
통과하지 못한다** — 적힌 규칙이 그 카나리로 실제 매칭되는지 실행으로 확인한다.
서류만 맞추면 통과하는 검사는 검사가 아니다.

### 규칙을 정당하게 고치는 법

| 하려는 일 | 함께 고쳐야 하는 것 |
|---|---|
| 규칙 추가 | `# @id:` 주석 · `positive.txt` 카나리 · `manifest.txt` 한 줄 |
| 규칙 삭제 | 위 셋을 함께 삭제 |
| 규칙 수정 | 카나리가 여전히 매칭되는지 확인 (안 되면 카나리도 고친다) |

네 곳을 함께 고치는 것이 번거로워 보이지만, 그 번거로움이 **규칙이 조용히 사라지지
않게** 하는 값이다. 삭제는 전부 diff 에 남아 리뷰에서 보인다.

### 독립 oracle (`--oracle-selftest`)

같은 입력을 생산 스캐너 `verify.sh` 로도 판정해 두 경로를 대조한다. 두 판정기가 규칙
파일을 각자 정제하는데, 정제가 갈리면 서로 다른 규칙 집합을 보게 된다 — 이 저장소는
2026-08-07 에 그것으로 이미 한 번 갈렸다.

**한계**: 두 경로 모두 같은 정규식 엔진(`grep -Ei`)과 같은 규칙 파일을 쓴다. 규칙 자체가
틀렸거나 엔진이 같은 방식으로 틀리면 이 대조는 그것을 보지 못한다. 드러내는 것은
적재·정제·배관의 차이(주석 절단, CRLF, 파일 합치기 순서)로 생기는 공통모드뿐이다.
